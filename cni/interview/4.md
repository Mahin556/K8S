## What is CNI?

**Full Form:** Container Network Interface

**Simple Definition from Transcript:**
"CNI basically is a software-defined network solution which provides Layer 3 networking in software form."

**Extended Definition:**
CNI is nothing but advanced software-defined switches that provide Layer 3 (routing) features in software form for containers. They act as smart virtual switches that can manage routing between containers across different nodes.

---

## Why Do We Need CNI? The Problem It Solves

### The Problem with Standard Docker Bridge:

The transcript explains this with the evolution of networking:

**1. Standard Linux Bridge (Docker's default bridge):**
- When Docker is installed, it creates a default bridge network (`docker0`)
- This bridge assigns IPs to containers on the same host
- Containers on the same host can communicate with each other
- **Limitation:** This bridge only works **within a single Docker host**
- It has **no routing capability** - it's like a Layer 2 non-manageable switch
- "वो ब्रिज सिर्फ विदन डॉकर होस्ट ही कम्युनिकेट करा पाता था बस" (That bridge could only communicate within the Docker host, that's it)

**2. The Cluster Challenge:**
- In Kubernetes, we have multiple worker nodes
- A container on Node-1 needs to communicate with a container on Node-2
- The standard bridge cannot handle cross-node communication
- Without port forwarding, cross-node communication is impossible with standard bridges

**3. What We Actually Need:**
- We need a bridge with **routing capabilities**
- We need each node's containers to reach other nodes' containers directly via IP
- We need **Layer 3 (routing) features** in the network switch

## How CNI Solves This Problem

CNI provides **software-defined Layer 3 switches** that:

1. **Assign IP addresses** to containers (like a bridge)
2. **Manage routing tables** for cross-node communication
3. **Share routing information** between nodes
4. **Enable direct container-to-container communication** across nodes without port forwarding

**The Analogy from Transcript:**
"ऐसा लगता है जैसे सभी कंटेनर को मैंने एक स्विच में लाकर जोड़ दिया है" (It feels like all containers are connected to a single switch)

---

## How CNI Works Across Nodes

### The Distributed Switch Concept:

1. **Each node has its own CNI switch (software)**
2. **These switches form a cluster among themselves**
3. **They share routing information** - each switch knows about containers on other nodes
4. **Routing tables are synced** between all switches in the background

**Key Quote from Transcript:**
"हर एक वर्कर नोड की अलग-अलग स्विच है... बट वो स्विच इंटरनली दे आर कनेक्टेड... स्विच के बीच में भी क्लस्टर काम कर रहा है सभी स्विच को पता है कि मेरे कितने नेवर है कितने पड़ोसी है एक स्विच की इंफॉर्मेशन दूसरी स्विच के पास सिंक हो रही है बैक एंड में"

Translation: "Each worker node has its own separate switch... but those switches are internally connected... a cluster is working between the switches themselves. Every switch knows how many neighbors it has. One switch's information is syncing to another switch in the backend."

## Why Containers Need Software Switches

**Physical switches can't work with containers:**

- Containers are **virtual objects**, not physical devices
- You cannot take a LAN cable and connect a container to a physical switch in the data center
- Therefore, you need **software-defined switches** that can manage virtual container networking

**Key Quote:**
"कंटेनर को हार्डवेयर स्विच के साथ में अटैच करना पॉसिबल है ही नहीं... कंटेनर एक वर्चुअल ऑब्जेक्ट है... तो सॉफ्टवेयर स्विचेस से कंटेनर को मैनेज करना पड़ेगा"

Translation: "It's not possible to attach a container to a hardware switch... a container is a virtual object... so we have to manage containers using software switches."

## Calico Architecture

### Components:

1. **Calico Node (per node):**
   - A pod that runs on EVERY node (master + worker)
   - Acts as the software-defined Layer 3 switch for that node
   - Manages IP assignment and routing for containers on that node

2. **Calico Controller:**
   - A central controller pod
   - Manages the overall network policy
   - Coordinates between all Calico nodes

### How It's Deployed:
- You deploy Calico ONCE from the master node
- The API server reads the Calico manifest
- The manifest contains a DaemonSet that ensures one Calico pod runs on every node
- Automatically deployed to all nodes without manual intervention

**Key Quote:**
"मैं मास्टर नोड के एपीआई से बोलूंगा एपीआई मुझे हर नोड पर कैल्को सर्विस चाहिए आई विल डिप्लॉयड कल्को की मेनिफेस्ट... एपीआई क्या करेगा उस मेनिफेस्ट को चलाएगा हर एक नोड पर जाकर एक एक कंटेनर डिपल करके आ जाएगा"

Translation: "I will tell the master node's API: 'API, I want Calico service on every node.' I will deploy Calico's manifest... The API will run that manifest and go to each node, deploying one container each."

## IP Pool Concept

### What is an IP Pool?
- A range of IP addresses reserved for pod networking
- Defined by the CNI plugin
- All pods across the entire cluster get IPs from this pool

### Default Calico IP Pool:
- If not specified: `172.16.0.0/16` or `192.168.0.0/16`

### How to Check:
```bash
kubectl get ippool -o yaml
```

### Key Quote:
"मैंने बाय डिफॉल्ट 172.16.0.0/16... इस क्लस्टर में जितने नोड बनेंगे सभी पॉड का आईपी रेंज इस नेटवर्क इस सीरीज का ही होगा"

Translation: "By default, 172.16.0.0/16... In this cluster, however many nodes are created, all pods' IP range will be from this network, this series."

## The Critical Role of CNI in Cluster Readiness

### Before CNI Installation:
- Nodes show **NotReady** status
- CoreDNS pods are stuck in **Pending** state
- No IP can be assigned to pods (except host network pods)

### After CNI Installation:
- Nodes become **Ready**
- CoreDNS pods automatically get IPs and start running
- All new pods can now get IPs from the IP pool

### This Proves the Dependency:
"इस बात से प्रूफ हो गया कि कोर डीएनएस जो पेंडिंग था ना वो आईपी ना मिलने की वजह से पेंडिंग था जैसे कैलक नेटवर्क की स्विच हर नोड पर डिप्लाई हुई... तुरंत क्या हो गया है कोर डीएनएस की सर्विस को आईपी मिलना स्टार्ट हो गया"

Translation: "This proves that CoreDNS was pending because it wasn't getting an IP. As soon as Calico network's switch was deployed on every node... immediately CoreDNS service started getting IPs."

## Summary: Standard Bridge vs CNI

| Feature | Standard Bridge | CNI (e.g., Calico) |
|---------|-----------------|---------------------|
| **Layer** | Layer 2 only | Layer 3 (routing) |
| **Scope** | Single host | Entire cluster (cross-node) |
| **Routing** | None | Full routing table management |
| **IP Management** | Basic per-host | Cluster-wide IP pool |
| **Cross-node Communication** | Not possible (without port forwarding) | Direct IP-to-IP |
| **Information Sharing** | None | Syncs routing info between all switches |
| **Type** | Simple virtual switch | Smart software-defined Layer 3 switch |

## Key Interview Points to Remember:

1. **CNI is mandatory** for a Kubernetes cluster to be fully functional
2. **Calico is the standard** for on-premises deployments
3. **Without CNI, nodes stay NotReady** because containers can't get IPs
4. **CNI provides Layer 3 networking** - routing between containers across nodes
5. **Each node gets its own CNI pod** that acts as a software switch
6. **CNI switches form a cluster** and sync routing information among themselves
7. **The IP pool** defines the range from which all pods get their IP addresses
8. **Flannel and Weave are deprecated** - Calico is the current standard
9. **CNI solves** the fundamental limitation of Docker's default bridge which cannot route traffic between different hosts
10. **Physical switches can't manage containers** because containers are virtual objects - software switches are the only solution
