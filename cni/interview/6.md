You've hit on a really important distinction in Kubernetes. The **64 IPs** from our `/26` block size example is a limitation of the *networking setup*, not the actual maximum number of pods that can run on a node. **Yes, you can often run more than 64 pods on a node**, because the total pod limit is controlled by the `kubelet` and is often much higher.

Let's break down the two different limits at play here.

### 1. The Network Limit (What we calculated: the `/26` example)

This is the constraint we discussed, and it applies to the **Calico** CNI plugin. Based on its configuration, Calico carves out a `/26` subnet (64 IP addresses) for each node. Every pod that isn't using the host's network directly gets an IP from this pool.

*   **Usable IPs**: Out of the 64 IPs, not all are for pods. 2 IPs are typically reserved for the network and broadcast addresses, leaving 62 usable IPs for pods on that node.
*   **The Conflict**: If your application needs more than 62 pods on a single node, Calico will not be able to give new pods an IP address, and they will get stuck in a `Pending` state.

### 2. The Kubelet Limit (The default: `maxPods`)

This is the node-level cap configured by the `kubelet`, the main "node agent" that starts pods. It's often set to a much higher number than the network limit.

*   **The Default**: Most cloud providers and default installations set the `--max-pods` parameter for the kubelet to **110 pods per node**.
*   **Configurability**: You can change this value by editing the kubelet configuration and restarting the service. Some platforms set it even higher, up to 250 pods.

### Which Limit is Enforced?

The effective limit on a node is the **lower of these two values**:
`Maximum Pods = Minimum(Network Limit, Kubelet Limit)`.

Here’s how it plays out with a 62-IP network limit:

| **Kubelet (`maxPods`) Limit** | **Calico `/26` Network Limit** | **Effective Max Pods on Node** | **What Happens?** |
| :--- | :--- | :--- | :--- |
| 110 | 62 | **62** | The network is the bottleneck. You can start 62 pods and then run out of IPs. |
| 50 | 62 | **50** | The `kubelet` is the bottleneck. You can start 50 pods. The remaining 12 IPs in the subnet will be unused. |
| 62 | 62 | **62** | The limits match, which is an ideal and balanced configuration. |

### How to Fit More Pods on a Node

If you need more than 62 pods per node, you have two main options:

1.  **Adjust the Calico Block Size**: You can configure Calico to use a smaller block size, like `/25` (128 IPs) or `/24` (256 IPs). This directly increases the network limit per node. The trade-off is that the total number of nodes your cluster can support will decrease because you're carving out larger pieces of your main CIDR block.
2.  **Increase the Kubelet Limit**: If you adjust the network limit, you'll likely need to raise the kubelet's `maxPods` limit to match it. This is done by modifying the `--max-pods` flag in the kubelet's configuration file (often found at `/usr/lib/systemd/system/kubelet.service.d/10-kubeadm.conf`).

### A Word of Caution

Just because you *can* run more pods on a node doesn't always mean you *should*. Increasing the pod limit can cause other issues:
*   **IP Exhaustion**: You could run out of pod IPs faster across the cluster.
*   **Resource Strain**: More pods means more CPU, memory, and I/O pressure on that single node.
*   **Performance Overhead**: The `kubelet` itself has to manage more containers, which can affect its performance.

In summary, the 64-IP `/26` block size is a specific, configurable network limit in Calico, while the kubelet's `maxPods` is a separate, more general node limit. The actual number of pods you can run is determined by whichever limit you hit first.
