* `imagePullSecrets` is defined at the **Pod level**, not inside individual containers.

* Structure example:

  ```yaml
  apiVersion: v1
  kind: Pod
  metadata:
    name: my-pod
  spec:
    imagePullSecrets:
      - name: my-secret
    containers:
      - name: app1
        image: private-registry/app1:latest
      - name: app2
        image: private-registry/app2:latest
  ```

* Because it is under `spec:` (same level as `containers:`), it applies to **all containers in that Pod**.

---

* What this means practically:

  * Every container in that Pod:

    * Must pull from the same private registry
    * Or from registries that accept the same credentials

  * Kubernetes does NOT support:

    * One container using Secret A
    * Another container using Secret B
    * Inside the same Pod

---

* If different credentials are required:

  * You must:

    * Place containers in **separate Pods**
    * Or use separate Deployments

---

* Important internal behavior (good for EX188 + deep understanding):

  * When kubelet pulls images:

    * It checks `imagePullSecrets` at Pod level
    * It passes those credentials to the container runtime (CRI-O / containerd)
    * Runtime tries to authenticate using those credentials

  * If one image needs different credentials:

    * Pull fails → `ImagePullBackOff`

---

* Better production approach:

  * Attach `imagePullSecrets` to a **ServiceAccount** instead of each Pod:

  ```bash
  kubectl patch serviceaccount default \
    -p '{"imagePullSecrets":[{"name":"my-secret"}]}'
  ```

  * Then all Pods using that ServiceAccount inherit it.

---

* Key concept to remember:

  * Pod = smallest deployable unit
  * Networking + storage + secrets are scoped at Pod level
  * Containers inside a Pod share that configuration
