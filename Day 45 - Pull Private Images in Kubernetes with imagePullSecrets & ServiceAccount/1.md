How Kubelet Pulls Images

**Kubelet** manages container image pulling by interacting with the container runtime (e.g., containerd, cri-o) via the CRI (Container Runtime Interface). When a Pod is scheduled to a node, the Kubelet:

1. **Reads the PodSpec** to determine the container image and configuration.
2. **Checks if the image exists locally** on the node by querying the container runtime.
3. **Evaluates the `imagePullPolicy`**:
   - If `Always`: Always pulls the image from the registry.
   - If `IfNotPresent`: Pulls only if the image is not already cached.
   - If `Never`: Only uses the local image (fails if not present).
4. **Pulls the image** if required, using credentials from `imagePullSecrets` if the registry is private.
5. **Passes the image to the container runtime** to create the container.
6. **Stores the image** in the node’s storage (e.g., `/var/lib/containerd` for containerd).

After a successful pull, the image remains cached until no running containers reference it, at which point it may be garbage collected. The process is optimized by default with **serial image pulls**, but can be configured for **parallel pulls** using `serializeImagePulls: false` in the Kubelet config.
