## Pre-Upgrade Checklist (Critical!)

### Checklist Items

```bash
# 1. Backup etcd (ESSENTIAL!)
ETCDCTL_API=3 etcdctl snapshot save backup-$(date +%s).db \
  --endpoints=127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 2. Check cluster health
kubectl get nodes  # All should be Ready
kubectl get pods -A | grep -i "not ready" || echo "All pods healthy"

# 3. Note current versions
kubectl version --short
kubeadm version

# 4. Check target version availability
apt-cache policy kubeadm
# Lists available versions: 1.26.0-1.26.1-1.27.0-1.27.1 etc

# 5. Test in staging cluster first
# Use exact same version path
# 1.25 → 1.26 (same path as production)

# 6. Check CRD compatibility
kubectl get crd
helm list -A | while read release; do
  helm search repo $release --version <new-k8s-version>
done

# 7. Review release notes
# https://github.com/kubernetes/kubernetes/releases/tag/v1.X.Y
# Look for: Breaking changes, deprecations, known issues

# 8. Plan downtime window
# Control plane: 30-120 seconds
# Workers: 5-30 minutes each
```

## Complete Upgrade Workflow

### Phase 0: Pre-Upgrade (Same for all upgrades)

```bash
#!/bin/bash
# Pre-upgrade checklist

echo "=== PRE-UPGRADE CHECKLIST ==="

# 1. Backup
echo "Step 1: Backing up etcd..."
ETCDCTL_API=3 etcdctl snapshot save /backups/etcd-$(date +%Y%m%d-%H%M%S).db \
  --endpoints=127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
echo "✓ Backup complete"

# 2. Health check
echo -e "\nStep 2: Checking cluster health..."
UNHEALTHY=$(kubectl get nodes | grep -v Ready | grep -v NAME)
if [ -n "$UNHEALTHY" ]; then
  echo "❌ Unhealthy nodes found:"
  echo "$UNHEALTHY"
  exit 1
fi
echo "✓ All nodes healthy"

# 3. Current versions
echo -e "\nStep 3: Current versions:"
kubectl version --short
kubeadm version

# 4. Staging test
echo -e "\nStep 4: Test in staging cluster first!"
echo "Upgrade staging to same version path before production"

# 5. CRD check
echo -e "\nStep 5: Checking CRD compatibility..."
echo "Ensure Helm charts support new Kubernetes version"

echo -e "\n✓ Pre-upgrade checks complete!"
```

### Phase 1: Control Plane Upgrade (1.25 → 1.26)

```bash
#!/bin/bash
# Control plane upgrade

TARGET_VERSION="1.26.0"

echo "=== CONTROL PLANE UPGRADE ==="
echo "Target: v$TARGET_VERSION"

# SSH to control plane
ssh ubuntu@control-plane

# Step 1: Upgrade kubeadm
echo "Step 1: Upgrading kubeadm..."
sudo apt-get update
sudo apt-get install -y kubeadm=$TARGET_VERSION-00

# Verify
kubeadm version

# Step 2: Plan the upgrade
echo -e "\nStep 2: Planning upgrade..."
sudo kubeadm upgrade plan

# Output will show:
# Components that will be upgraded
# What changed
# Confirmation command to run

# Step 3: Apply the upgrade
echo -e "\nStep 3: Applying upgrade..."
echo "⚠️  API server will be down for 30-120 seconds"
sudo kubeadm upgrade apply v$TARGET_VERSION --yes

# Output:
# [upgrade/successful] SUCCESS! Your cluster was upgraded...
# [upgrade/version] Now that your cluster is upgraded...

# Step 4: Upgrade kubelet and kubectl
echo -e "\nStep 4: Upgrading kubelet and kubectl..."
sudo apt-mark unhold kubelet kubectl
sudo apt-get install -y kubelet=$TARGET_VERSION-00 kubectl=$TARGET_VERSION-00
sudo apt-mark hold kubelet kubectl

# Step 5: Restart kubelet
echo -e "\nStep 5: Restarting kubelet..."
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# Step 6: Verify
echo -e "\nStep 6: Verifying control plane..."
sleep 30  # Wait for kubelet to restart

# Check from local machine (not on control plane)
kubectl get nodes

# Output should show:
# NAME              STATUS   ROLES           VERSION
# control-plane     Ready    control-plane   v1.26.0  ← Updated!

echo "✓ Control plane upgrade complete!"
```

### Phase 2: Worker Node Upgrades (One at a time)

```bash
#!/bin/bash
# Upgrade each worker node

TARGET_VERSION="1.26.0"
NODES=$(kubectl get nodes -o jsonpath='{.items[?(@.metadata.labels.node-role\.kubernetes\.io/control-plane!="true")].metadata.name}')

echo "=== WORKER NODE UPGRADES ==="
echo "Nodes to upgrade: $NODES"

for NODE in $NODES; do
  echo ""
  echo "=========================================="
  echo "Upgrading node: $NODE"
  echo "=========================================="
  
  # Step A: Drain node
  echo "Step A: Draining node..."
  kubectl drain $NODE \
    --ignore-daemonsets \
    --force \
    --delete-emptydir-data
  
  # Pods are evicted, scheduled on other nodes
  echo "✓ Node drained (pods evicted)"
  
  # Step B: SSH and upgrade
  echo -e "\nStep B: Upgrading kubelet..."
  ssh ubuntu@$NODE "bash -s" <<EOF
    # Update kubeadm
    sudo apt-get update
    sudo apt-get install -y kubeadm=$TARGET_VERSION-00
    
    # Upgrade node
    sudo kubeadm upgrade node
    
    # Update kubelet and kubectl
    sudo apt-mark unhold kubelet kubectl
    sudo apt-get install -y kubelet=$TARGET_VERSION-00 kubectl=$TARGET_VERSION-00
    sudo apt-mark hold kubelet kubectl
    
    # Restart kubelet
    sudo systemctl daemon-reload
    sudo systemctl restart kubelet
EOF
  
  echo "✓ Node upgraded"
  
  # Step C: Wait for node to be ready
  echo -e "\nStep C: Waiting for node to be ready..."
  for i in {1..60}; do
    STATUS=$(kubectl get node $NODE -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}')
    if [ "$STATUS" = "True" ]; then
      echo "✓ Node is Ready"
      break
    fi
    echo "Waiting... ($i/60)"
    sleep 5
  done
  
  # Step D: Uncordon node
  echo -e "\nStep D: Bringing node back online..."
  kubectl uncordon $NODE
  
  echo "✓ Node $NODE upgrade complete"
  
  # Brief pause between nodes
  sleep 10
done

echo ""
echo "=========================================="
echo "✓ All worker nodes upgraded!"
echo "=========================================="
```

### Phase 3: Verification

```bash
#!/bin/bash
# Post-upgrade verification

echo "=== POST-UPGRADE VERIFICATION ==="

# 1. Check all nodes
echo "Step 1: Node status"
kubectl get nodes
# All should be Ready with v1.26.0

# 2. Check all pods
echo -e "\nStep 2: Pod status"
kubectl get pods -A | grep -i "CrashLoopBackOff\|Error" || echo "✓ All pods healthy"

# 3. Check metrics
echo -e "\nStep 3: Checking metrics..."
kubectl top nodes
kubectl top pods -A | head -10

# 4. Check cluster info
echo -e "\nStep 4: Cluster info"
kubectl cluster-info
kubectl version --short

# 5. Quick application test
echo -e "\nStep 5: Testing sample application..."
kubectl run test-pod --image=nginx:latest
sleep 10
kubectl get pod test-pod
kubectl logs test-pod
kubectl delete pod test-pod

# 6. API server latency
echo -e "\nStep 6: API server latency check..."
time kubectl get nodes

echo ""
echo "✓ Post-upgrade verification complete!"
```

## Version Compatibility Rules

### Rule: Control Plane ≥ Worker Nodes

```
✓ Safe configurations:
├─ Control plane: 1.26 | Workers: 1.26 (same)
├─ Control plane: 1.26 | Workers: 1.25 (older okay)
└─ Control plane: 1.26 | Workers: 1.26, 1.25 (mixed okay)

✗ Unsafe configurations:
├─ Control plane: 1.25 | Workers: 1.26 (workers too new!)
├─ Control plane: 1.24 | Workers: 1.26 (gap too large)
└─ Control plane: 1.25 | Workers: 1.27 (workers ahead)

Rule: Control plane can never be OLDER than workers!
```

## Common Mistakes to Avoid

```bash
# ❌ WRONG: Skipping versions
kubectl upgrade apply 1.27  # From 1.25, skipping 1.26!
# Result: Not supported, breaks

# ✅ RIGHT: Sequential upgrades
1.25 → 1.26 → 1.27

---

# ❌ WRONG: Upgrading all workers at once
for node in $(kubectl get nodes); do
  upgrade $node &  # All at once!
done
# Result: Service downtime, all pods evicted

# ✅ RIGHT: One worker at a time
for node in $(kubectl get nodes); do
  drain $node
  upgrade $node
  uncordon $node
  wait_for_ready
done

---

# ❌ WRONG: No backup
kubeadm upgrade apply 1.26  # No backup!
# Fails: Can't rollback, complete loss

# ✅ RIGHT: Always backup first
ETCDCTL_API=3 etcdctl snapshot save backup.db
kubeadm upgrade apply 1.26

---

# ❌ WRONG: Upgrading workers before control plane
upgrade_workers_first
upgrade_control_plane_second
# Result: API errors, workers too new

# ✅ RIGHT: Control plane first
upgrade_control_plane_first
upgrade_workers_second
```

## Interview Answer

**Question: "What is the correct order to upgrade a Kubernetes cluster?"**

**Answer:**

```
There's a specific order that MUST be followed. Breaking this
order causes downtime or data loss.

THE SEQUENCE:

PRE-UPGRADE:
1. Backup etcd (most critical - full cluster recovery)
2. Test in staging cluster first
3. Check CRD/Helm chart compatibility
4. Verify cluster health
5. Plan maintenance window

PHASE 1: CONTROL PLANE
1. SSH to control plane node
2. Upgrade kubeadm binary
3. Run: kubeadm upgrade plan (preview changes)
4. Run: kubeadm upgrade apply v1.X.Y (API server down 30-120s)
5. Upgrade kubelet and kubectl on control plane
6. Restart kubelet
7. Wait for API server to be ready (30 seconds)

PHASE 2: WORKER NODES (One at a time!)
For each worker node:
1. kubectl drain node --ignore-daemonsets --force
   └─ Evicts pods, reschedules on other nodes
2. SSH to worker node
3. Upgrade kubeadm binary
4. Run: kubeadm upgrade node
5. Upgrade kubelet and kubectl
6. Restart kubelet
7. kubectl uncordon node (bring back online)
8. Wait for node to be Ready
9. Wait 10 seconds, move to next node

POST-UPGRADE:
1. Verify all nodes are Ready
2. Verify all pods are Running
3. Check metrics are working
4. Test applications
5. Monitor for issues

CRITICAL RULES:
✓ Always backup etcd first
✓ Control plane BEFORE workers
✓ One minor version at a time (1.25→1.26→1.27, not skip)
✓ One worker node at a time (never all at once)
✓ Upgrade CRDs before cluster upgrade
✓ Test in staging cluster first

WHY THIS ORDER:
- Control plane first: API server must support new APIs from workers
- Workers one at a time: Prevents complete service downtime
- Backup first: Can rollback if anything goes wrong
- Drain before upgrade: No pod interruption/migration
- Sequential versions: Each version tested, unsupported skips break things

KEY INSIGHT:
The order prevents:
├─ API incompatibility (control plane first)
├─ Service downtime (rolling worker upgrades)
├─ Data loss (etcd backup)
└─ Unknown issues (staging test first)
```
