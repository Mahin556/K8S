These questions are based on real-world scenarios (like the EKS upgrade demo covered in your video) and cover general Kubernetes concepts, managed cloud services (EKS/AKS/GKE), and advanced troubleshooting.

## Category 1: Foundational Concepts & Versioning

**Q1: What is the difference between upgrading the Control Plane and upgrading the Worker Nodes?**
> **Ideal Answer**: The Control Plane (Master nodes) manages the cluster state, API server, and scheduler. Upgrading it changes the Kubernetes API version. Worker Nodes are where your application pods run. Upgrading worker nodes updates the `kubelet` version and the underlying OS. **Upgrading the Control Plane does NOT automatically upgrade the worker nodes.**

**Q2: Can I skip minor versions when upgrading a Kubernetes cluster?**
> **Ideal Answer**: **No.** Kubernetes only supports upgrading **one minor version at a time** (e.g., `1.33` → `1.34`). You cannot jump from `1.30` to `1.34` directly. You must pass through `1.31`, `1.32`, and `1.33` sequentially. This is due to the deprecation of API versions and the version skew policy.

**Q3: What is the Kubernetes Version Skew Policy?**
> **Ideal Answer**: It defines the maximum version difference allowed between components. For example:
> - The `kube-apiserver` can be at most **1 minor version** ahead of the `kubelet`.
> - `kubectl` can be 1 version behind or 1 version ahead of the API server.
> This is exactly why you must upgrade nodes *after* the control plane, not before.

## Category 2: The Upgrade Hierarchy & Order of Operations

**Q4: What is the exact order of upgrading components in a production Kubernetes cluster?**
> **Ideal Answer**: 
> 1. **Control Plane** (Master).
> 2. **Add-ons** (CoreDNS, kube-proxy, CNI/VPC-CNI).
> 3. **Node Groups** (Worker nodes).
> 4. **Workloads** (Optional – only if API versions used in the workload are deprecated).
> You must never do this in reverse.

**Q5: Why do we need to upgrade Add-ons (CoreDNS/kube-proxy/CNI) separately?**
> **Ideal Answer**: The Control Plane exposes new API endpoints and features. Add-ons like `kube-proxy` and `CNI` rely on internal communication channels (like the API server). If they remain on an older version, they may use deprecated APIs or lack compatibility with the new `kubelet` communication standards, causing networking failures.

**Q6: If I only upgrade the Control Plane, does my cluster completely move to the new version?**
> **Ideal Answer**: **No.** This is a common misconception. The cluster version is determined by the Control Plane, but the cluster is *fully upgraded* only when Nodes and Add-ons match the Control Plane version. If you stop after the Control Plane, you are in a mixed-version state, which is supported temporarily but not recommended for long-term production.

## Category 3: Zero Downtime & Rolling Updates

**Q7: How do you upgrade worker nodes without causing application downtime?**
> **Ideal Answer**: By using a **Rolling Update Strategy** (especially in managed node groups).
> **The Process**:
> 1. A new node with the updated version is provisioned and joins the cluster.
> 2. `kubectl cordon` is applied to the old node (marking it unschedulable).
> 3. `kubectl drain` is applied, evicting pods gracefully (respecting `PodDisruptionBudgets`).
> 4. Pods reschedule onto the new node.
> 5. The old node is terminated.
> This cycle repeats for each node, ensuring at least one node is always serving traffic.

**Q8: What is `kubectl cordon` and `kubectl drain`? Why are they critical?**
> - **Cordon**: Marks a node as unschedulable, preventing new pods from landing on it.
> - **Drain**: Safely evicts all pods from a node, respecting `terminationGracePeriodSeconds` and PDBs.
> - **Critical**: If you terminate a node without draining, you cause sudden pod terminations, leading to 5xx errors or data corruption.

**Q9: How do `PodDisruptionBudgets` (PDBs) help during a cluster upgrade?**
> **Ideal Answer**: PDBs limit the number of pods that can be voluntarily evicted at the same time. During a `kubectl drain`, Kubernetes checks the PDB. If evicting a pod would violate the PDB (e.g., dropping below the minimum replicas), the drain pauses, ensuring high availability is maintained throughout the node upgrade.

## Category 4: Pre-Upgrade Checks & Troubleshooting

**Q10: What pre-upgrade checks should you perform before starting the upgrade?**
> **Ideal Answer**: 
> 1. **Check Upgrade Insights** (in EKS) or `kubeadm upgrade plan` (for self-managed) to find deprecated APIs.
> 2. **Verify all nodes are healthy** (`kubectl get nodes`).
> 3. **Check add-on versions** – ensure they are compatible with the target version.
> 4. **Review Deprecated APIs** – use `kubectl get apiservices` or tools like `Pluto` to ensure no workloads are using removed API versions.
> 5. **Backup etcd** (for self-managed clusters).

**Q11: You run the pre-upgrade check and see "errors" in the Upgrade Insights. What do you do?**
> **Ideal Answer**: **Fix the errors first.** Never proceed with an upgrade if existing errors are present. In the demo, we intentionally downgraded `kube-proxy`. The fix was to upgrade it back to the latest compatible version for the *current* cluster version. If you ignore errors, the upgrade will likely fail or leave the cluster in a broken state.

**Q12: During the upgrade, an Add-on (like CoreDNS) gets stuck in a "Pending" state. How do you troubleshoot?**
> **Ideal Answer**:
> 1. Check events: `kubectl describe pods -n kube-system`.
> 2. Check if the new version requires an updated `ConfigMap` or IAM permissions (for EKS).
> 3. Check if the Control Plane fully finished upgrading (sometimes the API server is unstable immediately after the upgrade).
> 4. Manually rollback the add-on to the previous working version, investigate the logs, and attempt the upgrade again with the correct parameters.

## Category 5: Managed Services (EKS / AKS / GKE)

**Q13: How does upgrading an EKS cluster differ from upgrading a self-managed `kubeadm` cluster?**
> **Ideal Answer**:
> - **EKS**: AWS manages the Control Plane upgrade for you (just click a button or CLI). However, you are **responsible** for upgrading the Managed Node Groups and Add-ons (VPC-CNI, CoreDNS, kube-proxy) separately.
> - **kubeadm**: You run `kubeadm upgrade apply` on the master nodes and `kubeadm upgrade node` on the workers, and you must handle etcd backups and certificate rotations manually.

**Q14: In EKS, why can't I just patch an existing Node Group; why do I need to "Update" it?**
> **Ideal Answer**: EKS Managed Node Groups are immutable. You cannot change the AMI or Kubernetes version of an existing running EC2 instance. Instead, the "Update" action triggers a rolling replacement. It launches new instances with the new AMI and version, drains the old ones, and terminates them. 

**Q15: What happens if I upgrade the Control Plane in EKS but forget to upgrade the Node Groups?**
> **Ideal Answer**: The cluster will be in a "mixed-version" state. Nodes will remain on `1.33` while the API server is on `1.34`. This is allowed by the version skew policy for a short period. However, some new features will be unavailable, and eventually, `kubelet`/API server communication may break if the version gap exceeds the allowed skew (which is typically 2 minor versions). You must complete the node upgrade within a reasonable timeframe.

## Category 6: Advanced/Scenario-Based Questions

**Q16: You upgraded the Control Plane, but a critical Pod keeps crashing. You suspect the API version is deprecated. How do you debug?**
> **Ideal Answer**: 
> 1. Check the pod logs: `kubectl logs <pod> --previous`.
> 2. Check the API server audit logs for rejected requests.
> 3. Use `kubectl explain <resource>` to see if the `apiVersion` used in the YAML is still supported in the new version.
> 4. If the API is removed (e.g., `v1beta1` vs `v1`), update the YAML manifest and re-apply it, or use the conversion webhook if available.

**Q17: What is the biggest risk when doing a cluster upgrade and how do you mitigate it?**
> **Ideal Answer**: The **biggest risk is database schema/data compatibility**, followed by **API deprecation**. Mitigations:
> - **Test in a Staging Environment** first (identical configuration).
> - **Take screenshots/backups** of current state (as shown in the demo).
> - **Read the release notes** for the target version carefully.
> - **Maintain a strict rollout sequence** and have a documented rollback plan (e.g., "If this fails, we revert the Control Plane to the previous version, though Control Plane rollbacks are highly discouraged and usually require restoring from etcd snapshots").

**Q18: Can you roll back a Control Plane upgrade if it fails?**
> **Ideal Answer**: **It is extremely risky and generally not recommended.** For managed services (EKS/AKS/GKE), downgrading the Control Plane is **not supported** via the UI/CLI. For self-managed clusters, you can theoretically restore from an etcd snapshot, but it involves downtime. **Best Practice**: Always test thoroughly in lower environments first, and rely on rolling back Worker Nodes/Add-ons if they fail, rather than downgrading the Control Plane.

**Q19: How does upgrading affect the `etcd` database?**
> **Ideal Answer**: When you upgrade the Control Plane, the API server updates its internal storage versioning. `etcd` itself may be automatically upgraded by the cloud provider (EKS) or manually (`kubeadm`). You must ensure the `etcd` version is compatible with the new Kubernetes version. **Always take an etcd snapshot backup before any Control Plane upgrade in self-managed clusters.**

**Q20: You have 10 microservices. The upgrade breaks only the "Payment" service. How do you roll back without affecting the other 9?**
> **Ideal Answer**: Since the Node Groups and Control Plane are already upgraded, you **cannot roll them back easily**. Instead:
> 1. Roll back the **Workload** by reverting the Deployment's image tag to the previous stable version.
> 2. If the issue is due to a missing API in the new version, update the Payment service's YAML to use the new API version and redeploy it.
> 3. This isolates the rollback/fix to the specific service, leaving the other 9 intact. (This is why upgrading workloads is optional).

## Quick "Cheat Sheet" for the Interviewer's Favorite Question

**If an interviewer asks: *"Walk me through how you would upgrade a production EKS cluster from 1.33 to 1.34."***

Your concise answer should be:
> *"First, I check Upgrade Insights to ensure no blocking errors. I fix any errors (e.g., updating kube-proxy). I upgrade the Control Plane. Once active, I sequentially upgrade the Add-ons: CoreDNS, VPC-CNI, and kube-proxy. I then upgrade the Node Groups using a Rolling Update to ensure zero downtime (cordon + drain). Finally, I verify deprecated APIs and decide if Workloads need patching. I take screenshots before and after to document the state."*
