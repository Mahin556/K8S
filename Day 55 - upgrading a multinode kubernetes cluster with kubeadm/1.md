# Comprehensive Guide: Upgrading an Amazon EKS Cluster (1.33 to 1.34)

Upgrading a Kubernetes cluster—especially in production—is **not** a single-click or single-command operation. It requires a structured, phased approach to ensure zero downtime and stability.

This guide walks you through the exact hierarchy, prerequisites, and practical steps to upgrade an Amazon EKS cluster from version **1.33 to 1.34**, including handling errors, upgrading add-ons, and rolling out worker nodes.

---

## 1. Core Concepts & Upgrade Hierarchy

### The Golden Rule of Upgrades
Executing a command like `aws eks update-cluster-version` **only upgrades the Control Plane (Master Nodes)**. It does *not* upgrade your worker nodes, add-ons, or workloads.

To fully upgrade a cluster, you must follow a strict **Hierarchy**:

1.  **Upgrade the Control Plane** (Master nodes).
2.  **Upgrade Add-Ons** (Networking components: `kube-proxy`, `CoreDNS`, `VPC-CNI`).
3.  **Upgrade Node Groups** (Worker nodes).
4.  **Upgrade Workloads** (Optional, only if your pod specifications require the new version).

### The "No Skip" Version Rule
**You cannot skip minor versions.** 
If your cluster is on `1.30` and you want to reach `1.34`, you must go sequentially:
`1.30` → `1.31` → `1.32` → `1.33` → `1.34`.

## 2. Prerequisites & Tool Setup

To follow this demo on a local machine (Windows, using VS Code), ensure the following tools are installed and added to your system's `PATH`.

| Tool | Purpose |
| :--- | :--- |
| **AWS CLI** | To interact with AWS services. |
| **`eksctl`** | To create and manage EKS clusters. |
| **`kubectl`** | To communicate with the Kubernetes API server. |
| **IAM User** | *Do not use root*. Create a dedicated IAM user with `AdministratorAccess` (for demo purposes) and generate Access Keys. |

**Setup Commands (Conceptual)**:
```bash
# Configure AWS CLI with your IAM user credentials
aws configure

# Verify tools are accessible

```

## 3. Phase 0: Setting Up the Demo Scenario

We will create a cluster on version **1.33**, intentionally introduce an error (by downgrading `kube-proxy`), and deploy an NGINX workload to test for downtime.

**1. Create the EKS Cluster (v1.33)**
```bash
eksctl create cluster \
  --name product-upgrade-demo \
  --region ap-south-1 \
  --version 1.33 \
  --nodegroup-name ng-1 \
  --node-type t3.medium \
  --nodes 2 \
  --managed
```
*Wait for CloudFormation to finish provisioning the stack.*

**2. Introduce an Error (Simulating Real-World Mess)**
In the AWS Console:
- Navigate to **EKS** → Your Cluster → **Add-ons**.
- Select `kube-proxy` → Click **Edit**.
- Downgrade it to the **oldest available version**.
- Click **Save Changes**.
- Go to the **Upgrade Insights** tab and click **Refresh Insights**. You will see errors here.

**3. Deploy a Workload (To Verify Zero Downtime)**
```bash
kubectl create deployment nginx-deploy --image=nginx
kubectl get pods -w
```
*Keep this terminal open to watch if the pods restart during the upgrade.*

---

## 4. Phase 1: Pre-Upgrade Checks (Fixing Errors)

**Crucial Rule**: *Never* upgrade a cluster if it has existing errors.
Before upgrading the Control Plane, you must fix the errors displayed in **Upgrade Insights**.

**1. Fix `kube-proxy`**:
- Go back to **Add-ons** → `kube-proxy` → **Edit**.
- Select the **latest version compatible with 1.33** (e.g., if current is `1.30`, upgrade to `1.33`).
- Click **Save Changes**.

**2. Verify Errors are Resolved**:
- Go to **Upgrade Insights** and click **Refresh Insights**.
- Confirm all checks now show a **"Passing"** status.
- *Take Screenshots*: It is a best practice to screenshot the current state (versions, node status, pods) before proceeding.

---

## 5. Phase 2: Upgrade the Control Plane

Now that the cluster is healthy, upgrade the master nodes.

1.  In the EKS Console, click the **Upgrade** button.
2.  Select the **next available version** (Since you are on `1.33`, select `1.34`).
3.  Click **Upgrade**.
    *Wait for the status to change to `Active` (takes 5-10 minutes).*

**Update `kubectl` locally** (Optional but recommended):
Download the `1.34` version of `kubectl` and add it to your `PATH` so your client matches the server.

---

## 6. Phase 3: Upgrade Add-Ons (Networking)

With the Control Plane on `1.34`, the add-ons must be updated to match the new API versions.

**Upgrade these three components in the AWS Console:**

1.  **CoreDNS**: Go to Add-ons → `coredns` → Edit → Select the latest version → Save.
2.  **VPC-CNI**: Go to Add-ons → `vpc-cni` → Edit → Select the latest version → Save.
3.  **kube-proxy**: Go to Add-ons → `kube-proxy` → Edit → Select the latest `1.34` compatible version → Save.

*Wait until all statuses show **"Active"** before proceeding.*

---

## 7. Phase 4: Upgrade Node Groups (Worker Nodes)

This is where we ensure **zero downtime**. We will use a **Rolling Update** strategy.

**Mechanism of a Rolling Update (Diagrammatic)**:
- *Initial State*: Node A (Old) & Node B (Old).
- *Step 1*: Node C (New) joins the cluster.
- *Step 2*: Pods are drained/scheduled from Node A to Node C.
- *Step 3*: Node A (Old) is terminated.
- *Step 4*: Node D (New) joins the cluster.
- *Step 5*: Pods are drained from Node B to Node D.
- *Step 6*: Node B (Old) is terminated.

**How to execute**:
1.  In the EKS Console, go to your Cluster → **Compute** → Select your Node Group (`ng-1`).
2.  Click **Update**.
3.  Under **Update strategy**, ensure **Rolling Update** is selected.
4.  Click **Update**.

**Monitor in real-time**:
Run this command to watch the nodes change:
```bash
kubectl get nodes -w
```
You will see new nodes appear (with the `1.34` version) and old nodes terminate.
Run this to verify your NGINX pods never restarted:
```bash
kubectl get pods
```
*(The AGE column will show they have been running for a long time, confirming zero downtime).*

---

## 8. Phase 5: Upgrade Workloads (Optional)

If your applications require specific Kubernetes API versions that are deprecated in `1.34`, you will need to update your Deployment YAMLs (e.g., changing `apiVersion` for `Ingress` or `CRDs`).

In our demo, NGINX does not require an upgrade, so we **skip** this phase.

---

## 9. Post-Upgrade Verification & Audit

Once everything is complete:

1.  **Verify Cluster Version**:
    ```bash
    kubectl version
    ```
2.  **Verify Node Versions**:
    ```bash
    kubectl get nodes
    ```
    *(Should show `v1.34.x` for all nodes)*.
3.  **Verify Add-Ons**: In the Console, ensure all add-ons show the updated version numbers.
4.  **Take Screenshots**: Capture the final state of the cluster, nodes, and add-ons to share with your team or manager as proof of successful upgrade.

---

## 10. Cleanup (To avoid AWS Charges)

After the demo, delete the cluster:
```bash
eksctl delete cluster product-upgrade-demo --region ap-south-1
```

---

## Key Takeaways for Production Upgrades

| Best Practice | Why it matters |
| :--- | :--- |
| **Fix Errors First** | Upgrading a broken cluster will likely fail or compound issues. |
| **Never Skip Versions** | EKS only supports upgrading one minor version at a time. |
| **Use Rolling Updates** | Prevents application downtime by spinning up new nodes before draining old ones. |
| **Upgrade Add-Ons Separately** | Networking components must be compatible with the new Control Plane version. |
| **Screenshot Everything** | Provides an audit trail and helps revert if a configuration change is lost. |
| **Check Workload Compatibility** | Ensure your YAML manifest API versions are not deprecated in the new Kubernetes release. |
