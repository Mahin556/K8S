## Why CPU/Memory alone often lies to you

The core problem: **CPU usage ≠ actual user-facing load**, especially for I/O-bound or queue-based systems. Let me show you exactly how this breaks down with numbers.

### Example: The "moderate CPU but users are suffering" trap

Imagine an API server that mostly does this per request:

```
1. Receive request          (negligible CPU)
2. Query Postgres           (waits 200ms — CPU idle during wait)
3. Call external payment API (waits 300ms — CPU idle)
4. Return response          (negligible CPU)
```

Even with **500 concurrent users**, CPU might sit at **35%** because the pod spends most of its time *waiting*, not *computing*. Your HPA target is `averageUtilization: 70` — so HPA does nothing. Meanwhile, request queues build up, latency climbs, and users see timeouts. CPU-based HPA is **blind to this entirely**, because it was never measuring the right thing.

## Custom Metrics: 3 real-world setups with full configs

### 1. Queue Length (for background workers — Kafka/SQS/RabbitMQ)

Say you have a worker pod consuming from an SQS queue. Low CPU, but queue depth tells the real story.

**Step 1**: Expose queue depth as a Prometheus metric (via your app or an exporter like `sqs-exporter`):
```
sqs_queue_depth{queue_name="order-processing"} 4500
```

**Step 2**: Prometheus Adapter config to expose this to Kubernetes' Custom Metrics API:
```yaml
rules:
- seriesQuery: 'sqs_queue_depth{queue_name="order-processing"}'
  resources:
    overrides:
      namespace: {resource: "namespace"}
  name:
    matches: "sqs_queue_depth"
    as: "sqs_queue_depth_order_processing"
  metricsQuery: 'avg(sqs_queue_depth{queue_name="order-processing"})'
```

**Step 3**: HPA using this metric:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-worker-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-worker
  minReplicas: 2
  maxReplicas: 50
  metrics:
  - type: External
    external:
      metric:
        name: sqs_queue_depth_order_processing
      target:
        type: AverageValue
        averageValue: "100"   # target: each pod should handle ~100 queued messages
```

**What this means in practice**: If queue depth = 4500 and target = 100 per pod → HPA computes `desired replicas ≈ 4500 / 100 = 45 pods`. CPU might show 20% the whole time — completely irrelevant. The queue depth is the *real* signal of backlog pressure.

> **Note**: In real-world practice, people often use **KEDA** instead of raw Prometheus Adapter for exactly this use case — KEDA has built-in scalers for SQS, Kafka, RabbitMQ, etc., and is much less boilerplate. Worth mentioning if you're setting this up for real.

### 2. Request Rate (RPS) — for APIs/frontends

Say you expose this Prometheus metric via your app (or via Istio/Envoy sidecar metrics):
```
http_requests_total{service="checkout-api"}
```

You'd typically compute RPS using a Prometheus query like `rate(http_requests_total[1m])`, then expose it via the adapter:

```yaml
rules:
- seriesQuery: 'http_requests_total{service="checkout-api"}'
  resources:
    overrides:
      namespace: {resource: "namespace"}
      pod: {resource: "pod"}
  name:
    matches: "http_requests_total"
    as: "http_requests_per_second"
  metricsQuery: 'sum(rate(http_requests_total{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)'
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-api
  minReplicas: 3
  maxReplicas: 60
  metrics:
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "50"    # each pod should handle ~50 RPS
```

**Real scenario**: Black Friday traffic hits 3000 RPS total. With target = 50 RPS/pod → HPA scales to `3000/50 = 60 pods` (hits maxReplicas). CPU during this might only be at 45% per pod — well under any CPU threshold — but RPS-based scaling correctly anticipates the load *before* CPU even becomes a bottleneck, because RPS often rises before CPU saturates.

### 3. Latency / Error Rate — proactive scaling before SLA breach

```
http_request_duration_seconds_bucket{service="checkout-api"}  (histogram)
```

Prometheus query to get p95 latency:
```
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket{service="checkout-api"}[5m]))
```

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-api-latency-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-api
  minReplicas: 3
  maxReplicas: 60
  metrics:
  - type: External
    external:
      metric:
        name: checkout_api_p95_latency_seconds
      target:
        type: Value
        value: "0.5"    # if p95 latency exceeds 500ms, scale up
```

**Why this matters**: CPU at 60% might look "healthy," but if p95 latency has crept from 100ms to 600ms (maybe due to a slow downstream dependency, lock contention, or GC pauses), users are already feeling pain. Scaling on latency catches degradation **before** it shows up as a CPU spike — sometimes it never does, because the bottleneck might be elsewhere (e.g., a database connection pool), and simply adding more pods that each open more connections genuinely helps relieve that pressure.

## Side-by-side: combining multiple metrics in one HPA

You can combine built-in and custom metrics in a single HPA — HPA evaluates **all of them** and picks whichever metric demands the **most replicas**:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: checkout-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: checkout-api
  minReplicas: 3
  maxReplicas: 60
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "50"
  - type: External
    external:
      metric:
        name: checkout_api_p95_latency_seconds
      target:
        type: Value
        value: "0.5"
```

**How HPA decides here**: it computes the desired replica count separately for CPU, RPS, and latency — then **takes the maximum** of all three. So even if CPU says "you're fine, stay at 5 pods," but latency says "you need 20 pods," HPA scales to 20. This is the practical realization of the doc's main point: *CPU is just one signal among many, and often not the most honest one.*

## Quick comparison table

| Metric type | Best for | Blind spot if used alone |
|---|---|---|
| **CPU/Memory** (built-in) | Compute-heavy workloads (video encoding, ML inference) | Misses I/O-bound bottlenecks, queue backlogs, latency issues |
| **Queue length** (external) | Background workers (Kafka, SQS, RabbitMQ consumers) | Doesn't capture per-request performance directly |
| **Request rate / RPS** (custom) | Web APIs, frontend services | Doesn't catch slow requests if RPS is steady but latency rises |
| **Latency / error rate** (external) | SLA-sensitive customer-facing services | Reactive in nature — by the time latency rises, some users have already been affected; needs careful thresholds |

The doc's core message, in one line: **CPU/memory tell you about the machine; custom/external metrics tell you about the application's actual experience of load** — and for most modern, distributed, I/O-heavy systems, it's the latter that should really be driving scaling decisions.
