# Kubernetes DNS Debugging — Complete Guide

---

## Part 1 — How DNS Resolution Actually Works (BTS)

Before debugging, understand the exact chain every DNS query travels.
Most debugging mistakes come from checking the wrong layer.

```
Pod wants to reach "payment-service"
          │
          ▼
1. Pod's /etc/resolv.conf (check this FIRST)
   nameserver 10.96.0.10       ← CoreDNS Service ClusterIP
   search default.svc.cluster.local svc.cluster.local cluster.local
   options ndots:5

2. Pod sends UDP query to 10.96.0.10:53

3. kube-proxy / iptables routes 10.96.0.10 → CoreDNS pod IP

4. CoreDNS receives query

5. CoreDNS checks its Corefile zones:
   ├── cluster.local → kubernetes plugin (talks to kube-apiserver)
   ├── in-addr.arpa  → kubernetes plugin (reverse DNS)
   └── . (dot)       → forward to upstream (node's DNS)

6. kubernetes plugin queries kube-apiserver:
   "give me endpoint for payment-service.default.svc.cluster.local"

7. kube-apiserver returns Service ClusterIP

8. CoreDNS returns A record: payment-service → 10.96.45.23

9. Pod connects to 10.96.45.23
```

### What `ndots:5` means and why it causes failures

The `ndots:5` setting is the #1 source of DNS latency issues in Kubernetes
and is often confused with actual resolution failures.

When a pod queries `payment-service` (a name with 0 dots, which is < 5):
```
Kubernetes tries these IN ORDER until one resolves:
1. payment-service.default.svc.cluster.local  ← succeeds, stops here
2. payment-service.svc.cluster.local          ← never tried (already found)
3. payment-service.cluster.local
4. payment-service.<node-domain>
5. payment-service.                           ← bare name (absolute)

But for "api.external.example.com" (3 dots, still < 5):
1. api.external.example.com.default.svc.cluster.local  ← fails (NXDOMAIN)
2. api.external.example.com.svc.cluster.local           ← fails
3. api.external.example.com.cluster.local               ← fails
4. api.external.example.com.<node-domain>               ← fails
5. api.external.example.com.                            ← succeeds finally
   = 5 DNS queries instead of 1 = latency spike
```

This is why external DNS lookups from pods are slow — 4 unnecessary queries
before the real one. Fix: use FQDNs with a trailing dot for external names,
or reduce ndots for pods that primarily call external services.

## Part 2 — The Four DNS Policies (With Real Use Cases)

### ClusterFirst (default — use for almost everything)
```yaml
dnsPolicy: ClusterFirst
# Pod's /etc/resolv.conf will contain:
# nameserver <CoreDNS ClusterIP>
# search <namespace>.svc.cluster.local svc.cluster.local cluster.local
# options ndots:5
```
Queries → CoreDNS first → if not cluster name, forward to node's upstream DNS.
Use for: every standard workload.

### Default (misleadingly named — NOT the default)
```yaml
dnsPolicy: Default
# Pod's /etc/resolv.conf COPIED from the host node's /etc/resolv.conf
# nameserver 8.8.8.8  (or whatever the node uses)
# NO cluster DNS search domains
# NO CoreDNS
```
This pod CANNOT resolve Kubernetes service names at all.
Use for: pods that specifically must NOT use cluster DNS (rare).
Common mistake: people write `dnsPolicy: Default` thinking it's the default
policy, then wonder why service discovery is broken.

### ClusterFirstWithHostNet
```yaml
hostNetwork: true         # pod shares node's network namespace
dnsPolicy: ClusterFirstWithHostNet   # MUST use this, not ClusterFirst
# Without this: hostNetwork pods use node DNS (can't resolve services)
# With this: hostNetwork pods can still reach CoreDNS
```
Use for: DaemonSets, CNI plugins, monitoring agents that need host networking
but still need to call Kubernetes services.

### None
```yaml
dnsPolicy: None
dnsConfig:                # REQUIRED when policy is None
  nameservers:
    - 1.1.1.1
    - 8.8.8.8
  searches:
    - custom.domain.local
  options:
    - name: ndots
      value: "2"
```
Pod ignores ALL Kubernetes DNS. You configure everything manually.
Use for: custom DNS servers, specific resolver requirements.

## Part 3 — Systematic Debugging (In Order)

Never jump to "restart CoreDNS" first. Follow this sequence:

### Step 1 — Confirm the problem is actually DNS, not the service itself
```bash
# First: is the service there and does it have endpoints?
kubectl get svc payment-service -n default
# NAME              TYPE        CLUSTER-IP     PORT(S)
# payment-service   ClusterIP   10.96.45.23    8080/TCP

kubectl get endpoints payment-service -n default
# NAME              ENDPOINTS          AGE
# payment-service   10.244.1.5:8080    5m
# If ENDPOINTS is <none> → service selector doesn't match pod labels
# → DNS works but there's nothing to route to — DIFFERENT problem

# Check service selector vs pod labels:
kubectl describe svc payment-service -n default | grep Selector
# Selector: app=payment  ← must match pod label

kubectl get pods -n default --show-labels | grep payment
# payment-pod   Running   app=payments  ← TYPO: "payments" ≠ "payment"
```

### Step 2 — Verify DNS from inside the failing pod
```bash
# Run a debug container in the SAME pod's namespace
kubectl exec -it <failing-pod> -n default -- /bin/sh

# Check resolv.conf — this is what's actually used
cat /etc/resolv.conf
# Expected output:
# nameserver 10.96.0.10       ← must point to CoreDNS ClusterIP
# search default.svc.cluster.local svc.cluster.local cluster.local
# options ndots:5

# If nameserver is NOT the CoreDNS ClusterIP:
kubectl get svc kube-dns -n kube-system
# This shows the CoreDNS ClusterIP — compare with resolv.conf

# Test DNS resolution manually (use nslookup or dig)
nslookup payment-service
# Expected: Address: 10.96.45.23

nslookup payment-service.default.svc.cluster.local
# Full FQDN — if this works but short name doesn't:
# → search domain problem in resolv.conf

nslookup kubernetes.default.svc.cluster.local
# Test if CoreDNS itself responds — kubernetes service is always present
# If THIS fails: CoreDNS is the problem
# If THIS succeeds but payment-service fails: service definition problem
```

### Step 3 — Deploy a dedicated DNS debugging pod
```bash
# If the failing pod has no networking tools (distroless images):
kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: dnsutils
  namespace: default
spec:
  containers:
    - name: dnsutils
      image: registry.k8s.io/e2e-test-images/jessie-dnsutils:1.3
      command:
        - sleep
        - "infinity"
  restartPolicy: Always
EOF

kubectl exec -it dnsutils -n default -- nslookup payment-service
kubectl exec -it dnsutils -n default -- dig payment-service.default.svc.cluster.local
```

### Step 4 — Check CoreDNS health
```bash
# Are CoreDNS pods running?
kubectl get pods -n kube-system -l k8s-app=kube-dns
# NAME                       READY   STATUS    RESTARTS
# coredns-5d78c9869d-2xvf9   1/1     Running   0
# coredns-5d78c9869d-q8r7k   1/1     Running   0
# READY must be 1/1, not 0/1

# Are CoreDNS pods crash-looping?
kubectl get pods -n kube-system -l k8s-app=kube-dns -w
# Watch for RESTARTS count climbing

# Check CoreDNS logs for actual errors:
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50
# Real error patterns to look for:
# [ERROR] plugin/errors: 2 SERVFAIL     ← upstream DNS failing
# [ERROR] Failed to list *v1.Service     ← can't reach kube-apiserver
# [WARNING] Shutting down                ← OOMKilled, check resource limits

# CoreDNS metrics (if Prometheus is running):
kubectl port-forward svc/kube-dns -n kube-system 9153:9153
curl localhost:9153/metrics | grep coredns_dns_requests_total
```

### Step 5 — Check CoreDNS ConfigMap
```bash
kubectl get configmap coredns -n kube-system -o yaml
```

Expected Corefile:
```
.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
       max_concurrent 1000
    }
    cache 30
    loop
    reload
    loadbalance
}
```

Common misconfiguration patterns:
```
# BROKEN: wrong cluster domain
kubernetes wrong.domain in-addr.arpa ip6.arpa   ← doesn't match --cluster-domain flag

# BROKEN: forward plugin pointing to unreachable DNS
forward . 192.168.1.1 {                         ← that IP isn't reachable from pods

# BROKEN: loop plugin missing
# Without "loop", if upstream DNS forwards back to CoreDNS:
# CoreDNS → node DNS → CoreDNS → node DNS → infinite loop
# → entire cluster DNS becomes unresponsive
```

### Step 6 — Check CoreDNS Service and RBAC
```bash
# CoreDNS needs a ClusterIP Service for pods to reach it
kubectl get svc kube-dns -n kube-system
# NAME       TYPE        CLUSTER-IP   PORT(S)
# kube-dns   ClusterIP   10.96.0.10   53/UDP,53/TCP

# If this service is missing or has wrong ClusterIP:
# ALL pods in cluster will have wrong nameserver in resolv.conf

# Check CoreDNS RBAC — it needs to list/watch Services and Endpoints:
kubectl get clusterrolebinding system:coredns
kubectl describe clusterrole system:coredns
# Must include: list, watch on services, endpoints, namespaces
```

### Step 7 — Network policy blocking DNS traffic
```bash
# If you have NetworkPolicies, they might be blocking port 53 to CoreDNS
kubectl get networkpolicies -n default

# Check if DNS traffic (UDP/TCP 53) to kube-system is allowed:
kubectl describe networkpolicy <policy-name> -n default
# Look for: is egress to port 53 allowed?

# Fix: add egress rule allowing DNS:
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: default
spec:
  podSelector: {}                    # applies to all pods in namespace
  policyTypes:
    - Egress
  egress:
    - ports:
        - port: 53
          protocol: UDP
        - port: 53
          protocol: TCP             # TCP needed for responses > 512 bytes
EOF
```

## Part 4 — Common Failure Modes and Exact Fixes

### Failure 1: NXDOMAIN for service in same namespace

```bash
# Test:
nslookup payment-service
# Server: 10.96.0.10
# ** server can't find payment-service: NXDOMAIN

# Diagnosis path:
nslookup payment-service.default.svc.cluster.local
# If THIS works: search domain is wrong in /etc/resolv.conf
# If this ALSO fails: service doesn't exist or CoreDNS can't see it

kubectl get svc payment-service -n default
# Error from server (NotFound): services "payment-service" not found
# → You're looking in wrong namespace, OR service name is wrong
```

### Failure 2: DNS works intermittently (50% failure rate)

```bash
# Symptom: nslookup sometimes works, sometimes doesn't
# Cause: CoreDNS pod is OOMKilled and restarting

kubectl describe pod -n kube-system <coredns-pod> | grep -A5 "OOMKilled"
# Reason: OOMKilled  ← confirms memory issue

# Fix: increase CoreDNS memory limits
kubectl edit deployment coredns -n kube-system
# resources:
#   limits:
#     memory: 170Mi    ← default, increase to 512Mi or more
#   requests:
#     cpu: 100m
#     memory: 70Mi
```

### Failure 3: DNS resolves but very slowly (external names)

```bash
# External DNS queries taking 2-5 seconds instead of milliseconds
# Root cause: ndots:5 causing 4 failed searches before real query

# Measure it:
time nslookup api.github.com    # from inside a pod
# real 0m4.237s  ← 4 failed cluster.local searches first

# Fix option 1: use FQDN with trailing dot
curl https://api.github.com./v3/  # trailing dot = absolute name, 1 query

# Fix option 2: reduce ndots for pods that mainly call external services
dnsConfig:
  options:
    - name: ndots
      value: "2"    # only append search domains for names with < 2 dots
                    # "api.github.com" has 2 dots → goes direct, no search

# Fix option 3: enable autopath in CoreDNS
# CoreDNS autopath plugin short-circuits the search domain expansion
# server-side, reducing 5 client queries to 1-2
```

### Failure 4: CoreDNS can't reach kube-apiserver

```bash
# CoreDNS logs show:
# [ERROR] Failed to list *v1.Service: Get "https://10.96.0.1:443/api/v1/services":
# dial tcp 10.96.0.1:443: connect: connection refused

# CoreDNS RBAC is broken, or the kubernetes service itself is down
kubectl get svc kubernetes -n default
# NAME         TYPE        CLUSTER-IP   PORT(S)
# kubernetes   ClusterIP   10.96.0.1    443/TCP

# Check RBAC:
kubectl auth can-i list services --as=system:serviceaccount:kube-system:coredns
# no ← RBAC is broken, CoreDNS can't talk to API server
# Fix: reapply CoreDNS RBAC
```

### Failure 5: hostNetwork pod can't resolve services

```bash
# Pod spec:
hostNetwork: true
dnsPolicy: ClusterFirst   # ← WRONG for hostNetwork pods

# Fix:
hostNetwork: true
dnsPolicy: ClusterFirstWithHostNet   # ← CORRECT
```

### Failure 6: Pod has wrong dnsPolicy

```bash
# Pod was deployed with dnsPolicy: Default (not the default!)
kubectl get pod my-pod -o jsonpath='{.spec.dnsPolicy}'
# Default  ← using NODE's DNS, not CoreDNS

# Check what /etc/resolv.conf looks like inside:
kubectl exec my-pod -- cat /etc/resolv.conf
# nameserver 8.8.8.8   ← node's DNS, no cluster.local search domains

# Fix: update deployment to use ClusterFirst
kubectl patch deployment my-deployment -p \
  '{"spec":{"template":{"spec":{"dnsPolicy":"ClusterFirst"}}}}'
```

## Part 5 — DNS Debugging Cheatsheet

```bash
# ─── Quick diagnostic sequence ───────────────────────────────────────────

# 1. Is the service there?
kubectl get svc,endpoints <service-name> -n <namespace>

# 2. Does CoreDNS respond at all?
kubectl exec -it <pod> -- nslookup kubernetes.default.svc.cluster.local

# 3. Can I reach the specific service?
kubectl exec -it <pod> -- nslookup <service>.<namespace>.svc.cluster.local

# 4. What does the pod use for DNS?
kubectl exec -it <pod> -- cat /etc/resolv.conf

# 5. Is CoreDNS healthy?
kubectl get pods -n kube-system -l k8s-app=kube-dns
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=20

# 6. Is NetworkPolicy blocking port 53?
kubectl get netpol -n <namespace>

# 7. Enable CoreDNS query logging temporarily (disable after debug):
kubectl edit configmap coredns -n kube-system
# Add "log" to the Corefile:
# .:53 {
#     log          ← add this line
#     errors
#     ...
# }
# Then watch logs to see exactly what queries are coming in and failing

# ─── DNS resolution test from scratch ────────────────────────────────────

kubectl run dns-test --image=busybox:1.28 --rm -it --restart=Never -- \
  nslookup <service-name>.<namespace>.svc.cluster.local
```
