## What is `/etc/resolv.conf`?
It tells the system:
* Which DNS servers to use
* How DNS resolution should behave
* Search domains
* Resolver behavior options

---

### Main Configuration Directives

## nameserver
Defines DNS server IP address.
```bash
nameserver 8.8.8.8
nameserver 1.1.1.1
```
* System queries these in order
* Max usually 3 entries
* Can be IPv4 or IPv6


## search
Defines domain suffix search list.
```bash
search example.com corp.local
```
If you type:
```bash
ping server1
```
System tries:
```
server1.example.com
server1.corp.local
```
Very common in enterprise networks.


## domain
Defines default domain.
```bash
domain example.com
```
Older directive.
Usually replaced by `search`.


## options
Controls resolver behavior.
Example:
```bash
options timeout:2 attempts:3 rotate
```
Common options:


### timeout:n
Wait time (seconds) before retry.
```
options timeout:2
```
Default ~5 seconds.

### attempts:n
Number of retry attempts per server.
```
options attempts:3
```

### rotate
Rotate between nameservers instead of always starting from first.
```
options rotate
```
Good for load balancing DNS queries.

### ndots:n
How many dots must exist before absolute query.
```
options ndots:2
```
Example:
If `ndots:1`
* `example.com` → treated as FQDN
* `server1` → search domain appended
Very important in Kubernetes (ndots:5 by default).

### single-request
Prevents sending IPv4 + IPv6 queries in parallel.
```
options single-request
```
Fixes some firewall/DNS bugs.

### single-request-reopen
Fixes broken NAT/firewall DNS issues.

### use-vc
Forces TCP instead of UDP for DNS.
```
options use-vc
```
Rarely used.

## Example Complete resolv.conf
```bash
nameserver 8.8.8.8
nameserver 1.1.1.1
search example.com corp.local
options timeout:2 attempts:3 rotate ndots:1
```

```
────────────────────────────────────────────────────────
BOX — ndots Explained in Simple Way
────────────────────────────────────────────────────────

# ndots decides:
# Should the resolver try the name directly
# OR try adding search domains first?

Rule:
# If number of dots in the name >= ndots
# → Try the name directly (absolute lookup)

# If number of dots < ndots
# → Try search domains first

--------------------------------------------------------

Example config:

options ndots:1
search example.com

--------------------------------------------------------

Case 1:

ping example.com

# example.com has 1 dot
# 1 >= 1 → direct lookup first

Resolver tries:
example.com

--------------------------------------------------------

Case 2:

ping server1

# server1 has 0 dots
# 0 < 1 → search domain used first

Resolver tries:
server1.example.com

--------------------------------------------------------

Now in Kubernetes:

options ndots:5
search default.svc.cluster.local svc.cluster.local cluster.local

If inside pod:

curl google.com

# google.com has 1 dot
# 1 < 5 → search domains tried first

Resolver tries:
google.com.default.svc.cluster.local
google.com.svc.cluster.local
google.com.cluster.local
google.com   ← finally correct one

--------------------------------------------------------

Result in Kubernetes:
# Extra DNS queries
# Slower external lookups
# More DNS load

--------------------------------------------------------

How to force direct lookup:

curl google.com.

# Adding trailing dot makes it fully qualified
# No search domains will be added

--------------------------------------------------------

Why ndots exists:

# Helps internal short names
# Example:
database
# becomes:
database.corp.local

--------------------------------------------------------

Quick summary:

ndots small  → external names resolve faster
ndots large  → internal service discovery preferred
────────────────────────────────────────────────────────
```

```text
────────────────────────────────────────────────────────
BOX — search Order Explained Simply
────────────────────────────────────────────────────────

# Yes, order in "search" absolutely matters.

The resolver:
# Tries search domains exactly in the order written.
# Stops at the first successful match.

--------------------------------------------------------

Example:

search corp.local example.com dev.internal

You run:

ping server1

Resolver tries in order:

1) server1.corp.local
2) server1.example.com
3) server1.dev.internal

# It stops when one works.

--------------------------------------------------------

Why order matters:

1) Performance

# If first domain does not exist
# Resolver waits for timeout
# Then tries the next one
# This causes delay

--------------------------------------------------------

2) Correctness

Example:

search dev.local prod.local

If both have "api":

api.dev.local
api.prod.local

Running:

curl api

# Will resolve to dev first
# Even if you wanted prod

--------------------------------------------------------

3) Security

Wrong order can:

# Resolve internal names externally
# Cause DNS leaks
# Route traffic incorrectly

--------------------------------------------------------

Interaction with ndots:

Resolver logic:

# If dots < ndots
# → Try search domains first (in order)

# Then try absolute name

So when ndots is high (like 5 in Kubernetes),
search order becomes even more important.

--------------------------------------------------------

How to check your config:

cat /etc/resolv.conf

--------------------------------------------------------

Quick summary:

Order matters? → Yes
Tried in order? → Yes
Stops at first success? → Yes
Can wrong order cause delay? → Yes

────────────────────────────────────────────────────────
```
