### DNS TTL Behavior & IP Change Strategy (Simplified)

* 🔹 **TTL (Time To Live)**

  * TTL is set in DNS record (in seconds).
  * It tells resolvers how long they can cache the record.

* 🔹 Example

  * If TTL = `600` seconds
  * Resolver (like ISP DNS or `8.8.8.8`) will cache it for **10 minutes**.
  * During those 10 minutes:

    * Even if you change the IP on authoritative DNS
    * Users may still get the **old (stale) IP**

* 🔹 Important

  * TTL starts counting when the resolver receives the response.
  * TTL changes are **NOT retroactive**.
  * If someone cached old TTL = 3600, lowering it later won’t affect them.

---

### 🚀 Best Practice Before Changing IP

1️⃣ Lower TTL in advance:

Example:

```text
From: 3600 (1 hour)
To:   60   (1 minute)
```

2️⃣ Wait several hours (at least old TTL duration).

3️⃣ After that, change the IP address.

4️⃣ Traffic will switch faster because resolvers now refresh quickly.

---

### ⚠️ Why This Matters

If you don’t lower TTL:

* Some users may hit old server
* Temporary downtime
* Load balancer / migration issues
* Split traffic between old and new IP

---

### 🔎 How to Check TTL

```bash
dig example.com
```

Look at the TTL column in the answer section.

---

### 🎯 DevOps Migration Strategy (Safe Way)

Day before migration:

* Lower TTL to 60 or 120

Migration time:

* Change A record

After stable:

* Increase TTL back to 3600 or higher
