## What the Original Answer Gets Right

The core concern is valid — you cannot do a naive rolling update on a database the same way you would a stateless app:

```
❌ WHY naive rolling update breaks for MySQL:

Pod 1 (MySQL 5.7) → writing to /var/lib/mysql (PVC)
Pod 2 (MySQL 8.0) starts → mounts SAME PVC → tries to read 5.7 data format
→ MySQL 8.0 sees 5.7 data structures → possible corruption or crash

Also: MySQL uses file-level locks and expects exclusive access
Two mysqld processes sharing the same data directory = undefined behavior
```

## What the Original Answer Gets Wrong

The blanket "use Recreate" statement is inaccurate. It ignores how databases are **actually** deployed in Kubernetes:

### Modern databases are NOT deployed as a single pod
```
Original answer assumes this:
  ┌─────────────────┐
  │   MySQL Pod     │  ← single pod, all state here
  │   (one replica) │
  └─────────────────┘

Reality in production:
  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
  │  Primary     │    │  Replica-1   │    │  Replica-2   │
  │  (writes)    │───►│  (reads)     │    │  (reads)     │
  └──────────────┘    └──────────────┘    └──────────────┘
       pod-0               pod-1               pod-2
   StatefulSet with its own PVC per pod (no shared storage)
```

With a StatefulSet + replication, a form of ordered rolling upgrade IS how you update databases — it's just much more controlled than a Deployment rolling update.

## The Actual Upgrade Strategies by Database Type

### Strategy 1 — Recreate (only valid for single-instance, non-production)
```yaml
spec:
  strategy:
    type: Recreate
# Stop pod → data safe in PVC → start new version → upgrade data files
# Downtime: YES (seconds to minutes depending on DB size)
# Use for: dev/test, single-instance, acceptable downtime window
```

### Strategy 2 — StatefulSet ordered rolling upgrade (production standard)
StatefulSets have a built-in update strategy specifically designed for this:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  replicas: 3
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 3      # ← start here: update NO pods (canary gate)
```

The upgrade sequence for a 3-node MySQL InnoDB Cluster:
```
Step 1: partition: 3 → 0 pods updated (safe to test config first)

Step 2: partition: 2 → only pod-2 (replica) gets updated
        MySQL 8.0 replica joins cluster, catches up via replication
        Verify replication lag = 0, no errors

Step 3: partition: 1 → pod-1 (replica) gets updated
        Now 2 of 3 nodes on new version
        Verify again

Step 4: partition: 0 → pod-0 (primary) gets updated
        This is the controlled failover moment:
        → MySQL InnoDB Cluster elects new primary (pod-1 or pod-2)
        → pod-0 upgrades
        → pod-0 rejoins as replica of new version
        → Zero downtime if done correctly

kubectl patch statefulset mysql -p \
  '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
# Verify → then partition:1 → verify → then partition:0
```

### Strategy 3 — Operator-managed upgrades (production best practice)
Most production databases on Kubernetes use an Operator that handles upgrades with full awareness of database state:

```yaml
# MySQL Operator (Oracle's official K8s operator)
# Percona XtraDB Cluster Operator
# PostgreSQL: CloudNativePG, Zalando postgres-operator
# MongoDB: MongoDB Community Operator

# These operators know:
# - Which pod is the primary
# - What the replication lag is
# - Whether it's safe to upgrade this pod NOW
# - How to trigger a controlled failover before upgrading primary
# - How to roll back if the new version fails health checks

# Example: CloudNativePG PostgreSQL upgrade
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: postgres-cluster
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:16.2
  # Operator handles the upgrade automatically:
  # 1. Upgrades replicas first (one at a time)
  # 2. Verifies streaming replication on each
  # 3. Triggers controlled switchover (replica becomes primary)
  # 4. Upgrades old primary last
  # 5. Zero downtime for reads AND writes
  primaryUpdateStrategy: unsupervised
```

## The Real Rule — It Depends on What "Version" Means

```
Database upgrade type         Safe strategy
─────────────────────────────────────────────────────────
Minor version (8.0.33→8.0.34) Ordered rolling (replicas first)
Major version (5.7→8.0)       More caution required, but still
                               NOT necessarily Recreate — depends
                               on whether data format changes need
                               mysql_upgrade to run

Schema migration (new column)  NOT an image version change at all
                               Use tools: Flyway, Liquibase, gh-ost
                               for online schema changes — separate
                               from pod rolling update entirely

Config change only             kubectl rollout restart — safe
                               (no data format change)
```

## Corrected One-Line Answer for the Interview

Instead of "databases must use Recreate," the accurate answer is:

> **Single-instance databases in dev/test can use Recreate for simplicity. Production databases run as StatefulSets with replication and use ordered rolling upgrades — replicas first, primary last — with partition-based rollout control or a database operator. The actual data corruption risk is shared storage between two versions, which StatefulSets avoid by giving each pod its own PVC. Schema migrations are a separate concern from pod version upgrades and use online migration tools, not pod restart strategies.**
