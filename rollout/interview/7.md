## What are the Deployment Strategies in Kubernetes?

**Scenario:** When you need to move an application from one version to another in production, what strategies does Kubernetes support? Explain each one with their differences and use cases.

### The Four Major Deployment Strategies

#### 1. Rolling Update Strategy (Ramp Strategy)

**Also known as:** Rolling Update, Ramp Strategy, Default Strategy

**What it is:**
This is the **default deployment strategy** in Kubernetes. When you change the image version in a Deployment, Kubernetes gradually replaces old pods with new ones.

**How it works (with example of 10 pods):**
- If you have 10 pods running the old version
- Kubernetes creates 25% new pods first (~3 pods with new version)
- Simultaneously terminates 25% old pods (~3 pods with old version)
- This process continues until all pods are updated
- At any point, 7 old pods + 3 new pods are running
- Traffic flows to both old and new pods during the transition

**Key Characteristics:**
- **Zero downtime** - Application remains available throughout
- Old and new versions run simultaneously during transition
- Gradually phases out old version
- Client eventually sees ONLY the new version
- Configurable with `maxUnavailable` and `maxSurge` parameters

**Default Behavior:**
- Maintains last 10 revisions by default (`revisionHistoryLimit: 10`)
- You can rollback up to 10 versions back

**Real-world example:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25%
      maxSurge: 25%
  template:
    spec:
      containers:
      - name: app
        image: nginx:1.18  # Changed from 1.17
```

#### 2. Recreate Strategy

**What it is:**
All existing pods are **terminated first**, then new pods with the new version are created.

**How it works:**
- When version is changed, Kubernetes terminates ALL old pods
- After all old pods are gone, new pods are created
- There is a period where NO pods are running

**Key Characteristics:**
- **Downtime is guaranteed** - Application is unavailable during transition
- No two versions run simultaneously
- Simple and predictable

**When to use:**
1. **Stateful applications** - Databases like MySQL, PostgreSQL, Oracle
   - Cannot have two versions writing to same storage simultaneously
   - Old version writing + New version writing = **DATA CORRUPTION**
2. **Development/Testing environments** - Where downtime doesn't matter
3. **Applications that can't handle multiple versions running together**

**Why NOT for databases:**
- MySQL has Master-Slave architecture
- If you run old and new versions simultaneously:
  - Both would try to write to the same storage
  - Data would get corrupted (Split Brain problem)
- Must terminate old completely before starting new

**Configuration:**
```yaml
spec:
  strategy:
    type: Recreate
```

#### 3. Canary Deployment

**What it is:**
A method where you run **both old and new versions simultaneously** for an extended period. A small percentage of traffic goes to the new version while most traffic continues on the old version.

**How it works:**
- Deploy new version with fewer replicas (e.g., 1 pod)
- Keep old version with more replicas (e.g., 3 pods)
- Traffic distribution is based on pod count ratio
- Example: 3 old pods + 1 new pod = ~75% traffic to old, ~25% to new
- Gradually increase new version replicas and decrease old version
- Both versions visible to clients simultaneously

**Key Characteristics:**
- Both versions run together for a long time (weeks/months)
- Traffic split based on replica count
- Clients can interact with both versions
- Gradual confidence building in new version

**Real-world example:**
- AWS dashboard redesign - users had option to switch between old and new UI
- New features rolled out gradually to get market feedback
- If issues found, instantly rollback by scaling canary to zero

**How Service distributes traffic:**
- Service uses **iptables** with probability-based distribution
- Formula: Probability = Individual pod count / Total pod count
- Example: 3 v1 pods + 1 v2 pod = 33% probability per v1 pod, 33% per v2 pod
- v1 gets ~66% traffic (2×33%), v2 gets ~33% traffic

**Practical Implementation:**
```bash
# Create v1 deployment with 3 replicas
kubectl create deployment v1 --image=nginx:1.17 --replicas=3

# Create v2 deployment with 1 replica (canary)
kubectl create deployment v2 --image=nginx:1.18 --replicas=1

# Both deployments share same label
# Service selector matches both → traffic splits by pod count

# Gradually increase v2, decrease v1
kubectl scale deployment v2 --replicas=3
kubectl scale deployment v1 --replicas=1
```

**Important:** Canary is a **methodology/technique**, NOT a Kubernetes keyword. It's not written in the deployment YAML as a strategy type.

#### 4. Blue-Green Deployment

**What it is:**
Two **completely separate but identical clusters/environments**. One serves live traffic (Blue), while the other is used for development/testing of the new version (Green).

**How it works:**
- **Blue environment:** Currently live, serving all production traffic
- **Green environment:** Identical infrastructure, new version deployed and tested here
- When Green is fully tested and ready:
  - Switch traffic from Blue to Green via load balancer
  - Green becomes the new live environment
  - Blue becomes available for next development cycle
- Instant rollback: Switch traffic back to Blue

**Key Characteristics:**
- **Two completely separate clusters/environments**
- NOT just different namespaces (that wouldn't provide true isolation)
- Same infrastructure cost and effort for both environments
- Zero downtime during switch
- Instant rollback capability
- 100% availability

**Infrastructure Requirements:**
- Two clusters with identical:
  - Master nodes configuration
  - Worker nodes capacity
  - Network configuration
  - Storage configuration
  - All manifests and configurations
- External load balancer/Ingress pointing to active cluster

**How traffic switching works:**
```bash
# Blue cluster Ingress IP → Configured in external Load Balancer
# When Green is ready:
# Change Load Balancer to point to Green cluster's Ingress IP
# Traffic instantly moves to Green

# Rollback:
# Change Load Balancer back to Blue cluster's Ingress IP
```

### Comparison Table

| Feature | Rolling Update | Recreate | Canary | Blue-Green |
|---------|---------------|----------|--------|------------|
| **Downtime** | Zero | Yes (full) | Zero | Zero |
| **Versions running** | Both temporarily | One at a time | Both for extended period | One live, one standby |
| **Kubernetes keyword** | `RollingUpdate` | `Recreate` | N/A (methodology) | N/A (methodology) |
| **Configuration** | In deployment YAML | In deployment YAML | Via replica scaling | Via load balancer |
| **Rollback speed** | Rollout undo | Redeploy old | Scale canary to 0 | Switch LB back |
| **Resource usage** | Same cluster | Same cluster | Same cluster | Double infrastructure |
| **Use case** | Stateless apps | Stateful apps (DBs) | User acceptance testing | Mission-critical apps |
| **Client sees** | One version eventually | One version | Both versions | One version |
