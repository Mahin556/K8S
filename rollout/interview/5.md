The solution is correct and works — but it has real limitations that matter in production. Let me complete the picture.

## What the Original Solution Does Well

The pod-count ratio approach is a valid, zero-dependency way to do canary deployments. The shared `app: web-app` label on both deployments, with the Service selecting only that label, is exactly right. It's worth understanding before moving to more complex tooling.

## The Three Real Limitations

**1. Traffic split is approximate, not exact**
```
5 stable + 1 canary = 6 total pods
kube-proxy distributes to any ready pod randomly
Theoretical: 1/6 = 16.7% canary

Reality: you cannot get exactly 10% or 5%
with whole-number pod counts:
  10% = 1 canary, 9 stable = 1/10 ✅ (works)
  5%  = 1 canary, 19 stable = 1/20 (need 20 pods for 5%)
  1%  = 1 canary, 99 stable (100 pods for 1% canary)

For small traffic percentages you either waste resources
OR accept imprecise splits.
```

**2. Same user can get both versions in the same session**
```
User A: Request 1 → stable (v1), sees old UI
User A: Request 2 → canary (v2), sees new UI  ← jarring/broken UX
User A: Request 3 → stable (v1), sees old UI again

With pod-count canary: no session stickiness between versions
Every request is independently routed — users flip between versions.
For stateless APIs this is tolerable.
For UI changes this causes inconsistent user experience.
```

**3. No automated promotion or rollback based on metrics**
```
The original solution requires a human to:
- Watch Grafana manually
- Decide "metrics look good"
- Run kubectl scale commands manually

There's no automated trigger for:
- Error rate threshold crossed → auto rollback
- p99 latency spiked → pause rollout
- Success rate good for 10 minutes → auto-promote
```

## Production Option 1 — NGINX Ingress Canary Annotations (Exact % without a service mesh)

```yaml
# Stable Ingress — handles 100% of traffic by default
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-stable
spec:
  ingressClassName: nginx
  rules:
    - host: webapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service-v1    # points to stable deployment only
                port:
                  number: 80
---
# Canary Ingress — NGINX routes an exact percentage here
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-app-canary
  annotations:
    nginx.ingress.kubernetes.io/canary: "true"

    # Option A: exact weight-based (10% to canary regardless of pod count)
    nginx.ingress.kubernetes.io/canary-weight: "10"

    # Option B: header-based (only requests with this header go to canary)
    # nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
    # nginx.ingress.kubernetes.io/canary-by-header-value: "true"

    # Option C: cookie-based (sticky — same user always gets same version)
    # nginx.ingress.kubernetes.io/canary-by-cookie: "canary_user"
spec:
  ingressClassName: nginx
  rules:
    - host: webapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-service-v2    # points to canary deployment only
                port:
                  number: 80
```

**Gradual promotion without touching pod counts:**
```bash
# Increase canary weight incrementally
kubectl annotate ingress web-app-canary \
  nginx.ingress.kubernetes.io/canary-weight="25" --overwrite

kubectl annotate ingress web-app-canary \
  nginx.ingress.kubernetes.io/canary-weight="50" --overwrite

# Full cutover: delete canary ingress, update stable service to v2
kubectl delete ingress web-app-canary
kubectl set image deployment/app-v1-stable web=webapp:2.0
```

## Production Option 2 — Argo Rollouts (Automated metric-driven promotion)

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: web-app
spec:
  replicas: 5
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
        - name: web
          image: webapp:2.0
          ports:
            - containerPort: 80

  strategy:
    canary:
      # Canary traffic is controlled by weight, not replica count
      canaryService: web-service-canary    # Service pointing to canary pods
      stableService: web-service-stable    # Service pointing to stable pods

      # Ingress tells NGINX to split traffic by weight
      trafficRouting:
        nginx:
          stableIngress: web-app-stable

      # Automated promotion gates
      analysis:
        startingStep: 1    # start analysis at step 1 (10% canary)
        templates:
          - templateName: success-rate    # defined below

      steps:
        # Step 1: 10% canary, run analysis
        - setWeight: 10
        - pause: {duration: 5m}     # wait 5 minutes with traffic

        # Step 2: check metrics (automated gate)
        - analysis:
            templates:
              - templateName: success-rate

        # Step 3: increase to 30% if analysis passed
        - setWeight: 30
        - pause: {duration: 5m}

        # Step 4: 60%
        - setWeight: 60
        - pause: {duration: 10m}

        # Step 5: 100% (full cutover)
        - setWeight: 100
---
# AnalysisTemplate — defines what "metrics look good" means precisely
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
    # Metric 1: HTTP success rate must be >= 99%
    - name: success-rate
      interval: 60s
      count: 5               # check 5 times
      successCondition: result[0] >= 0.99
      failureLimit: 1        # if fails once → automatic rollback
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            sum(rate(http_requests_total{
              job="web-app",
              status!~"5..",
              version="{{ args.canary-version }}"
            }[5m]))
            /
            sum(rate(http_requests_total{
              job="web-app",
              version="{{ args.canary-version }}"
            }[5m]))

    # Metric 2: p99 latency must be under 500ms
    - name: latency-p99
      interval: 60s
      count: 5
      successCondition: result[0] < 0.5
      failureLimit: 1
      provider:
        prometheus:
          address: http://prometheus.monitoring.svc:9090
          query: |
            histogram_quantile(0.99,
              sum(rate(http_request_duration_seconds_bucket{
                job="web-app",
                version="{{ args.canary-version }}"
              }[5m])) by (le)
            )
```

**What Argo Rollouts gives you over manual kubectl scale:**
```bash
# Watch the automated rollout in real time
kubectl argo rollouts get rollout web-app --watch

# Output:
# Name:            web-app
# Status:          ॥ Paused
# Strategy:        Canary
#   Step:          2/6
#   SetWeight:     10
#   ActualWeight:  10
# Images:
#   webapp:1.0 (stable)
#   webapp:2.0 (canary)
# Replicas:
#   Desired:       5
#   Current:       5
#   Stable:        4
#   Canary:        1

# Manual promote if you want to skip ahead:
kubectl argo rollouts promote web-app

# Manual abort (immediate rollback):
kubectl argo rollouts abort web-app

# Automatic rollback: happens when AnalysisTemplate fails
# error rate > 1% → rollout aborts → all traffic returns to stable → alert fired
```

## Production Option 3 — Istio (Exact % + header routing + session stickiness)

```yaml
# VirtualService — exact traffic percentages regardless of pod count
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: web-app
spec:
  hosts:
    - webapp.example.com
  http:
    # Rule 1: always send internal testers to canary (header-based)
    - match:
        - headers:
            x-canary-user:
              exact: "true"
      route:
        - destination:
            host: web-service
            subset: v2        # canary
          weight: 100

    # Rule 2: weighted split for everyone else
    - route:
        - destination:
            host: web-service
            subset: v1        # stable
          weight: 90
        - destination:
            host: web-service
            subset: v2        # canary
          weight: 10          # exact 10% — no pod count math needed
---
# DestinationRule — defines subsets by pod labels
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: web-app
spec:
  host: web-service
  subsets:
    - name: v1
      labels:
        version: v1           # routes to stable pods
    - name: v2
      labels:
        version: v2           # routes to canary pods
  trafficPolicy:
    # Session stickiness — same user always gets same version
    loadBalancer:
      consistentHash:
        httpCookie:
          name: canary_session
          ttl: 0s
```

## Decision Guide — Which Approach to Use

| Situation | Use |
|---|---|
| Quick test, no extra tools | Pod-count ratio (original solution) |
| Need exact % without service mesh | NGINX Ingress canary annotations |
| Need automated metric-based promotion | Argo Rollouts |
| Need header routing + session stickiness + exact % | Istio VirtualService |
| Need all three + distributed tracing + mTLS | Istio + Argo Rollouts combined |

## Updated Key Points (Replacing Original)

```
Original says: "Traffic distribution based on replica count ratio"
Better:         That's ONE approach. Production uses weight annotations
                or VirtualServices for exact percentages.

Original says: "Scale up canary replicas to increase traffic"
Better:         Scaling pods to control traffic means wasting resources.
                Change the weight annotation or VirtualService weight instead.

Original says: "If metrics look good" (human decision)
```
