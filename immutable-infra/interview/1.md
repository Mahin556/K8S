# Immutable Infrastructure in Kubernetes — Complete Implementation Guide

---

## What "Immutable Infrastructure" Actually Means (Precisely)

The original answer treats immutable infrastructure as "store YAML in Git."
That's version control — necessary but not sufficient. Immutable infrastructure
means specifically:

> **You never modify a running artifact. You replace it.**

In Kubernetes terms, this means:
- Container images are never patched in place — new image = new build
- Running pods are never SSH'd into and modified — replace the pod
- No `kubectl exec` to fix config — fix the manifest and redeploy
- No mutable tags like `:latest` — every image is pinned to a digest
- Cluster state is always driven FROM Git — never from direct kubectl apply
- If Git and the cluster diverge (drift), the cluster is wrong, not Git

---

## The 6 Pillars of Immutable Infrastructure in Kubernetes

```
1. IMAGE IMMUTABILITY     → tag by digest, never by mutable tag
2. MANIFEST IMMUTABILITY  → Git is the single source of truth (GitOps)
3. RUNTIME IMMUTABILITY   → pods cannot be modified while running
4. SUPPLY CHAIN           → sign and verify every artifact
5. SECRETS IMMUTABILITY   → no secrets in Git, injected externally
6. DRIFT DETECTION        → cluster state continuously reconciled to Git
```

## Pillar 1 — Image Immutability: Pin by Digest, Never by Tag

This is the most technically specific thing the original answer misses entirely.
`:latest` and even `:v1.2.0` are MUTABLE — a registry can overwrite what they
point to at any time. A digest (`sha256:abc123...`) is cryptographically
immutable — it cannot point to different content ever.

```yaml
# ❌ WRONG — mutable, not reproducible
image: myapp:v1.2.0
# Registry admin can push a different image to v1.2.0 tag tomorrow.
# Your "pinned" deployment is not actually pinned.

# ✅ CORRECT — immutable, cryptographically verifiable
image: myapp@sha256:a8b9c4d2e1f3...
# This can NEVER point to different content.
# If the digest changes, it's a different image — full stop.
```

### How to get the digest:
```bash
# Build and get the digest
docker build -t myapp:v1.2.0 .
docker push myapp:v1.2.0

# Get the digest:
docker inspect --format='{{index .RepoDigests 0}}' myapp:v1.2.0
# myapp@sha256:a8b9c4d2e1f3...

# Or from registry directly:
crane digest myapp:v1.2.0
# sha256:a8b9c4d2e1f3...
```

### How this works in CI/CD — image digest promotion:
```yaml
# .github/workflows/build.yml
- name: Build and push
  id: build
  uses: docker/build-push-action@v6
  with:
    push: true
    tags: myapp:${{ github.sha }}

# The action outputs the digest automatically:
- name: Update manifest with digest
  run: |
    DIGEST="${{ steps.build.outputs.digest }}"
    # digest = sha256:abc123...
    
    # Update the deployment manifest with the IMMUTABLE digest
    yq e -i '.spec.template.spec.containers[0].image = "myapp@'"$DIGEST"'"' \
      k8s/deployment.yaml
    
    git config user.email "ci@example.com"
    git add k8s/deployment.yaml
    git commit -m "chore: promote myapp@$DIGEST"
    git push
    # ArgoCD sees this commit and deploys the exact digest — immutable
```

## Pillar 2 — Manifest Immutability: GitOps with Strict Separation

The original answer says "store manifests in Git." GitOps means something more
specific: the cluster reconciles itself TO Git continuously — not just "apply
when we decide to deploy."

### Repository Structure (two-repo pattern — best practice):
```
app-source-repo/          ← developers work here
├── src/
├── Dockerfile
├── .github/workflows/
│   └── build.yml         ← builds image, opens PR to config-repo
└── tests/

k8s-config-repo/          ← ArgoCD watches this repo only
├── apps/
│   ├── myapp/
│   │   ├── base/
│   │   │   ├── deployment.yaml   ← contains pinned digest
│   │   │   ├── service.yaml
│   │   │   └── kustomization.yaml
│   │   └── overlays/
│   │       ├── staging/
│   │       └── production/
└── argocd/
    └── applications.yaml
```

Why two repos? Separating source code from deployment config means:
- A git push to app-source-repo doesn't automatically redeploy (CI decides when)
- Config repo has its own access control (ops team reviews deployment PRs)
- Config repo audit log is clean — only deployment changes, not code changes

### ArgoCD Application — sync policy:
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: myapp-production
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/org/k8s-config-repo
    targetRevision: HEAD
    path: apps/myapp/overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true         # delete resources removed from Git
      selfHeal: true      # revert manual kubectl changes within ~3 minutes
    syncOptions:
      - CreateNamespace=true
      - RespectIgnoreDifferences=true
  # selfHeal is what makes this truly immutable:
  # someone does `kubectl set image deployment/myapp myapp=myapp:hacked`
  # → ArgoCD detects drift and reverts to the Git-committed digest
  # → cluster ALWAYS matches Git, no exceptions
```

## Pillar 3 — Runtime Immutability: Prevent Container Modification

Declaring images as immutable is meaningless if someone can exec into a running
container and modify it. Kubernetes security contexts enforce this at runtime.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  template:
    spec:
      # Pod-level security context
      securityContext:
        runAsNonRoot: true          # never run as root
        runAsUser: 1000
        runAsGroup: 3000
        fsGroup: 2000
        seccompProfile:
          type: RuntimeDefault      # restrict syscalls

      containers:
        - name: myapp
          image: myapp@sha256:abc123...
          
          # Container-level security context
          securityContext:
            readOnlyRootFilesystem: true   # KEY: container filesystem is immutable
                                            # Any write attempt fails immediately
                                            # Prevents: `exec` → modify binary/config
            allowPrivilegeEscalation: false
            capabilities:
              drop:
                - ALL                # drop every Linux capability
              add:
                - NET_BIND_SERVICE   # only add back what's strictly needed

          # If app needs to write ANYTHING, use explicit volumes
          # This makes all write paths explicit and auditable:
          volumeMounts:
            - name: tmp
              mountPath: /tmp           # app can write temp files here only
            - name: cache
              mountPath: /app/cache     # explicit cache directory
            # Everything else in the container: READ-ONLY

      volumes:
        - name: tmp
          emptyDir: {}              # ephemeral, dies with pod — immutable pattern
        - name: cache
          emptyDir:
            medium: Memory          # RAM-backed, never touches disk
            sizeLimit: 128Mi        # bounded — can't grow unbounded
```

### Enforce this cluster-wide with Pod Security Standards:
```yaml
# Apply to namespace — Kubernetes built-in enforcement
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    # enforce: any pod violating restricted profile is REJECTED at admission
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.29
    # warn: also warn during dry-run and kubectl apply
    pod-security.kubernetes.io/warn: restricted
    # audit: log violations to audit log
    pod-security.kubernetes.io/audit: restricted
# "restricted" profile requires: non-root, read-only root filesystem,
# no privilege escalation, seccomp RuntimeDefault — exactly what we set above
```

## Pillar 4 — Supply Chain Security: Sign and Verify Every Artifact

This is completely absent from most "immutable infrastructure" answers.
Pinning to a digest prevents tag mutation, but doesn't prove the image
was built from your source by your CI system. Image signing closes this gap.

### Cosign — sign images in CI:
```yaml
# .github/workflows/build.yml
- name: Install Cosign
  uses: sigstore/cosign-installer@v3

- name: Sign the image
  run: |
    cosign sign \
      --key cosign.key \
      myapp@${{ steps.build.outputs.digest }}
    # This creates an immutable attestation in the registry:
    # "this exact digest was signed by this private key at this timestamp"
    # Verifiable by anyone with the corresponding public key
```

### Policy Controller / Kyverno — verify at admission:
```yaml
# Kyverno ClusterPolicy — reject any pod using an unsigned image
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-signed-images
spec:
  validationFailureAction: Enforce    # REJECT pods with unsigned images
  background: false
  rules:
    - name: check-image-signature
      match:
        any:
          - resources:
              kinds: ["Pod"]
              namespaces: ["production", "staging"]
      verifyImages:
        - imageReferences:
            - "myapp*"
            - "registry.example.com/*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      MFkwEwYHKoZIzj0CAQY...
                      -----END PUBLIC KEY-----
          # If the image digest doesn't have a valid signature from
          # this key, the pod is REJECTED at the API server.
          # An attacker who pushes a malicious image cannot bypass this
          # because they don't have your signing private key.
```

### Generate SBOM (Software Bill of Materials):
```bash
# Generate SBOM and attach it to the image as an attestation
syft myapp@sha256:abc123... -o cyclonedx-json > sbom.json

cosign attest \
  --predicate sbom.json \
  --type cyclonedx \
  --key cosign.key \
  myapp@sha256:abc123...

# Now anyone can verify: "what's in this image?"
cosign verify-attestation \
  --key cosign.pub \
  --type cyclonedx \
  myapp@sha256:abc123...
```

## Pillar 5 — Secrets: The Hardest Part of Immutable Infrastructure

Secrets cannot go in Git (even encrypted Git has risks). But secrets must
come from somewhere declarative and versioned. External Secrets Operator
solves this: secret definitions are in Git, secret VALUES are in Vault/AWS SM.

```yaml
# This IS in Git — defines which secret to fetch, not the value itself
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: database-credentials
  namespace: production
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
  target:
    name: database-credentials   # K8s Secret created with this name
    creationPolicy: Owner
    template:
      type: Opaque
      # Immutable K8s Secret — cannot be modified once created
      immutable: true
  data:
    - secretKey: DB_PASSWORD
      remoteRef:
        key: production/database
        property: password
        version: "42"              # pin to SPECIFIC secret version
                                   # change = update this file in Git = PR + review
```

### Secret rotation in the immutable model:
```
Old approach (mutable): → SSH into app server → update /etc/app.conf → restart
Immutable approach:     → Update secret in Vault with new version
                        → Update ExternalSecret version field in Git → PR
                        → PR merged → ArgoCD syncs → pods get new secret
                        → Old pods terminated → new pods with new secret start
                        → Full audit trail in Git + Vault audit log
```

## Pillar 6 — Drift Detection and Enforcement

Drift is when the running cluster state diverges from what Git says it should be.
In immutable infrastructure, drift = violation. It must be detected and reversed.

### ArgoCD self-heal (continuous reconciliation):
```yaml
# Already shown above — selfHeal: true means:
# 1. ArgoCD continuously compares cluster state to Git (every 3 minutes)
# 2. If any resource differs from Git (image tag, replica count, env var)
# 3. ArgoCD reverts the cluster to match Git — automatically
# 4. This is logged in ArgoCD's audit log

# Check for drift manually:
argocd app diff myapp-production
# Shows: what's in Git vs what's in the cluster (like git diff)
```

### Alert on drift:
```yaml
# PrometheusRule — alert when ArgoCD detects drift
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: argocd-drift-alert
spec:
  groups:
    - name: argocd
      rules:
        - alert: ArgoCDAppOutOfSync
          expr: argocd_app_info{sync_status="OutOfSync"} == 1
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "App {{ $labels.name }} has drifted from Git"
            description: "Cluster state no longer matches Git. Manual change detected."
```

### Audit who made the change:
```bash
# Kubernetes audit log captures every API call:
# Who made the kubectl set image that caused drift?
kubectl get events --field-selector reason=SyncFailed -n argocd

# Full audit trail in cloud provider:
# AWS: CloudTrail + EKS audit logs
# GCP: Cloud Audit Logs + GKE audit logs
# On-prem: Falco captures kubectl exec / kubectl edit events in real-time
```

## Putting It All Together — The Immutable Delivery Pipeline

```
Developer pushes code
         │
         ▼
CI Pipeline (GitHub Actions):
  1. Run tests
  2. Build Docker image
  3. Tag with git SHA: myapp:abc1234
  4. Push to registry
  5. Sign image with Cosign private key
  6. Generate + attest SBOM
  7. Get digest: sha256:xyz...
  8. Open PR to k8s-config-repo:
     Update deployment.yaml: image = myapp@sha256:xyz...
         │
         ▼
PR Review (k8s-config-repo):
  - Human reviews: "is this the right image? right digest?"
  - Automated check: digest in PR == digest signed by CI? ✅
  - Automated check: SBOM has no critical CVEs? ✅
  - Merge PR
         │
         ▼
ArgoCD detects new commit in k8s-config-repo:
  1. Downloads manifest (image = myapp@sha256:xyz...)
  2. Admission controller verifies: is sha256:xyz signed? ✅
  3. Deploys with readOnly root filesystem, non-root user
  4. Continuously reconciles: if cluster drifts → revert
         │
         ▼
Running cluster:
  - Every pod runs an immutable, signed, digest-pinned image
  - Root filesystem read-only
  - No secrets in any manifest
  - Any drift → auto-reverted + alert fired
  - Full audit trail: Git log + ArgoCD log + K8s audit log + Falco
```
