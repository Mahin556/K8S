## Challenge 1: Resource Sharing Between Multiple Teams

### The Problem:

You have a Kubernetes cluster shared between multiple development teams (web team, payments team, delivery team, etc.). Each team deploys their microservices to the same cluster. The cluster has limited resources—let's say 100 CPU and 100 GB RAM across all worker nodes.

**The Issue:** One microservice in the payments namespace starts **leaking memory**. Instead of using its allocated 2 GB RAM, it starts consuming 32 GB RAM. This causes other services in completely different namespaces to crash due to **OOMKilled** (Out of Memory Killed). The **blast radius** is the **entire cluster**.

### The Solution:

**Step 1: Implement Resource Quotas on Namespaces**
```bash
# Limit total resources per namespace
kubectl create quota compute-quota \
  --hard=cpu=15,memory=15Gi \
  -n payments-ns
```

Resource Quota sets a hard limit on the total resources a namespace can consume. If the payments namespace is limited to 15 GB RAM, even a memory leak cannot affect other namespaces. The blast radius is reduced from **cluster → namespace**.

**Step 2: Implement Resource Limits on Each Pod**
```yaml
resources:
  requests:
    memory: "2Gi"
  limits:
    memory: "8Gi"    # Maximum this pod can use
```

Resource Limits restrict individual pods. If one pod exceeds its limit (e.g., 8 GB), it gets OOMKilled, but other pods in the same namespace are unaffected. The blast radius is reduced further from **namespace → single pod**.

### Key Interview Talking Points:

"As a DevOps engineer, when I joined the organization, one pod leaking memory would bring down the entire cluster. I implemented:

1. **Resource Quotas** on namespaces—so each team gets their allocated share
2. **Resource Limits** on each pod—so a single misbehaving pod only crashes itself

This reduced the blast radius from cluster-wide to a single pod. I also worked with development teams to get performance benchmarking data before setting these limits."

## Challenge 2: Handling OOMKilled (Out of Memory) Errors

### The Problem:

Even after setting Resource Quotas and Resource Limits, a pod still goes into **CrashLoopBackOff** due to **OOMKilled** error. The development team claimed it only needs 8 GB RAM based on performance benchmarking, but it's still crashing.

### The Solution - For Java Applications:

**Step 1: Take Thread Dump**
```bash
# Inside the pod
kill -3 <java-pid>
```

**Step 2: Take Heap Dump**
```bash
# Using jstack/jmap
jstack <java-pid> > thread_dump.txt
jmap -dump:live,format=b,file=heap_dump.hprof <java-pid>
```

**Step 3: Share with Development Team**
- Provide the thread dump and heap dump to the development team
- They analyze which thread is leaking memory
- They create a fix, build a new version, and you deploy it

### Key Interview Talking Points:

"As a DevOps engineer, my scope is to identify the issue, collect the evidence (thread dumps, heap dumps), and provide it to the development team. I cannot fix a memory leak in the application code—that's the developer's responsibility. But I can:

1. Set up the resource boundaries (quotas and limits)
2. Identify the exact pod causing the issue
3. Collect diagnostic data (thread dumps, heap dumps)
4. Share with the development team for resolution"

## Challenge 3: Kubernetes Cluster Upgrades

### The Problem:

Upgrading a production Kubernetes cluster (e.g., from v1.29 to v1.30) is risky. Without proper planning, the cluster could go down, breaking changes could affect applications, or deprecated features could cause failures.

### The Solution - Create a Detailed Upgrade Manual:

**Pre-Upgrade Steps:**

1. **Backup etcd:**
   ```bash
   ETCDCTL_API=3 etcdctl snapshot save snapshot.db
   ```

2. **Read Release Notes:**
   - Check for breaking changes
   - Identify deprecated features you might be using
   - Note features moving from alpha → beta → stable

3. **Document Impact Analysis:**
   - Which features might impact your cluster
   - Any API version changes

**Control Plane Upgrade Steps:**

1. Start with **etcd** upgrade
2. Upgrade **kube-apiserver**
3. Upgrade **kube-scheduler**
4. Upgrade **kube-controller-manager**
5. Follow the documented order precisely

**Worker Node Upgrade Steps:**

1. **Drain** one worker node:
   ```bash
   kubectl drain <node-name> --ignore-daemonsets --delete-emptydir-data
   ```

2. **Cordon** the node (make it unschedulable):
   ```bash
   kubectl cordon <node-name>
   ```

3. **Upgrade** kubelet and kubectl on that node

4. **Uncordon** the node:
   ```bash
   kubectl uncordon <node-name>
   ```

5. **Repeat** for each worker node one at a time

### Key Interview Talking Points:

"As a DevOps engineer, I've created a detailed manual for Kubernetes upgrades that includes:

- **Backup procedures** (etcd snapshots, resource backups)
- **Release notes analysis**—what might break in our cluster
- **Step-by-step control plane upgrade**—in the correct order
- **Worker node upgrade strategy**—drain, cordon, upgrade, uncordon, one node at a time
- **Rollback plan**—in case something goes wrong

I follow this manual for every upgrade, and it has prevented any downtime during our version migrations."

## Summary: The Three Real-Time Challenges

| Challenge | Problem | Solution |
|-----------|---------|----------|
| **Resource Sharing** | One misbehaving pod affects entire cluster | Resource Quotas (namespace level) + Resource Limits (pod level) |
| **OOMKilled Errors** | Pod crashes due to memory issues | Collect thread dumps/heap dumps, share with dev team for code fix |
| **Cluster Upgrades** | Risk of downtime during version upgrades | Detailed manual: backup, release notes, drain-cordon-upgrade-uncordon |

### The Blast Radius Progression:

```
No Limits:     Pod crashes → Cluster affected (100% blast radius)
Resource Quota: Pod crashes → Namespace affected (reduced blast radius)
Resource Limit: Pod crashes → Only that pod affected (minimal blast radius)
```
