# Intermittent Pod → External DB Connection Failures — Complete Guide

---

## Critical Distinction: Intermittent vs Consistent Failures

The original answer lists Network Policies and Security Groups as causes.
These are WRONG for intermittent failures:

```
Network Policy blocking egress:   fails 100% of time — NOT intermittent
Security Group wrong rule:        fails 100% of time — NOT intermittent

Real intermittent causes:
  - Connection pool exhaustion     → fails under load, works at low traffic
  - Ephemeral port exhaustion      → one node "goes bad", others fine
  - conntrack table full           → random drops at high throughput
  - TCP keepalive missing          → idle connections silently dropped
  - SNAT port collision            → random RST packets mid-connection
  - DNS ndots:5 timeout            → external queries slow, timeouts
  - DB connection limit hit        → fails when too many pods connect
  - Pod IP SNAT race condition     → random RST on new connections
```

Rule of thumb: if it fails EVERY time → firewall/policy.
If it fails SOMETIMES → one of the causes below.

## Cause 1 — Connection Pool Exhaustion (Most Common)

### What happens
Your app reuses DB connections via a pool. If max pool size is too small
for the traffic load, new requests wait for a free connection. If nothing
frees up within the timeout, the request fails — appears "intermittent"
because it only fails when the pool is saturated.

### Diagnose
```bash
# Count active established connections from the pod to the DB
kubectl exec -it <pod-name> -- ss -tn state established \
  'dport = :3306'

# Watch it over time:
watch -n 1 'kubectl exec -it <pod-name> -- ss -tn state established \
  dport = :3306 | wc -l'

# If count is always at the pool maximum and never drops → exhausted

# Check application logs for pool wait timeout messages:
kubectl logs <pod-name> | grep -i "pool\|timeout\|connection\|wait"
# HikariCP: "Connection is not available, request timed out after 30000ms"
# DBCP: "Cannot get a connection, pool error Timeout waiting for connection"
# SQLAlchemy: "TimeoutError: QueuePool limit of size 5 overflow 10 reached"
```

### Fix
```yaml
# Option 1: increase pool size in app config
# (example: HikariCP in Java application.properties)
spring.datasource.hikari.maximum-pool-size=20
spring.datasource.hikari.connection-timeout=10000

# Option 2: use a connection pooler OUTSIDE the app (PgBouncer for PostgreSQL)
# PgBouncer sits between pods and the real DB, multiplexing connections
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pgbouncer
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: pgbouncer
          image: pgbouncer/pgbouncer:latest
          env:
            - name: DB_HOST
              value: "your-db.example.com"
            - name: DB_PORT
              value: "5432"
            - name: POOL_MODE
              value: "transaction"      # transaction pooling: most efficient
            - name: MAX_CLIENT_CONN
              value: "500"             # accepts up to 500 pod connections
            - name: DEFAULT_POOL_SIZE
              value: "20"              # only 20 real DB connections needed
```

## Cause 2 — Ephemeral Port Exhaustion (Node-Level Problem)

### What happens
Every outbound TCP connection needs a source port from the ephemeral range
(32768-60999 by default = ~28,000 ports). When pods on a node make many
short-lived connections to the DB, closed connections enter TIME_WAIT for
60 seconds — tying up their port during that window.

The critical Kubernetes-specific wrinkle: CNI SNAT means ALL pods on a node
share the node's ephemeral port range. A 50-pod node is sharing ~28K ports
across all pods for external connections. This is why one specific node
"goes bad" while others are fine — it hit exhaustion, others didn't yet.

### Diagnose
```bash
# Check TIME_WAIT count on the problem pod's node
kubectl debug node/<node-name> -it --image=nicolaka/netshoot -- bash

# Once on the node:
ss -tan state time-wait | grep 3306 | wc -l
# If thousands → TIME_WAIT exhaustion

# Check ephemeral port range:
cat /proc/sys/net/ipv4/ip_local_port_range
# 32768 60999 → 28,231 available

# If TIME_WAIT count is close to the range size → exhausted
# Connections will fail with: "cannot assign requested address"

# Check from inside the pod (look for SNAT source port):
kubectl exec -it <pod-name> -- ss -tan | grep 3306
```

### Fix
```bash
# Fix 1: Widen the ephemeral port range on every node
# Apply via DaemonSet to all nodes:
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: sysctl-tuner
spec:
  template:
    spec:
      initContainers:
        - name: sysctl
          image: busybox
          securityContext:
            privileged: true
          command:
            - /bin/sh
            - -c
            - |
              sysctl -w net.ipv4.ip_local_port_range="1024 65535"
              sysctl -w net.ipv4.tcp_tw_reuse=1     # reuse TIME_WAIT ports
              sysctl -w net.ipv4.tcp_fin_timeout=15  # reduce FIN_WAIT time
      containers:
        - name: pause
          image: gcr.io/google_containers/pause:3.9

# Fix 2: Use connection pooling (same fix as Cause 1)
# Fewer, longer-lived connections → fewer TIME_WAIT accumulations

# Fix 3: Enable TCP keepalive to keep connections alive
# rather than making new short-lived ones constantly
```

## Cause 3 — TCP Keepalive Not Configured (Idle Connection Drops)

### What happens
Cloud firewalls, NAT gateways, and load balancers silently drop idle TCP
connections after a timeout (AWS NLB: 350s, AWS NAT Gateway: 350s,
Azure LB: 240s, many firewalls: 300s). Your connection pool holds
a "healthy" connection that is actually dead on the network layer.
Next query attempt → connection timeout or RST → "intermittent" failure.
This is especially common on weekends or overnight when traffic is low
and connections sit idle.

### Diagnose
```bash
# Check if failures correlate with idle periods
# If failures happen after quiet periods → keepalive issue

# Check current TCP keepalive settings inside pod:
kubectl exec -it <pod-name> -- cat /proc/sys/net/ipv4/tcp_keepalive_time
# Default: 7200 (2 hours) → way too long for cloud firewalls

kubectl exec -it <pod-name> -- cat /proc/sys/net/ipv4/tcp_keepalive_intvl
# Default: 75 seconds

kubectl exec -it <pod-name> -- cat /proc/sys/net/ipv4/tcp_keepalive_probes
# Default: 9 probes → 9*75 = 675s before kernel detects dead connection
```

### Fix
```yaml
# Set TCP keepalive at OS level (pod spec):
spec:
  initContainers:
    - name: sysctl
      image: busybox
      securityContext:
        privileged: true
      command:
        - /bin/sh
        - -c
        - |
          sysctl -w net.ipv4.tcp_keepalive_time=60    # start probing after 60s idle
          sysctl -w net.ipv4.tcp_keepalive_intvl=10   # probe every 10s
          sysctl -w net.ipv4.tcp_keepalive_probes=6   # 6 probes → 60s to detect dead

# Set keepalive at application/driver level (preferred — no privilege needed):
# MySQL JDBC:
jdbc:mysql://host:3306/db?autoReconnect=true&socketTimeout=30000
# PostgreSQL JDBC:
jdbc:postgresql://host:5432/db?tcpKeepAlive=true&socketTimeout=30
# Go database/sql:
db.SetConnMaxLifetime(5 * time.Minute)    # recycle connections before firewall kills them
db.SetConnMaxIdleTime(1 * time.Minute)    # close idle connections quickly
# Python SQLAlchemy:
pool_pre_ping=True         # test connection before use → detects dead connections
pool_recycle=3600          # recycle connections every hour
```

## Cause 4 — conntrack Table Exhaustion

### What happens
Linux netfilter maintains a connection tracking table for every TCP/UDP
connection through the node. In Kubernetes with high pod density,
this table fills up. When full, new connections are dropped — completely
silently from the application's perspective.

```bash
# Diagnose: check if table is full on the node
kubectl debug node/<node-name> -it --image=nicolaka/netshoot -- bash

cat /proc/sys/net/netfilter/nf_conntrack_count   # current entries
cat /proc/sys/net/netfilter/nf_conntrack_max      # maximum
# If count ≈ max → exhausted → new connections silently dropped

# Watch it:
watch -n 1 'cat /proc/sys/net/netfilter/nf_conntrack_count'
```

### Fix
```bash
# Increase conntrack table size (apply via DaemonSet as above):
sysctl -w net.netfilter.nf_conntrack_max=524288     # double the default
sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=300  # reduce from 432000
# Note: each entry uses ~300 bytes RAM → 500K entries ≈ 150MB per node
```

## Cause 5 — DNS ndots:5 Causing External Query Timeout

### What happens
Kubernetes sets `ndots:5` in every pod's `/etc/resolv.conf`. For external
hostnames like `prod-db.us-east-1.rds.amazonaws.com` (3 dots, < 5),
the pod tries 4 search-domain lookups that all fail with NXDOMAIN before
finally resolving the real hostname. Each failed lookup takes up to the
DNS timeout (default 5s). Under load, CoreDNS can become a bottleneck
and these timeouts compound into visible connection failures.

```bash
# Measure DNS resolution time from inside the pod:
kubectl exec -it <pod-name> -- time nslookup prod-db.us-east-1.rds.amazonaws.com
# If > 100ms → DNS is part of the problem

# Check resolv.conf:
kubectl exec -it <pod-name> -- cat /etc/resolv.conf
# options ndots:5 ← this causes 4 failed searches for external names

# Watch CoreDNS for errors under load:
kubectl logs -n kube-system -l k8s-app=kube-dns -f | grep -i "error\|timeout"
```

### Fix
```yaml
# Fix 1: Use fully-qualified domain name with trailing dot (1 query, not 5)
# In DB connection string:
DB_HOST: "prod-db.us-east-1.rds.amazonaws.com."   # trailing dot = FQDN

# Fix 2: Reduce ndots for pods connecting mainly to external services
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"    # external hostnames with 2+ dots go direct, no search
      - name: timeout
        value: "2"    # reduce per-query timeout
      - name: attempts
        value: "3"

# Fix 3: Cache the resolved IP in environment variable at startup
# (app-level, not K8s-level fix — but very effective)
```

## Cause 6 — DB Server Connection Limit Hit

### What happens
MySQL default max_connections = 151. PostgreSQL default max_connections = 100.
If you have 20 pods × 5 connections per pool = 100 connections → at the limit.
New connection attempts get "Too many connections" error from the DB itself.

```bash
# Diagnose: check from inside the pod
kubectl exec -it <pod-name> -- mysql -h $DB_HOST -u $DB_USER -p$DB_PASS \
  -e "SHOW STATUS WHERE Variable_name = 'Threads_connected';"
# If Threads_connected ≈ max_connections → at the limit

# For PostgreSQL:
kubectl exec -it <pod-name> -- psql $DATABASE_URL \
  -c "SELECT count(*), max_conn FROM pg_stat_activity, \
      (SELECT setting::int AS max_conn FROM pg_settings WHERE name='max_connections') s;"
```

### Fix
```
Option 1: Increase DB max_connections (requires DB restart usually)
Option 2: Reduce pool size per pod: max_pool = floor(max_connections / num_pods)
Option 3: Use PgBouncer/ProxySQL as connection multiplexer (best long-term solution)
          20 pods × 50 client connections → PgBouncer → 10 real DB connections
```

## Complete Systematic Debug Sequence

```bash
# Step 1: Establish the failure PATTERN
# Run continuous probe for 10 minutes, record timestamps of failures:
kubectl run probe --rm -it --image=alpine -- sh -c \
  "while true; do
     nc -zw3 $DB_HOST $DB_PORT && echo \$(date) OK || echo \$(date) FAIL
     sleep 5
   done"
# Questions to answer:
# - Does it fail at specific times? (→ idle/keepalive issue)
# - Does it fail on specific nodes? (→ port exhaustion or conntrack)
# - Does it fail only under load? (→ pool exhaustion or DB limit)
# - Does it fail randomly across all pods? (→ DNS or conntrack)

# Step 2: Check which node the failing pod is on
kubectl get pod <pod-name> -o wide   # note NODE column

# Step 3: Check that node for resource exhaustion
kubectl debug node/<node-name> -it --image=nicolaka/netshoot -- bash
ss -tan state time-wait | wc -l                         # TIME_WAIT count
cat /proc/sys/net/netfilter/nf_conntrack_count          # conntrack usage
cat /proc/sys/net/netfilter/nf_conntrack_max

# Step 4: Check connection pool from the pod
kubectl exec -it <pod-name> -- ss -tn state established 'dport = :3306' | wc -l

# Step 5: Check DNS timing
kubectl exec -it <pod-name> -- time nslookup $DB_HOST

# Step 6: Check DB connection count (run from pod)
kubectl exec -it <pod-name> -- mysql -h $DB_HOST -u $DB_USER -p$DB_PASS \
  -e "SHOW STATUS WHERE Variable_name IN ('Threads_connected','Max_used_connections');"

# Step 7: Packet capture to see what's actually happening
kubectl debug node/<node-name> -it --image=nicolaka/netshoot -- bash
tcpdump -i any host $DB_HOST and port $DB_PORT -nn
# Look for: RST packets (connection reset), SYN without SYN-ACK (timeout)
```
