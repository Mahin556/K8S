## The Kubernetes Troubleshooting Mindset

When a troubleshooting scenario is given in an interview, the **first and foremost command** you should mention is:

```bash
kubectl get pods
```

This tells you the status of your pods, which determines your next steps.

---

## Part 1: The Pod Troubleshooting Flowchart

### Step 1: Check Pod Status
```bash
kubectl get pods
kubectl get pods -o wide
```

### Step 2: If Pod is in `Pending` State

Follow this decision tree:

| Check | Command | If YES | If NO |
|-------|---------|--------|-------|
| **Is cluster full?** | `kubectl describe node` | Add more nodes | Continue |
| **Hitting resource quota?** | `kubectl get resourcequota` | Increase quota | Continue |
| **Pending PVC?** | `kubectl get pvc` | Fix storage/PV | Continue |
| **Pod assigned to node?** | `kubectl describe pod` | Check next | Issue with scheduler |

### Step 3: If Pod is NOT Running

```bash
# Check pod logs
kubectl logs <pod-name>

# Check previous container logs (if container restarted)
kubectl logs <pod-name> --previous

# Describe the pod for events
kubectl describe pod <pod-name>

# Port forward to test connectivity
kubectl port-forward pod/<pod-name> <local-port>:<pod-port>
```

---

## Part 2: The Three Key Components for Troubleshooting

Whenever you deploy on Kubernetes, you typically define **three components**:

| Component | Purpose | Key Troubleshooting Point |
|-----------|---------|---------------------------|
| **Deployment** | Manages pods and replicas | Check pod status, logs, events |
| **Service** | Exposes pods internally/externally | Check selector matches pod labels |
| **Ingress** | Routes external HTTP/HTTPS traffic | Check rules and backend service |

---

## Part 3: The Four Rule Theory (YAML Structure)

Every Kubernetes YAML file follows this structure. Remember these four:

| Rule | Description | Example |
|------|-------------|---------|
| **apiVersion** | API version of the resource | `apps/v1` |
| **kind** | Type of Kubernetes resource | `Deployment`, `Service`, `Ingress` |
| **metadata** | Name, labels, namespace | `name: my-app` |
| **spec** | Desired state of the resource | Container specs, selectors |

---

## Part 4: Connecting Deployment and Service

### The 5 Critical Checks:

1. **Service selector must match at least one pod label**
2. **Container port must be defined**
3. **Target port must be defined** (matches container port)
4. **Service port can be any number**
5. **Ingress port should match the service port**

### Troubleshooting Commands:
```bash
# Check pod labels
kubectl get pods --show-labels

# Check service selector
kubectl describe service <service-name>

# Test port forwarding
kubectl port-forward service/<service-name> <local-port>:<service-port>
```

---

## Part 5: Connecting Service and Ingress

### The Traffic Flow:
```
Browser → Ingress (Port 80/443) → Service → Pod (Container Port)
```

### Key Points:
- Ingress routes to a **service** (not directly to pods)
- Service routes traffic to **pods** based on selectors
- The ingress backend service name must match the service name

## Part 6: Common Pod Errors and Their Solutions

| Error | Cause | Troubleshooting |
|-------|-------|-----------------|
| **ImagePullBackOff** | Wrong image name/tag, registry unavailable | Check image name, check registry access, verify credentials |
| **CrashLoopBackOff** | Application crashes on startup | `kubectl logs <pod>`, check application config |
| **ErrImagePull** | Cannot pull image | Check image exists, check network/registry |
| **InvalidImageName** | Image name format wrong | Verify image name syntax |
| **OOMKilled** | Out of memory | Increase memory limits |
| **RunContainerError** | Container failed to start | Check command/args in spec |
| **CreateContainerError** | Container creation failed | Check volumes, configs, secrets |

## Part 7: Master Node Components (kube-system namespace)

```bash
kubectl get pods -n kube-system
```

| Component | Role |
|-----------|------|
| **etcd** | Cluster database |
| **kube-apiserver** | Front-end API |
| **kube-controller-manager** | Runs controllers |
| **kube-scheduler** | Schedules pods |
| **kube-proxy** | Network proxy |
| **CoreDNS** | DNS resolution |

## Part 8: Three Steps to Troubleshoot Any Kubernetes Deployment

### Step 1: Check Pods
```bash
kubectl get pods
kubectl get pods -o wide
```

### Step 2: Check Logs
```bash
kubectl logs <pod-name>
kubectl logs <pod-name> --previous
```

### Step 3: Check Details
```bash
kubectl describe pod <pod-name>
kubectl exec -it <pod-name> -- bash
```

---

## Part 9: Essential Troubleshooting Commands Cheat Sheet

| Command | Purpose |
|---------|---------|
| `kubectl get pods` | List all pods |
| `kubectl get pods -o wide` | Pods with node and IP details |
| `kubectl get pods --show-labels` | Pods with their labels |
| `kubectl describe pod <name>` | Detailed pod info + events |
| `kubectl logs <pod>` | View pod logs |
| `kubectl logs <pod> --previous` | View logs of previous crashed container |
| `kubectl exec -it <pod> -- bash` | Enter container shell |
| `kubectl port-forward pod/<pod> <local>:<pod>` | Forward local port to pod |
| `kubectl port-forward service/<svc> <local>:<svc>` | Forward local port to service |
| `kubectl get pods -n kube-system` | View system pods |
| `kubectl describe service <name>` | Service details and endpoints |
| `kubectl get endpoints` | Check service-to-pod mappings |
| `kubectl get events` | View cluster events |
| `kubectl describe ingress <name>` | Ingress details |
| `kubectl get pvc` | Check persistent volume claims |
| `kubectl get resourcequota` | Check resource quotas |
