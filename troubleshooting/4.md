## A Kubernetes cluster upgrade causes API server downtime or breaks workloads.

### Troubleshooting Steps:

```bash
# Step 1: Backup etcd data
ETCDCTL_API=3 etcdctl snapshot save snapshot.db \
  --endpoints=<etcd-endpoint>:2379

# Step 2: Upgrade kubeadm
sudo apt-get update && sudo apt-get install -y kubeadm

# Step 3: Apply the upgrade
sudo kubeadm upgrade apply <target-version>

# Step 4: Upgrade kubelet and kubectl
sudo apt-get install -y kubelet kubectl
sudo systemctl restart kubelet

# Step 5: Drain and upgrade nodes
kubectl drain <node-name> --ignore-daemonsets --force
sudo kubeadm upgrade node

# Step 6: Uncordon nodes
kubectl uncordon <node-name>
```

### Key Points:
- Always backup etcd before upgrade
- Upgrade CRDs before cluster upgrade
- Incompatibilities with older CRDs or Helm charts can cause issues

## Understanding Kubernetes Version Support

### Version Lifecycle

```
Kubernetes releases new minor version every ~3 months:

1.27 (released Apr 2023)
├─ Supported for ~10 months
├─ Gets patches: 1.27.0, 1.27.1, 1.27.2, etc.
├─ Support ends: Jan 2024 (EOL)
└─ Must upgrade before EOL

1.28 (released Aug 2023)
├─ Supported for ~10 months
├─ New features from 1.27
├─ Deprecations removed
└─ Support ends: May 2024

Key point: Support only 3 versions back
├─ If current is 1.28
├─ Supported: 1.28, 1.27, 1.26
└─ Unsupported: 1.25, 1.24 (EOL)
```

### Upgrade Rules

```
✓ Safe upgrade paths:
├─ 1.25 → 1.26 (one minor version)
├─ 1.26 → 1.27 (one minor version)
└─ 1.25 → 1.26 → 1.27 (sequential)

✗ NOT supported:
├─ 1.25 → 1.27 (skip version - not tested/supported)
├─ 1.27 → 1.25 (downgrade - not supported)
└─ 1.24 → 1.28 (too many versions)

Rule: Upgrade one minor version at a time!
```

## Pre-Upgrade Checklist

### 1. Backup etcd (CRITICAL)

```bash
# Check etcd endpoint
kubectl -n kube-system get pods | grep etcd

# Backup etcd
ETCDCTL_API=3 etcdctl snapshot save snapshot.db \
  --endpoints=127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Verify backup
ls -lh snapshot.db
ETCDCTL_API=3 etcdctl snapshot status snapshot.db

# Store backup somewhere safe
scp snapshot.db backup-server:/backups/etcd-1.25.db
```

**Why etcd backup is critical:**

```
etcd contains:
├─ All Kubernetes objects (pods, services, deployments, etc.)
├─ All cluster state
├─ All secrets (encrypted)
└─ Custom Resources (CRs)

If upgrade goes wrong:
├─ You can restore from backup
├─ 30 minutes lost, not everything
└─ Without backup: Complete cluster loss
```

---

### 2. Check Current Versions

```bash
# Check all component versions
kubectl get nodes -o wide

# Output:
NAME            STATUS   ROLES           VERSION
master-1        Ready    control-plane   v1.25.3
worker-1        Ready    <none>          v1.25.3
worker-2        Ready    <none>          v1.25.3

# Check API server version
kubectl version --short

# Check what versions are available
kubeadm version -o json
apt-cache policy kubeadm

# Available versions:
# kubeadm: 1.26.0-1.26.1-1.26.2-1.27.0 (etc.)
```

---

### 3. Check for Unsupported API Deprecations

```bash
# Find APIs that will be removed in next version
kubectl api-resources

# Check for deprecated APIs
kubectl get apiservice | grep -v "Local"

# Look for v1beta1 that will be removed
# Different Kubernetes versions deprecate different APIs

# Example: In Kubernetes 1.26, these were removed:
# - flowcontrol.apiserver.k8s.io/v1beta1
# - apiextensions.k8s.io/v1beta1 for CRDs

# Find if you're using deprecated APIs
kubectl get -A --all --show-kind=true | grep v1beta1
```

---

### 4. Check Helm Charts Compatibility

```bash
# List all Helm releases
helm list -A

# Check compatibility with target Kubernetes version
# Look at chart's kubeVersion field

helm show values <chart-name> --version <chart-version> \
  | grep -i "kubeVersion"

# Example output:
# kubeVersion: ">=1.24" (compatible with 1.25, 1.26, etc.)
# kubeVersion: ">=1.26" (NOT compatible with 1.25!)

# If incompatible:
helm repo update
helm upgrade <release> <chart> --version <new-chart-version>
```

---

### 5. Upgrade CRDs First

```bash
# Find all CRDs
kubectl get crd

# Check CRD versions
kubectl get crd -o yaml | grep "^  - name"

# Update CRDs (usually via Helm or operator)
# IMPORTANT: Do this BEFORE cluster upgrade!

# Example: Upgrade cert-manager CRDs
helm repo update jetstack
helm upgrade cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --version v1.13.0 \
  --reuse-values

# Verify CRDs are updated
kubectl get crd
```

## Control Plane Upgrade

### Step 1: Upgrade kubeadm on Control Plane

```bash
# SSH to control plane node
ssh ubuntu@control-plane-1

# Hold current version
sudo apt-mark hold kubelet kubectl

# Update package list
sudo apt-get update

# Install specific kubeadm version
sudo apt-get install -y kubeadm=1.26.0-00

# Verify installation
kubeadm version
# Output: kubeadm version: &version.Info{Major:"1", Minor:"26"...}
```

---

### Step 2: Plan the Upgrade

```bash
# Check what changes kubeadm will make
sudo kubeadm upgrade plan

# Output example:
# [upgrade/config] Making sure the configuration is correct:
# [preflight] Running pre-flight checks.
# [upgrade] This version of kubeadm supports the following versions:
#   - v1.25
#   - v1.26
# 
# [upgrade/available_versions]
# The latest stable version in this release channel is v1.26.0
# You can now apply the upgrade by executing the following command:
#
#  kubeadm upgrade apply v1.26.0
#
# Note: Before you do kubeadm upgrade apply version, you have to upgrade kubeadm to version v1.26.0
```

---

### Step 3: Apply the Upgrade

```bash
# Apply the upgrade (main step)
sudo kubeadm upgrade apply v1.26.0

# This will:
# ├─ Backup manifests
# ├─ Upgrade static pods (API server, controller-manager, scheduler, etcd)
# ├─ Upgrade kubelet configuration
# └─ Display upgrade summary

# Output:
# [upgrade/successful] SUCCESS! Your cluster was upgraded to "v1.26.0"
# [upgrade/version] Now that your cluster is upgraded, you must also
# upgrade the kubelet and kubectl on control plane nodes...
```

**Important:** API server may be down for 30-120 seconds during this step.

---

### Step 4: Upgrade kubelet and kubectl on Control Plane

```bash
# Unhold kubelet/kubectl
sudo apt-mark unhold kubelet kubectl

# Upgrade kubelet and kubectl
sudo apt-get install -y kubelet=1.26.0-00 kubectl=1.26.0-00

# Restart kubelet
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# Verify control plane is back up
kubectl get nodes

# Output:
# NAME            STATUS   ROLES           VERSION
# control-plane   Ready    control-plane   v1.26.0  ← Updated!
```

## Worker Node Upgrade

### For Each Worker Node:

```bash
# Step 1: Drain the node (move pods to other nodes)
kubectl drain <node-name> \
  --ignore-daemonsets \
  --force \
  --delete-emptydir-data

# What --ignore-daemonsets does:
# ├─ Evicts pods from node
# ├─ Ignores DaemonSet pods (they'll respawn)
# ├─ Waits for pods to gracefully terminate
# └─ Puts node in SchedulingDisabled state

# What --force does:
# ├─ Deletes pods without waiting
# ├─ Use if graceful termination takes too long
# └─ Can cause data loss if not careful

# Step 2: SSH to worker node
ssh ubuntu@worker-1

# Step 3: Upgrade kubeadm
sudo apt-get update
sudo apt-get install -y kubeadm=1.26.0-00

# Step 4: Upgrade kubelet
sudo kubeadm upgrade node
sudo apt-get install -y kubelet=1.26.0-00

# Step 5: Restart kubelet
sudo systemctl daemon-reload
sudo systemctl restart kubelet

# Step 6: Return to master and uncordon node
kubectl uncordon <node-name>

# Node is back in service, pods reschedule here

# Repeat for each worker node
```

## Complete Upgrade Workflow Example

```bash
#!/bin/bash
# Kubernetes 1.25 → 1.26 Upgrade Script

set -e  # Exit on error

# Colors for output
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[1;33m'
NC='\033[0m'

echo -e "${YELLOW}Starting Kubernetes upgrade 1.25 → 1.26${NC}"

# Step 1: Backup etcd
echo -e "${YELLOW}Step 1: Backing up etcd${NC}"
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-$(date +%s).db \
  --endpoints=127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key
echo -e "${GREEN}✓ etcd backup complete${NC}"

# Step 2: Check cluster status
echo -e "${YELLOW}Step 2: Checking cluster status${NC}"
kubectl get nodes
kubectl get pods -A | grep -i "not ready" && {
  echo -e "${RED}Error: Cluster has unhealthy nodes${NC}"
  exit 1
}
echo -e "${GREEN}✓ Cluster healthy${NC}"

# Step 3: Upgrade control plane
echo -e "${YELLOW}Step 3: Upgrading control plane${NC}"
ssh ubuntu@control-plane "bash -s" <<'EOF'
  sudo apt-get update
  sudo apt-get install -y kubeadm=1.26.0-00
  sudo kubeadm upgrade apply v1.26.0 --yes
  sudo apt-mark unhold kubelet kubectl
  sudo apt-get install -y kubelet=1.26.0-00 kubectl=1.26.0-00
  sudo systemctl daemon-reload
  sudo systemctl restart kubelet
EOF
echo -e "${GREEN}✓ Control plane upgraded${NC}"

# Wait for control plane to be ready
sleep 30
kubectl get nodes | grep "control-plane" | grep -q "Ready" || {
  echo -e "${RED}Error: Control plane not ready${NC}"
  exit 1
}

# Step 4: Upgrade worker nodes
echo -e "${YELLOW}Step 4: Upgrading worker nodes${NC}"
NODES=$(kubectl get nodes -o jsonpath='{.items[?(@.metadata.labels.node-role\.kubernetes\.io/control-plane!="true")].metadata.name}')

for NODE in $NODES; do
  echo -e "${YELLOW}Draining $NODE${NC}"
  kubectl drain $NODE --ignore-daemonsets --force --delete-emptydir-data
  
  echo -e "${YELLOW}Upgrading $NODE${NC}"
  ssh ubuntu@$NODE "bash -s" <<EOF
    sudo apt-get update
    sudo apt-get install -y kubeadm=1.26.0-00
    sudo kubeadm upgrade node
    sudo apt-mark unhold kubelet kubectl
    sudo apt-get install -y kubelet=1.26.0-00 kubectl=1.26.0-00
    sudo systemctl daemon-reload
    sudo systemctl restart kubelet
EOF
  
  echo -e "${YELLOW}Uncordoning $NODE${NC}"
  kubectl uncordon $NODE
  
  # Wait for node to be ready
  sleep 30
done

echo -e "${GREEN}✓ All worker nodes upgraded${NC}"

# Step 5: Verify upgrade
echo -e "${YELLOW}Step 5: Verifying upgrade${NC}"
kubectl get nodes
kubectl get pods -A | grep -i "CrashLoopBackOff" && {
  echo -e "${RED}Warning: Some pods in CrashLoopBackOff${NC}"
  kubectl get pods -A | grep -i "CrashLoopBackOff"
}

echo -e "${GREEN}✅ Kubernetes upgrade complete!${NC}"
```

## Rollback Procedure

### If Upgrade Goes Wrong

```bash
# Option 1: Wait for control plane to come back
# (Usually 1-2 minutes)
while ! kubectl get nodes &>/dev/null; do
  echo "Waiting for API server..."
  sleep 5
done

# Option 2: Restore from etcd backup
# (Only if things are truly broken)

# Step 1: Stop all Kubernetes components
sudo systemctl stop kubelet

# Step 2: Stop containers manually if needed
sudo docker stop $(sudo docker ps -q)
sudo docker rm $(sudo docker ps -aq)

# Step 3: Restore etcd from backup
ETCDCTL_API=3 etcdctl snapshot restore snapshot.db \
  --data-dir=/var/lib/etcd-backup \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Step 4: Replace etcd data
sudo mv /var/lib/etcd /var/lib/etcd-broken
sudo mv /var/lib/etcd-backup /var/lib/etcd

# Step 5: Restart kubelet
sudo systemctl start kubelet

# Step 6: Verify restoration
kubectl get nodes
kubectl get pods -A

# Note: This is drastic and loses all changes made after backup!
```

## Common Issues & Solutions

### Issue 1: API Server Won't Start After Upgrade

**Symptom:**
```
kubectl get nodes
# Error: The connection to the server was refused
```

**Check logs:**
```bash
# Check API server logs
kubectl -n kube-system logs -f deployment/kube-apiserver

# Or check kubelet logs
journalctl -u kubelet -f

# Common errors:
# - Failed to find certificate file
# - etcd connection refused
# - Storage encryption key mismatch
```

**Solutions:**
```bash
# Wait for API server to start (usually 30-120s)
for i in {1..60}; do
  kubectl version && break
  echo "Waiting... ($i/60)"
  sleep 2
done

# If still failing, check previous node upgrade
# and restart kubelet
sudo systemctl restart kubelet
```

---

### Issue 2: Pods Not Rescheduling After Uncordon

**Symptom:**
```
kubectl get pods -A
# Pods still on other nodes, not back on original node
```

**Root Cause:**
```
Kubernetes won't automatically move pods back.
They only move if original node fails/unavailable.
```

**Solution:**
```bash
# Manually delete pod (if stateless)
kubectl delete pod <pod-name> -n <namespace>

# Or use rollout restart
kubectl rollout restart deployment <name> -n <namespace>

# For StatefulSets
kubectl delete pod <statefulset-name>-0 -n <namespace>
# Pod will respawn on preferred node
```

---

### Issue 3: CRD Validation Fails After Upgrade

**Symptom:**
```
Error from server (InternalError): error when creating "resource.yaml":
Internal error occurred: failed calling webhook to validate crd request
```

**Root Cause:**
CRD webhook from old version incompatible with new Kubernetes.

**Solution:**
```bash
# Step 1: Update CRD operator/controller
helm repo update
helm upgrade my-operator <chart> --version <new-version>

# Step 2: Wait for operator to be ready
kubectl get deployment -n <operator-ns> -w

# Step 3: Retry CRD creation
kubectl apply -f resource.yaml
```

## Best Practices for Smooth Upgrades

```yaml
# 1. Use PodDisruptionBudgets
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: app-pdb
spec:
  minAvailable: 2  # Always keep 2 pods running
  selector:
    matchLabels:
      app: my-app

---
# 2. Use multiple replicas
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 3  # At least 3 for rolling upgrades
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1  # Only update 1 at a time
      maxSurge: 1        # Only create 1 extra pod

---
# 3. Use anti-affinity to spread pods
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: app
              operator: In
              values:
              - my-app
          topologyKey: kubernetes.io/hostname
```

## Interview Answer

**Question: "How would you handle a Kubernetes cluster upgrade that breaks workloads?"**

**Answer:**

```
Kubernetes upgrades require careful planning and execution.
Here's my approach:

PRE-UPGRADE:
1. Backup etcd data (critical!)
   - Store securely - it's the entire cluster state
   
2. Test in staging environment first
   - Same version, same workloads
   - Identify compatibility issues early
   
3. Check for API deprecations
   - Some APIs removed in each version
   - Update code/CRDs before upgrade
   
4. Verify CRD and Helm chart compatibility
   - Incompatible charts break immediately
   - Test: helm template, kubectl apply --dry-run

DURING UPGRADE:
1. Upgrade control plane first
   - Brief downtime (30-120s)
   - Be ready for kubectl timeouts
   
2. Upgrade worker nodes one at a time
   - Drain node (evict pods)
   - Upgrade kubelet
   - Uncordon node (accept new pods)
   
3. Monitor during upgrade
   - Watch for pod crashes
   - Check event logs
   - Alert on errors

POST-UPGRADE:
1. Verify cluster health
   - All nodes Ready
   - All pods Running
   - Metrics working
   
2. Test applications
   - Check connectivity
   - Verify functionality
   - Monitor for errors

IF THINGS BREAK:
1. Check logs first
   - kubectl logs, kubectl describe
   - journalctl on nodes
   
2. Common fixes
   - Restart kubelet if node not ready
   - Upgrade CRDs if custom resources fail
   - Restart pods if they're stuck
   
3. Worst case: Restore from etcd backup
   - Requires stopping everything
   - Restores cluster to pre-upgrade state
   - Better than complete loss

KEY PRACTICES:
✓ Always backup etcd
✓ Test in staging first
✓ Upgrade sequentially (1.25→1.26→1.27)
✓ Use PodDisruptionBudgets
✓ Run multiple replicas
✓ Have rollback plan ready
```
