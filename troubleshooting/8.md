## Overloaded API Server - High API server load affects performance and causes timeouts.

### Troubleshooting Steps:

```bash
# Step 1: Check API server logs
kubectl logs -n kube-system <api-server-pod-name>

# Step 2: Identify frequent API users
kubectl top pod -n kube-system

# Step 3: Enable client-side caching in kube-proxy
kubectl edit configmap kube-proxy -n kube-system
# Add:
# clusterCIDR: <CIDR-range>
# mode: iptables

# Step 4: Add replicas for HA
kubectl scale deployment kube-apiserver --replicas=3 -n kube-system
```

### Common Causes:
- Too many controllers
- High watch traffic
- Excessive requests from CI/CD pipelines

## Real-World Scenario: CI/CD Pipeline Overload

### The Problem

```
CI/CD pipeline has 50 workers
Each worker polls pod status every 1 second:

for i in 1..1000:
    status = kubectl get pod myapp-$i -o yaml
    sleep 1

Total requests:
50 workers × 60 polls/min × 60 min = 180,000 requests/hour
= 50 requests/second (continuous!)

Meanwhile, regular operations need:
100-200 requests/second

Total: 250+ requests/second → API server overloaded!
```

### Diagnosis

```bash
# Step 1: Check request sources
kubectl logs -n kube-system kube-apiserver-master-1 | \
  grep "ci-pipeline" | wc -l

# Output: 3000+ lines in last 10 minutes!
# Confirms: CI pipeline hammering API

# Step 2: Check request types
kubectl logs -n kube-system kube-apiserver-master-1 | \
  grep "ci-pipeline" | \
  grep -oP 'verb=\K[^ ]*' | \
  sort | uniq -c

# Output:
# 2800 get
# 200 list
# = Lots of GET requests (polling!)
```

### Solution 1: Fix CI/CD to Use Watches

**Bad approach (polling):**
```bash
#!/bin/bash
# Continuously polls every second
while true; do
  kubectl get pod myapp-123 -o yaml
  sleep 1
done
```

**Good approach (watching):**
```bash
#!/bin/bash
# Uses watch - only sends updates when pod changes
kubectl get pod myapp-123 --watch -o yaml
```

**Better approach (use events):**
```bash
#!/bin/bash
# Watch for pod changes via events
kubectl get events --field-selector involvedObject.name=myapp-123 --watch
```

## Common Solutions

### 1. Add More API Server Replicas

**Current setup (HA):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  replicas: 1  # ❌ Single point of failure
  selector:
    matchLabels:
      component: kube-apiserver
  template:
    metadata:
      labels:
        component: kube-apiserver
    spec:
      containers:
      - name: kube-apiserver
        image: kube-apiserver:v1.26.0
```

**Better setup (multiple replicas):**
```yaml
spec:
  replicas: 3  # ✅ Spreads load, HA
```

**Important notes:**
```
✓ Each replica connects to same etcd
✓ Load balancer distributes traffic
✓ Typical: 3-5 replicas for large clusters
✓ Don't need more than 5 (diminishing returns)
```

---

### 2. Optimize Controller Logic

**Bad controller (causes overload):**
```python
# Python operator example
import kopf

@kopf.on.event('v1', 'pods')
def watch_all_pods(event, **kwargs):
    # Gets called for EVERY pod change
    # List all pods (expensive!)
    all_pods = list_pods_from_api()
    
    # Process them
    for pod in all_pods:
        if pod.status == 'Pending':
            # Do something
            pass
```

**Good controller (optimized):**
```python
import kopf

@kopf.on.event('v1', 'pods',
               labels={'watch': 'true'},  # ← Filter!
               field_selector='status.phase=Pending')  # ← Filter!
def watch_pending_pods(event, **kwargs):
    # Only called for pods matching filter
    # No need to list - event already has the pod!
    pod = event['object']
    
    # Process just this pod
    if pod.status == 'Pending':
        # Do something
        pass
```

**Key differences:**
```
Bad approach:
├─ Watch: All pods
├─ Process: List all pods from API
├─ Decision: In code (every change)
└─ Overhead: Massive

Good approach:
├─ Watch: Only matching pods
├─ Process: Just the event object
├─ Decision: In selector (API-side)
└─ Overhead: Minimal
```

### 3. Fix Excessive Polling

**Bad CI/CD script:**
```bash
#!/bin/bash
# Polls every second
while true; do
    status=$(kubectl get pod myapp-123 -o jsonpath='{.status.phase}')
    if [ "$status" = "Running" ]; then
        break
    fi
    sleep 1
done
echo "Pod is ready!"
```

**Good approach with wait:**
```bash
#!/bin/bash
# Uses kubectl wait - more efficient
kubectl wait --for=condition=Ready pod/myapp-123 --timeout=300s
echo "Pod is ready!"
```

**Even better with watch:**
```bash
#!/bin/bash
# Watch for specific state
kubectl get pod myapp-123 --watch -o jsonpath='{.status.phase}' | \
    grep -m1 "Running"
echo "Pod is ready!"
```

### 4. Optimize List Calls

**Bad approach (get everything):**
```bash
# Fetches all pods from entire cluster
kubectl get pods -A

# With 10,000 pods, this is massive!
# Network: 100MB+ payload
# CPU: High parsing
# Memory: Large response
```

**Good approach (filter early):**
```bash
# Only get what you need
kubectl get pods -n my-namespace \
  -l app=myapp \
  --field-selector status.phase=Running

# Much smaller response
# Filter happens server-side (API handles it)
# Client only receives matching pods
```

**Using pagination:**
```bash
# For large lists, use limit/continue
kubectl get pods -A --limit=100
# Returns first 100 with 'continue' token

kubectl get pods -A --limit=100 --continue=<token>
# Returns next 100

# Prevents loading entire list in memory
```

---

### 5. Set Resource Limits on API Server

**Check current limits:**
```bash
kubectl describe deployment kube-apiserver -n kube-system | \
  grep -A 5 "Limits"
```

**If no limits, add them:**
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: kube-apiserver
  namespace: kube-system
spec:
  containers:
  - name: kube-apiserver
    resources:
      requests:
        cpu: 500m        # Minimum for stable operation
        memory: 1Gi      # Minimum
      limits:
        cpu: 2000m       # Max allowed
        memory: 4Gi      # Max allowed
```

**Healthy resource usage:**
```
Typical cluster (100-500 nodes):
├─ CPU: 200-800m average
├─ Memory: 1-2Gi average
└─ Peaks: 1000m CPU, 3Gi memory

With limits:
├─ Prevents runaway consumption
├─ Protects other components
└─ Force you to optimize
```

```bash
#!/bin/bash
# API Server Overload Troubleshooting

echo "=== API Server Health Check ==="

# 1. Check pod status
echo "1. Pod status:"

# 2. Check resource usage

  grep -i "slow\|latency" | \
  head -10

# 5. Top requesters
echo -e "\n5. Top request users:"
kubectl logs -n kube-system kube-apiserver-master-1 | \
  grep -oP 'user=\K[^ ]*' | \
  sort | uniq -c | sort -rn | head -5

# 6. Top request verbs (GET, LIST, WATCH, etc)
echo -e "\n6. Top request types:"
kubectl logs -n kube-system kube-apiserver-master-1 | \
  grep -oP 'verb=\K[^ ]*' | \
  sort | uniq -c | sort -rn

# 7. Check etcd latency
echo -e "\n7. etcd latency:"
kubectl logs -n kube-system etcd-master-1 2>/dev/null | \
  grep -i "slow\|latency" | \
  head -5

# 8. Suggest fixes
echo -e "\n=== Recommended Actions ==="
if kubectl logs -n kube-system kube-apiserver-master-1 | \
   grep -q "slow request"; then
    echo "⚠️  Slow requests detected - reduce API load"
fi

if kubectl top pod -n kube-system kube-apiserver-master-1 | \
   tail -1 | awk '{print $2}' | grep -q "m$"; then
    CPU=$(kubectl top pod -n kube-system kube-apiserver-master-1 | \
          tail -1 | awk '{print $2}' | sed 's/m//')
    if [ "$CPU" -gt 800 ]; then
        echo "⚠️  API server CPU high ($CPU m) - consider more replicas"
    fi
fi

echo "✓ Check kube-proxy configuration"
echo "✓ Audit CI/CD pipeline for excessive polling"
echo "✓ Use kubectl wait instead of loops"
echo "✓ Filter watches with selectors"
```

## Prevention: Best Practices

```yaml
# 1. Use smart selectors in watches
apiVersion: v1
kind: Pod
metadata:
  name: my-operator
spec:
  containers:
  - name: operator
    env:
    - name: WATCH_LABEL_SELECTOR
      value: "app=myapp,tier=backend"
    # Only watch pods with these labels
    # Not all pods in cluster

---
# 2. Use informer pattern (if using Go)
# Instead of:
#   watch all pods
#   process all events
# 
# Do:
#   watch pods with selector
#   cache them
#   process only when needed

---
# 3. Set appropriate timeouts
apiVersion: v1
kind: ConfigMap
metadata:
  name: controller-config
data:
  api-timeout: "30s"       # Don't wait forever
  list-limit: "500"        # Paginate large lists
  sync-period: "30m"       # Periodic resync
  burst-qps: "100"         # Limit burst requests
```

## Interview Answer

**Question: "How would you troubleshoot an overloaded API server?"**

**Answer:**

```
An overloaded API server manifests as slow kubectl commands,
timeouts, and timeouts. Here's my troubleshooting approach:

DIAGNOSIS:
1. Check API server metrics
   - Request rate: 100-500 req/s healthy, >5000 = overloaded
   - Latency: p99 < 100ms healthy, >1s = problem
   - CPU/Memory: Check resource usage

2. Check logs for offenders
   - grep for "slow request"
   - Identify top request users (CI/CD, operators)
   - See which verbs are most frequent

3. Common culprits:
   ├─ CI/CD polling: kubectl get pod every second
   ├─ Too many watches: Controllers not filtering
   ├─ Inefficient list: Getting all pods instead of filtering
   ├─ Operators: Badly written reconcile loops
   └─ Large objects: ConfigMaps/Secrets > 1MB

SOLUTIONS:
1. Short term:
   - Scale to 3-5 API server replicas
   - Set resource limits to prevent runaway
   - Restart problematic controllers

2. Medium term:
   - Fix CI/CD to use kubectl wait instead of polling
   - Optimize controller watches with selectors
   - Use pagination for large list calls

3. Long term:
   - Implement admission webhooks for validation
   - Use informer pattern for controllers
   - Monitor request patterns continuously

PREVENTION:
✓ Use kubectl wait, not loops
✓ Filter watches with label selectors
✓ Paginate large list operations
✓ Monitor API server metrics
✓ Set resource requests/limits
✓ Use multiple replicas (HA)
```
