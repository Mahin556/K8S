### Labels
- Labels are key-value pairs attached to Kubernetes objects like nodes, pods, services, and deployments. 
- They used to organize, filter, and select resources to target them.
- Unlike taints, labels don't directly affect scheduling but are useful for organizing resources.

**Examples of Labels:**
- `environment: production`
- `type: backend`
- `tier: frontend`
- `application: my-app`

#### Types of labels
* **User-Defined Labels(custom)**:
  * Created manually by users or automation tools.
  * Help identify or organize resources for management, deployment, or selection.
  * Commonly used for:
    * Environment (env=dev, env=prod)
    * Application (app=nginx, app=frontend)
    * Component (tier=backend, tier=database)
    * Team or owner (team=devops, owner=mahin)
  
* **System (or Built-in) Labels**
  * Automatically added by Kubernetes to identify internal system information.
  * You should not modify these — they’re used by the scheduler and controllers.

    | Label                              | Description                                              |
    | ---------------------------------- | -------------------------------------------------------- |
    | `kubernetes.io/hostname`           | Node’s name (unique per node).                           |
    | `kubernetes.io/os`                 | Operating system of the node (e.g., `linux`, `windows`). |
    | `kubernetes.io/arch`               | CPU architecture (`amd64`, `arm64`, etc.).               |
    | `topology.kubernetes.io/region`    | Region where the node is located.                        |
    | `topology.kubernetes.io/zone`      | Zone (e.g., availability zone in cloud).                 |
    | `node.kubernetes.io/instance-type` | Node’s instance type (like EC2 size).                    |
    | `kubernetes.io/metadata.name`      | Automatically set in namespaces to reflect their name.   |

* **Topology Labels**
  * Used for zone/region-aware scheduling and fault-tolerant deployments.
  * Commonly applied to nodes.
    ```bash
    topology.kubernetes.io/region=us-east1
    topology.kubernetes.io/zone=us-east1-b
    ```
  * Helps distribute Pods across multiple zones for high availability.
  * Used with:
    * Pod topology spread constraints
    * Affinity / anti-affinity rules

* **Controller / Operator Labels**
  * Added automatically by controllers (like Deployments, ReplicaSets, DaemonSets).
  * Used to track resource relationships and ownership.
    ```bash
    app.kubernetes.io/name: nginx
    app.kubernetes.io/instance: my-nginx
    app.kubernetes.io/component: web
    app.kubernetes.io/part-of: myapp
    app.kubernetes.io/managed-by: Helm
    ```
  * These labels are part of the Kubernetes recommended labeling convention (defined in official docs).

* **Cloud Provider / Platform Labels**
  * Automatically added by cloud environments or managed clusters (EKS, GKE, AKS, etc.)
  * Describe node hardware, location, or provider metadata.
    ```bash
    failure-domain.beta.kubernetes.io/zone=us-west-2a
    eks.amazonaws.com/nodegroup=my-node-group
    cloud.google.com/gke-nodepool=default-pool
    ```

* **Custom Automation Labels**
  * Added by CI/CD tools, GitOps pipelines, or configuration management systems.
  * Useful for identifying deployment source, version, or rollout stage.
    ```bash
    pipeline=jenkins
    build=45
    version=1.2.3
    deployed-by=argo
    ```


```bash
#View labels
kubectl get pod --show-labels
kubectl get nodes --show-labels
kubectl get pod nginx --show-labels #Specific

#Add a label
kubectl label pods foo unhealthy=true
kubectl label node mynode region=us-east

#Label multiple resource at once
kubectl label pods pod1 pod2 pod3 env=dev

#Overwrite a label
kubectl label --overwrite pods foo status=unhealthy
kubectl label nodes <node-name> app=database --overwrite

#Use a specific kubeconfig file(`--kubeconfig`)
kubectl label pods foo app=db --kubeconfig=/path/config

#Run as another user(`--as`)
kubectl label pods foo owner=team --as admin

#Specify API server(`-s, --server`)
kubectl label pods foo zone=us-east -s https://my-api:6443

#Add label for all pod in default namespace\
kubectl label pods --all status=unhealthy
kubectl label pods --all status=unhealthy -n demo #Specific namespace
```

```bash
# Create Deployment Manifest
cat <<EOF > deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deploy
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
      - name: nginx
        image: nginx
EOF

# Apply Deployment To Cluster
kubectl apply -f deployment.yaml

# Verify Deployment (No app=web label yet)
kubectl get deploy myapp-deploy --show-labels

# Add Label Using File
kubectl label -f deployment.yaml app=web

# Verify Label Added In Cluster
kubectl get deploy myapp-deploy --show-labels

# Multiple Labels
kubectl label -f deployment.yaml app=web tier=frontend

# Overwrite Existing Label
kubectl label -f deployment.yaml app=backend --overwrite

# Label All Resources In Directory
kubectl label -f ./manifests/ env=prod

# Label From URL
kubectl label -f https://raw.githubusercontent.com/kubernetes/website/main/content/en/examples/controllers/nginx-deployment.yaml team=dev


# =========================================
# IMPORTANT THEORY
# =========================================
# -f means:
#   "Find resource defined in this file and update it in the cluster"
#
# It does NOT modify local YAML file.
#
# It sends PATCH request to Kubernetes API.
#
# Same logic works with:
#   kubectl delete -f
#   kubectl annotate -f
#   kubectl patch -f
#   kubectl apply -f
#
# =========================================
```

```bash
# PRACTICAL: kubectl label --local

# 1. Create Pod Manifest
cat <<EOF > pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-pod
  labels:
    app: demo
spec:
  containers:
  - name: nginx
    image: nginx
EOF

# 2. Modify YAML Locally (NO API CALL)
kubectl label -f pod.yaml env=staging --local -o yaml


# What This Does
# - Reads pod.yaml
# - Adds label under metadata.labels:
#     env: staging
# - Prints modified YAML
# - Does NOT create pod
# - Does NOT contact API server


# 3. Save Modified Output To New File
kubectl label -f pod.yaml env=staging --local -o yaml > new-pod.yaml

cat new-pod.yaml

# 4. Apply After Local Modification
kubectl label -f pod.yaml env=staging --local -o yaml | kubectl apply -f -

# 5. Without --local (Touches Cluster)
kubectl label -f pod.yaml env=staging

# 6. Modern Alternative
kubectl label -f pod.yaml env=prod --dry-run=client -o yaml

# Difference Summary
# --local            → No API call
# --dry-run=client   → No API call (modern replacement)
# --dry-run=server   → Validates with API server, no persistence
```

```bash
# PRACTICAL: kubectl label with different output formats (-o)

# 1. Create pod.yaml
cat <<EOF > pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: demo-pod
  labels:
    app: demo
spec:
  containers:
  - name: nginx
    image: nginx
EOF


# 2. YAML Output
kubectl label -f pod.yaml app=api --dry-run=client -o yaml
# Prints full modified YAML
# Does NOT apply to cluster


# 3. JSON Output
kubectl label -f pod.yaml app=api --dry-run=client -o json
# Prints modified object in JSON format


# 4. Name Output
kubectl label -f pod.yaml app=api --dry-run=client -o name

# Output:
# pod/demo-pod


# 5. Wide Output (when resource exists in cluster)
kubectl apply -f pod.yaml
kubectl label pod demo-pod version=v1 -o wide


# SUMMARY

# -o yaml   → YAML format
# -o json   → JSON format
# -o name   → resource name only
# -o wide   → extra columns (for get/list commands)
```
```bash
# Apply labels using Kustomize directory (-k)
  # Directory structure:
  # kustomize-dir/
  # ├── deployment.yaml
  # └── kustomization.yaml

# Example deployment.yaml
cat <<EOF > kustomize-dir/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app1
spec:
  replicas: 1
  selector:
    matchLabels:
      app: app1
  template:
    metadata:
      labels:
        app: app1
    spec:
      containers:
      - name: nginx
        image: nginx
EOF

# kustomization.yaml
cat <<EOF > kustomize-dir/kustomization.yaml
resources:
- deployment.yaml
EOF

# Apply first
kubectl apply -k ./kustomize-dir

# Add label using -k
kubectl label -k ./kustomize-dir team=infra
kubectl get deploy app1 --show-labels


# Process all manifests in directory (-R)
  # Directory:
  # manifests/
  # ├── pod1.yaml
  # └── pod2.yaml

kubectl apply -f ./manifests

# Label all recursively
kubectl label -f ./manifests -R team=backend
kubectl get pods --show-labels

# Show managedFields (--show-managed-fields)
cat <<EOF > pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: test-pod
spec:
  containers:
  - name: nginx
    image: nginx
EOF

kubectl label -f pod.yaml env=test --dry-run=client -o yaml --show-managed-fields

# Output includes managedFields section

# Custom output formatting (--template)

kubectl run foo --image=nginx
kubectl label pods foo app=web

# Print only labels using Go template
kubectl label pods foo tier=frontend -o go-template --template='{{.metadata.labels}}'

# SUMMARY
# -k                 → Work with kustomize directory
# -R                 → Recursive directory processing
# --show-managed-fields → Include managedFields in output
# --template         → Custom formatted output
```
