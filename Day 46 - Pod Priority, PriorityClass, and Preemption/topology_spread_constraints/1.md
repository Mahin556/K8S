##### **Pod Topology Spread Constraints**
* We have multiple workernodes to achive fault toleration.
* To evenly distribute the workload around the cluster/topology-domain/workernodes we can use `topologySpreadConstraints`.
* Is distribute the pod evenly on all workernode, so if one workernode failes ourr application is still up because pods are running on other nodes.
* Prevent same application pods to run on same failure domain.
* we can use the `podAntiAffinity` but it does not evenly distribute the poods.
* Make application Highly available

```bash
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: frontend
```
* This tells the scheduler to evenly spread pods matching the selector across all topology domains (like zones or nodes).
* It prevents all replicas of a Deployment or StatefulSet from landing on a single node or zone.
```bash
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: web
        topologyKey: kubernetes.io/hostname
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: web
```
* Anti-affinity keeps two same pods off the same node.
* Spread constraint ensures even distribution across zones.
