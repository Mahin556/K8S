# 🔹 1️⃣ Default / Cluster-Level Constraints

This is configured in:

```yaml
apiVersion: kubescheduler.config.k8s.io/v1beta3
kind: KubeSchedulerConfiguration
```

Inside scheduler config:

```yaml
profiles:
- schedulerName: default-scheduler
  pluginConfig:
  - name: PodTopologySpread
    args:
      defaultConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
      defaultingType: List
```

---

## 🔎 What This Means

* These constraints apply to the **entire cluster**
* Every pod automatically follows them
* Unless:

  * Pod defines its own topologySpreadConstraints
  * Pod does not belong to Deployment / ReplicaSet / StatefulSet

---

## ✅ Example

If you deploy:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
spec:
  replicas: 6
  selector:
    matchLabels:
      app: demo
  template:
    metadata:
      labels:
        app: demo
    spec:
      containers:
      - name: nginx
        image: nginx
```

Even though you did NOT define topology spread,

Scheduler will automatically try to spread pods across zones.

Because of cluster-level default.

# 🔹 2️⃣ Built-in Default Constraints (Internal Scheduler Defaults)

From screenshot:

```yaml
defaultConstraints:
- maxSkew: 3
  topologyKey: kubernetes.io/hostname
  whenUnsatisfiable: ScheduleAnyway

- maxSkew: 5
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: ScheduleAnyway
```

---

## 🔎 What This Means

By default (even without custom config):

Scheduler tries to:

1️⃣ Spread across nodes

* maxSkew = 3

2️⃣ Spread across zones

* maxSkew = 5

But:

* These are soft rules
* whenUnsatisfiable = ScheduleAnyway

Meaning:

Pods will still schedule even if uneven.

---

## 🧠 Example

Cluster:

3 nodes
6 replicas

Ideal:

2-2-2

But scheduler might allow:

4-1-1

Because maxSkew = 3 is allowed.

This is why default behavior is not strict HA.

# 🔹 3️⃣ Full Pod-Level Topology Spread Example

From screenshot:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example-pod
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    minDomains: 2
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: demo
    matchLabelKeys:
    - app
    nodeAffinityPolicy: Honor
    nodeTaintsPolicy: Honor

  containers:
  - name: nginx
    image: nginx
```

# 🔍 Field Explanation With Examples

---

## 🔹 maxSkew

Maximum difference between domains.

Example:

ZoneA → 2 pods
ZoneB → 1 pod

Skew = 1 → allowed if maxSkew=1

---

## 🔹 minDomains (Beta Feature)

Minimum number of domains required.

Example:

You have 3 zones.

If minDomains = 3
But only 2 zones available → Pod stays Pending.

Used for strict HA.

---

## 🔹 topologyKey

Defines grouping:

* kubernetes.io/hostname → spread across nodes
* topology.kubernetes.io/zone → spread across zones
* topology.kubernetes.io/region → spread across regions

---

## 🔹 whenUnsatisfiable

Two options:

* DoNotSchedule → Strict
* ScheduleAnyway → Soft

Production HA → usually DoNotSchedule

---

## 🔹 labelSelector

Defines which pods are counted for skew.

Example:

If you deploy 3 replicas of app=demo

Only those are counted.

Other pods ignored.

---

## 🔹 matchLabelKeys (Newer Feature)

Allows dynamic label matching from pod.

Instead of hardcoding values.

Used in advanced scenarios.

---

## 🔹 nodeAffinityPolicy

If pod also has nodeAffinity:

Honor → respect affinity
Ignore → ignore affinity during spread calculation

---

## 🔹 nodeTaintsPolicy

If nodes are tainted:

Honor → respect taints
Ignore → ignore taints during spread calculation

---

# 🔥 Practical Production Example

Suppose:

* 3 zones
* 9 replicas
* maxSkew = 1
* whenUnsatisfiable = DoNotSchedule

Result:

ZoneA → 3
ZoneB → 3
ZoneC → 3

If ZoneC becomes unavailable:

Pods cannot be scheduled → Pending

Because strict HA rule.

# 🔥 Difference Summary

| Level                | Applies To    | Override Possible? |
| -------------------- | ------------- | ------------------ |
| Built-in defaults    | Whole cluster | Yes                |
| Cluster-level config | Whole cluster | Yes                |
| Pod-level config     | Specific pod  | No override        |

Pod-level always wins.

---

# 🔥 Real Interview Question

Q: If both cluster-level and pod-level topology spread are defined, which one applies?

Answer: Pod-level overrides cluster-level.
