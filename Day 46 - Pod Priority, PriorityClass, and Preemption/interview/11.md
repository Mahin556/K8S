### Machine learning pipeline with data pre-processing and model training pods. For performance, training pods should run on the same node/zone as pre-processing pods to minimize data transfer latency.

**Pre-processing Pod:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pre-processing-pod
  labels:
    role: pre-process
    app: ml-pipeline
spec:
  containers:
  - name: pre-processor
    image: ml-preprocess:latest
```

**Training Pod with Affinity Rules:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: training-pod
  labels:
    role: training
    app: ml-pipeline
spec:
  affinity:
    podAffinity:
      # Preferred rule - Node level (weight 100)
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: role
              operator: In
              values:
              - pre-process
          topologyKey: "kubernetes.io/hostname"
      
      # Fallback rule - Zone level (weight 50)
      - weight: 50
        podAffinityTerm:
          labelSelector:
            matchExpressions:
            - key: role
              operator: In
              values:
              - pre-process
          topologyKey: "topology.kubernetes.io/zone"
  
  containers:
  - name: trainer
    image: ml-training:latest
```

**Key Points:**
- **Pod Affinity** attracts pods to specific nodes/zones
- `preferredDuringSchedulingIgnoredDuringExecution`: Soft rule, scheduler tries its best
- Weight 100 (node-level): Maximum preference to same node
- Weight 50 (zone-level): Fallback to same availability zone if same node unavailable
- `topologyKey: kubernetes.io/hostname` = same node
- `topologyKey: topology.kubernetes.io/zone` = same availability zone
- Using `preferred` (not `required`) prevents blocking if node is unavailable
- Minimizes data transfer latency by keeping pods close together
