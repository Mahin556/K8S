Yes, absolutely. You can use **Node Affinity** instead of `nodeSelector` to direct a pod to a specific tainted node. In fact, `nodeAffinity` is the more modern and flexible replacement for `nodeSelector`.

The core dependency remains the same: **Toleration gives you access, but Affinity/Selector gives you direction.**

Here is the breakdown of why and how you would use Affinity instead.

---

### Why Use Node Affinity Instead of nodeSelector?

The transcript points out a key limitation of `nodeSelector`: it only works on **equality-based** matching. It's a simple "key=value" check.

`nodeAffinity` is much more powerful because it supports:
1.  **Set-based matching:** Operators like `In`, `NotIn`, `Exists`, `DoesNotExist`.
2.  **Multiple conditions:** You can have complex rules (e.g., "Run in region A or B, but prefer zone 1").
3.  **Soft preferences:** You can use `preferredDuringScheduling` to give the scheduler a "wish" instead of a hard requirement (`requiredDuringScheduling`).

### How the Dependency Works with Affinity

The logic from the transcript still applies perfectly:

1.  **Toleration (The Access Pass):** The node is tainted, so it repels all pods. Your pod needs the matching `Toleration` just to get through the gate. Without it, it doesn't matter what affinity you set.
2.  **Node Affinity (The Direction):** Once the pod has the access pass, it still needs to know which node to go to. `nodeAffinity` is the rule that tells the scheduler, "From all the nodes you are allowed to run on, go to the one with these specific labels."

### Example Scenario

Let's recreate the scenario from the transcript where we have a **dedicated node** (`worker-2`) for a critical application.

**Step 1: Taint the Node (Dedicated Tenancy)**
```bash
kubectl taint nodes worker-2 critical=true:NoSchedule
```
This prevents any pod without the right toleration from running here.

**Step 2: Use Node Affinity + Toleration in the Pod Spec**

Instead of a simple `nodeSelector`, we use `nodeAffinity` to direct the pod. The `toleration` is still there to lift the taint.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: critical-app
spec:
  # 1. Toleration: The Access Pass
  tolerations:
  - key: "critical"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"

  # 2. Node Affinity: The Direction
  affinity:
    nodeAffinity:
      # Hard requirement: MUST run on a node with label 'node=worker-2'
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node
            operator: In
            values:
            - worker-2

  containers:
  - name: nginx
    image: nginx
```

In this file:
- The **Toleration** says, "I am allowed to run on nodes tainted with `critical=true`."
- The **Node Affinity** says, "From the allowed nodes, I MUST run on the one with the label `node=worker-2`."

This is the exact same dependency described in the transcript, just using the more advanced `nodeAffinity` feature to provide the "direction" instead of the simpler `nodeSelector`.
