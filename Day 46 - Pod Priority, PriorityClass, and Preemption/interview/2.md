## 25. What are Affinity and Anti-Affinity in Kubernetes?

In Kubernetes, Affinity and Anti-Affinity are scheduling rules used to control where Pods should or should not run.

They help Kubernetes make smarter scheduling decisions based on:

* Node labels
* Existing Pods
* Availability zones
* Performance requirements

---

# 1. Node Affinity

Node Affinity controls:

* Which nodes a Pod can run on

based on:

* Node labels

It is a more advanced and flexible version of:

* `nodeSelector`

---

## Example Use Cases

* Run GPU workloads only on GPU nodes
* Run production workloads on dedicated nodes
* Use SSD-backed nodes for databases

---

## Example

```yaml id="5m2p8"
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: disktype
          operator: In
          values:
          - ssd
```

This schedules the Pod only on:

* Nodes labeled `disktype=ssd`

---

# 2. Pod Affinity

Pod Affinity attracts Pods toward other Pods.

Used when Pods should run:

* Close together

---

## Example Use Cases

* Application and cache in same zone
* Reduce network latency
* Co-locate microservices

---

## Example

```yaml id="8k1n4"
podAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchExpressions:
      - key: app
        operator: In
        values:
        - backend
    topologyKey: topology.kubernetes.io/zone
```

This places Pods:

* In the same availability zone
* As backend Pods

---

# 3. Pod Anti-Affinity

Pod Anti-Affinity repels Pods away from other Pods.

Used to:

* Spread workloads
* Improve high availability

---

## Example Use Cases

* Avoid running replicas on same node
* Prevent single point of failure
* Improve fault tolerance

---

## Example

```yaml id="3x7q2"
podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
  - labelSelector:
      matchExpressions:
      - key: app
        operator: In
        values:
        - web
    topologyKey: kubernetes.io/hostname
```

This ensures:

* Web Pods are spread across different nodes.

---

# Important Types of Rules

| Type                                              | Meaning             |
| ------------------------------------------------- | ------------------- |
| `requiredDuringSchedulingIgnoredDuringExecution`  | Mandatory rule      |
| `preferredDuringSchedulingIgnoredDuringExecution` | Soft/preferred rule |

---

# High-Level Difference

| Feature  | Affinity                 | Anti-Affinity                      |
| -------- | ------------------------ | ---------------------------------- |
| Purpose  | Bring workloads together | Keep workloads apart               |
| Used For | Performance, locality    | High availability, fault isolation |

---

# Real-World Example

## Affinity

* App Pod + Redis Pod in same zone for low latency

## Anti-Affinity

* Replicas distributed across multiple nodes to survive node failure

---

# Scheduling Flow

```text id="6v1m5"
Scheduler Checks Rules
        ↓
Find Matching Nodes/Pods
        ↓
Apply Affinity or Anti-Affinity Constraints
        ↓
Select Best Node
```

---

# Interview-Ready Answer

“Affinity and Anti-Affinity are Kubernetes scheduling rules that control Pod placement. Node Affinity schedules Pods onto specific nodes based on node labels, while Pod Affinity and Anti-Affinity control placement relative to other Pods. Affinity is used to place related workloads together for performance or locality, whereas Anti-Affinity spreads workloads apart to improve high availability and fault tolerance.”
