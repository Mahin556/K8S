#### Q9: In your Kubernetes environment, a master or worker node suddenly fails. What happens?
**Scenario-Based Answer:**

**A: Master Node Failure (Single Master Setup)**
- **Effect:** **Catastrophic Management Failure.** You cannot run `kubectl`. New pods won't schedule. Scaling doesn't work.
- **Workload Status:** **Existing Pods on Worker Nodes continue to run.** Kubernetes is designed such that the data plane (Kubelet, Container Runtime) runs independently of the control plane for a limited time.
- **Recovery:** Restore the master from a snapshot of `/var/lib/etcd`. If etcd data is lost permanently, the cluster must be rebuilt from scratch.

**B: Worker Node Failure (Node goes "NotReady")**
- **Detection:** The **Node Controller** (in Controller Manager) monitors node heartbeats from Kubelet. After a timeout (default ~40s), the node is marked `NotReady`.
- **Pod Eviction:** After a grace period (default **5 minutes**), the **Node Controller** initiates pod eviction. It tells the API Server to delete the Pod objects that were on the dead node.
- **Rescheduling:** The **Scheduler** sees new Pods needing placement and schedules them onto healthy worker nodes.
- **StatefulSets:** If the failed node had a StatefulSet pod (e.g., `db-1`), Kubernetes **will not** start a new `db-1` automatically elsewhere because of the identity guarantee. You must manually force-delete the pod or wait for the node to return.
