#### You have an application deployed on Kubernetes that is experiencing increased traffic. How would you scale the application to handle the increased load?
**Detailed Answer & Strategy:**

**1. Immediate Triage & Analysis (Identify the Bottleneck):**
- **Metrics:** Use `kubectl top pods` and `kubectl top nodes` to check immediate CPU and Memory usage.
- **Observability Stack:** Use Prometheus + Grafana dashboards to analyze historical trends and identify specific latency issues (e.g., is the DB slow? Is the application throwing 5xx errors?).
- **Network:** Check Ingress Controller metrics for dropped connections.

**2. Horizontal Scaling (The Preferred Method):**
- **Manual Scaling:** `kubectl scale deployment <deployment-name> --replicas=<new-number>`
- **Automated Scaling (HPA):** The **Horizontal Pod Autoscaler** automatically scales the number of pods in a deployment or replica set based on observed CPU utilization or custom metrics.
    - **Configuration Example:**
      ```bash
      kubectl autoscale deployment my-app --cpu-percent=70 --min=2 --max=20
      ```
    - **Advanced:** Using **KEDA** (Kubernetes Event-Driven Autoscaling) to scale based on external event sources like Kafka Lag or AWS SQS queue depth.

**3. Vertical Scaling (VPA):**
- **Use Case:** If the application is not designed to run in multiple replicas (e.g., legacy monolithic stateful apps) or if increasing replicas doesn't help due to a single-threaded bottleneck.
- **Vertical Pod Autoscaler (VPA):** Automatically adjusts the `resources.requests` and `resources.limits` of a pod. **Caveat:** VPA *requires* pod restarts to apply new resource limits, which can cause downtime unless managed carefully (VPA in "Recommendation" mode only).

**4. Cluster-Level Scaling:**
- If the node runs out of capacity, even scaling pods won't help. Use **Cluster Autoscaler** to automatically add new worker nodes to the cluster when pods fail to schedule.
