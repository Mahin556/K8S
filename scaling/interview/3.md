## 23. Describe How a Horizontal Pod Autoscaler (HPA) Works

The Horizontal Pod Autoscaler (HPA) in Kubernetes automatically scales the number of Pod replicas based on resource usage or custom metrics.

Its goal is to:

* Handle increased traffic/load
* Optimize resource usage
* Improve application availability

---

# How HPA Works

The HPA continuously monitors metrics such as:

* CPU utilization
* Memory utilization
* Custom metrics
* External metrics

using:

* Metrics Server
* Prometheus adapters
* External monitoring systems

---

# HPA Workflow

```text id="5m2p8"
Application Load Increases
          ↓
Metrics Server Collects Metrics
          ↓
HPA Compares Metrics with Target
          ↓
HPA Increases/Decreases Pod Replicas
          ↓
Deployment Creates or Removes Pods
```

---

# Example Scenario

Suppose:

* Target CPU usage = 70%
* Current CPU usage = 90%

HPA will:

* Increase Pod replicas

to distribute the load.

When traffic decreases:

* HPA scales Pods down automatically.

---

# Example HPA Configuration

```yaml id="8k1n4"
apiVersion: autoscaling/v2

kind: HorizontalPodAutoscaler

metadata:
  name: webserver-mem-hpa

spec:
  minReplicas: 1
  maxReplicas: 5

  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: webserver

  metrics:
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageValue: 2Mi
```

---

# Important Fields

| Field            | Purpose                     |
| ---------------- | --------------------------- |
| `minReplicas`    | Minimum Pods always running |
| `maxReplicas`    | Maximum scaling limit       |
| `scaleTargetRef` | Workload to scale           |
| `metrics`        | Metric used for scaling     |

---

# Metrics Types Supported

## Resource Metrics

* CPU
* Memory

---

## Custom Metrics

Examples:

* Requests per second
* Queue length

---

## External Metrics

Examples:

* Cloud monitoring metrics
* Kafka lag
* SQS queue depth

---

# Components Involved

| Component             | Role                     |
| --------------------- | ------------------------ |
| HPA Controller        | Makes scaling decisions  |
| Metrics Server        | Provides metrics         |
| Deployment/ReplicaSet | Creates/removes Pods     |
| Kube Scheduler        | Places new Pods on nodes |

---

# Important Requirement

HPA works best when:

* Resource requests are defined

Example:

```yaml id="3x7q2"
resources:
  requests:
    cpu: "500m"
```

Without requests:

* CPU utilization calculations become inaccurate.

---

# Difference Between HPA and Cluster Autoscaler

| Feature | HPA                 | Cluster Autoscaler     |
| ------- | ------------------- | ---------------------- |
| Scales  | Pods                | Nodes                  |
| Trigger | App metrics         | Pending Pods           |
| Purpose | Application scaling | Infrastructure scaling |

---

# Production Best Practices

* Always define resource requests/limits
* Use realistic scaling thresholds
* Avoid aggressive scaling to prevent flapping
* Combine HPA with Cluster Autoscaler
* Monitor scaling events

---

# Interview-Ready Answer

“The Horizontal Pod Autoscaler automatically scales the number of Pod replicas based on observed metrics such as CPU, memory, or custom metrics. It continuously collects metrics through the Metrics Server, compares them with the configured target values, and increases or decreases replicas accordingly. This helps applications handle varying traffic loads efficiently while optimizing resource utilization.”
