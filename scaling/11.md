Good explanation — let me add a **concrete numeric example** to make the calculation crystal clear.

## First, the formula

HPA uses this formula for `Resource` metrics:

```
desiredReplicas = ceil[ currentReplicas × ( currentUtilization / targetUtilization ) ]
```

And to calculate `currentUtilization`:

```
currentUtilization = (sum of actual CPU usage across counted containers) / (sum of requested CPU across counted containers) × 100
```

**Key point**: "Counted containers" means **only containers that have `resources.requests` defined.**

## Detailed example: using your same pod

Say the deployment has **3 pods**, each with the same 2 containers (`my-app-container` + `sidecar`):

```yaml
containers:
  - name: my-app-container
    resources:
      requests:
        cpu: 100m
  - name: sidecar
    image: log-agent:latest
    # NO cpu request defined
```

And the target is: `averageUtilization: 60`

### Actual usage (as reported by metrics-server)

| Pod | my-app-container usage | sidecar usage |
|---|---|---|
| Pod 1 | 80m | 200m |
| Pod 2 | 90m | 150m |
| Pod 3 | 70m | 300m |

### Case 1: `type: Resource` (default Kubernetes behavior)

Since the sidecar has no `requests.cpu`, it's **completely excluded from the calculation** — even though it's using 200-300m!

```
Total usage (app container only) = 80 + 90 + 70 = 240m
Total requests (app container only) = 100 + 100 + 100 = 300m
Average Utilization = 240/300 × 100 = 80%
```

→ **80% > target (60%)** → HPA will scale up.

Notice the problem here: the sidecar is using 200-300m (which is actually *more* than the app container!), but since it has no request defined, **it's not counted in the calculation at all.** If the sidecar has a CPU spike or memory leak, HPA **won't see it**, because the `Resource` metric only looks at containers that have requests set — and averages purely over those.

### Case 2: `type: ContainerResource` (explicit, target only the app container)

```yaml
metrics:
- type: ContainerResource
  containerResource:
    name: cpu
    container: my-app-container   # explicitly specify
    target:
      type: Utilization
      averageUtilization: 60
```

In this case, the result is the same (80%) since we're only targeting `my-app-container` — but the difference is that this is **explicit and predictable**. If you want to monitor the sidecar separately too, you can create **2 separate metric entries**:

```yaml
metrics:
- type: ContainerResource
  containerResource:
    name: cpu
    container: my-app-container
    target:
      type: Utilization
      averageUtilization: 60
- type: ContainerResource
  containerResource:
    name: cpu
    container: sidecar
    target:
      type: Utilization
      averageUtilization: 80
```

(But for this, the sidecar also needs `requests.cpu` defined, otherwise `ContainerResource` won't be able to evaluate it either.)

## The real-world danger this highlights

Think about common production scenarios: **Istio/Envoy sidecars**, **logging agents**, or **service mesh proxies** — some of these containers run **without CPU requests** (sometimes devs forget, sometimes it's intentional).

| Scenario | What happens |
|---|---|
| Sidecar's CPU usage is **low**, no request set | No problem — calculation stays accurate |
| Sidecar's CPU usage **spikes suddenly** (noisy neighbor), no request set | **HPA has no idea** — the scaling decision is based only on the app container's data, which can give a misleading picture even though total load on the node has gone up |
| Sidecar **permanently uses a lot of CPU**, no request set | Total resource consumption (on the node) is high, but HPA "thinks" usage is low — risk of **under-scaling** |

## Quick summary table

| | `type: Resource` | `type: ContainerResource` |
|---|---|---|
| **Which containers it counts** | All containers that have requests defined (implicitly) | Only the container you explicitly name |
| **Level of control** | Implicit — you might not even realize which containers are included unless you check manually | Explicit — you decide exactly |
| **Best use case** | Simple pods, single main container | Multi-container pods (sidecars, init containers) where precision matters |
| **Requirement** | Container must have `requests` set | Same container must have `requests` set **and** be explicitly named |

**Bottom line**: If your pods have sidecars (especially CPU-heavy ones — logging, mesh proxies, etc.), using `ContainerResource` is **safer and more predictable**, because you explicitly control which container's data the scaling decision is based on — no guessing about what `Resource` type is automatically including.
