Quick clarification needed to nail the exact fix, but here's what's almost certainly going on, regardless of which exact error you're hitting — there are two genuinely different failure modes that both produce an `x509: certificate signed by unknown authority` error, and this flag only fixes one of them.

## What this flag actually does (and doesn't do)

`--kubelet-certificate-authority` tells metrics-server which CA to trust when it **scrapes stats from each kubelet** (port 10250) — that's its only job. It has **zero effect** on a completely different, similarly-worded error that shows up in `authentication.go` logs, which is about the API server's *aggregation layer* authenticating requests *to* metrics-server, not metrics-server authenticating kubelets. Mixing these two up is the #1 reason people report "this flag doesn't work" — they're often hitting the second problem and trying to fix it with a flag meant for the first.

**Check your actual error message:**

| Error pattern | What's actually broken | Does `--kubelet-certificate-authority` help? |
|---|---|---|
| `unable to fetch metrics from Kubelet ... x509: certificate signed by unknown authority` | metrics-server can't verify the **kubelet's** serving cert | ✅ Yes, this is the right flag |
| `Unable to authenticate the request due to an error: x509: certificate signed by unknown authority` (in `authentication.go`) | The **front-proxy/aggregation layer** can't authenticate incoming requests | ❌ No — unrelated, different fix needed |

## If you're hitting the first error (kubelet scrape failure) — why the flag still fails

Even with the right error type, pointing at `/var/run/secrets/kubernetes.io/serviceaccount/ca.crt` specifically fails very often, for one of two reasons:

**1. It's simply the wrong CA.** This service-account-mounted cert is your **cluster's** CA (used for API server / service account token verification) — but kubelet **serving** certificates are frequently signed by a *different* CA entirely, depending on your distro. The kubelet certificate must be signed by the cluster Certificate Authority — if it isn't, you'll see exactly this authentication error. On EKS specifically, the correct CA to use is the one returned by:
```bash
aws eks describe-cluster --name YOUR_CLUSTER --query "cluster.certificateAuthority.data" --output text | base64 -d > ca.crt
```
Mount *that* into metrics-server and point the flag at it instead — not the generic service-account path.

**2. Your kubelets might be using self-signed certs, with no CA that would ever match.** Unless your cluster has **kubelet server certificate rotation** explicitly enabled (the `RotateKubeletServerCertificate` feature + CSR auto-approval), many kubelets generate a **self-signed** serving cert with no real CA backing it at all — in that case, **no CA file you supply will ever work**, because there genuinely isn't one that signed it. This explains the GitHub threads where people tried multiple different CA paths and *none* worked: "Per the FAQ, I tried to set `--kubelet-certificate-authority` to the kops CA, but still got this error... The only thing that worked for me was setting `--kubelet-insecure-tls`."

**The practical workaround**, used widely in exactly this situation:
```yaml
- --kubelet-insecure-tls
```
This skips kubelet cert verification entirely. This parameter doesn't verify the CA of serving certificates presented by kubelets — only use it for testing purposes, not production clusters, but it's genuinely the standard pragmatic fix when proper kubelet cert rotation isn't configured cluster-wide, which describes the vast majority of real-world clusters, including most EKS managed node groups by default.

## If you're hitting the second error (`authentication.go`)

This is unrelated to kubelets entirely — it's about whether metrics-server trusts the certificate the kube-apiserver presents *to it* via the aggregation layer's front-proxy. In bare-metal/kubeadm clusters this often shows specifically as "verification error while trying to verify candidate authority certificate front-proxy-ca." The fix here usually involves the **`extension-apiserver-authentication`** ConfigMap in `kube-system` (which metrics-server reads automatically to discover the correct front-proxy CA) rather than any flag on metrics-server's own deployment — if that ConfigMap is missing or misconfigured, that's the actual root cause, not anything fixable via `--kubelet-certificate-authority`.
