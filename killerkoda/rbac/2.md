## 🎯 Scenario Overview

### Your Mission

Configure RBAC for a GitLab CI/CD integration by:
1. Creating a **ClusterRole** with specific permissions
2. Binding it to a **ServiceAccount** using a **ClusterRoleBinding**
3. Generating a **time-limited token** for API authentication
4. Using that token to interact with the Kubernetes API directly

### The Context

You are integrating **GitLab CI/CD** with your Kubernetes cluster:

- The CI/CD pipeline needs programmatic access to manage pods, deployments, and jobs
- A ServiceAccount named `gitlab-cicd-sa` already exists in the `gitlab-cicd` namespace
- A test pod named `gitlab-cicd-nginx` is running for verification

### Problem Statement

| Task | Details |
|------|---------|
| **1. Create ClusterRole** | Name: `gitlab-cicd-role` |
| | Verbs: `get`, `list`, `watch`, `create`, `patch`, `delete` |
| | Resources: `pods`, `deployments`, `jobs` |
| **2. Create ClusterRoleBinding** | Name: `gitlab-cicd-rb` |
| | Bind to: `gitlab-cicd-sa` in `gitlab-cicd` namespace |
| **3. Generate Token** | Duration: `2 hours` |
| **4. API Request** | List pods in `gitlab-cicd` namespace |
| | Store output in `/gitlab-cicd/pod-details.json` |

## 🧠 Conceptual Summary

### RBAC Components

| Component | Description | Scope |
|-----------|-------------|-------|
| **ClusterRole** | Defines a set of permissions (verbs on resources) | Cluster-wide |
| **ClusterRoleBinding** | Grants ClusterRole permissions to a user/SA across all namespaces | Cluster-wide |
| **Role** | Defines permissions for a specific namespace | Namespace-specific |
| **RoleBinding** | Grants Role permissions in a specific namespace | Namespace-specific |
| **ServiceAccount** | Provides an identity for processes running in a Pod | Namespace-specific |
| **Token** | Time-limited credential for API authentication | Generated on-demand |

### How It All Works Together

```
ServiceAccount (gitlab-cicd-sa)
        ↓
ClusterRoleBinding (gitlab-cicd-rb)
        ↓
ClusterRole (gitlab-cicd-role)
        ↓
Permissions: get, list, watch, create, patch, delete
        ↓
Resources: pods, deployments, jobs (cluster-wide)
```

### Authentication & Authorization Flow

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         Complete Auth Flow                                  │
│                                                                             │
│   1. Generate Token                                                         │
│      kubectl create token gitlab-cicd-sa --duration=2h                     │
│                        ↓                                                    │
│   2. Extract CA Certificate                                                 │
│      kubectl config view --raw -o jsonpath='{...}' | base64 -d             │
│                        ↓                                                    │
│   3. Make API Request                                                       │
│      curl --cacert ca.cert -H "Authorization: Bearer $TOKEN" ...           │
│                        ↓                                                    │
│   4. API Server Validation                                                  │
│      - Verifies token signature                                            │
│      - Extracts identity: system:serviceaccount:gitlab-cicd:gitlab-cicd-sa│
│                        ↓                                                    │
│   5. RBAC Authorization Check                                               │
│      - Checks ClusterRoleBinding: gitlab-cicd-rb                          │
│      - References ClusterRole: gitlab-cicd-role                           │
│      - Verifies: Can I "list" "pods" in "gitlab-cicd"?                   │
│                        ↓                                                    │
│   6. Response                                                               │
│      ✅ Allowed → Return pod data                                         │
│      ❌ Forbidden → 403 Forbidden                                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 📋 Step-by-Step Solution

### Step 1: Create the ClusterRole

```bash
kubectl create clusterrole gitlab-cicd-role \
  --verb=get,list,watch,create,patch,delete \
  --resource=pods,deployments,jobs
```

**Expected Output:**
```
clusterrole.rbac.authorization.k8s.io/gitlab-cicd-role created
```

**Verify the ClusterRole:**
```bash
kubectl get clusterrole gitlab-cicd-role
kubectl describe clusterrole gitlab-cicd-role
```

**YAML Equivalent:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: gitlab-cicd-role
rules:
- apiGroups:
  - ""
  - apps
  - batch
  resources:
  - pods
  - deployments
  - jobs
  verbs:
  - get
  - list
  - watch
  - create
  - patch
  - delete
```

### Step 2: Create the ClusterRoleBinding

```bash
kubectl create clusterrolebinding gitlab-cicd-rb \
  --clusterrole=gitlab-cicd-role \
  --serviceaccount=gitlab-cicd:gitlab-cicd-sa
```

**Expected Output:**
```
clusterrolebinding.rbac.authorization.k8s.io/gitlab-cicd-rb created
```

**Verify the ClusterRoleBinding:**
```bash
kubectl get clusterrolebinding gitlab-cicd-rb
kubectl describe clusterrolebinding gitlab-cicd-rb
```

**YAML Equivalent:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: gitlab-cicd-rb
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: gitlab-cicd-role
subjects:
- kind: ServiceAccount
  name: gitlab-cicd-sa
  namespace: gitlab-cicd
```

### Step 3: Create a 2-Hour Valid Token

```bash
kubectl create token gitlab-cicd-sa \
  --namespace=gitlab-cicd \
  --duration=2h > token.txt
```

**Store the token in a variable:**
```bash
TOKEN=$(cat token.txt)
echo $TOKEN
```

### Step 4: Extract the CA Certificate

```bash
kubectl config view --raw -o jsonpath='{.clusters[0].cluster.certificate-authority-data}' | base64 -d > ca.cert
```

**Verify the certificate:**
```bash
ls -lh ca.cert
```

### Step 5: Get the API Server Address

```bash
APISERVER=$(kubectl config view --raw -o jsonpath='{.clusters[0].cluster.server}')
echo $APISERVER
```

**Expected Output (based on scenario):**
```
https://172.30.1.2:6443
```

### Step 6: Make the API Request

```bash
curl --cacert ca.cert \
  -H "Authorization: Bearer $TOKEN" \
  https://172.30.1.2:6443/api/v1/namespaces/gitlab-cicd/pods/ \
  > /gitlab-cicd/pod-details.json
```

### Step 7: Verify the Output

```bash
cat /gitlab-cicd/pod-details.json
```

**Optional: Format for better readability**
```bash
cat /gitlab-cicd/pod-details.json | jq '.items[].metadata.name'
```

**Expected Output:**
```json
{
  "kind": "PodList",
  "apiVersion": "v1",
  "metadata": {
    "resourceVersion": "12345"
  },
  "items": [
    {
      "metadata": {
        "name": "gitlab-cicd-nginx",
        "namespace": "gitlab-cicd",
        ...
      },
      "spec": {
        "containers": [...]
      },

        "phase": "Running"
```

## 🔍 Deep Dive: Understanding the Configuration

### ClusterRole Structure

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: gitlab-cicd-role
rules:
- apiGroups:
  - ""          # Core API group (pods)
  - apps        # apps API group (deployments)
  - batch       # batch API group (jobs)
  resources:
  - pods
  - deployments
  - jobs
  verbs:
  - get
  - list
  - watch
  - create
  - patch
  - delete
```

### API Groups Explained

| API Group | Resources | Common Use |
|-----------|-----------|------------|
| `""` (core) | pods, services, configmaps, secrets | Core Kubernetes resources |
| `apps` | deployments, replicasets, statefulsets | Workload resources |
| `batch` | jobs, cronjobs | Batch processing resources |
| `networking.k8s.io` | ingresses, networkpolicies | Networking resources |

### Verbs Explained

| Verb | Permission | Use Case |
|------|-----------|----------|
| `get` | Read specific resource | Fetch pod details |
| `list` | Read all resources | List all pods |
| `watch` | Watch for changes | Monitor pod status |
| `create` | Create new resources | Deploy new pods |
| `patch` | Update existing resources | Update deployment |
| `delete` | Delete resources | Remove old pods |

### ServiceAccount Binding Format

```bash
# Format: --serviceaccount=<namespace>:<serviceaccount-name>
--serviceaccount=gitlab-cicd:gitlab-cicd-sa
```

## 🔐 ServiceAccount Tokens: Pre-1.24 vs Post-1.24

### Before Kubernetes 1.24

```yaml
# Tokens were automatically created as Secrets
apiVersion: v1
kind: Secret
metadata:
  name: gitlab-cicd-sa-token-xxx
  annotations:
    kubernetes.io/service-account.name: gitlab-cicd-sa
type: kubernetes.io/service-account-token
data:
  token: <base64-encoded-token>
```

**Characteristics:**
- ❌ Non-expiring by default (security concern)
- ❌ Tokens stored in Secrets (visible to anyone with access)
- ❌ Manual cleanup required
- ❌ No built-in expiration

### After Kubernetes 1.24 (Current)

```bash
# Tokens generated on-demand using TokenRequest API
kubectl create token gitlab-cicd-sa --namespace=gitlab-cicd --duration=2h
```

**Characteristics:**
- ✅ Time-limited by default (more secure)
- ✅ Generated on-demand when needed
- ✅ Can specify custom duration
- ✅ Auditable token issuance
- ✅ No token stored in Secret

### Comparison

| Feature | Pre-1.24 (Legacy) | Post-1.24 (Current) |
|---------|-------------------|-------------------|
| **Creation** | Automatic via Secret | Manual `kubectl create token` |
| **Expiration** | Never expires | Time-limited |
| **Storage** | Stored in Secret | Not stored |
| **Security** | Lower (unlimited validity) | Higher (limited validity) |
| **Auditability** | Limited | Full audit trail |

## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **403 Forbidden Error** | Insufficient RBAC permissions | Verify ClusterRole verbs and ClusterRoleBinding |
| **401 Unauthorized Error** | Invalid or expired token | Generate new token with `kubectl create token` |
| **Certificate Verification Failed** | Wrong CA certificate | Extract CA cert from kubeconfig |
| **Token Expired** | Duration exceeded | Increase `--duration` when creating token |
| **No Output File** | Permissions on directory | Check directory permissions: `ls -la /gitlab-cicd` |
| **ClusterRole Not Found** | Wrong name | Check `kubectl get clusterrole` |
| **ServiceAccount Not Found** | Wrong namespace | Check `kubectl get sa -n gitlab-cicd` |
| **Wrong API Path** | Incorrect API version | Use `kubectl explain pod` to verify correct path |

## 💡 Real-World Use Cases & Best Practices

### Real-World Use Cases

| Use Case | Description | RBAC Configuration |
|----------|-------------|-------------------|
| **CI/CD Pipelines** | GitLab, Jenkins, GitHub Actions deploying to Kubernetes | ClusterRole with deployment permissions |
| **Infrastructure as Code** | Terraform or Pulumi managing Kubernetes resources | ClusterRole with full resource management |
| **Monitoring Tools** | Prometheus, Grafana accessing cluster metrics | ClusterRole with get/list/watch permissions |
| **Backup Solutions** | Velero performing cluster backups | ClusterRole with read permissions on all resources |
| **Custom Controllers** | Operators needing specific resource access | ClusterRole with specific resource permissions |

### Security Best Practices

#### Token Management

| Practice | Why |
|----------|-----|
| **Use time-limited tokens** | Always specify `--duration` for temporary access |
| **Principle of least privilege** | Grant only required permissions |
| **Rotate tokens regularly** | For long-running integrations, automate rotation |
| **Store tokens securely** | Use secret management systems (Vault, Sealed Secrets) |
| **Audit token usage** | Monitor API access logs for suspicious activity |

#### RBAC Design

| Practice | Why |
|----------|-----|
| **Use ClusterRole for cluster-wide access** | Appropriate for CI/CD across namespaces |
| **Separate roles by function** | Create granular roles for different purposes |
| **Avoid wildcard permissions** | Specify exact verbs and resources |
| **Regular audits** | Review and prune unused roles and bindings |
| **Test permissions** | Use `kubectl auth can-i` to verify access |

### Least Privilege Example

```yaml
# BAD: Too many permissions
verbs: ["*"]
resources: ["*"]

# GOOD: Specific permissions
verbs: ["get", "list", "watch", "create", "patch", "delete"]
resources: ["pods", "deployments", "jobs"]
```

## 📊 Role vs ClusterRole Comparison

| Feature | Role | ClusterRole |
|---------|------|-------------|
| **Scope** | Namespace-specific | Cluster-wide |
| **Binding** | RoleBinding (namespace) | ClusterRoleBinding (cluster) or RoleBinding (namespace) |
| **Cluster resources** | ❌ Cannot access | ✅ Can access (nodes, PVs, etc.) |
| **Cross-namespace access** | ❌ Limited to namespace | ✅ Can access all namespaces |
| **Use case** | App-specific permissions | Cross-namespace or admin tasks |
| **Binding to ServiceAccount** | Same namespace only | Any namespace |

### When to Use Which

```yaml
# Use Role + RoleBinding for namespace-specific permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: gitlab-cicd
  name: gitlab-cicd-role
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list"]

# Use ClusterRole + ClusterRoleBinding for cluster-wide permissions
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: gitlab-cicd-role
rules:
- apiGroups: ["", "apps", "batch"]
  resources: ["pods", "deployments", "jobs"]
  verbs: ["get", "list", "watch", "create", "patch", "delete"]
```
