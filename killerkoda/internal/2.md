That is an **excellent** question. You have correctly identified the critical distinction in Kubernetes networking: **some components run with `hostNetwork: true`** (or as host processes) and bypass the service ClusterIP entirely.

Let's break down exactly **which** components use the ClusterIP (`kubernetes.default.svc`) to talk to the API server, and **which** don't—and **why** the certificate SAN update (adding the new ClusterIP) is still absolutely mandatory.

---

### ✅ Components that **DO** communicate via the ClusterIP

These components run as **regular Pods** (without `hostNetwork`). They rely on the internal cluster DNS (`kubernetes.default.svc.cluster.local`) which resolves to the `ClusterIP` of the `kubernetes` service (e.g., `100.96.0.1`).

| Component | Why it uses the ClusterIP |
| :--- | :--- |
| **Regular Application Pods** | Any app that needs to talk to the API server (e.g., to check its own status, list resources, or for service discovery) uses the service ClusterIP. This is the default for 99% of in‑cluster clients. |
| **CoreDNS** | CoreDNS uses the `kubernetes` plugin to watch Services, Endpoints, and Pods. It connects to the API server via the `kubernetes.default.svc` ClusterIP. |
| **Controller Managers (non‑static)** | For example, the `calico-kube-controllers` or `ingress-controllers` run as standard Deployments. They use the in‑cluster Config and the ClusterIP to authenticate and watch the API. |
| **Admission Webhooks & Mutating Webhooks** | Typically run as standard Services and Deployments. They call back to the API server or the API server calls them, but their internal dashboards/health checks use the ClusterIP. |
| **Metrics Server** | The Metrics Server runs as a regular Deployment and uses the ClusterIP to fetch node/pod metrics from the API server's `/metrics` endpoint. |
| **Operators (e.g., Postgres Operator, Prometheus Operator)** | These run as normal Pods and use the in‑cluster Config (via service account tokens) to watch CRDs. They hit the API server's ClusterIP. |

---

### ❌ Components that **DO NOT** use the ClusterIP (The "HostNetwork" Gang)

These components run either as **static Pods with `hostNetwork: true`** or as **native host processes** (like `kubelet`). They bypass the virtual IP entirely and connect directly to the API server's actual IP or `127.0.0.1`.

| Component | How it connects (instead of ClusterIP) |
| :--- | :--- |
| **Kubelet** (worker node agent) | It is a host binary. It reads its `kubeconfig` (usually pointing to the API server's **advertise address** or load balancer IP). It never resolves `kubernetes.default.svc`. |
| **Kube-scheduler** (control plane) | Static Pod with `hostNetwork: true`. It connects to `https://127.0.0.1:6443` (localhost) or the node's IP to avoid dependency on the service network. |
| **Kube-controller-manager** (control plane) | Static Pod with `hostNetwork: true`. It connects to `127.0.0.1:6443` (localhost). |
| **CNI Plugins (Calico, Canal, Cilium DaemonSets)** | These run with `hostNetwork: true` because they need raw access to host interfaces (`eth0`, `veth`). They frequently talk to the API server using the **node's IP** or **localhost**, *not* the ClusterIP. |
| **Etcd** | Etcd does not talk to the API server over the network. The API server talks to *it* (via localhost or advertised peer URLs). |

---

### 🧠 Why does the Certificate *still* need the new ClusterIP (`100.96.0.1`)?

This is the "gotcha" you are driving at. If the `kubelet` and `CNI DaemonSets` don't use the ClusterIP, why does changing the CIDR and adding the ClusterIP to the certificate matter at all? 

Because **CoreDNS and ALL application pods *do* use it**. 

During the service CIDR migration:

1. **CoreDNS** restarts. It reads the new `kubernetes.default.svc` IP (e.g., `100.96.0.1`) from the environment or the API.
2. CoreDNS tries to dial `https://100.96.0.1:443` to establish a watch connection.
3. The API server receives the request, presents its `apiserver.crt` certificate, and checks the SNI (Server Name) or IP against the certificate's **Subject Alternative Names (SANs)**.
4. If `100.96.0.1` is **not** in the SANs, CoreDNS fails with `x509: certificate is valid for 10.96.0.1, not 100.96.0.1`. 
5. CoreDNS crashes or fails to sync. Then **every pod in the cluster** cannot resolve DNS (since CoreDNS is down).

Similarly, the **CNI Controller** (like `calico-kube-controllers`, which is a *regular* Deployment, not a DaemonSet) uses the ClusterIP to manage IP pools. If it cannot trust the API server's certificate on the new IP, the entire network reconciliation breaks.

### 📝 Summary Table

| Component Type | Uses ClusterIP? | Why? |
| :--- | :--- | :--- |
| **User Pods (Deployments, Jobs)** | **Yes** | Default pod networking, rely on kube-dns for service discovery. |
| **CoreDNS** | **Yes** | Needs to watch API for Services/Endpoints. Breaks without valid SAN. |
| **Operators / Webhooks** | **Yes** | In‑cluster Config and standard service accounts. |
| **CNI DaemonSets (Canal, Calico node)** | **No** | `hostNetwork: true`; uses node IP or localhost. |
| **Kubelet** | **No** | Host binary; `kubeconfig` points to API advertise IP. |
| **Scheduler / Controller‑Manager** | **No** | Static Pods with `hostNetwork: true`; uses localhost (`127.0.0.1`). |

---

### ✅ The Golden Rule for Service CIDR Changes

Even if *you* don't connect to the API via the ClusterIP, **the cluster itself does**. 

- The **kubelet's kubeconfig** points to the advertise IP (we changed that in the `config.yaml` for DNS, but the actual *server* address in the kubeconfig stays the same).
- The **service account tokens** mounted into pods use the ClusterIP.

Therefore, adding `100.96.0.1` (and keeping `10.96.0.1` for backward compatibility during the rollout) to the API server's certificate SAN list is **not optional**—it is the linchpin that keeps the internal service discovery and control loops healthy after a CIDR shift.
