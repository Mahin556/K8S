This is a fantastic question that gets to the heart of how the Kubernetes control plane bootstraps itself. Let me break it down into the three distinct parts you asked about:

---

### 1️⃣ Why does the `kubernetes` Service exist in the `default` Namespace?

The `kubernetes` Service (with ClusterIP `10.96.0.1` or `100.96.0.1`) represents the **API server's internal endpoint**. 

It is placed in the `default` namespace for **historical convention** and **DNS simplicity**. 

- When you are inside a Pod and want to talk to the API server, the DNS name is `kubernetes.default.svc.cluster.local`. 
- If it were in `kube-system`, you would have to type `kubernetes.kube-system.svc.cluster.local`. 
- The `default` namespace is the catch-all, default place for resources when you don't specify a namespace. Since the API server is the cluster's "default" gateway, putting it in the `default` namespace makes the FQDN slightly shorter and more intuitive for beginners and tools.

> ⚠️ **Correction to the Question**: You asked *"why not in other"* (namespaces). There is only **one** API server endpoint for the entire cluster. Therefore, there is only **one** Kubernetes Service needed to represent it. You cannot have multiple active services representing the same API server IP in different namespaces (it would cause IP conflicts). So the controller places it in `default` by design.

---

### 2️⃣ Why did we DELETE and then RECREATE (or re-issue) it?

In your lab, you explicitly ran:
```bash
kubectl -n default delete svc kubernetes
```

**Why did we delete it?**

We changed the API server's command-line flag:
`--service-cluster-ip-range=100.96.0.0/12`

The `kubernetes` Service was created **before** we made this change. Therefore, it was frozen with the old IP (`10.96.0.1`). 

The API server's new CIDR range (`100.96.0.0/12`) does **not** include `10.96.0.1`. If we left it alone:
- The Service would point to an IP that is no longer routable/allocated by the API server.
- Pods trying to connect to `10.96.0.1` would either time out or hit the wrong network segment.
- CoreDNS and other components would break because they rely on this endpoint.

**Why did it "recreate" automatically?**
When you deleted it, the **`kube-controller-manager`** (specifically the `service-controller` loop) immediately detected that the `kubernetes` default Service was missing. Because this is a **hard-coded system service**, the controller automatically regenerated a brand new Service object, this time allocating the **first available IP from the *new* CIDR range**, which happened to be `100.96.0.1`. 

**In summary:**
- **You** deleted the old Service.
- **The Controller Manager** automatically recreated the new Service.

*(In your lab, the `kubernetes` service got re-created automatically, which is why I wrote in the solution: "The kubernetes service gets re-created automatically, so no need to apply the YAML".)*

---

### 3️⃣ What about the `kube-dns` Service? Why did we manually recreate that?

You might ask: *"Why did we manually apply YAML for kube-dns, but not for kubernetes?"*

- **`kubernetes` Service**: It is a **singleton** hard-coded into the controller manager's source code. The controller manager *knows* it must exist and recreates it with the correct Type (`ClusterIP`).
- **`kube-dns` (CoreDNS)**: This is a **regular user-defined Service** (even though it is critical). The controller manager does **not** recreate it automatically if deleted. We had to apply the YAML manifest manually to give it a fresh IP from the new CIDR.

---

### 🔥 Crucial Takeaway

The `kubernetes` default Service is the **DNS anchor** for the API server. 

- When you changed the CIDR, deleting it was **mandatory** to force the IP shift to `100.96.0.1`. 
- If you had *not* deleted it, it would have stubbornly kept `10.96.0.1`, and your cluster's internal service discovery (and your certificate SANs, which we also updated) would have been completely misaligned, breaking all in-cluster API traffic.
