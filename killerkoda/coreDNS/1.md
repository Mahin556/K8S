## 🎯 Scenario Context

As a Kubernetes administrator, your organization mandates that **all external DNS queries** (queries for domains outside the cluster, e.g., `kubernetes.io`) must be resolved through specific upstream DNS resolvers (`8.8.8.8` and `1.1.1.1`). You will modify the CoreDNS `ConfigMap`, restart the pods, and verify the configuration using a temporary test pod.

---

## ❓ The Task

1. **Configure CoreDNS** to forward external DNS queries to `8.8.8.8` and `1.1.1.1`.
2. **Create a temporary pod** (`busybox` or `nicolaka/netshoot`).
3. From the pod, run `nslookup kubernetes.io 8.8.8.8` and `nslookup kubernetes.io 1.1.1.1`.
4. **Save** the combined output of both commands to **`/root/dns-server.txt`** on the host.
5. **Restart** CoreDNS to apply changes without deleting any other resources.

---

## 🧠 Why This Matters

- **Default behavior**: CoreDNS forwards external DNS queries to the node's `/etc/resolv.conf` (which usually points to the host's network DNS).
- **The problem**: The host DNS may vary across cloud providers (AWS, Azure) or internal corporate DNS. Hardcoding `8.8.8.8` and `1.1.1.1` provides a consistent, reliable, and compliant external resolution policy across all cluster nodes.
- **CKA Exam alignment**: Modifying system components via `ConfigMaps` and `Deployments` is a core CKA skill (Cluster Architecture, Installation & Configuration).

## 🛠️ Step-by-Step Implementation

### Step 1: Inspect Current CoreDNS Configuration

Always check the current configuration first to understand what you are changing.

```bash
kubectl get configmap coredns -n kube-system -o yaml
```

Look for the `Corefile` section. By default, you will see:
```yaml
data:
  Corefile: |
    .:53 {
        forward . /etc/resolv.conf   # 👈 This is what we need to replace
        ...
    }
```

---

### Step 2: Edit the CoreDNS ConfigMap

You have three methods to modify the ConfigMap. Choose the one you find fastest for the CKA exam.

#### Method A: `kubectl edit` (Recommended for quick fixes)
```bash
kubectl edit configmap coredns -n kube-system
```
Find the line `forward . /etc/resolv.conf` and replace it with:
```
forward . 8.8.8.8 1.1.1.1
```
Save and exit (in `vi`, press `Esc` -> `:wq`).

#### Method B: `kubectl patch` (Single line command, very efficient)
```bash
kubectl patch configmap coredns -n kube-system --type='json' -p='[
  {"op": "replace", "path": "/data/Corefile", "value":".:53 {\n    errors\n    health {\n      lameduck 5s\n    }\n    ready\n    kubernetes cluster.local in-addr.arpa ip6.arpa {\n      pods insecure\n      fallthrough in-addr.arpa ip6.arpa\n      ttl 30\n    }\n    prometheus :9153\n    forward . 8.8.8.8 1.1.1.1\n    cache 30\n    loop\n    reload\n    loadbalance\n}\n"}
]'
```

#### Method C: `sed` + `kubectl apply` (File-based, good for backups)
```bash
kubectl get configmap coredns -n kube-system -o yaml > /tmp/coredns.yaml
sed -i 's|forward . /etc/resolv.conf|forward . 8.8.8.8 1.1.1.1|g' /tmp/coredns.yaml
kubectl apply -f /tmp/coredns.yaml
```

---

### Step 3: Verify the ConfigMap Change

Check that the `forward` directive is correctly set:
```bash
kubectl describe configmap coredns -n kube-system | grep -A 3 "forward"
```
*Expected:* `forward . 8.8.8.8 1.1.1.1`

---

### Step 4: Restart CoreDNS Pods

CoreDNS pods run as a `Deployment`. To make the configuration take effect, you must restart them.

```bash
# Restart the deployment
kubectl rollout restart deployment/coredns -n kube-system

# Wait for the rollout to complete (optional but recommended)
kubectl rollout status deployment/coredns -n kube-system

# Wait for all pods to be ready
kubectl wait --for=condition=Ready pods -l k8s-app=kube-dns -n kube-system --timeout=60s

# Verify pods are running
kubectl get pods -n kube-system -l k8s-app=kube-dns
```
> 💡 **Note**: The `k8s-app=kube-dns` label is the default selector for CoreDNS resources.

---

### Step 5: Create the Test Pod

You need a pod with `nslookup` or `dig` installed.

**Option A: Using `busybox:1.28`** (Small, fast, but limited tools)
```bash
kubectl run dns-test --image=busybox:1.28 --restart=Never -- sleep 3600
```

**Option B: Using `nicolaka/netshoot`** (Recommended for full networking toolkit)
```bash
kubectl run dns-test --image=nicolaka/netshoot --restart=Never -- sleep 3600
```

Wait for the pod to be ready:
```bash
kubectl wait --for=condition=Ready pod/dns-test --timeout=60s
```

---

### Step 6: Execute `nslookup` and Save Output

The requirement is to save the output to **`/root/dns-server.txt`** on the *host* (not just inside the pod). We use `kubectl exec` to run the commands inside the pod and redirect the output to the host file.

```bash
# Run first query (8.8.8.8) - This will create the file
kubectl exec dns-test -- nslookup kubernetes.io 8.8.8.8 > /root/dns-server.txt

# Run second query (1.1.1.1) - This will append to the file
kubectl exec dns-test -- nslookup kubernetes.io 1.1.1.1 >> /root/dns-server.txt
```

**Alternative (One-liner without persistent pod):**
If you don't want to keep a pod running, you can use the `--rm` flag which removes the pod after execution.
```bash
kubectl run dns-test --image=busybox:1.28 --restart=Never --rm -i -- nslookup kubernetes.io 8.8.8.8 > /root/dns-server.txt
kubectl run dns-test --image=busybox:1.28 --restart=Never --rm -i -- nslookup kubernetes.io 1.1.1.1 >> /root/dns-server.txt
```
> ⚠️ **Note**: The `--rm` option might print `pod "dns-test" deleted` to stderr. This doesn't affect the `stdout` redirection.

---

### Step 7: Clean Up

```bash
# Delete the test pod
kubectl delete pod dns-test
```

---

### Step 8: Verify the Output

Check the file content:
```bash
cat /root/dns-server.txt
```

**Expected output structure:**
```
Server:    8.8.8.8
Address 1: 8.8.8.8 dns.google

Name:      kubernetes.io
Address 1: 34.120.177.178

Server:    1.1.1.1
Address 1: 1.1.1.1 one.one.one.one

Name:      kubernetes.io
Address 1: 34.120.177.178
```

## 🔍 Advanced Troubleshooting

| Problem | Diagnostic Command | Solution |
| :--- | :--- | :--- |
| **CoreDNS pods stuck in CrashLoopBackOff** | `kubectl logs -n kube-system -l k8s-app=kube-dns` | Check the `Corefile` for syntax errors in the `ConfigMap`. Typos in the `forward` directive or mis-matched brackets are common. |
| **CoreDNS pods restarting indefinitely** | `kubectl describe pod -n kube-system -l k8s-app=kube-dns` | If the ConfigMap is fixed, delete the pods manually: `kubectl delete pod -n kube-system -l k8s-app=kube-dns` (they will auto-restart). |
| **`nslookup` returns `;; connection timed out`** | `kubectl exec dns-test -- ping 8.8.8.8` | If ping fails, the pod network cannot reach the external DNS servers. Check cluster egress policies or Calico network policies. |
| **Pod stuck in `Pending`** | `kubectl describe pod dns-test` | Node might be tainted or have insufficient resources. |
| **`nslookup` command not found** | N/A | Use the `nicolaka/netshoot` image which has `dig`, `nslookup`, and `curl` pre-installed. |
| **`forward` plugin doesn't seem to work** | Check CoreDNS logs: `kubectl logs -n kube-system deployment/coredns --tail=50` | Look for lines containing "forward" or "Failed to connect". Ensure your network firewall allows outbound UDP port 53 to 8.8.8.8 and 1.1.1.1. |

## 🧩 Understanding the CoreDNS `forward` Plugin

The `forward` plugin is responsible for proxying DNS queries to upstream nameservers.

**Syntax:**
```coredns
forward . <NAMESERVER_1> <NAMESERVER_2> { optional_policies }
```

- **`.` (The domain)**: The forward plugin matches all domains (`.` is the root zone). If you wanted to forward only specific domains (e.g., `internal.company.com`), you could customize this.
- **`8.8.8.8 1.1.1.1`**: The list of upstream servers. CoreDNS uses a **round-robin** load-balancing strategy across these by default.
- **Fallback**: If the first server fails to respond, CoreDNS falls back to the second one automatically.

**Difference between `/etc/resolv.conf` and static IPs:**
- `/etc/resolv.conf` points to the node's local DNS (which may be tied to cloud provider metadata IPs or a corporate resolver). Changing to `8.8.8.8` ensures **deterministic** behavior across all cloud environments.


## 🎓 CKA Exam Tips

1. **Don't delete the ConfigMap** — always `edit` or `patch` it.
2. **Speed matters**: `kubectl edit cm coredns -n kube-system` is faster than exporting, sed-ing, and applying.
3. **Check the namespace**: CoreDNS lives in `kube-system`.
4. **Rollout restart**: After changing the ConfigMap, the `reload` plugin should detect changes automatically (default: 5 seconds), but the CKA exam *usually* requires you to explicitly restart for safety.
5. **Save output** to the exact path: `/root/dns-server.txt` (case sensitive).
6. **Append `>>`**: For the second `nslookup`, use `>>` to append; otherwise, you'll overwrite the first result.
