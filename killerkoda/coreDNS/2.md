## 🎯 Scenario Overview

**Context**: As a Kubernetes administrator, you are required to force all external DNS queries (domains outside the cluster, e.g., `kubernetes.io`) to be resolved through specific upstream DNS servers for compliance, monitoring, and performance reasons.

**Objective**:  
- Configure CoreDNS to forward external queries to `8.8.8.8` (Google) and `1.1.1.1` (Cloudflare).  
- Create a temporary test pod, execute `nslookup` commands against both servers, and save the combined output to `/root/dns-server.txt` on the host.  
- Restart CoreDNS to apply the new configuration without deleting any existing resources.

**Skills Tested**:  
- Editing Kubernetes ConfigMaps  
- Understanding CoreDNS `forward` plugin  
- Restarting Deployments  
- Using `kubectl exec` to run commands and redirect output  
- Basic DNS troubleshooting

## 📝 Step-by-Step Configuration

### Step 1: Inspect the Current CoreDNS ConfigMap

```bash
kubectl get configmap coredns -n kube-system -o yaml
```

Look for the `Corefile` entry. The default `forward` line usually points to `/etc/resolv.conf`.

### Step 2: Edit the ConfigMap

You have three options. Choose the fastest for the exam.

#### Option A: `kubectl edit` (Recommended)
```bash
kubectl edit configmap coredns -n kube-system
```
Find the line:
```
forward . /etc/resolv.conf
```
Replace with:
```
forward . 8.8.8.8 1.1.1.1
```
Save and exit.

#### Option B: `kubectl patch` (One‑liner)
```bash
kubectl patch configmap coredns -n kube-system --type='json' -p='[
  {"op": "replace", "path": "/data/Corefile", "value":".:53 {\n    errors\n    health {\n      lameduck 5s\n    }\n    ready\n    kubernetes cluster.local in-addr.arpa ip6.arpa {\n      pods insecure\n      fallthrough in-addr.arpa ip6.arpa\n      ttl 30\n    }\n    prometheus :9153\n    forward . 8.8.8.8 1.1.1.1\n    cache 30\n    loop\n    reload\n    loadbalance\n}\n"}
]'
```

#### Option C: File‑based (Good for backups)
```bash
kubectl get configmap coredns -n kube-system -o yaml > /tmp/coredns.yaml
sed -i 's|forward . /etc/resolv.conf|forward . 8.8.8.8 1.1.1.1|g' /tmp/coredns.yaml
kubectl apply -f /tmp/coredns.yaml
```

### Step 3: Verify the Change

```bash
kubectl describe configmap coredns -n kube-system | grep -A 3 "forward"
```

Expected output: `forward . 8.8.8.8 1.1.1.1`

### Step 4: Restart CoreDNS Pods

```bash
kubectl rollout restart deployment/coredns -n kube-system
kubectl rollout status deployment/coredns -n kube-system
kubectl wait --for=condition=Ready pods -l k8s-app=kube-dns -n kube-system --timeout=60s
kubectl get pods -n kube-system -l k8s-app=kube-dns
```

### Step 5: Create a Test Pod

```bash
kubectl run dns-test --image=nicolaka/netshoot --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/dns-test --timeout=60s
```

### Step 6: Execute `nslookup` and Save Output

```bash
# First query (8.8.8.8) - create file
kubectl exec dns-test -- nslookup kubernetes.io 8.8.8.8 > /root/dns-server.txt

# Second query (1.1.1.1) - append
kubectl exec dns-test -- nslookup kubernetes.io 1.1.1.1 >> /root/dns-server.txt
```

**Alternative (one‑shot, no persistent pod):**
```bash
kubectl run dns-test --image=busybox:1.28 --restart=Never --rm -i -- nslookup kubernetes.io 8.8.8.8 > /root/dns-server.txt
kubectl run dns-test --image=busybox:1.28 --restart=Never --rm -i -- nslookup kubernetes.io 1.1.1.1 >> /root/dns-server.txt
```

### Step 7: Clean Up

```bash
kubectl delete pod dns-test
```

### Step 8: Verify the Output

```bash
cat /root/dns-server.txt
```

Expected output includes the server IP, address, and resolved IP for `kubernetes.io`.

## 🧠 Conceptual Architecture & DNS Flow

### CoreDNS Architecture

- **CoreDNS**: A flexible, extensible DNS server written in Go. It is the default DNS server in Kubernetes, providing service discovery and external name resolution.
- **ConfigMap (`coredns`)**: Stores the `Corefile` configuration that defines how CoreDNS handles queries.
- **Corefile**: The configuration file using a plugin‑based architecture. Each block defines a zone (like `.` for all domains) and a list of plugins.
- **`forward` Plugin**: Proxies DNS queries to upstream DNS servers for external name resolution.

### How DNS Works in Kubernetes

```
Pod DNS Query (kubernetes.io)
        ↓
CoreDNS Service (kube-dns) — ClusterIP: 10.96.0.10
        ↓
CoreDNS Pod reads Corefile
        ↓
Checks if query matches kubernetes cluster.local (or in‑addr.arpa, ip6.arpa)
        ↓
NO → Forward to upstream (8.8.8.8 or 1.1.1.1)
        ↓
Upstream DNS resolves external domain
        ↓
Response returns to Pod
```

### DNS Resolution Flow Diagram

```
-------------------------------------------------------------------
1. Pod → kube-dns Service (CoreDNS)
2. CoreDNS checks query type:
   - cluster.local domains → Kubernetes API (via kubernetes plugin)
   - External domains → Forward to upstream
3. Forward plugin sends query to 8.8.8.8 or 1.1.1.1 (round‑robin)
4. Response cached (30s default TTL)
5. Response returned to requesting pod
-------------------------------------------------------------------
```

### CoreDNS Configuration Breakdown

```coredns
.:53 {                         # Listen on port 53 for all domains
    errors                     # Log errors to stdout
    health { lameduck 5s }     # Health check endpoint :8080
    ready                      # Readiness probe endpoint :8181
    kubernetes cluster.local in-addr.arpa ip6.arpa {   # Service discovery
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus :9153           # Metrics endpoint
    forward . 8.8.8.8 1.1.1.1 # 🔑 Upstream DNS servers
    cache 30                   # Cache responses for 30 seconds
    loop                       # Detect forwarding loops
    reload                     # Auto‑reload on Corefile changes
    loadbalance                # Round‑robin load balancing
}
```

- **`.:53`**: Matches any domain; listens on port 53 (standard DNS).
- **`kubernetes`**: Handles queries for cluster DNS (services, pods).
- **`forward`**: Sends all other (external) queries to the listed upstream servers.
- **`cache`**: Improves performance by caching positive responses for 30 seconds.
- **`loop`**: Prevents infinite forwarding loops (critical).
- **`reload`**: Automatically detects changes to the ConfigMap and reloads without restarting pods.
- **`loadbalance`**: Distributes A/AAAA/MX records in round‑robin fashion.

## 🔑 CoreDNS Plugins Reference

| Plugin | Description | Example |
|--------|-------------|---------|
| **errors** | Logs errors to stdout (visible via `kubectl logs`) | `errors` |
| **health** | Exposes HTTP health check at `:8080/health` | `health { lameduck 5s }` |
| **ready** | Exposes readiness probe at `:8181/ready` | `ready` |
| **kubernetes** | Handles service discovery for `cluster.local`, `in‑addr.arpa`, `ip6.arpa` | `kubernetes cluster.local in-addr.arpa ip6.arpa { ... }` |
| **prometheus** | Exposes Prometheus metrics at `:9153/metrics` | `prometheus :9153` |
| **forward** | Proxies DNS queries to upstream servers | `forward . 8.8.8.8 1.1.1.1` |
| **cache** | Caches DNS responses to improve performance | `cache 30` |
| **loop** | Detects and prevents infinite forwarding loops | `loop` |
| **reload** | Automatically reloads Corefile when the ConfigMap changes | `reload` |
| **loadbalance** | Round‑robin load balancing for A/AAAA/MX records | `loadbalance` |
| **template** | Responds with custom DNS records (advanced) | `template IN A example.com "{{ .Name }}"` |
| **hosts** | Serves static records from a hosts‑like file | `hosts /etc/coredns/hosts` |

### Forward Plugin Syntax

```
forward . <NAMESERVER_1> [NAMESERVER_2 ...] { optional_policies }
```

**Examples:**

- Single DNS server: `forward . 8.8.8.8`
- Multiple servers (order tried): `forward . 8.8.8.8 1.1.1.1`
- Use system resolv.conf: `forward . /etc/resolv.conf`
- Conditional forwarding for a specific domain:
  ```
  example.com:53 {
      forward . 10.0.0.1
  }
  ```
- DNS over TLS: `forward . tls://1.1.1.1 { tls_servername cloudflare-dns.com }`

## 🔧 Common CoreDNS Configuration Patterns

### 1. Multiple Upstream Servers (Failover)
```
forward . 8.8.8.8 8.8.4.4 1.1.1.1 1.0.0.1
```
CoreDNS tries in order; if first fails, moves to the next.

### 2. Split‑Horizon DNS (Internal vs External)
```
.:53 {
    kubernetes cluster.local
    forward . 8.8.8.8
}

corp.local:53 {
    forward . 10.0.0.53   # Internal DNS for corporate domain
}
```

### 3. DNS over TLS (Encrypted Queries)
```
forward . tls://1.1.1.1 {
    tls_servername cloudflare-dns.com
}
```

### 4. Conditional Forwarding (except internal domain)
```
.:53 {
    kubernetes cluster.local
    forward . /etc/resolv.conf {
        except example.com
    }
}

example.com:53 {
    forward . 10.0.0.1
}
```

### 5. Caching with Extended TTL (for performance)
```
cache 300   # 5 minutes instead of default 30 seconds
```

### 6. Increase Concurrency for High Load
```
forward . 8.8.8.8 1.1.1.1 {
    max_concurrent 1000
}
```

## 💡 Real-World Use Cases

1. **Corporate Compliance**: Organizations mandate using specific DNS servers for audit trails and monitoring of all external queries.
2. **Split‑Horizon DNS**: Different resolvers for internal (private) vs external (public) domains.
3. **DNS Filtering**: Using filtered DNS services (e.g., Cloudflare for Families, Quad9) to block malware or adult content.
4. **Performance Optimization**: Using geographically closer DNS servers to reduce latency.
5. **Multi‑Cloud Environments**: Routing DNS based on cloud provider to avoid cross‑regional costs.
6. **Disaster Recovery**: Configuring fallback DNS servers for high availability.
7. **Traffic Shaping**: Directing specific domain queries to internal resolvers for caching or interception.

## 🛠️ Troubleshooting DNS Issues

### Issue 1: DNS Resolution Fails

**Diagnose:**
```bash
# Check CoreDNS pod status
kubectl get pods -n kube-system -l k8s-app=kube-dns

# Check CoreDNS logs
kubectl logs -n kube-system -l k8s-app=kube-dns --tail=50

# Test from a pod
kubectl run dns-debug --image=busybox:1.28 --rm -it -- nslookup kubernetes.io
```

**Likely causes:** Misconfigured `forward` directive, network policy blocking egress UDP 53, or CoreDNS pod crashes.

---

### Issue 2: CoreDNS Pods in CrashLoopBackOff

**Diagnose:**
```bash
# Inspect pod events
kubectl describe pod -n kube-system -l k8s-app=kube-dns

# Check ConfigMap syntax for typos
kubectl get configmap coredns -n kube-system -o yaml | grep -A 20 "Corefile"
```

**Solution:**  
- Correct any syntax errors in the `Corefile` (e.g., missing braces, incorrect plugin order).  
- Restart the deployment after fixing.  
- If needed, delete the pods manually: `kubectl delete pod -n kube-system -l k8s-app=kube-dns`.

---

### Issue 3: Slow DNS Resolution

**Diagnose:** Check cache and forward timeouts.

**Solutions:**
- Increase cache TTL: `cache 300` (5 minutes).
- Increase `max_concurrent` in forward plugin.
- Scale CoreDNS replicas:
  ```bash
  kubectl scale deployment coredns -n kube-system --replicas=3
  ```

---

### Issue 4: DNS Queries Timing Out

**Diagnose:** Test upstream connectivity from node:
```bash
nslookup kubernetes.io 8.8.8.8
```

**Solutions:**
- Verify firewall rules allow outbound UDP 53 to the upstream IPs.
- Ensure no loop (CoreDNS forwarding to itself). Check that `forward .` does **not** point back to the CoreDNS service IP.
- Add a `health` check to detect unhealthy upstream servers.

---

### Issue 5: `nslookup` Returns `;; connection timed out`

**Diagnose:** Check if pod can reach the upstream IPs:
```bash
kubectl exec dns-test -- ping 8.8.8.8
```

**Solutions:**
- Check cluster egress policies (NetworkPolicies, Calico policies).
- Ensure pod network allows outbound traffic to the internet.
- Verify the node’s network configuration.

## 🔍 DNS Debugging Commands

### Test DNS from within a Pod

```bash
# Create debug pod (netshoot has dig, nslookup, curl, etc.)
kubectl run dns-test --image=nicolaka/netshoot --rm -it -- bash

# Inside pod:
nslookup kubernetes.io
dig kubernetes.io
host kubernetes.io

# Test specific DNS server
nslookup kubernetes.io 8.8.8.8
dig @8.8.8.8 kubernetes.io
```

### Test Kubernetes Service DNS

```bash
# Create a service
kubectl create deployment nginx --image=nginx
kubectl expose deployment nginx --port=80

# Query the service DNS
kubectl run dns-test --image=busybox:1.28 --rm -it -- nslookup nginx.default.svc.cluster.local
```

### Check DNS Configuration in a Pod

```bash
kubectl run dns-test --image=busybox:1.28 --rm -it -- cat /etc/resolv.conf
```

**Expected output:**
```
nameserver 10.96.0.10    # CoreDNS service ClusterIP
search default.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

### Verify CoreDNS Endpoints and Health

```bash
# Check CoreDNS service
kubectl get svc -n kube-system kube-dns

# Check endpoints
kubectl get endpoints -n kube-system kube-dns

kubectl exec -n kube-system $COREDNS_POD -- wget -O- http://localhost:8080/health
```

## 🎓 CKA Exam Tips & Best Practices

1. **Know the namespace**: CoreDNS lives in `kube-system`.
2. **Restart after changes**: Although the `reload` plugin can auto‑detect changes, the exam often expects you to explicitly restart the deployment for safety.
3. **Use `kubectl edit`**: It’s the fastest way to modify ConfigMaps during the exam.
4. **Save output to exact path**: `>/root/dns-server.txt` (case‑sensitive).
5. **Append vs overwrite**: Use `>` for the first command, `>>` for the second.
6. **Choose the right test image**: `nicolaka/netshoot` has more tools; `busybox:1.28` is smaller but may lack `dig`; both have `nslookup`.
7. **Check logs**: `kubectl logs -n kube-system -l k8s-app=kube-dns` is your friend for debugging.
8. **Use aliases** to save time (if allowed):  
   ```bash
   alias k=kubectl
   alias kgp='kubectl get pods'
   alias kecm='kubectl edit configmap'
   ```
