To understand where CoreDNS stores DNS records, it's helpful to know that it doesn't have a single, default database. Instead, its storage is **determined by its configuration, which is defined in a `ConfigMap`** in the `kube-system` namespace. How it stores records depends on which **plugin** you enable as its "backend".

In a standard Kubernetes cluster, CoreDNS doesn't store records at all; it retrieves them live from the Kubernetes API. However, it can be configured to use different backends for permanent storage.

Here is a breakdown of the main "storage" mechanisms.

---

### 1. The Default in Kubernetes: No Persistent Storage (The `kubernetes` Plugin)

This is the most important scenario to understand. **In a default Kubernetes cluster, CoreDNS does not persistently store any DNS records in a database or on disk**.

Instead, it uses the **`kubernetes` plugin**. This plugin does not read from a static file or a database. It **directly queries the Kubernetes API server in real-time**.

When a Pod asks for the IP of a Service, CoreDNS:
1.  Receives the query (e.g., `my-service.my-namespace.svc.cluster.local`).
2.  Uses the `kubernetes` plugin to ask the Kubernetes API for the `Service` object.
3.  Retrieves its `ClusterIP`.
4.  Returns that IP to the Pod.

Because of this, all DNS records are dynamic and reflect the current state of the cluster. If a Service or Pod is deleted, it disappears from DNS lookups instantly, with no need to manually update any files.

### 2. Persistent Storage Backends (Pluggable)

While the `kubernetes` plugin is the default, CoreDNS can be configured to use other plugins to store records in an external system. This is useful for custom or non-Kubernetes DNS needs.

*   **`etcd` Plugin**: This plugin allows CoreDNS to use an **`etcd`** key-value store as its backend. Records are stored under a specific path in etcd, like `/skydns/`. This is a common choice for dynamic DNS management outside of Kubernetes.

*   **`file` Plugin**: This plugin enables CoreDNS to **serve records from a standard DNS zone file** on disk. This is similar to a traditional DNS server like BIND.

*   **Other Backend Plugins**: CoreDNS's plugin architecture supports many other backends. This includes:
    *   **`consulkv`**: Stores records in **HashiCorp Consul's** KV store.
    *   **`route53`**: Integrates with **AWS Route 53**.
    *   **`redis_cache`**: Uses **Redis** as a shared cache for DNS responses.

### Summary Table

| Storage Mechanism | Plugin Used | Where Records Are Stored | Key Characteristic |
| :--- | :--- | :--- | :--- |
| **Default (Kubernetes)** | `kubernetes` | **Nowhere** (retrieved live from API) | Always up-to-date with cluster state |
| **External Database** | `etcd` | In an `etcd` key-value store | Good for managing records outside Kubernetes |
| **Static File** | `file` | In a zone file on disk | Similar to a traditional DNS server |
| **Other Backends** | `consulkv`, `route53`, etc. | In Consul, AWS, etc. | Integrates with external systems |

---

### How to Check Your Configuration

To see which plugin (and therefore which storage mechanism) your CoreDNS is using, you can view its `ConfigMap`:

```bash
kubectl get configmap coredns -n kube-system -o yaml
```

Look for the `Corefile` section. If you see a `kubernetes` block, it's using the default, API-based mechanism. If you see `etcd` or `file`, it's configured to store records externally.

### Analogy

To simplify, think of it this way:

*   **Default CoreDNS** is like a **building concierge** who, when asked for a tenant's room number, **looks up the current tenant list** (the Kubernetes API) every single time. They have no permanent list of their own.
*   **CoreDNS with etcd** is like a concierge who **maintains their own personal directory** (an `etcd` database) that they consult.
