## 🧠 Conceptual Summary

### Pod vs Deployment

| Aspect | Pod | Deployment |
|--------|-----|------------|
| **Purpose** | Single instance | Managed replicas |
| **Self-Healing** | ❌ No | ✅ Yes |
| **Rolling Updates** | ❌ No | ✅ Yes |
| **Rollback** | ❌ No | ✅ Yes |
| **Replica Management** | ❌ No | ✅ Yes |
| **Use Case** | Testing, single-run tasks | Production workloads |

### Why Convert to Deployment?

✅ **High Availability** → Multiple replicas ensure uptime  
✅ **Self-Healing** → Deployment controller recreates failed pods  
✅ **Rolling Updates** → Zero-downtime updates  
✅ **Rollback** → Easy revert to previous version  
✅ **Scalability** → Easily scale up/down

## 🔒 Understanding securityContext

### What is securityContext?

`securityContext` defines privilege and access control settings for a Pod or container. It implements **security best practices** by restricting what a container can do.

### Container-Level vs Pod-Level

| Scope | Applies To | Use Case |
|-------|------------|----------|
| **Pod-level** | All containers in Pod | Shared security settings |
| **Container-level** | Single container | Specific container requirements |

### Key Security Settings

| Setting | Purpose |
|---------|---------|
| **`allowPrivilegeEscalation: false`** | Prevents processes from gaining more privileges than their parent |
| **`privileged: false`** | Prevents running in privileged mode (access to host devices) |
| **`runAsUser`** | Runs container with specific user ID |
| **`readOnlyRootFilesystem`** | Makes root filesystem read-only |
| **`capabilities`** | Drops/ adds Linux capabilities |

### Why These Settings Matter

```
Without Security Context:
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Privileged Container                                     │
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                    Container (root)                                  │   │
│   │                                                                     │   │
│   │   ❌ Has access to host devices                                     │   │
│   │   ❌ Can escalate privileges                                        │   │
│   │   ❌ Can mount host filesystems                                     │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│   ⚠️ Security risk if container is compromised                            │
└─────────────────────────────────────────────────────────────────────────────┘

With Security Context:
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Restricted Container                                     │
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                    Container (non-root)                              │   │
│   │                                                                     │   │
│   │   ✅ No access to host devices                                      │   │
│   │   ✅ Cannot escalate privileges                                     │   │
│   │   ✅ Cannot mount host filesystems                                  │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│   ✅ Secure even if container is compromised                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 📋 Step-by-Step Solution

### Step 1: Examine the Existing Pod File

```bash
cat /opt/course/9/holy-api-pod.yaml
```

**Current State (Single Pod):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: holy-api
  namespace: pluto
  labels:
    app: holy-api
spec:
  containers:
  - name: app
    image: public.ecr.aws/docker/library/busybox:stable
    command: ["/bin/sh", "-c", "sleep 1d"]
```

### Step 2: Create the Deployment YAML

```bash
touch /opt/course/9/holy-api-deployment.yaml
vi /opt/course/9/holy-api-deployment.yaml
```

**Deployment YAML (After Conversion):**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: holy-api
  namespace: pluto
  labels:
    app: holy-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: holy-api
  template:
    metadata:
      labels:
        app: holy-api
    spec:
      containers:
      - name: app
        image: public.ecr.aws/docker/library/busybox:stable
        command: ["/bin/sh", "-c", "sleep 1d"]
        securityContext:
          allowPrivilegeEscalation: false
          privileged: false
```

### Step 3: Apply the Deployment

```bash
kubectl -n pluto apply -f /opt/course/9/holy-api-deployment.yaml
```

**Expected Output:**
```
deployment.apps/holy-api created
```

### Step 4: Delete the Original Pod

```bash
kubectl -n pluto delete pod holy-api
```

**Expected Output:**
```
pod "holy-api" deleted
```

### Step 5: Verify the Deployment

```bash
kubectl -n pluto rollout status deploy/holy-api --timeout=120s
```

**Expected Output:**
```

```

### Step 6: Check the Deployment

```bash
kubectl -n pluto get deploy holy-api -o wide
```

**Expected Output:**
```

```

### Step 7: Verify Pods


**Expected Output:**

## 🔍 Deep Dive: Understanding the Configuration

### Complete YAML Breakdown

```yaml
apiVersion: apps/v1
# ↑ API group and version for Deployment

kind: Deployment
# ↑ Resource type

metadata:
  name: holy-api
  # ↑ Deployment name

  namespace: pluto
  # ↑ Namespace where Deployment is created

  labels:
    app: holy-api
  # ↑ Labels for the Deployment itself

spec:
  # ↑ Specification of the Deployment

  replicas: 3
  # ↑ Number of Pod replicas (high availability)

  selector:
    matchLabels:
      app: holy-api
  # ↑ Labels used to select Pods owned by this Deployment

  template:
    # ↑ Pod template for creating new Pods

    metadata:
      labels:
        app: holy-api
      # ↑ Labels for Pods created by this Deployment

    spec:
      # ↑ Pod specification

      containers:
      - name: app
        # ↑ Container name (same as original Pod)

        image: public.ecr.aws/docker/library/busybox:stable
        # ↑ Container image

        command: ["/bin/sh", "-c", "sleep 1d"]
        # ↑ Command to keep container running

        securityContext:
          # 🔥 Container-level security settings

          allowPrivilegeEscalation: false
          # ↑ Prevents privilege escalation (security best practice)

          privileged: false
          # ↑ Not running in privileged mode (security best practice)
```

### Key Changes from Pod to Deployment

| Aspect | Original Pod | New Deployment |
|--------|--------------|----------------|
| **Kind** | `Pod` | `Deployment` |
| **API Version** | `v1` | `apps/v1` |
| **Replicas** | N/A (single) | `3` |
| **Selector** | N/A | `matchLabels: app: holy-api` |
| **Template** | N/A | Pod template embedded |
| **Security Context** | ❌ Missing | ✅ Added |

### Why the Selector is Important

```
Deployment → Selector → Pods
    ↓
Selector matches labels on Pods
    ↓
Deployment manages all Pods with matching labels
    ↓
If Pods have wrong labels, Deployment won't manage them
```

### Label Consistency

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    Label Consistency                                         │
│                                                                             │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                    Deployment Labels                                 │   │
│   │                                                                     │   │
│   │   selector:                                                         │   │
│   │     matchLabels:                                                    │   │
│   │       app: holy-api    ←──────────┐                               │   │
│   └─────────────────────────────────────┼───────────────────────────────┘   │
│                                         │                                   │
│                                         ▼                                   │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │                    Pod Template Labels                               │   │
│   │                                                                     │   │
│   │   template:                                                         │   │
│   │     metadata:                                                       │   │
│   │       labels:                                                       │   │
│   │         app: holy-api    ←──────────┘ (Must match)                │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│   ✅ Both labels match! Deployment can manage Pods                        │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Deployment not creating pods** | Wrong selector | Check `selector` matches `template.labels` |
| **Pods not starting** | Image pull error | Check image name and registry |
| **Original Pod not deleted** | Wrong namespace | Use `-n pluto` flag |
| **SecurityContext not applied** | Wrong indentation | Verify YAML structure |
| **Deployment stuck** | Missing selector | Ensure `selector` is defined |
| **Replicas not matching** | Pending pods | Check node resources: `kubectl describe pods` |
| **Original Pod still exists** | Misspelled name | Check pod name: `kubectl get pods -n pluto` |

### Debugging Commands

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Always use Deployments for production** | Self-healing, updates, rollbacks |
| **Set securityContext** | Security best practice |
| **Set `allowPrivilegeEscalation: false`** | Prevent privilege escalation |
| **Set `privileged: false`** | Not running privileged |
| **Use labels consistently** | Selector must match template labels |
| **Save manifests to files** | Version control and reproducibility |
| **Delete old resources** | Clean up after migration |

### SecurityContext Best Practices

| Setting | Recommended Value | Why |
|---------|-------------------|-----|
| **`allowPrivilegeEscalation`** | `false` | Prevents gaining more privileges |
| **`privileged`** | `false` | Not running privileged |
| **`runAsUser`** | Non-root user | Least privilege |
| **`readOnlyRootFilesystem`** | `true` | Prevents writing to root |
| **`capabilities.drop`** | `["ALL"]` | Drop all capabilities |

### Real-World Use Cases

| Use Case | Description | Why Deployment? |
|----------|-------------|-----------------|
| **Web Application** | HTTP service with multiple replicas | High availability |
| **API Gateway** | Traffic routing | Scalability |
| **Background Worker** | Processing queue | Self-healing |
| **Microservices** | Service components | Rolling updates |

### Complete Security Context Example

```yaml
securityContext:
  allowPrivilegeEscalation: false
  privileged: false
  runAsUser: 1000           # Run as non-root user
  runAsGroup: 1000          # Run with non-root group
  readOnlyRootFilesystem: true   # Read-only root
  capabilities:
    drop:                   # Drop all capabilities
    - ALL
```
