## 🎯 Scenario Overview

### The Story
**Japan Railway (JR)** has deployed three microservices in the `jp-bullet-train-app-prod` namespace:

| Service | Purpose |
|---------|---------|
| **`available`** | Real-time train availability |
| **`books`** | Booking status |
| **`travellers`** | Passenger manifest |

### The Mission
Expose these services externally using the **Kubernetes Gateway API** with TLS termination and path-based routing at `https://bullet.train.io`.

### Your Tasks

1. **Create a Gateway** named `bullet-train-gateway` in namespace `jp-bullet-train-gtw` with:
   - GatewayClassName: `nginx`
   - Protocol: `HTTPS` on port `443`
   - Hostname: `bullet.train.io`
   - TLS Mode: `Terminate`
   - TLS Certificate: `bullet-train-tls` (existing secret)

2. **Create an HTTPRoute** named `bullet-train-route` in namespace `jp-bullet-train-gtw`:
   - Parent Gateway: `bullet-train-gateway`
   - Hostname: `bullet.train.io`
   - Path-based routing:
     - `/available` → `available` service (port 80) in `jp-bullet-train-app-prod`
     - `/books` → `books` service (port 80) in `jp-bullet-train-app-prod`
     - `/travellers` → `travellers` service (port 80) in `jp-bullet-train-app-prod`
   - Path Match Type: `PathPrefix` for all routes

3. **Configure local DNS** by adding `bullet.train.io` to `/etc/hosts` with the Gateway's LoadBalancer IP

4. **Test** all three endpoints using `curl -k`

## 🧠 Conceptual Summary

### What is the Kubernetes Gateway API?

The **Gateway API** is the next generation of Kubernetes networking, offering a more expressive, extensible, and role-oriented API for managing traffic routing.It represents the successor to Ingress for routing traffic into cluster Services.

### Key Principles

| Principle | Description |
|-----------|-------------|
| **Role-Oriented** | Modeled after organizational roles (Infrastructure Provider, Cluster Operator, Application Developer) |
| **Portable** | Specifications are defined as Custom Resources supported by many implementations |
| **Expressive** | Supports header-based matching, traffic weighting, and more |
| **Extensible** | Allows custom resources to be linked at various layers |

### Why Gateway API?

✅ **Protocol-Agnostic** → Supports HTTP, HTTPS, TCP, UDP, gRPC  
✅ **Advanced Routing** → Header matching, query parameters, traffic splitting  
✅ **Role Separation** → Different teams manage different resources  
✅ **Cross-Namespace** → Routes can reference services in other namespaces (with ReferenceGrant)  
✅ **Cleaner Configuration** → No annotation overload

### Three Core Resources

The Gateway API has three stable API kinds:

| Resource | Scope | Purpose |
|----------|-------|---------|
| **GatewayClass** | Cluster-scoped | Defines a set of gateways with common configuration and behavior; managed by a controller |
| **Gateway** | Namespace-scoped | Defines an instance of traffic handling infrastructure (load balancer, listeners, TLS) |
| **HTTPRoute** | Namespace-scoped | Defines HTTP-specific rules for mapping traffic from a Gateway listener to backend Services |

### Relationship Between Resources

```
GatewayClass (Cluster-scoped)
    ↓ (references)
Gateway (Namespace-scoped)
    ↓ (parentRefs)
HTTPRoute (Namespace-scoped)
    ↓ (backendRefs)
Service (Namespace-scoped)
```

A Gateway object is associated with exactly one GatewayClass; the GatewayClass describes the gateway controller responsible for managing Gateways of this class.

### Step 1: Create the Gateway

```bash
cat > /tmp/gateway.yaml <<'EOF'
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: bullet-train-gateway
  namespace: jp-bullet-train-gtw
spec:
  gatewayClassName: nginx
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: bullet.train.io
    tls:
      mode: Terminate
      certificateRefs:
      - name: bullet-train-tls
EOF

kubectl apply -f /tmp/gateway.yaml
```

**YAML Breakdown:**

| Field | Value | Description |
|-------|-------|-------------|
| `apiVersion` | `gateway.networking.k8s.io/v1` | Gateway API version |
| `kind` | `Gateway` | Resource type |
| `metadata.name` | `bullet-train-gateway` | Gateway name |
| `metadata.namespace` | `jp-bullet-train-gtw` | Gateway namespace |
| `spec.gatewayClassName` | `nginx` | Gateway controller class |
| `spec.listeners[0].protocol` | `HTTPS` | Listener protocol |
| `spec.listeners[0].port` | `443` | Port for HTTPS |
| `spec.listeners[0].hostname` | `bullet.train.io` | Domain name |
| `spec.listeners[0].tls.mode` | `Terminate` | TLS termination at Gateway |
| `spec.listeners[0].tls.certificateRefs[0].name` | `bullet-train-tls` | TLS secret reference |

## 🔍 Deep Dive: Gateway API Components

### GatewayClass

**What it is:** A cluster-scoped resource that defines a set of gateways with common configuration and behavior.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: nginx
spec:
  controllerName: gateway.nginx.org/nginx-gateway-controller
```

**Key Points:**
- Must have at least one GatewayClass defined to have functional Gateways
- Similar to IngressClass for Ingress or StorageClass for PersistentVolumes
- Each GatewayClass is handled by a single controller

### Gateway

**What it is:** A namespace-scoped resource that defines an instance of traffic handling infrastructure.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: bullet-train-gateway
  namespace: jp-bullet-train-gtw
spec:
  gatewayClassName: nginx
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    hostname: bullet.train.io
    tls:
      mode: Terminate
      certificateRefs:
      - name: bullet-train-tls
```

**Key Points:**
- Defines a request for a specific load balancer config
- May omit fields like addresses or TLS settings, allowing the controller to provide them
- Can filter the routes that may be attached to its listeners

### HTTPRoute

**What it is:** A namespace-scoped resource that defines HTTP-specific rules for mapping traffic.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: bullet-train-route
  namespace: jp-bullet-train-gtw
spec:
  parentRefs:
  - name: bullet-train-gateway
  hostnames:
  - bullet.train.io
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /available
    backendRefs:
    - name: available
      namespace: jp-bullet-train-app-prod
      port: 80
```

**Key Points:**
- Routes are associated with Gateways via `parentRefs`
- Can reference backends in other namespaces (with ReferenceGrant)
- Supports multiple matching strategies (PathPrefix, Exact, RegularExpression)

## 🔐 Deep Dive: TLS Termination

### What is TLS Termination?

**TLS Termination** is the process of decrypting HTTPS traffic at the Gateway before forwarding it to backend services as plain HTTP.

```
Client ←→ (HTTPS) ←→ Gateway ←→ (HTTP) ←→ Service/Pod
                         ↑
                    TLS Termination
                    Certificate Decryption
```

### TLS Configuration in Gateway

```yaml
tls:
  mode: Terminate                    # Gateway decrypts traffic
  certificateRefs:
  - name: bullet-train-tls           # Secret containing certificate
```

### TLS Modes

| Mode | Description | Use Case |
|------|-------------|----------|
| **Terminate** | Gateway terminates TLS, forwards HTTP | Most common, centralizes certificate management |
| **Passthrough** | Gateway forwards encrypted traffic | Backend services handle their own SSL |
| **TLS** | Gateway performs TLS handshake | Mutual TLS scenarios |

### TLS Secret Requirements

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: bullet-train-tls
  namespace: jp-bullet-train-gtw
type: kubernetes.io/tls
data:
  tls.crt: <base64-encoded-certificate>
  tls.key: <base64-encoded-private-key>
```

**Key Points:**
- Secret must be in the **same namespace** as the Gateway
- Secret type must be `kubernetes.io/tls`
- `certificateRefs` must contain at least one element when mode is Terminate

### Why TLS Termination at Gateway?

| Benefit | Explanation |
|---------|-------------|
| **Centralized Management** | One certificate for all services |
| **Performance** | SSL/TLS offloaded from application pods |
| **Simplified Services** | Services don't need certificate configuration |
| **Security** | Consistent security policies |

## 🛣️ Deep Dive: Path-Based Routing

### Path Match Types

| Type | Description | Example |
|------|-------------|---------|
| **PathPrefix** | Matches the specified prefix and all sub-paths | `/api` matches `/api`, `/api/v1`, `/api/users` |
| **Exact** | Matches the exact path only | `/login` only matches `/login` |
| **RegularExpression** | Regex matching (implementation-specific) | `/api/v[0-9]+` |

### PathPrefix Matching Examples

```
Request: /available
         ↓
Path: /available (PathPrefix)
         ↓
✓ MATCHES! → available service

Request: /available/trains
         ↓
Path: /available (PathPrefix)
         ↓
✓ MATCHES! → available service (sub-path)

Request: /availablement
         ↓
Path: /available (PathPrefix)
         ↓
✗ DOES NOT MATCH! (different prefix)

Request: /books
         ↓
Path: /books (PathPrefix)
         ↓
✓ MATCHES! → books service
```

### Multiple Path Rules

```yaml
rules:
- matches:
  - path:
      type: PathPrefix
      value: /available
  backendRefs:
  - name: available
    port: 80
- matches:
  - path:
      type: PathPrefix
      value: /books
  backendRefs:
  - name: books
    port: 80
```

### Path Priority (Longest Match Wins)

```
Request: /available/shinkansen
         ↓
Path 1: /available (Prefix) ✓
Path 2: /available/shinkansen (Prefix) ✓ (More specific)
         ↓
Longest match wins! → available service with specific routing
```

## 🌐 Deep Dive: Cross-Namespace Routing with ReferenceGrant

### The Problem

In our scenario, the HTTPRoute is in `jp-bullet-train-gtw` namespace, but the Services are in `jp-bullet-train-app-prod` namespace. Without a ReferenceGrant, a cross-namespace reference is invalid.

### The Solution: ReferenceGrant

**ReferenceGrant** is a runtime verification mechanism that allows users to assert which cross-namespace object references are permitted.

### How ReferenceGrant Works

```
HTTPRoute (jp-bullet-train-gtw)
         ↓ wants to reference Service in another namespace
    ┌────────────────────────────────────────────────┐
    │ Is there a ReferenceGrant?                     │
    │                                                │
    │ If YES → Reference is ALLOWED                  │
    │ If NO  → Reference is INVALID (DENIED)         │
    └────────────────────────────────────────────────┘
```

### ReferenceGrant Example

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: ReferenceGrant
metadata:
  name: allow-gateway-to-services
  namespace: jp-bullet-train-app-prod          # Service namespace
spec:
  from:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    namespace: jp-bullet-train-gtw             # HTTPRoute namespace
  to:
  - group: ""                                   # Core API group for Services
    kind: Service
```

**Key Points:**
- ReferenceGrant resides in the **target namespace** (where Services live)
- `from` specifies which resources can reference
- `to` specifies what resources can be referenced
- Without a ReferenceGrant, cross-namespace references are invalid

### Security Considerations

| Aspect | Implication |
|--------|-------------|
| **Runtime Verification** | Implementations MUST watch for changes and recalculate validity |
| **Resource Removal** | Removing a grant revokes access |
| **Additive Effect** | Grants stack; they cannot conflict |
| **Namespace Restriction** | Only one namespace allowed per `from` struct |

## 🆚 Gateway API vs Ingress Comparison

| Feature | Ingress | Gateway API |
|---------|---------|-------------|
| **Expressiveness** | Basic routing | Advanced routing (headers, query params, weights) |
| **Role-Oriented** | No | Yes (GatewayClass, Gateway, Route separation) |
| **Protocol Support** | HTTP/HTTPS | HTTP, HTTPS, TCP, UDP, gRPC |
| **Protocol-Agnostic** | No | Yes |
| **Cross-Namespace** | No | Yes (via ReferenceGrant) |
| **Maturity** | GA (stable) | Beta (evolving) |
| **Traffic Splitting** | Vendor-specific | Native support |
| **Configuration** | Annotations | Native CRD fields |

### Why Gateway API is the Future

1. **Richer Model** → Supports traffic splitting, header-based routing
2. **Role Separation** → Infrastructure providers, cluster operators, app developers each manage their own resources
3. **Faster Configuration** → Structured resource model eliminates annotation parsing overhead
4. **Protocol-Agnostic** → Supports HTTP, TCP, gRPC, and more
5. **Cleaner Configuration** → No annotation overload

> **Note:** Ingress isn't disappearing tomorrow, but the direction is clear. The Gateway API offers a path to a more robust, secure, and manageable ingress strategy.

|-------|-----------|----------|
| **Gateway Status not "Programmed"** | Controller not ready | `kubectl get pods -n nginx-gateway` |

| **DNS Not Resolving** | /etc/hosts not updated | `cat /etc/hosts \| grep bullet.train.io` |

## 🚀 Advanced Gateway API Features

### Request Header Manipulation

```yaml
rules:
- matches:
  - path:
      type: PathPrefix
      value: /api
  filters:
  - type: RequestHeaderModifier
    requestHeaderModifier:
      add:
      - name: X-Custom-Header
        value: bullet-train
      remove:
      - X-Unwanted-Header
  backendRefs:
  - name: api-service
    port: 80
```

### Traffic Splitting (Canary Deployments)

```yaml
backendRefs:
- name: available-v1
  port: 80
  weight: 90
- name: available-v2
  port: 80
  weight: 10      # 10% of traffic to new version
```

### Request Redirection

```yaml
rules:
- matches:
  - path:
      type: PathPrefix
      value: /old-api
  filters:
  - type: RequestRedirect
    requestRedirect:
      path:
        type: ReplaceFullPath
        replaceFullPath: /new-api
      statusCode: 301
```

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Separate Gateway and HTTPRoute namespaces** | Platform team manages Gateway; App teams manage HTTPRoutes |
| **Use ReferenceGrants for security** | Explicitly authorize cross-namespace references |
| **Use meaningful names** | Clear naming helps troubleshooting |
| **Implement proper TLS** | Use cert-manager for automatic certificate renewal |
| **Monitor and log** | Enable access logs on Gateway; use metrics for analysis |
| **Test routes before production** | Use header-based routing for testing |
| **Set appropriate path types** | Use PathPrefix or Exact as needed |

### Real-World Use Cases

| Use Case | Description | Gateway API Configuration |
|----------|-------------|---------------------------|
| **Multi-Tenant Applications** | Single Gateway serves multiple teams | Each team manages their own HTTPRoutes |
| **Blue/Green Deployments** | Route based on header | Header-based routing |
| **Canary Releases** | Gradual traffic shifting | Traffic weighting with backendRefs weights |
| **API Versioning** | Different versions under same domain | Path-based routing with `/v1`, `/v2` |
| **Microservices** | Route to different services based on path | Path-based routing |
