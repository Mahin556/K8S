# 🎬 CKA: Gateway API Traffic Mirroring – Anime Streaming Platform

Welcome to this advanced Kubernetes networking challenge!  
You are tasked with configuring **traffic mirroring** (also called *traffic shadowing*) using the Kubernetes Gateway API. This technique allows you to test a new API version ( `api-v2` ) with **real production traffic** without **any impact** on your users – all responses come from the stable version ( `api-v1` ), while the new version receives a copy of each request for validation.

---

## 🧩 Problem Recap

- **Namespace** for the HTTPRoute: `prod`
- **Gateway**: `anime-app-gateway` in namespace `anime-gtw`
- **Host**: `anime.streaming.io` (DNS pre‑configured in `/etc/hosts`)
- **Path**: `/` (prefix match)
- **Primary backend** (handles user requests): `api-v1` (port `80`)
- **Mirror target** (receives copy, responses discarded): `api-v2` (port `80`)
- **HTTPRoute name**: `anime-api-httproute`
- **Manifest location**: `/root/api-route.yaml`

---

## 📄 The Solution – HTTPRoute with RequestMirror Filter

The key to traffic mirroring in the Gateway API is the `filters` section with `type: RequestMirror`.  
This duplicates each incoming request to a secondary backend, while the primary backend continues to serve the real user responses.

### Complete YAML Manifest

Save the following as `/root/api-route.yaml`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: anime-api-httproute
  namespace: prod
spec:
  parentRefs:
  - name: anime-app-gateway
    namespace: anime-gtw
  hostnames:
  - "anime.streaming.io"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: "/"
    backendRefs:
    - name: api-v1
      port: 80
    filters:
    - type: RequestMirror
      requestMirror:
        backendRef:
          name: api-v2
          port: 80
```

### 🔍 Field‑by‑Field Explanation

| Field | Value | Meaning |
|-------|-------|---------|
| `apiVersion` | `gateway.networking.k8s.io/v1` | The stable GA version of Gateway API. |
| `kind` | `HTTPRoute` | The resource that defines routing rules. |
| `metadata.name` | `anime-api-httproute` | A descriptive name for the route. |
| `metadata.namespace` | `prod` | The namespace where the route lives (and where the backends are located). |
| `parentRefs.name` | `anime-app-gateway` | The Gateway to which this route attaches. |
| `parentRefs.namespace` | `anime-gtw` | The Gateway’s namespace (cross‑namespace attachment is allowed). |
| `hostnames` | `["anime.streaming.io"]` | The domain this route responds to. |
| `rules[0].matches[0].path` | `type: PathPrefix, value: "/"` | Matches **all** paths that start with `/` (i.e., every request to the host). |
| `backendRefs[0]` | `name: api-v1, port: 80` | The **primary** backend – all user traffic goes here and responses are returned. |
| `filters[0]` | `type: RequestMirror` | This filter duplicates the request and sends the copy elsewhere. |
| `requestMirror.backendRef` | `name: api-v2, port: 80` | The **mirror** backend – receives a copy of every request, but its response is **ignored**. |

## 🔎 Verification – Confirm Correct Setup

### 1. Check HTTPRoute Status
The route should be `Accepted` by the Gateway controller.

```bash
kubectl describe httproute anime-api-httproute -n prod
```
Look for:
```
Status:
  Parents:
    Conditions:
      Type:    Accepted
      Status:  True
```

### 2. Verify Gateway Status
The Gateway must be ready to serve traffic.

```bash
kubectl get gateway anime-app-gateway -n anime-gtw
```
Ensure `READY` is `True`.

### 3. Test the API Endpoint
Send a request and inspect the response (from `api-v1`).

```bash
curl -s http://anime.streaming.io/ | jq
```
You should see a JSON response produced by `api-v1` – that is the data your users see.

## 📊 Logs Inspection – Proof of Mirroring

The mirror effect can be observed by checking the logs of **both** deployments.

```bash
# Check api-v1 logs (primary – handles every request)
kubectl logs --tail=5 deployment/api-v1 -n prod

# Check api-v2 logs (mirror – receives a copy of each request)
kubectl logs --tail=5 deployment/api-v2 -n prod
```

You will see that **both** deployments log each incoming request, proving that traffic is duplicated.  
The `api-v1` logs show the actual user requests; the `api-v2` logs show the same requests arriving, but their responses never leave the cluster.

> ⚠️ **Important:** The mirror backend’s responses are **discarded** by the Gateway. Users never see them – this is what makes traffic mirroring **completely safe** for production testing.

## 🧠 Concept Deep Dive – Traffic Mirroring

### What is Traffic Mirroring?
Traffic mirroring (also called *shadow traffic*) is a technique where **a copy of live production traffic** is sent to a secondary (test) service **without affecting** the primary service’s responses to users. This allows developers to:

- Validate new versions with **real‑world** traffic patterns.
- Test performance and error handling under **production‑scale** load.
- Identify bugs or regressions **before** any real users are exposed.

### How It Works (Visual Flow)

```
    User Request
         │
         ▼
  [Gateway] – anime-app-gateway
         │
         ▼
  [HTTPRoute] – anime-api-httproute
         │
    ┌────┴────┐
    │         │
Primary   Mirror
Backend   Backend
(api-v1)  (api-v2)
    │         │
    │    (response discarded)
    ▼         ▼
 Response   (ignored)
 sent to
  user ✅
```

### Key Characteristics

| Aspect | Description |
|--------|-------------|
| **User Impact** | **Zero** – users only see responses from the primary backend. |
| **Testing** | Runs in production with **real traffic** – no synthetic data needed. |
| **Risk** | **None** – a misbehaving mirror cannot affect users. |
| **Performance Overhead** | Additional load on the mirror backend and network, but no latency added to user responses. |
| **Rollback** | Simply remove the `RequestMirror` filter – no traffic re‑routing. |

## 🆚 Traffic Mirroring vs. Other Deployment Strategies

| Feature | **Traffic Mirroring** | **Canary Deployment** | **Blue/Green Deployment** |
|---------|------------------------|------------------------|---------------------------|
| **User‑visible changes** | ❌ No – users always see stable version | ✅ Some users (weighted) see new version | ✅ All users see one version at a time (switch) |
| **Risk level** | Zero – mirror cannot affect users | Low – small percentage impacted | Moderate – full switch can be rolled back |
| **Testing with real traffic** | ✅ Yes – 100% traffic mirrored | ⚠️ Partial – only canary % receives real traffic | ❌ No – tested in staging, not in production |
| **Response handling** | Mirror responses are discarded | All responses are sent to users | All responses are sent to users |
| **Rollback method** | Remove mirror filter | Adjust weights (instant) | Switch back to blue (instant) |
| **Use case** | Safe validation of new features, performance testing | Gradual rollout with user‑facing impact | Version upgrades with instant switch |
