## 📌 Scenario Recap
You have two services in the `hawkins` namespace:
- **`stv-v1`** – stable version (receives 90% of traffic)
- **`stv-v2`** – canary version (receives 10% of traffic)

A Gateway `stranger-gw` exists in namespace `str-gtw`.  
You must create an `HTTPRoute` named `stranger-canary-route` in `hawkins` that:
- Attaches to that Gateway via `parentRefs`.
- Matches host `api.stranger.things` and path prefix `/recommendations`.
- Splits traffic with weights: `90` to `stv-v1` and `10` to `stv-v2` (both on port `8080`).

---

## 📄 The HTTPRoute Manifest
Save this as `/root/st-canary.yaml`:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: stranger-canary-route
  namespace: hawkins
spec:
  parentRefs:
  - name: stranger-gw
    namespace: str-gtw
  hostnames:
  - "api.stranger.things"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: "/recommendations"
    backendRefs:
    - name: stv-v1
      port: 8080
      weight: 90
    - name: stv-v2
      port: 8080
      weight: 10
```

---

## 🚀 Apply the Configuration
```bash
kubectl apply -f /root/st-canary.yaml
```

---

## 🔍 Verification – Step by Step

### 1. Check the HTTPRoute status
```bash
kubectl get httproute stranger-canary-route -n hawkins
```
Look for `Accepted` condition in `status`.

### 2. Inspect the weights using `jsonpath`
Extract the backend weights programmatically:
```bash
kubectl get httproute stranger-canary-route -n hawkins -o jsonpath='{.spec.rules[*].backendRefs[*].weight}'
```
Example output: `90 10` (order may vary).  
To see which weight belongs to which service:
```bash
kubectl get httproute stranger-canary-route -n hawkins -o jsonpath='{range .spec.rules[*].backendRefs[*]}{.name}{" "}{.weight}{"\n"}{end}'
```
Expected:
```
stv-v1 90
stv-v2 10
```

### 3. Verify Gateway accepts the route
```bash
kubectl describe gateway stranger-gw -n str-gtw
```
Look for the `Routes` section – it should list `stranger-canary-route` as attached.

### 4. Test with `curl` – manual traffic distribution
Send multiple requests and observe which version responds:
```bash
for i in {1..20}; do curl -s http://api.stranger.things/recommendations | jq -r '.version'; done
```
You should see roughly 90% `v1` and 10% `v2` (the exact split may vary due to randomness).

To get a full JSON response each time:
```bash
curl -s http://api.stranger.things/recommendations | jq
```

### 5. Monitor logs from both deployments (in separate terminals or background)
```bash
kubectl logs -f deployment/stv-v1 -n hawkins &
kubectl logs -f deployment/stv-v2 -n hawkins &
```
As you send traffic, you’ll see logs appearing on each pod proportionally to the traffic weight.

### 6. Count the responses with `jq` (if the response contains a `version` field)
```bash
# Send 100 requests and count how many come from each version
for i in {1..100}; do curl -s http://api.stranger.things/recommendations | jq -r '.version'; done | sort | uniq -c
```
Expected output (approximately):
```
  91 v1
   9 v2
```

## 🧹 Clean Up (optional)
If you need to remove the canary route after testing:
```bash
kubectl delete httproute stranger-canary-route -n hawkins
```

---

## 📊 Explanation of the Canary Strategy
- **90% traffic** goes to the stable `stv-v1` – ensuring minimal risk.
- **10% traffic** goes to the new `stv-v2` – allowing you to monitor for errors or performance issues.
- If `stv-v2` behaves well, you can gradually increase its weight (e.g., to 50%, then 100%) and eventually decommission `v1`.
