# 🧩 Using Kustomize to Generate a ConfigMap and Secret

## 🎯 Objective
We are going to use Kustomize’s `configMapGenerator` and `secretGenerator` to create configuration data from literal key‑value pairs. We will then apply this configuration to a Pod that consumes both the ConfigMap and Secret via `envFrom`. This demonstrates how to keep sensitive and non‑sensitive configuration externalised and version‑controlled without manually writing separate YAML files.

---

## 🛠️ Step 1 – Scaffold the Base Kustomize Directory

First, create the directory structure that will hold our base resources.

```bash
mkdir -p kustomize-configmap-secret/base
```

---

## 📝 Step 2 – Create the Pod Definition

We need a Pod that references a ConfigMap and a Secret by name. We will use `envFrom` to pull all key‑value pairs from both sources into the container’s environment variables.

Inside the `base` directory, create the `pod.yaml` file:

```bash
cat <<'EOF_POD' > kustomize-configmap-secret/base/pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: busybox:1.36
    command: ["sh", "-c", "env && sleep 3600"]
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secret
EOF_POD
```

**What this Pod does:**
- It uses the `busybox:1.36` image.
- It runs `sh -c "env && sleep 3600"` – this prints all environment variables to stdout (useful for verification) and then keeps the container running so we can `exec` into it later.
- The `envFrom` block tells Kubernetes to load *all* keys from the ConfigMap named `app-config` and the Secret named `app-secret` as environment variables.

---

## 📄 Step 3 – Create the Kustomization File with Generators

This is the core of the exercise. We will use `configMapGenerator` and `secretGenerator` to dynamically create the configuration objects.

Create the `kustomization.yaml` file:

```bash
cat <<'EOF_K' > kustomize-configmap-secret/base/kustomization.yaml
resources:
  - pod.yaml
configMapGenerator:
  - name: app-config
    literals:
      - LOG_LEVEL=debug
      - FEATURE_FLAG=true
secretGenerator:
  - name: app-secret
    literals:
      - API_TOKEN=supersecret
      - API_URL=https://api.internal
EOF_K
```

**Theory behind `configMapGenerator` and `secretGenerator`:**
- **Literals**: Kustomize takes the key‑value pairs provided under `literals` and creates a ConfigMap or Secret object from them.
- **Hashing (Important!)**: Kustomize automatically appends a **suffix** (based on a hash of the data) to the names of the generated objects. For example, the ConfigMap name might become `app-config-56d6c9b56b`.
- **Automatic Patch**: Because the Pod references `app-config` (without the hash), Kustomize **patches** the Pod YAML to replace that generic name with the actual generated name (including the hash). This ensures that when the data changes, the hash changes, which forces the Pod to be restarted (if managed by a Deployment) – a best practice for configuration updates!

**About Secret Generation:**
- The `secretGenerator` works the same way as `configMapGenerator`, but Kustomize automatically **base64‑encodes** the literal values for you when creating the Secret object. When the Pod consumes it via `envFrom`, Kubernetes decodes the base64 data back into plaintext environment variables. This is a secure way to inject sensitive data.

---

## 🚀 Step 4 – Apply the Configuration to the Cluster

Now we deploy the rendered resources directly using `kubectl apply -k`. Kustomize will build the final YAML in‑memory and send it to the API server.

```bash
kubectl apply -k kustomize-configmap-secret/base
```

Kustomize will create:
1. The Pod (`app`).
2. The ConfigMap (`app-config-<hash>`).
3. The Secret (`app-secret-<hash>`).

> 💡 **HINT**: You can see the exact YAML that Kustomize generates by running `kubectl kustomize kustomize-configmap-secret/base`.

---

## 🔍 Step 5 – Verify the Pod Receives Both the ConfigMap and Secret

Because the Pod runs `env` on startup, we can `exec` into it and print specific environment variables to confirm they were injected correctly.

```bash
kubectl exec app -- printenv LOG_LEVEL FEATURE_FLAG API_TOKEN API_URL
```

**Expected output:**

```
debug
true
supersecret
https://api.internal
```

If you want to see all environment variables (including Kubernetes default ones like `KUBERNETES_SERVICE_HOST`), you can run:

```bash
kubectl exec app -- env
```

But the `printenv` command above cleanly targets the exact variables we defined.

## 🧠 Important Notes and Best Practices

- **Immutable Configuration**: Because Kustomize renames the generated ConfigMap/Secret with a hash suffix, any change to the `literals` will create a *new* object. If the Pod were part of a Deployment, the Deployment’s Pod template would be updated to point to the new name, triggering a rolling update.
- **`envFrom` Behavior**: Using `envFrom` mounts all keys from the ConfigMap/Secret as environment variables. If a key is invalid (e.g., starts with a digit), Kubernetes will skip it (and log a warning). For production, ensure your keys follow POSIX naming standards.
- **Security**: The `secretGenerator` stores data in the `Secret` resource. In a real cluster, you should enable **encryption at rest** for `Secret` objects via the API server’s `--encryption-provider-config` flag.
- **Alternatives**: Instead of `literals`, you can also use `files` or `envs` to pull configuration from `.properties` files or `.env` files, which is useful for larger configurations.
