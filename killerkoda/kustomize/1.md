## 📌 Understanding `commonLabels` in Kustomize

The `commonLabels` field in a `kustomization.yaml` file allows you to **apply a set of labels to all resources** defined in the `resources` list. This is incredibly useful for:

- **Unified tracking** – every object gets the same environment, team, or application labels.
- **Simplified queries** – you can list all resources belonging to a particular group with a single label selector.
- **Selector consistency** – Kustomize **automatically adds these labels to the `selector` fields** of Deployments, Services, etc., ensuring that the selectors match the labels on the Pods.

---

## 🏗️ Step 1 – Scaffold a Base Directory with a Deployment and a Service

Create the directory structure and the resource files.

```bash
mkdir -p kustomize-common-labels/base
```

**Deployment (`deployment.yaml`):**
```bash
cat <<'EOF_DEP' > kustomize-common-labels/base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api
  template:
    metadata:
      labels:
        app: api
    spec:
      containers:
      - name: api
        image: nginx:1.25
        ports:
        - containerPort: 80
EOF_DEP
```

**Service (`service.yaml`):**
```bash
cat <<'EOF_SVC' > kustomize-common-labels/base/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api
  ports:
  - port: 80
    targetPort: 80
EOF_SVC
```

**Kustomization (`kustomization.yaml`):**
```bash
cat <<'EOF_K' > kustomize-common-labels/base/kustomization.yaml
resources:
  - deployment.yaml
  - service.yaml
commonLabels:
  env: dev
  team: platform
EOF_K
```

> ℹ️ Notice that the `commonLabels` are defined at the top level. Kustomize will add `env: dev` and `team: platform` to **every** resource listed.

---

## 🚀 Step 2 – Apply the Configuration

Run the following command to deploy the resources to your cluster:

```bash
kubectl apply -k kustomize-common-labels/base
```

Kustomize renders the final YAML (combining the base resources with the common labels) and sends it to the API server.

---

## ✅ Step 3 – Verify That All Objects Carry the Shared Labels

Use a label selector to list only the objects that have the `team=platform` label, and display their labels explicitly.

```bash
kubectl get deploy,svc -l team=platform -o custom-columns=KIND:.kind,NAME:.metadata.name,ENV:.metadata.labels.env,TEAM:.metadata.labels.team
```

You should see output similar to:

```
KIND        NAME   ENV   TEAM
Deployment  api    dev   platform
Service     api    dev   platform
```

**What’s happening behind the scenes?**
- Kustomize injected `env: dev` and `team: platform` into the `metadata.labels` of both the Deployment and the Service.
- It also **automatically added these labels to the Deployment’s `spec.selector.matchLabels`** and the Service’s `spec.selector` to ensure they match the Pod’s labels. This is a built‑in safety feature – you don’t have to manually update the selectors.

---

## 🔍 Inspect the Rendered YAML (Optional)

To see the exact YAML Kustomize generates, run:

```bash
kubectl kustomize kustomize-common-labels/base
```

You will notice that the `selector` field in the Deployment now includes:
```yaml
selector:
  matchLabels:
    app: api
    env: dev
    team: platform
```
And the Pod template also gets those labels. The Service’s `selector` will likewise include them. This guarantees that the Service routes traffic to the correct Pods.

---

## 🧠 Important Notes

- **Selector Propagation** – By default, Kustomize adds `commonLabels` to both `metadata.labels` and **selectors** (for Deployment, Service, etc.). This ensures consistency, but if you need to prevent that, you can set `commonLabels: false` or use patches to override.
- **Overrides** – If a resource already defines a label with the same key, Kustomize **overwrites** it with the `commonLabels` value. To avoid surprises, define the base labels without conflicts.
- **Best Practice** – Use `commonLabels` to attach global metadata like environment (`env`), ownership (`team`), or version (`version`) to every object in a Kustomize overlay. This makes it easy to filter and manage resources across a large Kubernetes estate.
