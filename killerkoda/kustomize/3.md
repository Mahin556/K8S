# 🚀 Creating Multiple Kustomize Overlays (Dev & Prod) from a Base Deployment

## 🎯 Objective
We are building a **Kustomize project** with a shared **base** deployment and service, and then creating two **overlays** (`dev` and `prod`) that customise the base for different environments. This demonstrates the power of Kustomize to manage environment‑specific configurations (replicas, images, namespaces, prefixes) without duplicating YAML.

---

## 📁 Step 1 – Understand the Directory Layout

Your final project structure will look like this:

```
my-kustomize-project/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   └── kustomization.yaml
├── overlays/
│   ├── dev/
│   │   ├── kustomization.yaml
│   │   └── patch-deployment.yaml
│   └── prod/
│       ├── kustomization.yaml
│       └── patch-deployment.yaml
```

- **`base/`** – Contains the generic, environment‑agnostic resources.
- **`overlays/dev/`** – Customisations for the development environment.
- **`overlays/prod/`** – Customisations for the production environment.

> 💡 **Why overlays?** – Overlays allow you to maintain a single source of truth (the base) while applying environment‑specific changes. This reduces duplication and makes updates consistent across all environments.

---

## 📄 Step 2 – Create the Base Resources

The base consists of a Deployment and a Service. These are minimal and purposely generic so they can be customised per environment.

### Base Deployment (`base/deployment.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: my-app:latest
        ports:
        - containerPort: 80
```

### Base Service (`base/service.yaml`)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 80
```

### Base Kustomization (`base/kustomization.yaml`)

```yaml
resources:
  - deployment.yaml
  - service.yaml
```

## 🛠️ Step 3 – Create the Dev Overlay

The **dev** overlay will:
- Prefix all resource names with `dev-`.
- Place everything in the `dev` namespace.
- Reduce the replica count (or keep it at 1, but we'll override it anyway).
- Use a development image tag.

### Dev Overlay Kustomization (`overlays/dev/kustomization.yaml`)

```yaml
resources:
  - ../../base

patchesStrategicMerge:
  - patch-deployment.yaml

namePrefix: dev-
namespace: dev
```

**What each field does:**
- `resources: - ../../base` – This tells Kustomize to load the base resources as the starting point.
- `patchesStrategicMerge: - patch-deployment.yaml` – Apply the strategic merge patch to the base Deployment.
- `namePrefix: dev-` – Prefix all resource names with `dev-` (e.g., `my-app` becomes `dev-my-app`).
- `namespace: dev` – Place all resources into the `dev` namespace (the base did not specify a namespace, so this adds it).

### Dev Patch (`overlays/dev/patch-deployment.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 1
  template:
    spec:
      containers:
        - name: my-app
          image: my-app:dev
          env:
            - name: ENV
              value: "development"
```

> ℹ️ **Strategic Merge Patch**: This patch **overlays** changes onto the base Deployment. It matches by `name: my-app` and `kind: Deployment`. It will replace the `replicas`, `image`, and add an `env` array. Since the base Deployment has no `env` defined, Kustomize will add it.

## 🏭 Step 4 – Create the Prod Overlay

The **prod** overlay will:
- Prefix all resource names with `prod-`.
- Place everything in the `prod` namespace.
- Scale up to 3 replicas for high availability.
- Use a production‑tagged image and inject a production environment variable.

### Prod Overlay Kustomization (`overlays/prod/kustomization.yaml`)

```yaml
resources:
  - ../../base

patchesStrategicMerge:
  - patch-deployment.yaml

namePrefix: prod-
namespace: prod
```

### Prod Patch (`overlays/prod/patch-deployment.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: my-app
          image: my-app:prod
          env:
            - name: ENV
              value: "production"
```

---

## 🚀 Step 5 – Apply the Overlays

Now that everything is defined, we can apply each overlay to the cluster.

### Apply the Dev Overlay

```bash
kubectl apply -k overlays/dev/
```

Kustomize will build the final YAML by combining the base with the dev overlay, then apply it to your cluster. The resulting resources will be:
- Deployment: `dev-my-app` in namespace `dev`.
- Service: `dev-my-app` in namespace `dev`.

### Apply the Prod Overlay

```bash
kubectl apply -k overlays/prod/
```

The prod overlay produces:
- Deployment: `prod-my-app` in namespace `prod`.
- Service: `prod-my-app` in namespace `prod`.

> ⚠️ **Important**: The `dev` and `prod` namespaces must exist beforehand. If they don’t, you can create them with:
> ```bash
> kubectl create namespace dev
> kubectl create namespace prod
> ```

## 🔍 Step 6 – Verify the Results

### Check the Dev Deployment

```bash
kubectl get deploy -n dev
kubectl describe deploy dev-my-app -n dev
```

### Check the Prod Deployment

```bash
kubectl get deploy -n prod
kubectl describe deploy prod-my-app -n prod
```

You should see:
- **Dev**: 1 replica, image `my-app:dev`, env `ENV=development`.
- **Prod**: 3 replicas, image `my-app:prod`, env `ENV=production`.

### View the Rendered YAML (without applying)

To see exactly what Kustomize generates for each overlay without actually deploying, run:

```bash
kubectl kustomize overlays/dev/
kubectl kustomize overlays/prod/
```

This is great for debugging and validation before applying to a live cluster.

## 🧠 Key Concepts Explained

| Concept | Description |
| :--- | :--- |
| **Base** | The common, generic YAML that all environments inherit. |
| **Overlay** | A set of customisations applied on top of the base. |
| **Strategic Merge Patch** | A patch that merges fields from the patch file into the base, respecting list merges (by key, like `name` in containers). |
| **`namePrefix`** | Adds a prefix to the metadata.name of every resource defined in the overlay. This prevents name clashes when deploying multiple environments in the same cluster (though we use separate namespaces here). |
| **`namespace`** | Specifies the namespace for all resources in this overlay. If the base doesn’t have a namespace, this adds it. |
| **Environment variables** | Injected via the patch; each environment gets a different `ENV` value. |

---

## 📚 Bonus: DRY Principle in Action

Notice that the base Deployment contains **no** environment variables, **no** namespace, and uses a generic `my-app:latest` image. The overlays add **only the differences**. 

If you need to change the container port or add a new volume, you only update the **base**, and all environments inherit that change automatically. This is the essence of the **Don't Repeat Yourself (DRY)** principle in infrastructure as code.
