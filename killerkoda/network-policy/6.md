## 🏢 Scenario Overview

### Context
You are the **security engineer** for a microservices platform. Application pods in the `restricted` namespace need controlled outbound access to backend services.

### Problem Statement
Create a new **NetworkPolicy** named `allow-egress-or-logic` in the existing namespace `restricted` that meets these requirements:

| Requirement | Details |
|-------------|---------|
| **Destination 1** | Pods with label `app=database` in namespace `data` |
| **Destination 2** | Pods with label `role=cache` in namespace `cache` |
| **OR Logic** | Traffic can go to **either** Destination 1 **OR** Destination 2 |
| **Port** | TCP port `5432` for both destinations |
| **DNS** | Allowed only to `kube-dns` pods in `kube-system` namespace, port `53` (UDP and TCP) |
| **Default** | All other egress traffic is **denied** |

## 🧠 Conceptual Summary

### What is an Egress NetworkPolicy?

An **Egress NetworkPolicy** controls **outbound** traffic from pods. It defines:

- **WHERE** pods can send traffic (destinations)
- **WHAT** ports/protocols they can use
- **WHEN** traffic is allowed or denied

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Egress** | Outbound traffic from pods to external destinations |
| **Ingress** | Inbound traffic to pods from external sources |
| **`podSelector`** | Selects which pods the policy applies to |
| **`to`** | Specifies allowed destinations (similar to `from` for ingress) |
| **`namespaceSelector`** | Selects destinations by namespace labels |
| **`podSelector`** | Selects destinations by pod labels |
| **OR Logic** | Multiple items in a `to` list create OR conditions |
| **DNS Allowlist** | Explicitly allowing DNS resolution for service discovery |

### Why Egress Policies Matter

✅ **Zero-Trust Security** → Only allow necessary outbound connections  
✅ **Prevent Data Exfiltration** → Stop malicious pods from sending data externally  
✅ **Micro-segmentation** → Control east-west and north-south traffic  
✅ **Compliance** → Meet security and audit requirements  
✅ **Reduce Attack Surface** → Limit what pods can access if compromised

## 🏗️ NetworkPolicy Architecture & Flow

### Egress Traffic Flow Diagram

```
Application Pod (restricted namespace)
        ↓
   Outbound Request Initiated
        ↓
   Egress NetworkPolicy Evaluation
        ↓
    ┌───────────────────────────────┐
    │ Does traffic match ANY rule?   │
    └───────────────┬───────────────┘
                    ↓
    ┌───────────────┴───────────────┐
    │                               │
    ▼                               ▼
┌─────────────┐              ┌─────────────┐
│  Rule 1:    │              │  Rule 2:    │
│ Database OR │              │    DNS      │
│   Cache?    │              │             │
└──────┬──────┘              └──────┬──────┘
       ↓                            ↓
┌──────┴──────┐              ┌──────┴──────┐
│  to:        │              │  to:        │
│  - Database │              │  - kube-dns │
│  - Cache    │              └─────────────┘
└──────┬──────┘
       ↓
┌──────┴──────┐
│  ports:     │
│  - TCP 5432 │
└─────────────┘
       ↓
┌───────────────────────────────────────────────┐
│ ALLOW if matches ANY rule, otherwise DENY     │
└───────────────────────────────────────────────┘
```

### Complete NetworkPolicy Structure

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-or-logic
  namespace: restricted
spec:
  podSelector: {}                      # All pods in namespace
  policyTypes:
  - Egress                             # Egress = outbound traffic
  
  egress:
  # Rule 1: Database OR Cache (port 5432)
  - to:
    - namespaceSelector:               # Option 1: Database
        matchLabels:
          name: data
      podSelector:
        matchLabels:
          app: database
    - namespaceSelector:               # Option 2: Cache (OR)
        matchLabels:
          name: cache
      podSelector:
        matchLabels:
          role: cache
    ports:
    - protocol: TCP
      port: 5432
  
  # Rule 2: DNS
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

## 🔍 Deep Dive: Understanding OR Logic

### How OR Logic Works in NetworkPolicies

**Key Concept:** Multiple items in a `to` list create **OR** conditions.

```yaml
to:
- destination1            # Traffic can go here
- destination2            # OR here
- destination3            # OR here
```

This means traffic is allowed if it matches **ANY** of the listed destinations.

### OR Logic Implementation in Our Policy

```yaml
egress:
- to:
  - namespaceSelector:          # Option 1: Database
      matchLabels:
        name: data
    podSelector:
      matchLabels:
        app: database
  - namespaceSelector:          # Option 2: Cache (separate item = OR)
      matchLabels:
        name: cache
    podSelector:
      matchLabels:
        role: cache
  ports:
  - protocol: TCP
    port: 5432
```

### Visual Representation

```
Traffic from Pod
        ↓
┌─────────────────────────────────────────────────────┐
│ Is destination:                                     │
│                                                     │
│   (Option 1) database.data.svc:5432?               │
│        OR                                           │
│   (Option 2) cache.cache.svc:5432?                 │
│                                                     │
│   BOTH use TCP port 5432                           │
└─────────────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────────────┐
│ If YES → ALLOW                                      │
│ If NO → Check next rule (DNS)                       │
└─────────────────────────────────────────────────────┘
```

### Why This Matters

| Without OR Logic | With OR Logic |
|------------------|---------------|
| Need separate rules for each destination | Single rule with multiple destinations |
| More complex to manage | Cleaner, more maintainable |
| Harder to audit | Easy to understand at a glance |

## 📋 NetworkPolicy Structure Breakdown

### Complete YAML with Annotations

```yaml
apiVersion: networking.k8s.io/v1   # API version for NetworkPolicy
kind: NetworkPolicy                 # Resource type
metadata:                           # Metadata section
  name: allow-egress-or-logic      # Policy name
  namespace: restricted             # Namespace where policy applies
spec:                               # Specification
  podSelector: {}                   # Applies to ALL pods in namespace
  
  policyTypes:                      # Types of policies
  - Egress                          # This is an egress policy
  
  egress:                           # Egress rules (outbound)
  
  # ──────────────────────────────────────────────
  # RULE 1: Database OR Cache on port 5432
  # ──────────────────────────────────────────────
  - to:                             # Allowed destinations
    - namespaceSelector:            # Destination Option 1: Database
        matchLabels:
          name: data                # Namespace label: name=data
      podSelector:
        matchLabels:
          app: database             # Pod label: app=database
      
    - namespaceSelector:            # Destination Option 2: Cache (OR)
        matchLabels:
          name: cache               # Namespace label: name=cache
      podSelector:
        matchLabels:
          role: cache               # Pod label: role=cache
    
    ports:                          # Allowed ports
    - protocol: TCP                 # Protocol
      port: 5432                    # Port number
  
  # ──────────────────────────────────────────────
  # RULE 2: DNS to kube-dns on port 53
  # ──────────────────────────────────────────────
  - to:
    - namespaceSelector:            # Destination: kube-system
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns         # Pod label: k8s-app=kube-dns
    
    ports:
    - protocol: UDP                 # UDP for DNS queries
      port: 53
    - protocol: TCP                 # TCP for DNS zone transfers
      port: 53
```

### Component Breakdown Table

| Component | Description | Our Value |
|-----------|-------------|-----------|
| **`apiVersion`** | Kubernetes API version | `networking.k8s.io/v1` |
| **`kind`** | Resource type | `NetworkPolicy` |
| **`metadata.name`** | Policy name | `allow-egress-or-logic` |
| **`metadata.namespace`** | Namespace | `restricted` |
| **`spec.podSelector`** | Which pods this applies to | `{}` (all pods) |
| **`spec.policyTypes`** | Policy direction | `[Egress]` |
| **`spec.egress`** | List of egress rules | Two rules |
| **`spec.egress[].to`** | Allowed destinations | Database OR Cache |
| **`spec.egress[].ports`** | Allowed ports/protocols | TCP 5432 |
| **`spec.egress[].to[].namespaceSelector`** | Namespace labels | `name: data` or `name: cache` |
| **`spec.egress[].to[].podSelector`** | Pod labels | `app: database` or `role: cache` |

## 📊 Ingress vs Egress Comparison

| Aspect | Ingress Policy | Egress Policy |
|--------|----------------|---------------|
| **Direction** | Incoming to pods | Outgoing from pods |
| **Controls** | Who can access me | What I can access |
| **Keyword** | `from` | `to` |
| **Common Use** | Protect services | Prevent data exfiltration |
| **DNS Consideration** | Not needed | Almost always needed |
| **Default without policy** | Allow all | Allow all |
| **Default with policy** | Deny all except rules | Deny all except rules |
| **Example Use Case** | Allow only frontend to access backend | Allow backend only to access database |

### When to Use Egress Policies

✅ **Zero-Trust Architecture** → Only allow necessary outbound connections  
✅ **Prevent Data Exfiltration** → Stop malicious code from sending data externally  
✅ **Micro-segmentation** → Control east-west traffic between services  
✅ **Compliance** → Meet regulatory requirements (PCI-DSS, HIPAA)  
✅ **Audit** → Track and monitor outbound connections  

### Egress Policy Best Practices

| Best Practice | Why |
|---------------|-----|
| **Always allow DNS** | Pods need DNS for service discovery |
| **Use specific ports** | Avoid allowing all ports |
| **Use namespaceSelector** | Group related services together |
| **Use podSelector** | Target specific pods, not all |
| **Test thoroughly** | Verify before applying to production |
| **Document your policies** | Make them understandable to the team |
