## 🎯 Scenario Overview

### Your Mission

Configure a NetworkPolicy with **multi-label pod selection** to implement granular network security for a microservices platform.

### Problem Statement

Create a new NetworkPolicy named `allow-multi-pod-ingress` in the existing namespace `isolated`.

### Requirements

The NetworkPolicy must:

| Requirement | Details |
|-------------|---------|
| **Target Selection** | Select Pods with label `app=api` |
| **Source Condition** | Traffic comes from a Pod that carries **BOTH** labels together: `app=frontend` AND `role=proxy` |
| **Single Label Exclusion** | A Pod with only **one** of the two labels does NOT count |
| **Port Restriction** | Traffic is directed to TCP port `7000` |
| **Deny Conditions** | Traffic to any other port (e.g., 8080) must be denied |
| **Source Exclusion** | Traffic from any Pod that doesn't carry **both** required labels must be denied |

### Scope Note

> **Important:** A NetworkPolicy's `podSelector` decides which Pods the policy applies to — it isn't a namespace-wide lockdown. This policy only governs ingress to Pods labeled `app=api`. Pods without that label sit outside this policy's scope entirely. They are neither protected nor restricted by it.

## 🧠 Conceptual Summary

### What is Multi-Label Pod Selection?

**Multi-label pod selection** means applying multiple label requirements within a single `podSelector`. When you specify multiple labels in a `matchLabels` block, it creates an **AND** condition — the Pod must have **ALL** specified labels.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Single Selector, Multiple Labels** | A `podSelector` with multiple `matchLabels` creates an AND condition |
| **AND Logic** | The source Pod must have ALL specified labels |
| **Target Selector** | Selects which Pods the policy applies to |
| **Source Selector** | Selects which Pods can send traffic |
| **OR vs AND** | Multiple `podSelector` entries = OR; Multiple labels inside a `podSelector` = AND |

### Why Multi-Label Selection Matters

✅ **Granular Security** → Fine-grained access control  
✅ **Zero-Trust Networking** → Only allow traffic from specific, fully-labeled sources  
✅ **Defense in Depth** → Multiple conditions must be met  
✅ **Prevent Lateral Movement** → Require all required labels for access

## 🔍 Multi-Label Selection: Understanding AND Logic

### The Core Concept

When you specify multiple labels in a `matchLabels` block, it creates an **AND** condition:

```yaml
podSelector:
  matchLabels:
    app: frontend           # Label 1
    role: proxy             # Label 2 (Both required!)
```

This means the Pod must have **BOTH** labels:
- ✅ `app=frontend` **AND** `role=proxy` → **Valid**
- ❌ `app=frontend` only → **Invalid**
- ❌ `role=proxy` only → **Invalid**
- ❌ Neither label → **Invalid**

| Multiple `podSelector` entries | **OR** logic | Matches if ANY podSelector matches |

## 📋 Step-by-Step Solution

### Step 1: Understand the Requirements

We need to create a NetworkPolicy that:

1. ✅ **Target Selection**: Selects Pods with label `app=api`
2. ✅ **Source Condition**: Allows ingress ONLY from Pods with BOTH labels: `app=frontend` AND `role=proxy`
3. ✅ **Single Selector, Multiple Labels**: A single `podSelector` with both labels = AND logic
4. ✅ **Port Restriction**: Allows traffic ONLY to TCP port `7000`
5. ✅ **Default Deny**: Denies all other ingress traffic to `app=api` pods

**Scope Note:** This policy is scoped to ingress on `app=api` pods only. It does NOT restrict traffic between other pods in the namespace.

### Step 2: Create the NetworkPolicy

**Why use `kubectl apply` over `kubectl create`?**
- `kubectl apply` is **idempotent** — it won't error out if re-run after an earlier attempt
- `kubectl create` will fail with "AlreadyExists" if the object is already there

```bash
cat > networkpolicy.yaml <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-multi-pod-ingress
  namespace: isolated
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
          role: proxy
    ports:
    - protocol: TCP
      port: 7000
EOF

kubectl apply -f networkpolicy.yaml
```

**Expected Output:**
```
networkpolicy.networking.k8s.io/allow-multi-pod-ingress created
```

### Step 3: Verify the NetworkPolicy

```bash
# Check NetworkPolicy exists
kubectl get networkpolicy -n isolated

# View NetworkPolicy details
kubectl describe networkpolicy allow-multi-pod-ingress -n isolated

# View YAML
kubectl get networkpolicy allow-multi-pod-ingress -n isolated -o yaml
```

**Expected Output:**
```
NAME                        POD-SELECTOR   AGE
allow-multi-pod-ingress     app=api        10s
```

## 🔍 Deep Dive: Understanding the Configuration

### Complete YAML Breakdown

```yaml
apiVersion: networking.k8s.io/v1
# ↑ API group and version for NetworkPolicy

kind: NetworkPolicy
# ↑ Resource type

metadata:
  name: allow-multi-pod-ingress
  # ↑ Name of the NetworkPolicy object

  namespace: isolated
  # ↑ Namespace where this policy is applied

spec:
  # ↑ Specification of the NetworkPolicy

  podSelector:
    matchLabels:
      app: api
  # ↑ Selects which pods this policy applies to
  # Only Pods with label app=api are protected

  policyTypes:
  - Ingress
  # ↑ Specifies the type of traffic this policy controls
  # Ingress: Incoming traffic to the selected pods

  ingress:
  # ↑ List of ingress rules

  - from:
    # ↑ Sources that are allowed to send traffic

    - podSelector:
        matchLabels:
          app: frontend
          role: proxy
        # ↑ Source must have BOTH labels:
        #   app=frontend AND role=proxy
        # This is AND logic (not two separate selectors)

    ports:
    # ↑ Ports that are allowed

    - protocol: TCP
      port: 7000
      # ↑ Only allow traffic on TCP port 7000
```

### Key Fields Explained

| Field | Description | Our Value |
|-------|-------------|-----------|
| **`podSelector` (target)** | Selects which Pods the policy applies to | `app=api` |
| **`policyTypes`** | Direction of traffic control | `[Ingress]` (incoming traffic) |
| **`ingress[].from`** | Sources allowed to send traffic | Pods with BOTH labels |
| **`podSelector` (source)** | Selects source Pods by labels | `app=frontend`, `role=proxy` |
| **`ports`** | Allowed ports and protocols | TCP port `7000` |

### How the AND Logic Works

```yaml
ingress:
- from:
  - podSelector:
      matchLabels:
        app: frontend    # Condition 1
        role: proxy      # Condition 2 (AND with Condition 1)
```

This means:
- ✅ Source must have `app=frontend` **AND** `role=proxy`
- ❌ Source with `app=frontend` only → **DENIED**
- ❌ Source with `role=proxy` only → **DENIED**
- ❌ Source with neither label → **DENIED**

## 🧪 Verification & Testing

### Test Setup

Each test uses `curl` to check connectivity:
- HTTP 200+ → Connection successful (ALLOWED)
- Connection refused/timeout → Connection blocked (DENIED)

### Test 1: ✅ frontend-proxy-pod → api-pod:7000 (Should SUCCEED)

```bash
echo "Test 1: frontend-proxy-pod to api-pod:7000 (should SUCCEED)"
kubectl exec -n isolated frontend-proxy-pod -- curl -s --max-time 3 -o /dev/null -w "%{http_code}\n" api-pod:7000 \
  && echo "✅ ALLOWED" || echo "❌ BLOCKED (unexpected)"
```

**Expected:** ✅ ALLOWED (HTTP 200 or higher)

**Why it works:**
- Source Pod has BOTH labels: `app=frontend` ✅ AND `role=proxy` ✅
- Target Port: 7000 ✅

### Test 2: ❌ frontend-only-pod → api-pod:7000 (Should FAIL)

```bash
echo "Test 2: frontend-only-pod to api-pod:7000 (should FAIL)"
kubectl exec -n isolated frontend-only-pod -- curl -s --max-time 3 -o /dev/null -w "%{http_code}\n" api-pod:7000 \
  && echo "✅ ALLOWED (unexpected)" || echo "❌ BLOCKED"
```

**Expected:** ❌ BLOCKED

**Why it fails:**
- Source Pod has ONLY: `app=frontend` ✅ but missing `role=proxy` ❌
- Multi-label AND logic fails

### Test 3: ❌ database-pod → api-pod:7000 (Should FAIL)

```bash
echo "Test 3: database-pod to api-pod:7000 (should FAIL)"
kubectl exec -n isolated database-pod -- curl -s --max-time 3 -o /dev/null -w "%{http_code}\n" api-pod:7000 \
  && echo "✅ ALLOWED (unexpected)" || echo "❌ BLOCKED"
```

**Expected:** ❌ BLOCKED

**Why it fails:**
- Source Pod has NEITHER required label
- `app=database` ❌, `role=proxy` missing ❌

### Test 4: ❌ frontend-proxy-pod → api-pod-alt:8080 (Should FAIL)

```bash
echo "Test 4: frontend-proxy-pod to api-pod-alt:8080 (should FAIL)"
kubectl exec -n isolated frontend-proxy-pod -- curl -s --max-time 3 -o /dev/null -w "%{http_code}\n" api-pod-alt:8080 \
  && echo "✅ ALLOWED (unexpected)" || echo "❌ BLOCKED"
```

**Expected:** ❌ BLOCKED

**Why it fails:**
- Source Pod has BOTH labels ✅
- Target Port: 8080 ❌ (Policy only allows 7000)

## 🔍 Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Policy not applying** | Check CNI support | `kubectl get pods -n kube-system \| grep -E "calico\|flannel\|weave\|cilium"` |
| **frontend-proxy can't access api** | Check source pod labels | `kubectl describe pod frontend-proxy-pod -n isolated` |
| **frontend-only can access api** | Policy not applied correctly | `kubectl get networkpolicy -n isolated` |
| **Connection timeout** | NetworkPolicy blocking traffic | `kubectl describe networkpolicy allow-multi-pod-ingress -n isolated` |
| **Wrong AND logic** | Multiple podSelectors vs multiple labels | Single `podSelector` with multiple `matchLabels` = AND |
| **Wrong port allowed** | Check port definition | Policy only allows TCP 7000 |

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Use single podSelector with multiple labels for AND logic** | Ensures ALL required labels are present |
| **Be explicit about label requirements** | Clear documentation of security requirements |
| **Test with both valid and invalid source pods** | Verify policy works as intended |
| **Use meaningful labels** | Labels should reflect role and responsibility |
| **Regularly audit labels** | Ensure labels are consistent across pods |
| **Start with restrictive policies** | Deny all, then allow specifically |

### Real-World Use Cases

| Use Case | Description | Policy Configuration |
|----------|-------------|---------------------|
| **API Gateway** | Only API gateway can access backend services | Source requires both `app=gateway` and `role=api` |
| **Database Access** | Only specific service can access database | Source requires both `app=backend` and `role=db-access` |
| **Admin Access** | Only admin pods can access management endpoints | Source requires both `app=admin` and `role=management` |
| **Service Mesh** | Only services with specific labels can communicate | Multi-label selectors for microservices |

### Advanced Examples

#### Example 1: Multiple Label Requirements with Namespace

```yaml
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: internal
    podSelector:
      matchLabels:
        app: frontend
        role: proxy
  ports:
  - protocol: TCP
    port: 7000
```

#### Example 2: Multiple Source Selectors (OR Logic)

```yaml
ingress:
- from:
  - podSelector:
      matchLabels:
        app: frontend
        role: proxy
  - podSelector:
      matchLabels:
        app: backend
        role: api
  ports:
  - protocol: TCP
    port: 7000
```

#### Example 3: Deny Explicitly (Using NotIn)

```yaml
ingress:
- from:
  - podSelector:
      matchExpressions:
      - key: app
        operator: NotIn
        values:
        - untrusted
  ports:
  - protocol: TCP
    port: 7000
```
