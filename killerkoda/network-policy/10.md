## 🔒 CKA: Implement Network Security with NetworkPolicy – Complete Solution

This challenge requires creating a **NetworkPolicy** that restricts egress traffic from `app=backend` pods in the `project-snake` namespace. The policy must allow connections **only** to `db1` pods on port `1111` and `db2` pods on port `2222`. All other egress traffic (including to `vault` pods on port `3333`) must be blocked.

We'll walk through the full process – from initial investigation to final verification.

---

### 📌 Step 1 – Understand the Current Setup

First, inspect the pods and their labels in the `project-snake` namespace.

```bash
# List pods with labels
kubectl get pods -n project-snake --show-labels
```

Example output:
```
NAME         READY   STATUS    RESTARTS   AGE   LABELS
backend-0    1/1     Running   0          10m   app=backend
db1-0        1/1     Running   0          10m   app=db1
db2-0        1/1     Running   0          10m   app=db2
vault-0      1/1     Running   0          10m   app=vault
```

Get their IP addresses for testing:

```bash
kubectl get pods -n project-snake -o wide
```

---

### 🧪 Step 2 – Test Connectivity Before the Policy

Record the IPs of the different pods for later testing.

```bash
DB1_IP=$(kubectl get pod -n project-snake -l app=db1 -o jsonpath='{.items[0].status.podIP}')
DB2_IP=$(kubectl get pod -n project-snake -l app=db2 -o jsonpath='{.items[0].status.podIP}')
VAULT_IP=$(kubectl get pod -n project-snake -l app=vault -o jsonpath='{.items[0].status.podIP}')
```

Now, from a `backend` pod, test connectivity to each service (all should succeed initially because no policy is in place):

```bash
# Should work
kubectl -n project-snake exec backend-0 -- curl -m 2 $DB1_IP:1111
kubectl -n project-snake exec backend-0 -- curl -m 2 $DB2_IP:2222
kubectl -n project-snake exec backend-0 -- curl -m 2 $VAULT_IP:3333
```

All commands return a successful HTTP response (e.g., Nginx welcome page). This confirms that unrestricted egress exists.

---

### 📄 Step 3 – Create the NetworkPolicy Manifest

Create a YAML file named `np-backend.yaml` with the following content:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: np-backend
  namespace: project-snake
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
  - Egress
  egress:
  - to:
    - podSelector:
        matchLabels:
          app: db1
    ports:
    - protocol: TCP
      port: 1111
  - to:
    - podSelector:
        matchLabels:
          app: db2
    ports:
    - protocol: TCP
      port: 2222
```

**Explanation of each field:**

| Field | Value | Meaning |
|-------|-------|---------|
| `podSelector.matchLabels` | `app: backend` | The policy applies **only** to pods with this label. |
| `policyTypes` | `[Egress]` | We are restricting **outbound** traffic only. (Ingress is not restricted.) |
| `egress[0].to.podSelector` | `app: db1` | Allow connections to pods with label `app=db1`. |
| `egress[0].ports` | `port: 1111, protocol: TCP` | Only TCP port 1111 is allowed. |
| `egress[1]` | Similar for `app=db2` and port `2222`. |  |
| No egress rule for `vault` | → All traffic to `vault` pods (on any port) is **denied** by default. |  |

**Important:**  
- The policy is **namespace‑scoped** – it only affects pods in `project-snake`.  
- Because we did not specify any `namespaceSelector`, the rule only matches pods within the **same namespace**.  
- Traffic to the cluster’s DNS (kube‑dns) or other services is also blocked unless explicitly allowed; here we use IP‑based connections, so no DNS is needed.

---

### 🚀 Step 4 – Apply the NetworkPolicy

```bash
kubectl apply -f np-backend.yaml
```

Verify it was created:

```bash
kubectl get networkpolicy -n project-snake
```

Expected output:
```
NAME         POD-SELECTOR   AGE
np-backend   app=backend    5s
```

To see the detailed rules:

```bash
kubectl describe networkpolicy np-backend -n project-snake
```

---

### 🔍 Step 5 – Test Connectivity After the Policy

Now re‑run the same `curl` commands from the `backend` pod:

```bash
# These should still work
kubectl -n project-snake exec backend-0 -- curl -m 2 $DB1_IP:1111
kubectl -n project-snake exec backend-0 -- curl -m 2 $DB2_IP:2222

# This should now time out or fail
kubectl -n project-snake exec backend-0 -- curl -m 2 $VAULT_IP:3333
```

Expected results:

- ✅ Connection to `db1:1111` → succeeds (returns HTTP 200).
- ✅ Connection to `db2:2222` → succeeds.
- ❌ Connection to `vault:3333` → times out (`curl: (28) Connection timed out` or similar error).  
  This confirms the egress rule blocks traffic to `vault` pods.

---

### 🧹 Optional – Clean Up

If you want to remove the policy after testing:

```bash
kubectl delete networkpolicy np-backend -n project-snake
```

---

### 📊 Summary of the Security Improvement

| Before Policy | After Policy |
|---------------|--------------|
| `backend` could reach any pod on any port. | `backend` can **only** reach `db1:1111` and `db2:2222`. |
| Unrestricted egress allowed lateral movement. | Strict egress control prevents access to sensitive pods like `vault`. |

### 🧠 Key Takeaways for the CKA Exam

- **`podSelector`** defines which pods the policy applies to.
- **`policyTypes`** must include `Egress` to restrict outgoing traffic.
- Each **`egress`** rule contains a **`to`** (destination) and **`ports`** (optional).
- If you omit the `ports` section, all ports are allowed for that destination.
- Namespace‑scoped by default – use `namespaceSelector` for cross‑namespace rules.
- The policy is **deny‑by‑default** for egress traffic that is not explicitly allowed.
- **Testing with `curl` and Pod IPs** is a reliable way to verify the policy.
