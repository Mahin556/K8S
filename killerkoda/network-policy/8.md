## 🎯 Scenario Overview

### Your Mission

Configure a NetworkPolicy to allow traffic to the `fubar` namespace **only** from the `internal` namespace on specific ports, blocking all other access.

### Problem Statement

Create a new NetworkPolicy named `allow-port-from-namespace` in the existing namespace `fubar`.

The NetworkPolicy should allow incoming traffic to Pods in namespace `fubar` **only if all of the following conditions are met**:

| Condition | Requirement |
|-----------|-------------|
| **Source** | Traffic originates from Pods in the namespace `internal` |
| **Port** | Traffic is directed to TCP port `9000` |
| **Deny Conditions** | Pods that do not listen on port `9000` must not be accessible |
| **Namespace Restriction** | Pods from namespaces other than `internal` must not be allowed access |

## 🧠 Conceptual Summary

### What is a NetworkPolicy?

A **NetworkPolicy** is a Kubernetes resource that controls traffic flow to and from Pods. It acts as a **firewall** for your Pods, defining what traffic is allowed or denied.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Ingress** | Incoming traffic to Pods |
| **Egress** | Outgoing traffic from Pods |
| **podSelector** | Selects which Pods the policy applies to |
| **namespaceSelector** | Selects which Namespaces traffic can come from/go to |
| **Default Deny** | When a policy is applied, all traffic not explicitly allowed is denied |
| **PolicyTypes** | Specifies whether the policy controls Ingress, Egress, or both |

### Why Namespace Isolation Matters

✅ **Zero-Trust Security** → Only allow necessary access  
✅ **Multi-Tenancy** → Isolate tenant workloads  
✅ **Compliance** → Meet security and audit requirements  
✅ **Reduce Attack Surface** → Limit what can access sensitive services  
✅ **Defense in Depth** → Multiple layers of security

## 📋 Step-by-Step Solution

### Step 1: Create the NetworkPolicy YAML

```bash
cat > allow-port-from-namespace.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  # Name of the NetworkPolicy object
  name: allow-port-from-namespace

  # Namespace where this policy is applied
  namespace: fubar

spec:
  # Selects which pods this policy applies to.
  # An empty selector {} means "all pods in the namespace"
  podSelector: {}

  # Specifies the type of traffic this policy controls.
  # Ingress means incoming traffic to the selected pods
  policyTypes:
  - Ingress

  ingress:
  - from:
      # Allow traffic only from pods in namespaces
      # that match this label selector
    - namespaceSelector:
        matchLabels:
          # This matches namespaces labeled with:
          # kubernetes.io/metadata.name=internal
          kubernetes.io/metadata.name: internal

    ports:
      # Only allow traffic on TCP port 9000
    - protocol: TCP
      port: 9000
EOF
```

### Step 2: Apply the NetworkPolicy

```bash
kubectl apply -f allow-port-from-namespace.yaml
```

**Expected Output:**
```
networkpolicy.networking.k8s.io/allow-port-from-namespace created
```

### Step 3: Verify the NetworkPolicy

```bash
# Check NetworkPolicy exists
kubectl get networkpolicy -n fubar

# View NetworkPolicy details
kubectl describe networkpolicy allow-port-from-namespace -n fubar

# View YAML

```

**Expected Output:**

## 🔍 Deep Dive: Understanding the Configuration

### Complete YAML Breakdown

```yaml
apiVersion: networking.k8s.io/v1
# ↑ API group and version for NetworkPolicy

kind: NetworkPolicy
# ↑ Resource type

metadata:
  name: allow-port-from-namespace
  # ↑ Name of the NetworkPolicy object

  namespace: fubar
  # ↑ Namespace where this policy is applied

spec:
  # ↑ Specification of the NetworkPolicy

  podSelector: {}
  # ↑ Selects which pods this policy applies to
  # An empty selector {} means "all pods in the namespace"
  # You can also use specific selectors like:
  # matchLabels:
  #   app: web

  policyTypes:
  - Ingress
  # ↑ Specifies the type of traffic this policy controls
  # - Ingress: Incoming traffic to the selected pods
  # - Egress: Outgoing traffic from the selected pods
  # - Both: Both Ingress and Egress

  ingress:
  # ↑ List of ingress rules

  - from:
    # ↑ Sources that are allowed to send traffic

    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: internal
        # ↑ Allow traffic only from pods in namespaces
        # that match this label selector
        # This matches the namespace labeled with:
        # kubernetes.io/metadata.name=internal

    ports:
    # ↑ Ports that are allowed

    - protocol: TCP
      port: 9000
      # ↑ Only allow traffic on TCP port 9000
```

### Key Fields Explained

| Field | Description | Our Value |
|-------|-------------|-----------|
| **`podSelector`** | Selects which pods the policy applies to | `{}` (all pods in namespace) |
| **`policyTypes`** | Direction of traffic control | `[Ingress]` (incoming traffic) |
| **`ingress[].from`** | Sources allowed to send traffic | Pods from `internal` namespace |
| **`namespaceSelector`** | Selects namespaces by labels | `kubernetes.io/metadata.name: internal` |
| **`ports`** | Allowed ports and protocols | TCP port `9000` |

### How the Policy Works

1. **Apply to Pods**: The policy applies to ALL pods in the `fubar` namespace (`podSelector: {}`).

2. **Check Source**: When traffic arrives, it checks if the source pod is in a namespace labeled `kubernetes.io/metadata.name: internal`.

3. **Check Port**: If the source is from `internal`, it checks if the traffic is on TCP port `9000`.

4. **Allow or Deny**:
   - ✅ **ALLOW** if: Source = `internal` AND Port = `9000`
   - ❌ **DENY** if: Source ≠ `internal` OR Port ≠ `9000`

5. **Default Deny**: All traffic not matching the rule is blocked.

## 🔒 Security Rules Enforced

This NetworkPolicy guarantees that:

| Rule | Status | Explanation |
|------|--------|-------------|
| ✅ Only Pods from the internal namespace can send traffic | Enforced | `namespaceSelector` matches only `internal` |
| ✅ Only TCP port 9000 is accessible | Enforced | `ports` section specifies `TCP` and `9000` |
| ❌ Pods in fubar not listening on port 9000 remain unreachable | Enforced | Policy only allows port 9000 |
| ❌ Pods from any other namespace are completely blocked | Enforced | `namespaceSelector` is restrictive |
| 🔐 All other ingress traffic is implicitly denied | Enforced | Default deny behavior of NetworkPolicy |

## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Policy not applying** | Check namespace and labels | `kubectl get ns --show-labels` |
| **internal cannot access app-9000** | Check service/pod labels | `kubectl get pods -n fubar --show-labels` |
| **external can access app-9000** | Policy not applied correctly | Check `kubectl get networkpolicy -n fubar` |
| **Connection timeout** | NetworkPolicy blocking traffic | Check policy details: `kubectl describe networkpolicy -n fubar` |
| **Policy not found** | Wrong namespace | Ensure policy is in `fubar` namespace |
| **Service unavailable** | Pod not running | `kubectl get pods -n fubar` |
| **Wrong label selector** | Namespace label mismatch | Check labels: `kubectl get ns internal -o yaml` |

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Start with default deny** | Begin with a restrictive policy, then add allow rules |
| **Use namespaceSelector** | Group related services together |
| **Use specific ports** | Avoid allowing all ports |
| **Test thoroughly** | Verify before applying to production |
| **Document your policies** | Make them understandable to the team |
| **Monitor and audit** | Track policy violations |
| **Use network policy tools** | Tools like Cilium, Calico for advanced policies |

### Real-World Use Cases

| Use Case | Description | Policy Configuration |
|----------|-------------|---------------------|
| **Database Access** | Only application tier can access database | Ingress from app namespace to DB namespace on DB port |
| **API Gateway** | Only API gateway can access backend services | Ingress from gateway namespace to backend namespace |
| **Multi-Tenancy** | Isolate tenant namespaces | Each tenant has its own NetworkPolicy |
| **Microservices** | Control service-to-service communication | Granular ingress/egress policies |
| **Compliance** | Meet PCI-DSS, HIPAA requirements | Strict NetworkPolicies with logging |
