This is one of the most misread YAML traps in Kubernetes — a single dash vs two dashes changes your entire security posture. Let me make it completely clear.

## The YAML structure is everything

```yaml
# AND — one list item, two selectors inside it
from:
- namespaceSelector:    # ← one dash (one item)
    matchLabels:
      name: frontend
  podSelector:          # ← no dash, same item, BOTH must match
    matchLabels:
      app: frontend
```

```yaml
# OR — two list items, each with one selector
from:
- namespaceSelector:    # ← dash (item 1)
    matchLabels:
      name: frontend
- podSelector:          # ← dash (item 2), evaluated independently
    matchLabels:
      app: frontend
```

The YAML list item (`-`) is the boundary. Everything under one `-` is evaluated together as AND. Each new `-` creates an independent rule evaluated as OR.

## Why this matters for security — a real attack scenario

```
Your cluster has:
  - namespace: frontend (trusted)
  - namespace: compromised (attacker gained access)

Attacker's pod in "compromised" namespace has label: app=frontend
```

```yaml
# OR version — attacker gets through:
from:
- namespaceSelector:
    matchLabels:
      name: frontend       # rule 1: is it in frontend namespace?
- podSelector:
    matchLabels:
      app: frontend        # rule 2: does it have app=frontend label?

# Attacker's pod in "compromised" namespace with label app=frontend:
# Rule 1: namespace=compromised → NO
# Rule 2: app=frontend → YES ← attacker wins on rule 2
```

```yaml
# AND version — attacker is blocked:
from:
- namespaceSelector:
    matchLabels:
      name: frontend
  podSelector:
    matchLabels:
      app: frontend

# Attacker's pod in "compromised" namespace with label app=frontend:
# Must satisfy BOTH: namespace=frontend AND app=frontend
# namespace check fails → BLOCKED ✓
```

## Visual breakdown of the indentation

```
from:                          from:
- namespaceSelector:           - namespaceSelector:
    matchLabels:                   matchLabels:
      name: frontend                 name: frontend
  podSelector:               - podSelector:
    matchLabels:                   matchLabels:
      app: frontend                  app: frontend

  ↑ same dash = same item       ↑ two dashes = two items
  = AND                         = OR
```

## The `podSelector` alone (OR version) has a subtle extra trap

```yaml
from:
- podSelector:
    matchLabels:
      app: frontend
```

When `podSelector` appears alone without `namespaceSelector`, it matches pods with that label **in ALL namespaces** — including namespaces you never intended to allow. This surprises people because they assume it only matches pods in the same namespace as the NetworkPolicy. It does not.

```
podSelector alone matches:
  ✅ frontend/pod with app=frontend
  ✅ default/pod with app=frontend       ← probably not intended
  ✅ compromised/pod with app=frontend   ← definitely not intended
```

## How to verify what you actually deployed

```bash
# Always verify after applying a NetworkPolicy:
kubectl get networkpolicy <name> -n <namespace> -o yaml

# The from section will show you exactly what was parsed:
# One item under from = AND
# Multiple items under from = OR

# Test connectivity to confirm:
# From an allowed pod:
kubectl exec -it allowed-pod -- curl http://target-service

# From a pod that should be blocked:
kubectl exec -it blocked-pod -- curl --connect-timeout 3 http://target-service
# Should hang/timeout if NetworkPolicy is working correctly
```

## Complete correct example for most real use cases

The AND version is almost always what you want when protecting a service — you want to trust both the namespace AND the specific pod label:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-only
  namespace: backend        # policy lives in backend namespace
spec:
  podSelector:
    matchLabels:
      app: backend          # applies to backend pods
  ingress:
  - from:
    - namespaceSelector:    # AND: must be in frontend namespace
        matchLabels:
          name: frontend
      podSelector:          # AND: must have this label
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

This allows only pods that satisfy **both** conditions simultaneously — sitting in the `frontend` namespace **and** carrying the `app: frontend` label. A pod in `frontend` namespace without that label is blocked. A pod with that label in a different namespace is blocked. Only the intersection gets through.
