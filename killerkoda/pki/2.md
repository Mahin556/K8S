Great question — let me explain exactly what happens at the kernel/TLS/process level when that key disappears.

## What the API Server TLS Key Actually Does

First, understand what `apiserver.key` is:

```
/etc/kubernetes/pki/
├── apiserver.key          ← RSA/ECDSA PRIVATE key (this is what you hid)
├── apiserver.crt          ← Public certificate (signed by CA)
├── ca.crt                 ← Cluster Certificate Authority
└── ca.key                 ← CA private key
```

The private key and certificate work as a **mathematically linked pair**:

```
Private key (apiserver.key)     Public certificate (apiserver.crt)
        │                                    │
        │  Generated together                │
        │  by: kubeadm init                  │
        │                                    │
        └──── mathematically linked ─────────┘
              RSA: pub = priv^e mod n
              ECDSA: pub = priv × G (elliptic curve point)

You CANNOT use one without the other.
The certificate is useless without its private key.
The private key is useless without its certificate.
```

## The TLS Handshake — What Happens BTS

Every single connection to the API server goes through a TLS handshake. Here is the **exact sequence**:

```
Client (kubectl/kubelet/scheduler)       API Server
         │                                    │
         │ ── ClientHello ──────────────────► │
         │    "I support TLS 1.3"             │
         │    "Here are my cipher suites"     │
         │                                    │
         │ ◄── ServerHello ─────────────────  │
         │     "Let's use TLS_AES_256_GCM"    │
         │                                    │
         │ ◄── Certificate ─────────────────  │
         │     (apiserver.crt sent to client) │
         │                                    │
         │ ◄── CertificateVerify ───────────  │
         │     PROOF that server owns the key │
         │     = digital signature using      │
         │       apiserver.key PRIVATE KEY    │
         │     ← THIS IS WHERE IT FAILS       │
         │       if key is missing            │
         │                                    │
         │ ◄── Finished ────────────────────  │
         │                                    │
         ▼                                    ▼
         (encrypted session begins)
```

The `CertificateVerify` step is where the server **digitally signs a hash** of the handshake using its private key:

```
signature = Sign(SHA256(handshake_messages), apiserver.key)
```

The client then verifies:
```
Verify(signature, apiserver.crt.public_key) == true?
```

**Without `apiserver.key`, the API server cannot produce this signature.**
It cannot prove it owns the certificate. TLS handshake fails before any data is exchanged.

## What Happens at the Go Process Level

The API server is written in Go. It loads the TLS config at startup:

```go
// Simplified from k8s.io/apiserver source:
func (s *SecureServingOptions) ApplyTo(config **server.SecureServingInfo) error {
    tlsCert, err := tls.LoadX509KeyPair(
        s.ServerCert.CertKey.CertFile,   // apiserver.crt
        s.ServerCert.CertKey.KeyFile,    // apiserver.key  ← READ HERE
    )
    if err != nil {
        return fmt.Errorf("failed to load TLS cert/key: %v", err)
        // ↑ This error fires when key is missing
        // Process exits here with non-zero exit code
    }
    // ...
}
```

```
What Go's tls.LoadX509KeyPair does when key is missing:

1. Open apiserver.crt → succeeds (file exists)
2. Open apiserver.key → FAILS (file not found)
3. Returns: "open /etc/kubernetes/pki/apiserver.key: no such file or directory"
4. API server main() receives this error
5. Calls os.Exit(1)
6. Process dies immediately
```

This happens **before the API server even binds to port 6443**. It never listens for any connection.

## Why Everything Else Breaks

When the API server dies, the entire Kubernetes control plane loses its brain:

```
API Server DOWN
       │
       ├── kubectl get nodes  → connection refused (port 6443 not listening)
       │
       ├── kube-scheduler     → cannot watch /api/v1/pods
       │   "lost connection to API server, retrying..."
       │
       ├── kube-controller-manager → cannot reconcile anything
       │   "waiting for API server..."
       │
       ├── kubelet on all nodes → cannot report node status
       │   "Failed to update node status: Post https://api:6443: dial tcp..."
       │
       ├── CoreDNS pods → cannot get endpoint updates
       │
       └── etcd → still running (it doesn't talk to API server directly)
            but it's useless — no one can read/write it
```

However **running workloads keep running** — existing pods on worker nodes stay alive because kubelet manages them locally. The API server dying doesn't kill running containers. You just can't make any changes or even see what's there.

## Why Restoring the Key Fixes It Instantly

```
sudo mv /etc/kubernetes/pki/apiserver.key.bak /etc/kubernetes/pki/apiserver.key
           │
           ▼
kubelet's file watcher (inotify) detects manifest change
           │  (or existing restart loop timer fires)
           ▼
containerd starts kube-apiserver again
           │
           ▼
tls.LoadX509KeyPair(cert, key) → SUCCESS this time
           │
           ▼
API server binds to 0.0.0.0:6443
           │
           ▼
TLS handshake can now complete:
  - private key is loaded in memory
  - CertificateVerify signature can be produced
  - clients can verify the server's identity
           │
           ▼
kube-scheduler, controller-manager, kubelets reconnect
           │
           ▼
kubectl get nodes → works again
```

## One-line BTS summary per component

| Component | What fails and why |
|---|---|
| **TLS handshake** | CertificateVerify step cannot produce signature — no private key in memory |
| **Go process** | `tls.LoadX509KeyPair` returns error at startup → `os.Exit(1)` immediately |
| **containerd** | Sees exit code 1 → reports container as crashed |
| **kubelet** | Sees crashed static pod → applies exponential backoff restart loop |
| **Port 6443** | Never bound — API server died before `net.Listen()` was ever called |
| **kubectl** | `dial tcp api:6443: connect: connection refused` — port not open |
| **etcd** | Still running but unreachable — no API server to translate requests |
| **Running pods** | Unaffected — kubelet manages them locally without API server |

**The private key is crown jewels because without it, the server cannot prove its own identity to any client, and TLS — the foundation of all Kubernetes communication — cannot establish a session at all.**
