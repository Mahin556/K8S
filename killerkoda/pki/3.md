# 🚨 Disaster Simulation: The Kubernetes API Server TLS Key "Oh-No!" Moment

## 🎯 Objective
Simulate a **critical failure** – the loss of the API server’s TLS private key – and observe how the control plane reacts. Then, recover it and verify that the cluster comes back online.  
**Lesson:** The `/etc/kubernetes/pki` directory is **the crown jewels** of your Kubernetes control plane.

---

## 📋 Prerequisites
- A Kubernetes cluster (kubeadm-based) with **control plane node** accessible.
- `sudo` privileges on the control plane.
- Two terminal windows (Tab 1 and Tab 2) or tmux panes.

---

## ⚙️ Lab Steps (Execution)

### Phase 1 – Simulate the Disaster

**Tab 1 (Main terminal)**
1. **Hide the API server TLS private key**  
   ```bash
   sudo mv /etc/kubernetes/pki/apiserver.key /etc/kubernetes/pki/apiserver.key.bak
   ```

2. **Trigger a restart of the API server static Pod**  
   - Edit the manifest to force a reload (add a comment line at the top):  
     ```bash
     sudo sed -i '1s/^/# trigger reload\n/' /etc/kubernetes/manifests/kube-apiserver.yaml
     ```
   - Force‑delete the running API server container (if any):  
     ```bash
     sudo crictl ps | awk '/kube-apiserver/{print $1}' | xargs -r sudo crictl rm -f
     ```
   - Restart kubelet to pick up the manifest change:  
     ```bash
     sudo systemctl restart kubelet
     ```

3. **Test connectivity** – it should fail or hang:  
   ```bash
   kubectl get nodes
   ```

---

**Tab 2 (Log watcher)**
- **Start tailing the kubelet logs** before triggering the restart (or immediately after):  
  ```bash
  sudo journalctl -u kubelet -f
  ```
- You will see errors like:  
  ```
  unable to load server certificate: open /etc/kubernetes/pki/apiserver.key: no such file or directory
  ```
  The API server Pod will crash‑loop, and kubelet will keep trying to start it.

---

### Phase 2 – Recovery

**Tab 1 (Main terminal)**
4. **Restore the key** from the backup:  
   ```bash
   sudo mv /etc/kubernetes/pki/apiserver.key.bak /etc/kubernetes/pki/apiserver.key
   ```

5. **Verify recovery** – kubelet will automatically restart the API server with the restored key.  
   It may take a minute for the pod to become healthy.  
   ```bash
   kubectl get --raw='/readyz' | head
   kubectl get --raw='/readyz?verbose' | head
   ```
   Then:
   ```bash
   kubectl get nodes
   ```

---

## 🧠 Observations & Lessons Learned

| What happened | Why it matters |
|---------------|----------------|
| The API server failed to start without its TLS private key. | The key is required to establish secure TLS connections for all client and component communication. |
| The control plane became **unusable** – `kubectl` commands hung or timed out. | The API server is the heart of the cluster; without it, nothing works. |
| Kubelet logs clearly pointed to the missing key file. | Always check logs when debugging control plane issues. |
| Recovery was as simple as restoring the key. | **Backup your PKI files!** Losing them can mean rebuilding the cluster from scratch. |

---

## 🛡️ Best Practices for Protecting PKI Assets

- **Regular backups** – Backup `/etc/kubernetes/pki/` and the kubeconfig files (`/etc/kubernetes/admin.conf`).
- **Use secrets management** – Store certificates in a secure vault (e.g., HashiCorp Vault, AWS Secrets Manager) for production.
- **Enable automatic renewal** – kubeadm can renew certificates automatically; still, keep offline backups.
- **Restrict access** – Limit `sudo` to trusted admins; use RBAC and audit logging.
- **Document recovery procedures** – Practice this drill periodically so you know exactly what to do.

---

## 🔧 Additional Tip: If the API server fails to recover

- Check if the key file permissions are correct (should be `600` and owned by `root:root`).
- Verify the certificate matches the key:  
  ```bash
  openssl x509 -noout -modulus -in /etc/kubernetes/pki/apiserver.crt | openssl md5
  openssl rsa -noout -modulus -in /etc/kubernetes/pki/apiserver.key | openssl md5
  ```
  The output should match.

- If you don’t have a backup, you’ll need to **re‑issue** all control plane certificates using `kubeadm init phase certs all` and then restart components. But that’s a much bigger hassle – hence the importance of backups!

---

## 🏁 Conclusion

This hands‑on exercise shows **why** you should treat the PKI directory as critical infrastructure.  
A single missing file can bring down the entire cluster.  
Always backup, always verify, and always have a recovery plan.
