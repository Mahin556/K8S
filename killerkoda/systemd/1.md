This is the single most confusing part of `systemctl` for new users! 

Think of these three columns as **three distinct layers** of truth for a systemd unit. They answer three completely different questions:

1. **LOAD** = *Did systemd read the file correctly?* (Syntax/Definition)
2. **ACTIVE** = *Is it running or not?* (High-level State)
3. **SUB** = *What exact step is it on?* (Low-level Detail)

Here is the breakdown of each:

---

### 1. LOAD (The Definition Layer)
**Question answered:** *"Did systemd successfully parse the unit file from the disk into memory?"*

- This is a **syntax/availability** check. It tells you if the file exists and if the formatting is valid.
- **Common states:**
  - **`loaded`** (✅ Good): The unit file was found, the syntax is correct, and systemd has it in memory.
  - **`not-found`** (❌ Bad): The unit file doesn't exist in the filesystem.
  - **`masked`** (⚠️ Blocked): The unit file exists but is symlinked to `/dev/null`. It cannot be started until unmasked.
  - **`error`** (❌ Bad): The file exists but has a syntax error (systemd couldn't parse it).

---

### 2. ACTIVE (The High-Level State)
**Question answered:** *"Is this unit currently doing what it is supposed to do?"*

- This is a **generalized** summary of the unit's lifecycle. It means the same basic thing (running/not running) for all unit types (services, mounts, sockets).
- **Common states:**
  - **`active`** (✅ Running): The unit is running or has successfully completed its job.
  - **`inactive`** (⏸️ Off): The unit is not running.
  - **`activating`** (🔄 Starting): The unit is in the process of starting up.
  - **`deactivating`** (🔄 Stopping): The unit is in the process of shutting down.
  - **`failed`** (❌ Crashed): The unit failed to start or crashed during runtime.

---

### 3. SUB (The Low-Level Sub-State)
**Question answered:** *"Exactly what internal step is systemd executing right now?"*

- This is a **unit-type-specific** detail. It provides the nuanced technical detail behind the `ACTIVE` state. 
- Because this depends on what the unit is, the values vary wildly:

| Unit Type | ACTIVE State | SUB State (Meaning) |
| :--- | :--- | :--- |
| **Service** (long-running) | `active` | **`running`** (The process is actively running). |
| **Service** (oneshot/task) | `active` | **`exited`** (The script ran successfully and exited, which is a *success* for this type). |
| **Service** | `inactive` | **`dead`** (The process is stopped). |
| **Service** | `activating` | **`start`** or **`start-pre`** (Running the pre-start scripts). |
| **Mount** | `active` | **`mounted`** (The filesystem is attached). |
| **Socket** | `active` | **`listening`** (Waiting for incoming network traffic). |
| **Timer** | `active` | **`waiting`** (Waiting for the next scheduled trigger). |

---

### 🧠 The Golden Rule (The Hierarchy)

The **SUB** state is just an elaboration of the **ACTIVE** state. 
If `ACTIVE` is "Running", `SUB` tells you *how* it's running. 
If `ACTIVE` is "Stopped", `SUB` tells you *why* or *what step* it's stuck on.

> **Critical Rule:** **If LOAD is NOT "loaded", the ACTIVE and SUB columns are meaningless.** 
> If the file is masked or has a syntax error, systemd can't run it, so ACTIVE will just show `inactive` and SUB will show `dead`.

---

### 🎯 Practical Examples to cement it

| Command Output | Interpretation |
| :--- | :--- |
| `sshd.service` <br> `loaded` `active` `running` | **Perfect.** File is valid, service is running, processes are active. |
| `update-motd.service` <br> `loaded` `active` `exited` | **Normal.** This is a script that runs once and exits. It did its job correctly (ACTIVE) and exited (SUB). |
| `cron.service` <br> `loaded` `inactive` `dead` | **Installed but not running.** The file exists, but the process is not currently running. |
| `nginx.service` <br> `error` `inactive` `dead` | **Broken syntax.** The file exists but has a typo. Systemd can't load it, so it definitely can't run. |

---

### 💡 Pro-Tip for Debugging
If you see a service stuck on `activating` with a `SUB` of `start-pre`, it usually means the `ExecStartPre` script is hanging. 
If you see `failed` with a `SUB` of `failed`, always run `systemctl status <unit>` immediately, because the `SUB` column alone won't tell you the exit code—the `status` command will show you the specific error log!
