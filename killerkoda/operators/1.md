# 🐘 Hands‑On Lab: Deploying, Scaling, and Failure Recovery with Crunchy Data Postgres Operator (PGO)

This lab guides you through installing the Crunchy Data Postgres Operator (PGO) on a Kubernetes cluster, deploying a highly available PostgreSQL cluster, scaling it, and testing its self‑healing capabilities. By the end, you’ll understand how PGO automates PostgreSQL lifecycle management and how to handle common operational tasks.

---

## 📋 Prerequisites

- A running Kubernetes cluster (minikube, kind, kubeadm, or any cloud‑managed cluster) with `kubectl` configured.
- A GitHub account (to fork the examples repository).
- Basic familiarity with `kubectl` and YAML.

---

## 🚀 Step 1: Fork and Clone the Examples Repository

1. **Fork** the [postgres-operator-examples](https://github.com/CrunchyData/postgres-operator-examples) repository to your own GitHub account.

2. **Set your GitHub username** and clone your forked repo:
   ```bash
   export GITHUB_USERNAME="your-github-username"   # replace with your actual username
   git clone --depth 1 "https://github.com/${GITHUB_USERNAME}/postgres-operator-examples.git"
   cd postgres-operator-examples
   ```

> 💡 **Why fork?** – Forking lets you experiment with the manifests and push changes back if you want to customise the deployment.

---

## 📦 Step 2: Install PGO (Postgres Operator)

The operator is installed using Kustomize – it creates a dedicated namespace `postgres-operator` and all required resources.

```bash
# Create the namespace(postgres-operator) and base objects
kubectl apply -k kustomize/install/namespace

# Install the operator (using server‑side apply for CRDs)
kubectl apply --server-side -k kustomize/install/default
```

**Check the installation progress:**

```bash
# Watch the operator pod become ready
kubectl -n postgres-operator get po -w

# List the PostgreSQL‑related CRDs
kubectl get crds | grep postgres
```

Expected output:
```
NAME                                READY   STATUS    RESTARTS   AGE
postgres-operator-9dd545d64-t4h8d   1/1     Running   0          3s
```

> 📘 **What just happened?** – PGO introduced a new Custom Resource Definition (CRD) called `PostgresCluster`, which will be used to define and manage PostgreSQL clusters.

---

## 🐘 Step 3: Create Your First PostgreSQL Cluster in postgres-operator (named `hippo`)

Deploy a simple cluster with one primary instance using the provided Kustomize overlay:

```bash
kubectl apply -k kustomize/postgres
```

**Monitor cluster creation:**

```bash
# Check the status of the PostgresCluster resource
kubectl -n postgres-operator get postgresclusters

# Describe for detailed events
kubectl -n postgres-operator describe postgresclusters hippo
```

When ready, you’ll see `Status: Ready` and the primary pod running.

---

## 🔑 Step 4: Connect to the PostgreSQL Cluster

As part of creating a Postgres cluster, the Postgres Operator creates a PostgreSQL user account. The credentials for this account are stored in a Secret that has the name hippo-pguser-rhino .
The operator automatically creates a `Secret` named `<cluster-name>-pguser-<user>` that contains the credentials for a default superuser. For `hippo` the user is `rhino`.

```bash
k -n postgres-operator get secrets
```

**Get the primary pod name and port‑forward:**

```bash
export PG_CLUSTER_PRIMARY_POD=$(kubectl get pod -n postgres-operator -o name -l postgres-operator.crunchydata.com/cluster=hippo,postgres-operator.crunchydata.com/role=master)

kubectl -n postgres-operator port-forward "${PG_CLUSTER_PRIMARY_POD}" 5432:5432
```

> 🖥️ **Open a second terminal tab** and run the port‑forward command there, leaving it running. Then in the main tab, set environment variables to connect.

**Extract credentials from the secret:**

Establish a connection to the PostgreSQL cluster. You can run the following commands to store the username, password, and database in an environment variable and connect.

```bash
export PG_CLUSTER_USER_SECRET_NAME=hippo-pguser-rhino
export PGPASSWORD=$(kubectl get secrets -n postgres-operator "${PG_CLUSTER_USER_SECRET_NAME}" -o go-template='{{.data.password | base64decode}}')
export PGUSER=$(kubectl get secrets -n postgres-operator "${PG_CLUSTER_USER_SECRET_NAME}" -o go-template='{{.data.user | base64decode}}')
export PGDATABASE=$(kubectl get secrets -n postgres-operator "${PG_CLUSTER_USER_SECRET_NAME}" -o go-template='{{.data.dbname | base64decode}}')
```

**Connect to the database:**

```bash
psql -h localhost
```

You should see the PostgreSQL interactive prompt.

---

## 📐 Step 5: Create a Schema

Inside the `psql` shell, create a schema owned by the `rhino` user:

```sql
CREATE SCHEMA rhino AUTHORIZATION rhino;
```

> 💡 **Why schemas?** – Schemas help organise database objects (tables, views, functions) and enforce access control. This is a best practice for multi‑tenant or microservice architectures.

Exit the `psql` client with `\q`.

---

## 📈 Step 6: Scale the PostgreSQL Cluster

Let’s scale from 1 instance (the primary) to 3 instances (one primary + two replicas).

**View the current cluster specification:**

```bash
kubectl -n postgres-operator get postgresclusters hippo -o yaml
```

Look for the `spec.instances` section – it currently has `replicas: 1`.

**Scale to 3 replicas:**

```bash
kubectl edit postgresclusters hippo -n postgres-operator
```

Change the `replicas` field from `1` to `3`:

```yaml
spec:
  instances:
  - name: instance1
    replicas: 3
```

Save and exit. The operator will detect the change and create two additional pods.

**Watch the new pods come up:**

```bash
kubectl -n postgres-operator get pods -w
```

You’ll see `hippo-instance1-1` and `hippo-instance1-2` being created (they will initially be `Pending` then `Running`).

**Verify replication:**

Connect again via `psql` and check if the cluster is in recovery mode (replica) or not (primary). Run:

```sql
SELECT pg_is_in_recovery();
```

On the **primary** it returns `f` (false), on replicas it returns `t` (true).  
If you port‑forward to the primary, you’ll always see `f` – but you can also port‑forward to a replica to see `t`.

## 💥 Step 7: Simulate a Pod Failure and Test Self‑Healing

Now we will delete a pod (in this case, the primary) and watch PGO automatically recover.

**List pods with roles:**

```bash
kubectl -n postgres-operator get pods --show-labels | grep role
```

Identify the primary (the label `role=master`). It will be the one with `-instance1-0` (since the first replica is the primary by default).

You can tell which pod is the leader with the following command.
```bash
k -n postgres-operator get pods --show-labels | grep role
```

**Delete the primary pod (simulate crash):**

```bash
kubectl -n postgres-operator delete pod hippo-instance1-0
```

**Watch the operator react:**

```bash
kubectl -n postgres-operator get pods -w
```

You’ll see:
- The deleted pod disappears.
- A new pod `hippo-instance1-0` (or similar) is created.
- The operator might promote one of the replicas to become the new primary.
- The old primary (when it comes back) becomes a replica.

**Check the cluster status:**

```bash
kubectl -n postgres-operator describe postgresclusters hippo
```

Look for events like:
- `Pod hippo-instance1-0 deleted`
- `Creating new pod...`
- `Promoting replica...`

**Check operator logs for details:**

```bash
kubectl logs -n postgres-operator -l postgres-operator.crunchydata.com/control-plane=postgres-operator
```

You’ll see messages about pod recreation, replica promotion, and synchronisation.

---

## 🔍 Step 8: Verify Replication and Health

After recovery, connect again to the database (you may need to re‑port‑forward to the new primary if its name changed). Check replication:

**Find the new primary pod name:**

```bash
kubectl -n postgres-operator get pods --show-labels | grep "role=master"
```

Update the `PG_CLUSTER_PRIMARY_POD` environment variable if necessary, and restart the port‑forward.

Then connect and run:

Connect to the PostgreSQL database and run some basic queries to ensure it is functioning properly.
```bash
psql -h localhost
```

```sql
SELECT pg_is_in_recovery();   -- should be 'f'
```

t : Indicates the node is a replica.
f : Indicates the node is the primary.

**Check replication on a replica:**

Since we deleted a replica, confirm replication is still functioning.
```bash
kubectl exec -it -n postgres-operator <replica-pod-name> -- psql -U postgres -d postgres
SELECT pg_last_wal_replay_lsn();
```

This shows the replication status from the primary’s perspective.

In another terminal, port‑forward to a replica pod and connect. Run:

```sql
SELECT pg_last_wal_replay_lsn();   -- shows the last replayed WAL position
```

This confirms that the replica is receiving and replaying WAL logs from the primary.

## 🎓 Key Learnings & Best Practices

| Concept | Why It Matters |
|---------|----------------|
| **Operator pattern** | PGO automates day‑2 operations: provisioning, scaling, failover, backups – reducing manual toil. |
| **Secrets management** | The operator creates and manages credentials securely. Always use `Secrets` for sensitive data. |
| **Horizontal scaling** | Adding replicas increases read capacity and provides high availability. |
| **Self‑healing** | When a pod fails, the operator detects it and recreates it; if it’s the primary, it promotes a replica. |
| **Replication** | PostgreSQL streaming replication ensures data is synchronised; use `pg_is_in_recovery()` and `pg_last_wal_replay_lsn()` to monitor. |
| **Readiness probes** | PGO uses readiness probes to ensure traffic only goes to healthy instances. |

## 🧠 Pro Tips

- **Backup your `PostgresCluster` YAML** – keep it in version control (the forked repo).
- **Use `kubectl explain`** to understand the CRD fields: `kubectl explain postgresclusters.spec.instances`
- **Monitor operator logs** regularly – they give deep insight into cluster state changes.
- **Test failover regularly** – simulate pod failures in a staging environment to ensure your applications can handle transient outages.
