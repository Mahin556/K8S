## 🎯 Scenario Overview

### The Story
**U.A. High School** is deploying a public **Hero Registration Portal** with two backend services:

- `/register` → `register-service` on port 80
- `/verify` → `verify-service` on port 80

The portal must be accessible at: **`heroes.ua-academy.com`**

**Izuku Midoriya** wants all hero data protected with **TLS**.

### The Mission
1. Create an Ingress named `hero-reg-ingress` in namespace `class-1a`
2. Use TLS termination with secret `ua-heroes-tls`
3. Route:
   - `heroes.ua-academy.com/register` → `register-service`
   - `heroes.ua-academy.com/verify` → `verify-service`
4. Configure DNS entry in `/etc/hosts` based on Ingress LoadBalancer IP
5. Test HTTPS access with `curl -k`

## 🧠 Conceptual Summary

### What is an Ingress?

**Ingress** is a Kubernetes resource that manages external access to services within a cluster, typically HTTP and HTTPS traffic. It provides:

- **Path-based routing** → Route traffic to different services based on URL path
- **Host-based routing** → Route traffic based on domain name
- **TLS termination** → Secure HTTPS connections
- **Load balancing** → Distribute traffic across multiple services
- **SSL offloading** → Terminate SSL at the Ingress layer

### Key Components

| Component | Description |
|-----------|-------------|
| **Ingress Resource** | Configuration rules for routing external traffic |
| **Ingress Controller** | The actual implementation (e.g., NGINX, Traefik, AWS ALB) |
| **TLS Secret** | Contains certificate and private key for HTTPS |
| **Service Backend** | Target service that receives routed traffic |
| **Path Rules** | URL path patterns that determine routing |

### Why Ingress Matters

✅ **Single Entry Point** → One IP for multiple services  
✅ **TLS Termination** → Secure HTTPS with certificates  
✅ **Path-Based Routing** → Different paths go to different services  
✅ **Host-Based Routing** → Different domains go to different services  
✅ **SSL Offloading** → Services don't need their own certificates  
✅ **Cost Efficiency** → One load balancer for many services

### HTTPS Request Flow (Detailed)

```
Client Request
     ↓
1. User enters: https://heroes.ua-academy.com/register
     ↓
2. DNS Resolution:
   /etc/hosts → maps to Ingress LoadBalancer IP
   Example: 192.168.1.100 heroes.ua-academy.com
     ↓
3. TCP Connection: Client → Ingress LoadBalancer IP on port 443
     ↓
4. TLS Handshake:
   - Ingress presents certificate from ua-heroes-tls
   - Client verifies certificate (using -k for insecure)
   - Secure tunnel established
     ↓
5. HTTP Request over TLS:
   GET /register
   Host: heroes.ua-academy.com
     ↓
6. Ingress Controller:
   - Matches host: heroes.ua-academy.com
   - Matches path: /register
   - Routes to register-service on port 80
     ↓
7. Ingress forwards HTTP (not HTTPS) to service
     ↓
8. Service forwards to Pod
     ↓
9. Response flows back the same path
```

### Step 1: Create the Ingress YAML File

```bash
cat > hero-reg-ingress.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hero-reg-ingress
  namespace: class-1a
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - heroes.ua-academy.com
    secretName: ua-heroes-tls
  rules:
  - host: heroes.ua-academy.com
    http:
      paths:
      - path: /register
        pathType: Prefix
        backend:
          service:
            name: register-service
            port:
              number: 80
      - path: /verify
        pathType: Prefix
        backend:
          service:
            name: verify-service
            port:
              number: 80
EOF
```

### Step 2: Apply the Ingress

```bash
kubectl apply -f hero-reg-ingress.yaml
```

## 🔒 Deep Dive: TLS Configuration

### What is TLS Termination?

**TLS Termination** is the process of decrypting HTTPS traffic at the Ingress layer before forwarding it to backend services as plain HTTP.

```
Client ←→ (HTTPS) ←→ Ingress ←→ (HTTP) ←→ Service/Pod
                         ↑
                    TLS Termination
                    Certificate Decryption
```

### Why TLS Termination?

| Benefit | Explanation |
|---------|-------------|
| **Centralized Management** | One certificate for all services |
| **Performance** | SSL/TLS offloaded from application pods |
| **Simplified Services** | Services don't need certificate configuration |
| **Security** | Consistent security policies |
| **Cost Savings** | One certificate instead of many |

### TLS Secret Structure

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ua-heroes-tls
  namespace: class-1a
type: kubernetes.io/tls
data:
  tls.crt: <base64-encoded-certificate>
  tls.key: <base64-encoded-private-key>
```

### TLS Configuration in Ingress

```yaml
tls:
- hosts:
  - heroes.ua-academy.com
  secretName: ua-heroes-tls
```

### How TLS Works in the Ingress

1. **Client connects** to `heroes.ua-academy.com:443`
2. **Ingress presents** the certificate from `ua-heroes-tls`
3. **Client verifies** certificate (or uses `-k` to skip)
4. **TLS handshake** completes
5. **Encrypted tunnel** established
6. **HTTP requests** sent over TLS
7. **Ingress decrypts** traffic
8. **Forwarded as HTTP** to services

### Types of TLS Termination

| Type | Description | Use Case |
|------|-------------|----------|
| **Edge Termination** | TLS terminates at Ingress | Most common, recommended |
| **Passthrough** | TLS passes through to Service | Services handle their own SSL |
| **Mutual TLS** | Both client and server authenticate | Zero-trust security |

### Common TLS Commands

```bash
# Check TLS secret
kubectl get secret ua-heroes-tls -n class-1a

# View TLS secret details
kubectl describe secret ua-heroes-tls -n class-1a

# Check certificate expiration
kubectl get secret ua-heroes-tls -n class-1a -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -text -noout

# Test SSL/TLS handshake
openssl s_client -connect heroes.ua-academy.com:443 -servername heroes.ua-academy.com
```

## 🔍 Deep Dive: Ingress Path Routing

### Path Types

| Path Type | Description | Example |
|-----------|-------------|---------|
| **Prefix** | Matches URL path prefix | `/register` matches `/register`, `/register/123` |
| **Exact** | Matches exact URL path | `/register` only matches `/register` |
| **ImplementationSpecific** | Depends on Ingress Controller | Not recommended |

### Path Matching Rules

```
Request: /register/123
         ↓
Path: /register (Prefix)
         ↓
✓ Matches! Request forwarded to register-service

Request: /register
         ↓
Path: /register (Exact)
         ↓
✓ Matches! Request forwarded to register-service

Request: /register/123
         ↓
Path: /register (Exact)
         ↓
✗ Does NOT match! Request not forwarded
```

### Multiple Path Routing Example

```yaml
http:
  paths:
  - path: /register
    pathType: Prefix
    backend:
      service:
        name: register-service
        port:
          number: 80
  - path: /verify
    pathType: Prefix
    backend:
      service:
        name: verify-service
        port:
          number: 80
  - path: /api
    pathType: Prefix
    backend:
      service:
        name: api-gateway
        port:
          number: 8080
```

### Path Priority (Longest Match Wins)

```
Request: /register/hero
         ↓
Path 1: /register (Prefix) ✓
Path 2: /register/hero (Prefix) ✓ (More specific)
         ↓
Longest match wins! → Path 2 → register-service
```

## ⚙️ MetalLB Setup & Configuration

### What is MetalLB?

**MetalLB** is a load-balancer implementation for bare-metal Kubernetes clusters that provides:

- **LoadBalancer** service type support
- **IP address allocation** for services
- **Layer 2 (ARP/NDP)** and **BGP** modes

### Why MetalLB?

| Feature | Benefit |
|---------|---------|
| **Bare-Metal Support** | LoadBalancer for on-premise clusters |
| **External IPs** | Services get public/external IPs |
| **Multiple Protocols** | Layer 2 (ARP), BGP |
| **Open Source** | Free to use |
| **Cloud Alternative** | Local development with cloud-like behavior |

### MetalLB Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│                      Kubernetes Cluster                         │
│                                                                 │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │                   MetalLB Controller                    │   │
│   │  - IP Address Management                               │   │
│   │  - Service Monitoring                                  │   │
│   └─────────────────────────────────────────────────────────┘   │
│                                                                 │
│   ┌─────────────────────┐   ┌──────────────────────────────┐  │
│   │    MetalLB Speaker   │   │    MetalLB Speaker           │  │
│   │    (Node 1)          │   │    (Node 2)                  │  │
│   │  - ARP/NDP Protocol  │   │  - BGP Protocol             │  │
│   └─────────────────────┘   └──────────────────────────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### MetalLB IP Address Pool

```yaml
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: default-pool
  namespace: metallb-system
spec:
  addresses:
  - 192.168.1.100-192.168.1.200
```

### MetalLB Layer 2 Advertisement

```yaml
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: default-advertisement
  namespace: metallb-system
spec:
  ipAddressPools:
  - default-pool
```

### How MetalLB Allocates IPs

1. **Service created** with type `LoadBalancer`
2. **MetalLB controller** assigns an IP from the pool
3. **MetalLB speaker** announces the IP on the network
4. **ARP/NDP** broadcasts the IP to the local network
5. **External clients** can now reach the service via that IP

```bash
# Check MetalLB logs
kubectl logs -n metallb-system -l app=metallb

# Check LoadBalancer services
kubectl get svc -A | grep LoadBalancer
```

## 🌐 DNS Configuration with /etc/hosts

### Why /etc/hosts?

In production, you would use **external DNS** (e.g., Route53, Cloudflare). In a test environment, `/etc/hosts` provides local DNS resolution.

### Adding the Entry

```bash
# Get Ingress IP
INGRESS_IP=$(kubectl get ingress hero-reg-ingress -n class-1a -o jsonpath='{.status.loadBalancer.ingress[0].ip}')

# Add to /etc/hosts
echo "${INGRESS_IP} heroes.ua-academy.com" | sudo tee -a /etc/hosts

# Verify
cat /etc/hosts | grep heroes.ua-academy.com
```

### /etc/hosts Format


## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Ingress not getting an IP** | MetalLB not running | `kubectl get pods -n metallb-system` |
| **No external IP shown** | LoadBalancer pending | Check MetalLB IP pool: `kubectl get IPAddressPool -n metallb-system` |
| **TLS handshake fails** | Secret missing/invalid | `kubectl get secret ua-heroes-tls -n class-1a` |
| **404 Not Found** | Wrong path or service | Check Ingress rules: `kubectl describe ingress hero-reg-ingress -n class-1a` |
| **Connection refused** | Ingress controller not running | `kubectl get pods -n ingress-nginx` |
| **DNS not resolving** | /etc/hosts not updated | `cat /etc/hosts \| grep heroes.ua-academy.com` |
| **Certificate error** | Self-signed certificate | Use `-k` flag with curl |
| **Wrong service routing** | Path mismatch | Check path: `kubectl get ingress -n class-1a -o yaml` |

## 📊 Ingress vs Other Service Types

| Service Type | Load Balancing | TLS | Path Routing | Host Routing | External IP |
|--------------|----------------|-----|--------------|--------------|-------------|
| **ClusterIP** | ❌ No | ❌ No | ❌ No | ❌ No | ❌ No |
| **NodePort** | ⚠️ Basic | ❌ No | ❌ No | ❌ No | ✅ Yes (node IP) |
| **LoadBalancer** | ✅ Yes | ❌ No | ❌ No | ❌ No | ✅ Yes (external IP) |
| **Ingress** | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes | ✅ Yes (via LB) |

### When to Use Each

| Service Type | Use Case |
|--------------|----------|
| **ClusterIP** | Internal services within the cluster |
| **NodePort** | Quick external access for development |
| **LoadBalancer** | Individual services needing external IPs |
| **Ingress** | Multiple services, path/host routing, TLS termination |

### Cost Comparison

| Service Type | Cost | Scalability |
|--------------|------|-------------|
| **ClusterIP** | Free | High |
| **NodePort** | Free | Low |
| **LoadBalancer** | $$$ (per service) | Medium |
| **Ingress** | $ (single LB) | High |

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Use TLS everywhere** | Protect data in transit |
| **Use path-based routing** | Avoid creating multiple Ingresses |
| **Use host-based routing** | Support multiple domains |
| **Set appropriate path types** | Use Prefix or Exact as needed |
| **Monitor TLS certificates** | Avoid expiration issues |
| **Use annotation for configuration** | Fine-tune Ingress behavior |
| **Regularly test HTTPS endpoints** | Ensure TLS is working |

### Real-World Use Cases

| Use Case | Description | Ingress Configuration |
|----------|-------------|----------------------|
| **Web Application** | Host multiple services under one domain | Path-based routing |
| **API Gateway** | Route different API versions | Path-based + Host-based |
| **Multi-tenant SAAS** | Different customers = different domains | Host-based routing |
| **Microservices** | Route to different services based on path | Path-based routing |
| **Security-Enhanced** | TLS termination + mutual TLS | TLS + mTLS configuration |

```yaml
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
```

### Complete YAML Template

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: hero-reg-ingress
  namespace: class-1a
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - heroes.ua-academy.com
    secretName: ua-heroes-tls
  rules:
  - host: heroes.ua-academy.com
    http:
      paths:
      - path: /register
        pathType: Prefix
        backend:
          service:
            name: register-service
            port:
              number: 80
      - path: /verify
        pathType: Prefix
        backend:
          service:
            name: verify-service
            port:
              number: 80
```
