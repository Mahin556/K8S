## 🎯 Scenario Overview

### Your Mission

Configure **PodAntiAffinity** for a MongoDB StatefulSet to ensure replicas are distributed across different failure domains (zones) for high availability.

### The Context

You are working in the **data platform team**:

- The company operates a production-grade MongoDB database on Kubernetes
- The StatefulSet is named `mongodb-users-db` with **2 replicas** in the `database-services` namespace
- Currently, MongoDB pods **could be scheduled on the same node**
- A single node failure could severely impact or completely take down the MongoDB service
- The database team requires **mandatory pod anti-affinity** so that MongoDB replicas MUST run on different failure domains

### Problem Statement

A StatefulSet manifest for MongoDB is stored at `/mongodb/mongodb-stateful.yaml`. The StatefulSet has NOT been applied to the cluster because it does not have PodAntiAffinity configured.

### Requirements

| Requirement | Details |
|-------------|---------|
| **Rule Type** | `requiredDuringSchedulingIgnoredDuringExecution` (hard constraint) |
| **Distribution** | No two MongoDB pods on the same node |
| **Topology Key** | `topology.kubernetes.io/zone` |
| **Action** | Update manifest and apply |

## 🧠 Conceptual Summary

### What is PodAntiAffinity?

**PodAntiAffinity** is a scheduling constraint that prevents Pods from being scheduled on the same node (or in the same failure domain) as other Pods that match certain labels.

### Why It Matters for Databases

```
Without PodAntiAffinity:
┌─────────────────────────────────────────────────────────────┐
│                    Single Node Failure                       │
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │                    Node 1                            │   │
│   │   ┌──────────────┐  ┌──────────────┐              │   │
│   │   │ MongoDB Pod  │  │ MongoDB Pod  │              │   │
│   │   │   Replica 1  │  │   Replica 2  │              │   │
│   │   └──────────────┘  └──────────────┘              │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                             │
│   ❌ Both replicas on same node → Complete DB outage!     │
└─────────────────────────────────────────────────────────────┘

With PodAntiAffinity:
┌─────────────────────────────────────────────────────────────┐
│                    Node Failure Survivability               │
│                                                             │
│   ┌──────────────────────┐   ┌──────────────────────────┐  │
│   │      Node 1          │   │        Node 2             │  │
│   │   ┌──────────────┐   │   │   ┌──────────────┐       │  │
│   │   │ MongoDB Pod  │   │   │   │ MongoDB Pod  │       │  │
│   │   │   Replica 1  │   │   │   │   Replica 2  │       │  │
│   │   └──────────────┘   │   │   └──────────────┘       │  │
│   └──────────────────────┘   └──────────────────────────┘  │
│                                                             │
│   ✅ If Node 1 fails → Replica 2 still available!         │
└─────────────────────────────────────────────────────────────┘
```

## 📊 PodAffinity vs PodAntiAffinity

### Comparison

| Feature | PodAffinity | PodAntiAffinity |
|---------|-------------|-----------------|
| **Purpose** | Co-locate Pods together | Spread Pods apart |
| **Use Case** | Performance, low latency | High availability, fault tolerance |
| **Analogy** | "Schedule near my team" | "Schedule away from my team" |
| **When to use** | Caching services, tightly coupled microservices | Databases, critical stateful services |

### Required vs Preferred

| Type | Description | When to Use |
|------|-------------|-------------|
| **requiredDuringSchedulingIgnoredDuringExecution** | Hard constraint — Pod MUST follow rule or remain Pending | Critical services, production databases |
| **preferredDuringSchedulingIgnoredDuringExecution** | Soft constraint — Scheduler tries but can violate | Non-critical services, development |

### Step 3: Edit the Manifest to Add PodAntiAffinity

```bash
vi /mongodb/mongodb-stateful.yaml
```

Add the affinity section under `spec.template.spec`:

**Modified State (After Adding Affinity):**

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongodb-users-db
  namespace: database-services
  labels:
    app: mongodb-users-db
    environment: production
    team: data-platform
  annotations:
    owner: "db-team"
spec:
  serviceName: "mongodb"
  replicas: 2
  selector:
    matchLabels:
      app: mongodb-users-db
  template:
    metadata:
      labels:
        app: mongodb-users-db
        environment: production
      annotations:
        description: "MongoDB users database"
    spec:
      # 🔥 ADD THIS AFFINITY SECTION 🔥
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - mongodb-users-db
            topologyKey: topology.kubernetes.io/zone
      containers:
      - name: mongodb
        image: mongo:5.0
        ports:
        - containerPort: 27017
          name: mongodb
        volumeMounts:
        - name: mongodb-data
          mountPath: /data/db
  volumeClaimTemplates:
  - metadata:
      name: mongodb-data
      labels:
        app: mongodb-users-db
    spec:
      storageClassName: local-path
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 500Mi
```

## 🔍 Deep Dive: Understanding the Configuration

### Complete Affinity Structure

```yaml
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - mongodb-users-db
      topologyKey: topology.kubernetes.io/zone
```

### Key Fields Explained

| Field | Value | Purpose |
|-------|-------|---------|
| **`affinity.podAntiAffinity`** | Object | Defines anti-affinity rules |
| **`requiredDuringSchedulingIgnoredDuringExecution`** | Array | Hard constraint — MUST be satisfied |
| **`labelSelector`** | `app: mongodb-users-db` | Which Pods to avoid scheduling near |
| **`matchExpressions`** | `operator: In` | Label selection logic |
| **`topologyKey`** | `topology.kubernetes.io/zone` | Scope of anti-affinity (zone-level) |

### How the AntiAffinity Rule Works

```
1. Scheduler receives Pod "mongodb-users-db-1" to schedule
         ↓
2. Scheduler checks existing Pods in the cluster
         ↓
3. Finds "mongodb-users-db-0" with label app=mongodb-users-db
         ↓
4. Checks topologyKey: topology.kubernetes.io/zone
         ↓
5. "mongodb-users-db-0" is in zone-a (controlplane)
         ↓
6. Scheduler MUST place new Pod in a DIFFERENT zone
         ↓
7. Only node with different zone is node01 (zone-b)
         ↓
8. Pod scheduled on node01
         ↓
✅ Perfect! Pods distributed across zones
```

### MatchExpressions Options

| Operator | Description | Example |
|----------|-------------|---------|
| **In** | Label value must be in the list | `values: [mongodb-users-db]` |
| **NotIn** | Label value must NOT be in the list | `values: [app1, app2]` |
| **Exists** | Label must exist (any value) | `operator: Exists` |
| **DoesNotExist** | Label must not exist | `operator: DoesNotExist` |

## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Pod stuck in Pending** | Anti-affinity cannot be satisfied | Check available nodes: `kubectl get nodes` |
| **Not enough nodes** | Only one zone available | Add more nodes or use `preferred` instead of `required` |
| **Pods on same node** | Anti-affinity not configured | Verify affinity section in StatefulSet |
| **Wrong topologyKey** | Node labels missing | Check `kubectl get nodes -L topology.kubernetes.io/zone` |
| **Label mismatch** | `matchExpressions` not matching | Check pod labels: `kubectl get pods --show-labels` |
| **StatefulSet update blocked** | Existing pods not deleted | `kubectl delete pod -n database-services -l app=mongodb-users-db` |
| **PVC issues** | Volume claim conflicts | Check PVC status: `kubectl get pvc -n database-services` |

## 📊 StatefulSet Specific Considerations

### Why StatefulSets for Databases?

| Feature | Benefit for MongoDB |
|---------|---------------------|
| **Stable network identities** | `mongodb-users-db-0`, `mongodb-users-db-1` — predictable DNS names |
| **Stable persistent storage** | Each pod gets its own PersistentVolumeClaim (PVC) |
| **Ordered deployment** | Pods created in sequence (0 → 1 → 2) |
| **Ordered rolling updates** | Updates happen in reverse order (2 → 1 → 0) |

### StatefulSet Ordering

```
StatefulSet Creation:
mongodb-users-db-0 → Created first
    ↓ (when ready)
mongodb-users-db-1 → Created second

StatefulSet Scaling Up:
mongodb-users-db-0 → mongodb-users-db-1 → mongodb-users-db-2

StatefulSet Scaling Down:
mongodb-users-db-2 → mongodb-users-db-1 → mongodb-users-db-0
```

### StatefulSet Components

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mongodb-users-db
spec:
  serviceName: "mongodb"               # Headless service for DNS
  replicas: 2
  selector:
    matchLabels:
      app: mongodb-users-db
  template:
    metadata:
      labels:
        app: mongodb-users-db
    spec:
      affinity:                         # ← PodAntiAffinity here
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - mongodb-users-db
            topologyKey: topology.kubernetes.io/zone
      containers:
      - name: mongodb
        image: mongo:5.0
        ports:
        - containerPort: 27017
        volumeMounts:
        - name: mongodb-data
          mountPath: /data/db
  volumeClaimTemplates:                  # ← Each pod gets its own PVC
  - metadata:
      name: mongodb-data
    spec:
      storageClassName: local-path
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 500Mi
```

## 💡 Real-World Use Cases & Best Practices

### When to Use PodAntiAffinity

| Use Case | Description |
|----------|-------------|
| **High Availability Databases** | Distribute MongoDB, PostgreSQL, MySQL replicas |
| **Microservices Resilience** | Ensure service replicas don't share failure domains |
| **Resource Contention Avoidance** | Prevent resource-intensive workloads from co-locating |
| **Compliance Requirements** | Meet regulatory requirements for data redundancy |
| **Noisy Neighbor Prevention** | Separate workloads that could interfere with each other |

### When to Use PodAffinity

| Use Case | Description |
|----------|-------------|
| **Data Locality** | Co-locate compute and storage Pods for low latency |
| **Microservices Communication** | Place tightly coupled services together |
| **Cost Optimization** | Group related workloads to minimize inter-zone costs |

### Best Practices

| Practice | Why |
|----------|-----|
| **Match replicas to zones** | Ensure each zone has at most one replica |
| **Use required for critical services** | Hard constraints for production databases |
| **Use preferred for non-critical** | Soft constraints for development/staging |
| **Choose correct topologyKey** | `topology.kubernetes.io/zone` for zone-level anti-affinity |
| **Test in dev first** | Validate anti-affinity rules before production |
| **Monitor pending pods** | Watch for scheduling issues |

### Topology Keys Reference

| Topology Key | Scope | Description |
|--------------|-------|-------------|
| `topology.kubernetes.io/zone` | Zone | Failure domain (AZ) |
| `topology.kubernetes.io/region` | Region | Geographic region |
| `kubernetes.io/hostname` | Node | Individual node |
| `failure-domain.beta.kubernetes.io/zone` | Zone | Legacy zone label |

### Production Considerations

```
Replicas vs Available Zones:
- 2 replicas + 2 zones → Perfect distribution
- 3 replicas + 3 zones → Perfect distribution
- 3 replicas + 2 zones → One zone gets 2 pods (still better than same node)
- 4 replicas + 2 zones → Two pods per zone (preferred anti-affinity recommended)
```

### AntiAffinity Quick Reference

```yaml
# Required AntiAffinity (Hard Constraint)
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - mongodb-users-db
      topologyKey: topology.kubernetes.io/zone

# Preferred AntiAffinity (Soft Constraint)
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values:
            - mongodb-users-db
        topologyKey: topology.kubernetes.io/zone

# Required AntiAffinity on hostname (node-level)
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values:
          - mongodb-users-db
      topologyKey: kubernetes.io/hostname
```
