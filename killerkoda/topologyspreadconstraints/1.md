## 🎯 Scenario Overview

### Your Mission

Configure a Deployment with **topologySpreadConstraints** to ensure Pods are evenly distributed across different deployment domains (zones) for high availability.

### The Context

You are working on a **Japan Tourism Platform** that needs high availability across multiple deployment domains (zones):

- A Deployment manifest is stored at `/japan-travel-application/japan-tourism.yaml`
- The Deployment has **7 replicas** that need to be distributed evenly across nodes
- Nodes have different topology domains labeled with `traveljp.io/deployment-domain`

### Problem Statement

Edit the Deployment to add `topologySpreadConstraints` with the following requirements:

| Requirement | Value |
|-------------|-------|
| **Minimum domains for balancing** | `2` |
| **Allowed difference between domains** | `1` |
| **Topology key** | `traveljp.io/deployment-domain` |
| **When unsatisfiable** | `DoNotSchedule` (hard constraint) |
| **LabelSelector** | `app.kubernetes.io/component: frontend` AND `app.kubernetes.io/version: v1.0.0` |

## 🧠 Conceptual Summary

### What is topologySpreadConstraints?

**topologySpreadConstraints** is a Kubernetes scheduling feature that ensures Pods are evenly distributed across different topology domains (zones, regions, nodes, etc.). It provides fine-grained control over Pod placement for high availability.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **topologySpreadConstraints** | Ensures Pods are evenly distributed across topology domains |
| **maxSkew** | Maximum allowed difference in Pod count between any two domains |
| **minDomains** | Minimum number of domains required for spreading to occur |
| **topologyKey** | Node label key identifying the topology domain |
| **whenUnsatisfiable** | Behavior when constraints cannot be met |
| **labelSelector** | Selects which Pods are counted for distribution |

### Why Use TopologySpreadConstraints?

✅ **High Availability** → Distribute Pods across failure domains  
✅ **Even Distribution** → Prevent overloading single nodes  
✅ **Fine-grained Control** → More flexible than podAntiAffinity  
✅ **Multi-AZ Deployments** → Ensure resilience across zones  
✅ **Cost Optimization** → Balance resource usage across nodes

## 🔍 Deep Dive: Understanding the Configuration

### Complete TopologySpreadConstraints Structure

```yaml
topologySpreadConstraints:
- maxSkew: 1                        # Maximum allowed difference between domains
  minDomains: 2                     # Minimum number of domains for spreading
  topologyKey: traveljp.io/deployment-domain  # Node label key for topology
  whenUnsatisfiable: DoNotSchedule  # Behavior when constraints can't be met
  labelSelector:                    # Which Pods to count for distribution
    matchLabels:
      app.kubernetes.io/component: frontend
      app.kubernetes.io/version: v1.0.0
```

### Key Fields Explained

| Field | Value | Purpose |
|-------|-------|---------|
| **`maxSkew`** | `1` | Maximum allowed difference in Pod count between any two domains |
| **`minDomains`** | `2` | Minimum number of domains required for spreading to occur |
| **`topologyKey`** | `traveljp.io/deployment-domain` | Node label key identifying the topology domain |
| **`whenUnsatisfiable`** | `DoNotSchedule` | Hard constraint — Pods remain Pending if conditions can't be met |
| **`labelSelector`** | `matchLabels` | Identifies which Pods are counted for distribution |

### How the Scheduler Calculates Distribution

```
1. Scheduler receives Pod to schedule
         ↓
2. Checks all nodes with topologyKey label
         ↓
3. Groups nodes by topologyKey value
   - Domain A: controlplane (4 Pods)
   - Domain B: node01 (3 Pods)
         ↓
4. Calculates skew for each potential placement
   - If placing Pod in Domain A: 5 vs 3 → skew = 2 ❌ (exceeds maxSkew)
   - If placing Pod in Domain B: 4 vs 4 → skew = 0 ✅ (within maxSkew)
         ↓
5. Schedules Pod in Domain B
         ↓
✅ Pod distributed to node01!
```

## 📊 Distribution Examples & Calculations

### Valid Distributions (7 Replicas, maxSkew: 1)

| Domain A | Domain B | Difference | Valid? |
|----------|----------|------------|--------|
| 4 | 3 | 1 | ✅ Valid |
| 3 | 4 | 1 | ✅ Valid |
| 4 | 4 | 0 | ✅ Valid (if another domain exists) |

### Invalid Distributions

| Domain A | Domain B | Difference | Valid? |
|----------|----------|------------|--------|
| 5 | 2 | 3 | ❌ Invalid (exceeds maxSkew) |
| 6 | 1 | 5 | ❌ Invalid (exceeds maxSkew) |
| 7 | 0 | 7 | ❌ Invalid (violates minDomains) |

### Distribution Formula

```
Allowed skew = maxDomains - minDomains ≤ maxSkew

Where:
- maxDomains = Largest Pod count in any domain
- minDomains = Smallest Pod count in any domain
- maxSkew = 1 (configured)

Example:
- Domain A: 4 Pods
- Domain B: 3 Pods
- Skew = 4 - 3 = 1 ≤ 1 ✅
```

### Impact of minDomains

```
Scenario: Only 1 domain available (tokyo-a-server)
- minDomains: 2
- Scheduler cannot meet requirement
- Pods remain Pending ❌

Scenario: 2 domains available (tokyo-a-server, tokyo-b-server)
- minDomains: 2
- Scheduler meets requirement
- Pods scheduled ✅
```

## 🛠️ Troubleshooting Common Issues

| Issue | Diagnosis | Solution |
|-------|-----------|----------|
| **Pods stuck in Pending** | Not enough domains available | Add more nodes with different topology labels |
| **Pods not spreading evenly** | maxSkew too high | Reduce maxSkew value |
| **Deployment rollout stuck** | minDomains not satisfied | Check available domains: `kubectl get nodes -L traveljp.io/deployment-domain` |
| **Wrong topologyKey** | Node labels missing | Add labels: `kubectl label node <node> traveljp.io/deployment-domain=zone-a` |
| **LabelSelector mismatch** | Pod labels don't match | Check Pod labels: `kubectl get pods --show-labels` |
| **whenUnsatisfiable issue** | Hard constraint too strict | Change to `ScheduleAnyway` for flexibility |
| **Skew calculation unexpected** | Other Pods with matching labels | Check other Pods in namespace with same labels |

## 📊 Comparison with Other Scheduling Features

| Feature | Use Case | When to Use |
|---------|----------|-------------|
| **nodeSelector** | Simple label-based node selection | Basic node filtering |
| **nodeAffinity** | Complex node selection rules | Advanced node selection |
| **podAffinity** | Co-locate Pods together | Performance, low latency |
| **podAntiAffinity** | Spread Pods apart (older approach) | Basic spreading |
| **topologySpreadConstraints** | Even distribution with fine control | Advanced spreading with skew control |

### TopologySpreadConstraints vs PodAntiAffinity

| Aspect | TopologySpreadConstraints | PodAntiAffinity |
|--------|---------------------------|-----------------|
| **Distribution Control** | ✅ Fine-grained (skew control) | ⚠️ Basic (only prevents co-location) |
| **Min Domains** | ✅ Can specify minimum | ❌ Not available |
| **Flexibility** | ✅ More options | ⚠️ Limited |
| **Complexity** | ✅ Moderate | ✅ Simple |
| **Use Case** | Multi-AZ, even distribution | Simple anti-affinity |

## 💡 Best Practices & Real-World Use Cases

### Best Practices

| Practice | Why |
|----------|-----|
| **Choose appropriate maxSkew** | Lower values (1-2) for strict balance, higher for flexibility |
| **Set minDomains wisely** | Ensures minimum fault tolerance (typically 2 or 3) |
| **Use with nodeAffinity** | Combine for complex placement requirements |
| **Consider whenUnsatisfiable** | Use `DoNotSchedule` for critical workloads, `ScheduleAnyway` for flexibility |
| **Monitor distribution** | Regularly check Pod placement to verify constraints are working |
| **Use descriptive topology keys** | Makes configuration more readable |

### Real-World Use Cases

| Use Case | Description | Configuration |
|----------|-------------|---------------|
| **Multi-AZ Deployments** | Distribute Pods across availability zones | `topologyKey: topology.kubernetes.io/zone` |
| **Geographic Distribution** | Spread workloads across regions | `topologyKey: topology.kubernetes.io/region` |
| **Node Failure Tolerance** | Ensure application survives node failures | `topologyKey: kubernetes.io/hostname` |
| **Cost Optimization** | Balance resource usage across instance types | `topologyKey: node.kubernetes.io/instance-type` |
| **Compliance Requirements** | Meet regulatory requirements for data distribution | Custom topologyKey |

### Example: Multi-Zone Deployment

```yaml
topologySpreadConstraints:
- maxSkew: 1
  minDomains: 3
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule

    matchLabels:
      app: critical-app
```
