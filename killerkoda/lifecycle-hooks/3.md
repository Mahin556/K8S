This documentation contains several important details that are easy to miss. Here's a practical explanation of each section.

---

# 1. Available Container Lifecycle Hooks

Kubernetes provides **three lifecycle actions**:

| Hook           | When it Runs                                                | Purpose                         |
| -------------- | ----------------------------------------------------------- | ------------------------------- |
| **PostStart**  | Immediately after the container is created                  | Perform initialization tasks    |
| **PreStop**    | Just before the container is terminated                     | Perform graceful shutdown tasks |
| **StopSignal** | Defines which signal Kubernetes sends to stop the container | Customize the shutdown signal   |

---

# 2. PostStart

## When does it execute?

Immediately after the container is created.

```
Container Created
       │
       ├─────────────► ENTRYPOINT starts
       │
       └─────────────► PostStart Hook starts
```

Notice both happen **at the same time**.

Kubernetes **does not wait** for your application to start before running the hook.

---

## Example Timeline

Suppose your container is

```dockerfile
ENTRYPOINT ["python","app.py"]
```

and

```yaml
postStart:
  exec:
    command:
      - sh
      - -c
      - echo "Started"
```

Timeline

```
0 sec
│
├── Container created
│
├── Python application starts
│
└── PostStart starts simultaneously
```

Your Python app might already be running before the hook finishes.

---

## Important Point

This statement from the docs:

> The hook runs concurrently with the ENTRYPOINT.

means

**NOT**

```
Container

↓

PostStart

↓

Application
```

Instead

```
Container

├── Application starts

└── PostStart starts
```

They happen together.

---

# 3. Why HTTP PostStart isn't recommended

Suppose

```yaml
postStart:
  httpGet:
    path: /startup
    port: 8080
```

Kubernetes immediately calls

```
GET http://localhost:8080/startup
```

But your application may still be starting.

```
Container

↓

Application still loading...

↓

Port 8080 not listening yet

↓

HTTP request fails
```

That's why the documentation says

> It generally doesn't make sense to use HTTP for PostStart.

Use **Exec** or an **Init Container** if startup work must complete before the app begins serving.

---

# 4. PostStart Can Delay Running State

Suppose

```yaml
postStart:
  exec:
    command:
      - sleep
      - "30"
```

Timeline

```
Container Created

↓

Application Running

↓

PostStart sleeping...

↓

30 seconds later

↓

Pod becomes Running
```

The application may already be running, but Kubernetes waits for the hook to complete before marking the container as **Running**.

---

# 5. PreStop

Runs immediately before Kubernetes terminates the container.

Example

```
kubectl delete pod nginx
```

Timeline

```
Delete Pod

↓

PreStop Hook

↓

TERM Signal

↓

Application exits

↓

Container removed
```

Notice

```
PreStop

↓

TERM
```

not

```
TERM

↓

PreStop
```

---

# 6. What starts first?

The documentation says

> terminationGracePeriodSeconds begins before the PreStop hook.

Example

```yaml
terminationGracePeriodSeconds: 60
```

```
Delete Pod

↓

60 second timer starts

↓

PreStop

↓

TERM

↓

Exit
```

The timer includes **everything**.

---

# Example

Suppose

```
terminationGracePeriodSeconds = 60
```

Hook

```bash
sleep 55
```

Application shutdown

```
10 seconds
```

Total

```
55 + 10 = 65 seconds
```

But only

```
60 seconds
```

are allowed.

Result

```
Delete Pod

↓

55 sec hook

↓

TERM

↓

Application still shutting down

↓

60 seconds reached

↓

SIGKILL
```

The application is forcefully killed.

---

# 7. StopSignal

Normally Kubernetes sends

```
SIGTERM
```

Example

```
Delete Pod

↓

SIGTERM

↓

Application exits
```

But you can override it.

Example

```yaml
lifecycle:
  stopSignal: SIGUSR1
```

Now

```
Delete Pod

↓

SIGUSR1

↓

Application exits
```

This overrides the Dockerfile

```
STOPSIGNAL SIGTERM
```

---

# 8. Hook Handler Types

Kubernetes supports three handler implementations.

---

## Exec

Runs a command **inside the container**.

```
Container

↓

sh

↓

echo hello
```

Example

```yaml
exec:
  command:
  - sh
  - -c
  - echo hello
```

---

## HTTP

Kubelet sends an HTTP request.

```
Container

↓

GET /shutdown
```

Example

```yaml
httpGet:
  path: /shutdown
  port: 8080
```

---

## Sleep

New in recent Kubernetes versions.

Instead of

```yaml
exec:
  command:
  - sleep
  - "10"
```

You can simply write

```yaml
sleep:
  seconds: 10
```

Much cleaner.

---

# 9. Where does each hook run?

This is important.

| Handler | Runs Where?                                                     |
| ------- | --------------------------------------------------------------- |
| Exec    | Inside the container                                            |
| HTTP    | Executed by the kubelet, which sends a request to the container |
| Sleep   | Managed by the kubelet (no process runs inside the container)   |

Example

```
Exec

Container

↓

Shell

↓

Command
```

Whereas

```
HTTP

Kubelet

↓

HTTP Request

↓

Container
```

---

# 10. If Hooks Fail

Suppose

```yaml
postStart:
  exec:
    command:
      - badcommand
```

```
Container Starts

↓

badcommand

↓

Failure

↓

Container killed

↓

Restart

↓

CrashLoopBackOff
```

Same for PreStop.

If the hook fails, Kubernetes treats it as a container failure.

---

# 11. Hook Delivery Guarantee

The docs say

> At least once.

Meaning

```
Delete Pod

↓

PreStop
```

Usually

```
Runs once
```

But in rare situations

```
PreStop

↓

Kubelet restarts

↓

PreStop again
```

So your hook should be **idempotent**—safe to run more than once.

Good example

```bash
rm -f /tmp/file
```

Running it twice is harmless.

Bad example

```bash
echo 100 >> balance.txt
```

If executed twice

```
100
100
```

You accidentally duplicate the operation.

---

# 12. Debugging Hooks

Check events

```bash
kubectl describe pod lifecycle-demo
```

You might see

```
FailedPostStartHook
```

or

```
FailedPreStopHook
```

Example

```
Events

Started container

↓

FailedPostStartHook

↓

Container killed

↓

Restarting
```

The actual hook output isn't shown in Pod events, so it's often helpful to have your hook write to a file or use the application's logging system.

# Complete Lifecycle

```text
                 POD CREATED
                      │
                      ▼
             Container Created
                      │
      ┌───────────────┴───────────────┐
      │                               │
      ▼                               ▼
 ENTRYPOINT Starts            PostStart Hook
      │                               │
      └───────────────┬───────────────┘
                      ▼
             Container Running
                      │
          kubectl delete pod
                      │
                      ▼
     terminationGracePeriodSeconds starts
                      │
                      ▼
                PreStop Hook
                      │
                      ▼
           Stop Signal (SIGTERM by default,
           or custom StopSignal if configured)
                      │
                      ▼
         Application Performs Cleanup
                      │
                      ▼
              Container Terminates
```

### Best Practices

* Use **`postStart`** only for lightweight initialization. If your application **must not start until setup is complete**, use an **init container** instead.
* Use **`preStop`** to gracefully stop accepting traffic, flush state, or notify other services.
* Make hooks **fast** and **idempotent** (safe if executed more than once).
* Ensure `terminationGracePeriodSeconds` is long enough to cover **both** the `preStop` hook execution time and the application's shutdown time.
* Prefer the built-in **`sleep`** handler over an `exec` that just runs `sleep` when all you need is a delay.
