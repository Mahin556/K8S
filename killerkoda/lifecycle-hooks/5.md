That's an accurate summary of how Kubernetes shuts down a container. Here's what each step means in practice:

**1. `preStop` hook runs first**
This is a hook you define in the pod spec (an exec command or an HTTP request). It runs *before* the process gets any signal. It's meant to give your app a chance to do cleanup — deregister from a load balancer, finish in-flight requests, flush logs, etc. — while it's still fully "alive" and able to respond normally.

**2. SIGTERM is sent**
Once the `preStop` hook finishes (or immediately, if there is no hook), Kubernetes sends SIGTERM to PID 1 in the container. This is the "please shut down gracefully" signal. Your application should catch it and start winding down: close open connections, stop accepting new work, save state, etc.

**3. `terminationGracePeriodSeconds` is the total clock**
This is important — it's not just the wait *after* SIGTERM. The grace period starts as soon as termination begins, so the `preStop` hook execution time and the time your app takes to react to SIGTERM both eat into this same budget. Default is 30 seconds.

**4. SIGKILL if it's still running**
If the container hasn't exited by the time the grace period expires, Kubernetes force-kills it with SIGKILL — immediate termination, no cleanup possible, no ignoring it.

A few practical implications worth knowing:

- If your `preStop` hook takes 25 seconds and your grace period is 30, your app only has 5 seconds to react to SIGTERM before getting killed.
- If your app doesn't handle SIGTERM at all (many default images/entrypoints don't forward it properly, e.g. shell wrappers), it'll just sit until SIGKILL hits — always killed "the hard way," even if 30s were available.
- You can override the grace period per-delete with `kubectl delete pod --grace-period=<seconds>`.
- `preStop` and SIGTERM handling are your two tools for a clean shutdown; the grace period is the deadline you're racing against.
