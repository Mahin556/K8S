## 🎯 Scenario Overview

**Context:** A Pod named `react-frontend-monitor` runs in the `react-frontend` namespace with two containers:
- **`frontend-app`** → Main container running nginx with defined resource requests and limits
- **`monitor-agent`** → Sidecar container running a monitoring script

**The Problem:** The monitoring script expects four environment variables, but they are not defined. As a result, it prints empty values for CPU and memory.

**The Solution:** Configure the Downward API to inject the main container's resource specifications as environment variables into the sidecar container.

---

## 🧠 What is the Downward API?

The **Downward API** is a mechanism that allows containers to consume information about themselves **without calling the Kubernetes API server**.

### Key Concepts

| Concept | Description |
|---------|-------------|
| **Downward API** | Exposes Pod/container metadata to containers |
| **`resourceFieldRef`** | Exposes container resource requests and limits |
| **`fieldRef`** | Exposes Pod metadata (name, namespace, labels, etc.) |
| **`containerName`** | Specifies which container's resources to reference |
| **Divisor** | Controls the unit of measurement (e.g., `1m` for millicores) |

### Why Use the Downward API?

✅ **No API calls needed** → Reduces latency and load on API server  
✅ **Simple configuration** → Just environment variables or volume files  
✅ **Lightweight** → No additional permissions or RBAC required  
✅ **Fast** → Values are injected at Pod startup  

---

## 🏗️ Architecture Flow

### Without Downward API
```
Sidecar Container → Cannot access main container's resource info
Monitor Script → Prints empty values ❌
```

### With Downward API (resourceFieldRef)
```
Kubernetes → Injects resource values as env vars
Sidecar Container → Reads APP_CPU_REQUEST, APP_MEM_LIMIT, etc.
Monitor Script → Displays: CPU_REQ=100m, MEM_LIM=256Mi ✅
```

---

## 📋 Required Environment Variables

The monitoring script expects these **four environment variables**:

| Environment Variable | Description | Source | Divisor |
|----------------------|-------------|--------|---------|
| `APP_CPU_REQUEST` | CPU request in millicores | `requests.cpu` | `1m` |
| `APP_CPU_LIMIT` | CPU limit in millicores | `limits.cpu` | `1m` |
| `APP_MEM_REQUEST` | Memory request in mebibytes | `requests.memory` | `1Mi` |
| `APP_MEM_LIMIT` | Memory limit in mebibytes | `limits.memory` | `1Mi` |

## ⚙️ Step-by-Step Solution

### Step 1: Examine the Monitoring Script

First, check what environment variables the script expects:

```bash
kubectl exec -n react-frontend react-frontend-monitor -c monitor-agent -- cat /opt/monitor/monitor.sh
```

You'll see the script expects:
- `APP_CPU_REQUEST`
- `APP_CPU_LIMIT`
- `APP_MEM_REQUEST`
- `APP_MEM_LIMIT`

### Step 2: Examine the Current Pod Manifest

```bash
cat /app/react-ui.yaml
```

**Initial State (Before Configuration):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: react-frontend-monitor
  namespace: react-frontend
  labels:
    app.kubernetes.io/name: react-frontend
    tier: frontend
spec:
  containers:
  - name: frontend-app
    image: nginx
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
  - name: monitor-agent
    image: busybox:1.36
    command: ["/bin/sh", "/opt/monitor/monitor.sh"]
    # ❌ No env section defined
    volumeMounts:
      - name: monitor-script
        mountPath: /opt/monitor
        readOnly: true
  volumes:
    - name: monitor-script
      configMap:
        name: monitor-agent-cm
        defaultMode: 0755
```

### Step 3: Edit the Pod Manifest

```bash
vi /app/react-ui.yaml
```

**Add the `env` section to the `monitor-agent` container:**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: react-frontend-monitor
  namespace: react-frontend
  labels:
    app.kubernetes.io/name: react-frontend
    tier: frontend
spec:
  containers:
  - name: frontend-app
    image: nginx
    resources:
      requests:
        cpu: "100m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
  
  - name: monitor-agent
    image: busybox:1.36
    command: ["/bin/sh", "/opt/monitor/monitor.sh"]
    
    # ✅ ADD THIS ENV SECTION
    env:
    - name: APP_CPU_REQUEST
      valueFrom:
        resourceFieldRef:
          containerName: frontend-app      # Reference the main container
          resource: requests.cpu            # Resource to expose
          divisor: 1m                       # Unit: millicores
    
    - name: APP_CPU_LIMIT
      valueFrom:
        resourceFieldRef:
          containerName: frontend-app
          resource: limits.cpu
          divisor: 1m
    
    - name: APP_MEM_REQUEST
      valueFrom:
        resourceFieldRef:
          containerName: frontend-app
          resource: requests.memory
          divisor: 1Mi                     # Unit: mebibytes
    
    - name: APP_MEM_LIMIT
      valueFrom:
        resourceFieldRef:
          containerName: frontend-app
          resource: limits.memory
          divisor: 1Mi
    
    volumeMounts:
      - name: monitor-script
        mountPath: /opt/monitor
        readOnly: true
  
  volumes:
    - name: monitor-script
      configMap:
        name: monitor-agent-cm
        defaultMode: 0755
```

### Step 4: Apply the Changes

Delete the existing Pod and apply the updated manifest:

```bash
kubectl delete pod react-frontend-monitor -n react-frontend
kubectl apply -f /app/react-ui.yaml
```

### Step 5: Wait for the Pod to be Ready

```bash
kubectl wait --for=condition=ready pod/react-frontend-monitor -n react-frontend --timeout=60s
```

### Step 6: Verify the Monitor Logs

Check that the monitor now displays correct resource values:

```bash
kubectl logs -n react-frontend react-frontend-monitor -c monitor-agent
```

**Expected Output:**

```
========================================
 🚀 React Frontend Resource Monitor
========================================
 ⚙️  CPU Request  : 100m
 ⚙️  CPU Limit    : 500m
 🧠 Mem Request: 128Mi
 🧠 Mem Limit  : 256Mi
----------------------------------------
2025-01-15T10:30:45+00:00  ⚙️ CPU_REQ=100m | CPU_LIM=500m | 🧩 MEM_REQ=128Mi | MEM_LIM=256Mi
```

## 🔍 Understanding the Configuration

### resourceFieldRef Breakdown

```yaml
- name: APP_CPU_REQUEST           # Environment variable name
  valueFrom:                       # Source of the value
    resourceFieldRef:              # Use resourceFieldRef
      containerName: frontend-app  # Which container to reference
      resource: requests.cpu       # Which resource field to expose
      divisor: 1m                  # Unit conversion
```

### What Each Field Does

| Field | Description |
|-------|-------------|
| **`containerName`** | Specifies which container's resources to reference (required when referencing another container) |
| **`resource`** | Which resource field to expose (`requests.cpu`, `limits.cpu`, `requests.memory`, `limits.memory`) |
| **`divisor`** | Controls the unit of measurement (`1m` for millicores, `1Mi` for mebibytes) |

### Divisor Values

| Divisor | Effect | Example |
|---------|--------|---------|
| `1m` | Millicores | `100m` → `100` |
| `1` | Core | `500m` → `0.5` |
| `1Mi` | Mebibytes | `256Mi` → `256` |
| `1Ki` | Kibibytes | `128Mi` → `131072` |
| `1` | Bytes | `256Mi` → `268435456` |

## 📊 Downward API Reference

### resourceFieldRef Fields

| Field | Description | Common Divisors |
|-------|-------------|-----------------|
| `requests.cpu` | CPU request value | `1m` (millicores) |
| `limits.cpu` | CPU limit value | `1m` (millicores) |
| `requests.memory` | Memory request value | `1Mi`, `1Ki`, `1` |
| `limits.memory` | Memory limit value | `1Mi`, `1Ki`, `1` |
| `requests.ephemeral-storage` | Ephemeral storage request | `1Mi`, `1Ki`, `1` |
| `limits.ephemeral-storage` | Ephemeral storage limit | `1Mi`, `1Ki`, `1` |

### fieldRef Fields (Pod Metadata)

| Field | Description |
|-------|-------------|
| `metadata.name` | Pod name |
| `metadata.namespace` | Pod namespace |
| `metadata.uid` | Pod UID |
| `metadata.labels['key']` | Specific label value |
| `metadata.annotations['key']` | Specific annotation value |
| `spec.serviceAccountName` | Service account name |
| `spec.nodeName` | Node name where Pod is running |
| `status.podIP` | Pod IP address |
| `status.hostIP` | Host node IP address |

## 🔍 Troubleshooting

| Problem | Solution |
|---------|----------|
| **Environment variables show empty** | Check `containerName` is correct and matches the main container name |
| **Wrong units (e.g., 0.5 instead of 500m)** | Ensure `divisor: 1m` is set for CPU values |
| **Memory shows in bytes instead of MiB** | Ensure `divisor: 1Mi` is set for memory values |
| **Pod fails to start** | Check YAML syntax with `kubectl apply --dry-run=client -f /app/react-ui.yaml` |
| **Script still shows empty values** | Verify the Pod was recreated: `kubectl get pod -n react-frontend` |
| **containerName not specified** | `containerName` is **required** when referencing another container's resources |

## 🔑 Best Practices

| Best Practice | Why |
|---------------|-----|
| **Use appropriate divisors** | Match the divisor to your application's needs (`1m` for millicores, `1Mi` for mebibytes) |
| **Specify containerName** | Always specify the source container when referencing resources from another container |
| **Handle missing values** | Applications should handle cases where Downward API values might be unavailable |
| **Use volumes for dynamic data** | Use downward API volumes instead of env vars for labels/annotations that might change |
| **Keep it simple** | Only expose the information your application actually needs |
| **Test after changes** | Always verify with `kubectl logs` after applying changes |

---

## 🎯 Comparison with Other Approaches

| Approach | Use Case | Pros | Cons |
|----------|----------|------|------|
| **Downward API (env)** | Static Pod/container info needed at startup | Simple, fast, no API calls | Values are static (no updates) |
| **Downward API (volume)** | Dynamic labels/annotations that may change | Updates automatically | Slightly more complex |
| **ConfigMap** | Application configuration data | Flexible, shareable | Can't access Pod metadata |
| **Secret** | Sensitive configuration data | Secure, encrypted | Can't access Pod metadata |
| **Kubernetes API** | Complex queries, cluster-wide information | Full access to all data | Requires permissions, higher latency |

## 📝 Quick Reference Cheat Sheet

```yaml
# Downward API - resourceFieldRef for another container
env:
- name: APP_CPU_REQUEST
  valueFrom:
    resourceFieldRef:
      containerName: frontend-app   # Source container
      resource: requests.cpu          # Resource field
      divisor: 1m                     # Unit (millicores)

- name: APP_MEM_REQUEST
  valueFrom:
    resourceFieldRef:
      containerName: frontend-app
      resource: requests.memory
      divisor: 1Mi                    # Unit (mebibytes)

# Downward API - fieldRef for Pod metadata
env:
- name: POD_NAME
  valueFrom:
    fieldRef:
      fieldPath: metadata.name

- name: POD_NAMESPACE
  valueFrom:
    fieldRef:
      fieldPath: metadata.namespace

- name: POD_IP
  valueFrom:
    fieldRef:
      fieldPath: status.podIP
```
