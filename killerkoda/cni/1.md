# 🧠 CKA: Installing Calico CNI with Tigera Operator for Single‑Node Platform

This comprehensive guide walks you through installing **Project Calico** as the Container Network Interface (CNI) plugin on a **single‑node Kubernetes cluster** using the **Tigera Operator**.  
We will:

- Verify the cluster is ready.
- Install the Tigera Operator.
- Create an `Installation` custom resource with the correct Pod CIDR.
- Verify all components are running.
- Test pod‑to‑pod connectivity and NetworkPolicy enforcement.

---

## 📌 Prerequisites

- A single‑node Kubernetes cluster initialised with `kubeadm`.
- The cluster is up but **may have a `NotReady` node** until a CNI is installed.
- `kubectl` is configured and working.
- The existing **Pod CIDR** (e.g., `10.244.0.0/16`) is known.

---

## 🚀 Step‑by‑Step Solution

### Step 1 – Verify the Cluster Status

Check that the cluster is initialised and the control‑plane components are running.

```bash
kubectl get nodes
```

If the node is `NotReady`, that is expected – we will fix it with Calico.

Check system pods:

```bash
kubectl get pods -n kube-system
```

CoreDNS may be in `Pending` state because no CNI is available yet.

---

### Step 2 – Determine the Existing Pod CIDR

We must configure Calico to use the **same Pod CIDR** that `kubeadm` was initialised with. This is usually defined in the `kubeadm-config` ConfigMap.

```bash
kubectl -n kube-system get cm kubeadm-config -o jsonpath='{.data.ClusterConfiguration}' | grep -i podsubnet
```

Alternatively, check the node’s pod CIDR:

```bash
kubectl describe node | grep -i podcidr
```

Example output:
```
PodCIDR:                      10.244.0.0/24
```

In our case, the cluster was configured with a **/16** Pod CIDR (e.g., `10.244.0.0/16`). Note this value – we will use it later.

---

### Step 3 – Install the Tigera Operator

The Tigera Operator manages Calico’s lifecycle. Apply its manifest from the official URL:

```bash
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.31.3/manifests/tigera-operator.yaml
```

Wait for the operator to be ready:

```bash
kubectl wait --for=condition=ready pod -l k8s-app=tigera-operator -n tigera-operator --timeout=300s
```

Verify it is running:

```bash
kubectl get pods -n tigera-operator
```

Expected output:
```
NAME                               READY   STATUS    RESTARTS   AGE
tigera-operator-xxxxxxxxxx-xxxxx   1/1     Running   0          30s
```

---

### Step 4 – Create the `Installation` Custom Resource

The `Installation` CR tells the Operator how to configure Calico. We need to specify:

- The **Pod CIDR** (from Step 2).
- The **encapsulation** type (`VXLANCrossSubnet` is a good default for single‑node).
- **NAT** settings.
- **Block size** (default `/26` – 64 IPs per node – is fine).

Create the following YAML and apply it:

```bash
kubectl create -f - <<EOF
apiVersion: operator.tigera.io/v1
kind: Installation
metadata:
  name: default
spec:
  calicoNetwork:
    ipPools:
    - blockSize: 26
      cidr: 10.244.0.0/16        # Must match your cluster’s Pod CIDR
      encapsulation: VXLANCrossSubnet
      natOutgoing: Enabled
      nodeSelector: all()
EOF
```

**Explanation of fields:**

| Field | Value | Meaning |
|-------|-------|---------|
| `metadata.name` | `default` | The installation must be named `default` – this is required. |
| `spec.calicoNetwork.ipPools[0].cidr` | `10.244.0.0/16` | The Pod CIDR range. Must match the cluster’s configuration. |
| `blockSize` | `26` | Each node gets a `/26` subnet (64 IPs). |
| `encapsulation` | `VXLANCrossSubnet` | Uses VXLAN only for cross‑subnet traffic; direct routing within the same subnet. |
| `natOutgoing` | `Enabled` | NAT is applied for traffic leaving the cluster (e.g., to external networks). |
| `nodeSelector` | `all()` | Applies the IP pool to all nodes. |

> ⚠️ **Important:** If your cluster uses a different Pod CIDR (e.g., `192.168.0.0/16`), replace it accordingly.

### Step 5 – Monitor Calico Deployment

After creating the `Installation`, the Operator will deploy Calico components. Watch the status:

```bash
watch kubectl get tigerastatus
```

Press `Ctrl+C` once all components show `Available: True`. Alternatively:

```bash
kubectl get tigerastatus -w
```

Wait for components like `calico`, `apiserver`, `typha` to become available.

---

### Step 6 – Verify Calico System Pods

Check that all Calico pods are running:

```bash
kubectl get pods -n calico-system
```

Expected pods:
- `calico-kube-controllers` (deployment)
- `calico-node` (daemonset – one pod per node)
- `calico-typha` (optional, for scaling)
- `csi-node-driver` (if using CSI)

Also check the Calico API server:

```bash
kubectl get pods -n calico-apiserver
```

---

### Step 7 – Verify Node Status

Now the node should become `Ready`. Check:

```bash
kubectl get nodes
```

If it is still `NotReady`, wait a minute and re‑check. Also verify that CoreDNS pods are now `Running`:

```bash
kubectl get pods -n kube-system
```

---

### Step 8 – Test Pod‑to‑Pod Connectivity and NetworkPolicy

**Objective:** Ensure pods get IPs from the correct CIDR and can communicate, then test a simple NetworkPolicy.

#### 8.1 Create a test namespace
```bash
kubectl create namespace policy-test
```

#### 8.2 Deploy two nginx pods
```bash
kubectl run frontend --image=nginx --namespace=policy-test
kubectl run backend --image=nginx --namespace=policy-test
```

Wait for them to be ready:
```bash
kubectl wait --for=condition=ready pod -l run=frontend -n policy-test --timeout=60s
kubectl wait --for=condition=ready pod -l run=backend -n policy-test --timeout=60s
```

#### 8.3 Check their IPs
```bash
kubectl get pods -n policy-test -o wide
```
Both IPs should be within the `/16` CIDR (e.g., `10.244.x.x`).

#### 8.4 Test connectivity (should work)
```bash
kubectl exec -n policy-test frontend -- curl -s --max-time 5 backend
```
This should return the Nginx welcome page.

#### 8.5 Apply a NetworkPolicy that denies all ingress to `backend`
```bash
kubectl create -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-ingress
  namespace: policy-test
spec:
  podSelector:
    matchLabels:
      run: backend
  policyTypes:
  - Ingress
EOF
```

Now test again (should fail / timeout):
```bash
kubectl exec -n policy-test frontend -- curl -s --max-time 5 backend || echo "✅ Blocked as expected"
```

#### 8.6 Allow traffic from `frontend` to `backend`
```bash
kubectl create -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
  namespace: policy-test
spec:
  podSelector:
    matchLabels:
      run: backend
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          run: frontend
    ports:
    - protocol: TCP
      port: 80
EOF
```

Now connectivity should be restored:
```bash
kubectl exec -n policy-test frontend -- curl -s --max-time 5 backend
```

## 🧩 Conceptual Summary

### How Calico Works with the Tigera Operator

```
Tigera Operator (deployment)
        │
        ├─ Watches Installation CR
        │
        └─ Deploys Calico components:
            ├─ calico-node (DaemonSet on every node)
            │   ├─ Felix – policy enforcement (iptables/eBPF)
            │   ├─ BIRD – BGP routing
            │   └─ confd – config management
            ├─ calico-kube-controllers – sync policies
            └─ calico-typha – scaling helper
```

### CNI Plugin Flow

1. **Pod created** → kubelet invokes CNI plugin (`/opt/cni/bin/calico`).
2. CNI plugin requests an IP from Calico IPAM.
3. IPAM allocates an IP from the configured pool (`10.244.0.0/16`).
4. CNI creates a veth pair, assigns IP, sets up routes.
5. `calico-node` updates routing and iptables rules.
6. Pod now has network connectivity with policies enforced.

### NetworkPolicy Enforcement

- When you create a `NetworkPolicy`, the API server stores it.
- `calico-kube-controllers` watches and syncs policies to Calico datastore.
- `calico-node` (Felix) converts the policy into kernel‑level rules (iptables or eBPF).
- Traffic is filtered in real time at the node level.

## 🎯 Key Takeaways for CKA

- **CNI is essential** – without it, nodes stay `NotReady` and pods can’t get IPs.
- **Tigera Operator** simplifies Calico lifecycle management via CRDs.
- The **`Installation` CR** must be named `default` and must specify the **correct Pod CIDR** (match the cluster’s).
- **Encapsulation** (`VXLANCrossSubnet`) is a safe default for most environments.
- Always verify with pod‑to‑pod connectivity and NetworkPolicy tests.
