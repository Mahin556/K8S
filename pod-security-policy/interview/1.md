## What is a Pod Security Policy (PSP)?

### What is PSP?
Pod Security Policy is a cluster-level resource that controls security-sensitive aspects of pod specification.

### Key Points:
- Went into **beta in Kubernetes 1.22**
- Became **GA (Generally Available) in Kubernetes 1.25**
- Defines a set of conditions that a pod must meet to be accepted into the cluster

### What PSP Controls:
- Running privileged containers
- Host namespace sharing
- Host networking and ports
- Volume types that can be used
- User and group IDs for containers
- Linux capabilities
- SELinux contexts
- And more...

"The reason this is important is because we have to use the latest version of Kubernetes. PSP is now GA, so interviewers will expect you to know about it."

## What is Pod Security Policy?

**Pod Security Policy (PSP)** is a cluster-level Kubernetes resource that **enforces security standards** for pods before they're allowed to run in your cluster.

Think of it as a **security gatekeeper** that checks every pod against a set of rules.

```
Pod Creation Request
        ↓
PSP Admission Controller
        ↓
Check against policies:
├─ Running as privileged? ❌ Denied
├─ Using hostPath volume? ❌ Denied
├─ Running as root? ❌ Denied
└─ Meets all criteria? ✅ Allow
        ↓
Pod scheduled (or rejected)
```

## Why PSP Matters (Security Perspective)

### Problem: Unrestricted Containers ❌

```yaml
# Anyone can deploy this:
apiVersion: v1
kind: Pod
metadata:
  name: malicious-pod
spec:
  containers:
  - name: bad-app
    image: evil:latest
    securityContext:
      privileged: true          # ❌ Full host access!
      runAsUser: 0              # ❌ Running as root!
    volumeMounts:
    - name: host-fs
      mountPath: /host
  volumes:
  - name: host-fs
    hostPath:
      path: /                    # ❌ Access entire host!
  hostNetwork: true             # ❌ Share host network!
  hostPID: true                 # ❌ See all processes!
```

**What this malicious pod can do:**

```
├─ Read all host files (secrets, configs)
├─ Access all host devices
├─ See all running processes
├─ Modify host filesystem
├─ Access host network
├─ Escape container and compromise host
└─ Attack other containers on same node
```

---

### Solution: Pod Security Policy ✅

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted
spec:
  # ❌ Prevent privileged containers
  privileged: false
  
  # ❌ Prevent running as root
  runAsUser:
    rule: 'MustRunAsNonRoot'
  
  # ❌ Drop dangerous capabilities
  requiredDropCapabilities:
  - ALL
  allowedCapabilities:
  - NET_BIND_SERVICE
  
  # ❌ Prevent namespace sharing
  hostNetwork: false
  hostPID: false
  hostIPC: false
  
  # ❌ Block host filesystem access
  volumes:
  - 'configMap'
  - 'emptyDir'
  - 'projected'
  - 'secret'
  - 'downwardAPI'
  - 'persistentVolumeClaim'
  # hostPath is NOT in the list - denied!
  
  # ✅ Require read-only root filesystem
  readOnlyRootFilesystem: true
  
  # ✅ Force specific SELinux context
  seLinux:
    rule: 'MustRunAs'
    seLinuxOptions:
      level: 's0:c123,c456'
```

**Now the malicious pod is REJECTED:**

```
Error: Pod violates PSP:
├─ ❌ privileged: true not allowed
├─ ❌ runAsUser: 0 (root) not allowed
├─ ❌ hostNetwork: true not allowed
├─ ❌ hostPID: true not allowed
├─ ❌ hostPath volume not allowed
└─ Pod creation REJECTED ❌
```

## Detailed PSP Controls

### 1. Privileged Container Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: no-privileged
spec:
  privileged: false  # ← Key line
```

**What it prevents:**

```
Privileged mode gives:
├─ Direct access to host devices (/dev/*)
├─ Ability to mount host filesystems
├─ No namespace isolation
└─ Essentially = host access

❌ Denied pods:
securityContext:
  privileged: true

✅ Allowed pods:
securityContext:
  privileged: false (or omitted)
```

---

### 2. Host Namespace Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: no-host-namespaces
spec:
  hostNetwork: false    # Don't share host network
  hostPID: false        # Don't see host processes
  hostIPC: false        # Don't share IPC
```

**What it prevents:**

```
Without these controls, pods can:
├─ See all host network interfaces
├─ Intercept network traffic (sniffing)
├─ See all host processes (hostPID)
├─ Communicate with host IPC sockets (hostIPC)
└─ Compromise other containers

❌ Denied pods:
spec:
  hostNetwork: true
  hostPID: true
  hostIPC: true

✅ Allowed pods:
# Uses pod network, process, IPC isolation
```

---

### 3. Volume Type Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted-volumes
spec:
  volumes:
  - 'configMap'                    # ✅ Safe
  - 'emptyDir'                     # ✅ Safe
  - 'secret'                       # ✅ Safe (with caution)
  - 'persistentVolumeClaim'        # ✅ Safe
  - 'projected'                    # ✅ Safe
  - 'downwardAPI'                  # ✅ Safe
  # hostPath removed - denied!
  # gcePersistentDisk removed - denied!
```

**What hostPath can do (dangerous):**

```
hostPath allows:
├─ Mount: /etc → Read system config
├─ Mount: /root → Read root's home
├─ Mount: /var/log → Read system logs
├─ Mount: / → Access entire host
└─ Can read sensitive files!

❌ Denied:
volumes:
- name: host-fs
  hostPath:
    path: /etc

✅ Allowed:
volumes:
- name: config
  configMap:
    name: app-config
```

---

### 4. User & Group ID Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restrict-user
spec:
  runAsUser:
    rule: 'MustRunAsNonRoot'    # ← Must not be root
  runAsGroup:
    rule: 'MustRunAs'
    ranges:
    - min: 1
      max: 65535
  fsGroup:
    rule: 'MustRunAs'
    ranges:
    - min: 1
      max: 65535
```

**Why non-root is important:**

```
Running as root:
├─ Can access ALL files (no permission checks)
├─ Can run ANY command
├─ If container compromised = full host access
└─ Maximum privilege = maximum risk

Running as non-root (e.g., uid: 1000):
├─ Limited file access
├─ Cannot elevate privileges
├─ If compromised = limited damage
└─ Least privilege = better security

❌ Denied:
securityContext:
  runAsUser: 0

✅ Allowed:
securityContext:
  runAsUser: 1000  # Regular user
```

---

### 5. Linux Capabilities Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: drop-capabilities
spec:
  # Remove ALL Linux capabilities
  requiredDropCapabilities:
  - ALL
  
  # Allow ONLY NET_BIND_SERVICE if needed
  allowedCapabilities:
  - NET_BIND_SERVICE
```

**What Linux capabilities are:**

```
Capabilities = Fine-grained root permissions

CAP_NET_ADMIN:
├─ Network configuration
├─ Can sniff traffic
└─ Very dangerous

CAP_SYS_ADMIN:
├─ System administration
├─ Can load kernel modules
└─ Extremely dangerous

CAP_DAC_OVERRIDE:
├─ Bypass file permissions
├─ Can read any file
└─ Very dangerous

Default: Containers start with many capabilities
PSP: Drop all, allow only what's needed
```

---

### 6. SELinux & AppArmor Control

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: selinux-controlled
spec:
  seLinux:
    rule: 'MustRunAs'
    seLinuxOptions:
      level: 's0:c100,c200'
  
  appArmor:
    defaultProfile: 'runtime/default'
    allowedProfiles:
    - 'runtime/default'
    - 'localhost/my-app-profile'
```

**What these do:**

```
SELinux (Security Enhanced Linux):
├─ Mandatory Access Control (MAC)
├─ Kernel-level enforcement
├─ Can restrict what processes can access
└─ Fine-grained security labels

AppArmor:
├─ Easier than SELinux
├─ Profile-based restrictions
├─ Can restrict system calls
└─ Path-based access control
```

## Complete PSP Example: Restrictive Policy

```yaml
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted
spec:
  # ❌ No privileged containers
  privileged: false
  allowPrivilegeEscalation: false
  
  # ❌ No root user
  runAsUser:
    rule: 'MustRunAsNonRoot'
  
  # ✅ Drop all dangerous capabilities
  requiredDropCapabilities:
  - ALL
  allowedCapabilities:
  - NET_BIND_SERVICE
  
  # ❌ No namespace sharing
  hostNetwork: false
  hostPID: false
  hostIPC: false
  hostPorts:
  - min: 1
    max: 65535
  
  # ✅ Safe volumes only
  volumes:
  - 'configMap'
  - 'emptyDir'
  - 'projected'
  - 'secret'
  - 'downwardAPI'
  - 'persistentVolumeClaim'
  
  # ✅ Read-only filesystem
  readOnlyRootFilesystem: true
  
  # ✅ Restrict groups
  fsGroup:
    rule: 'RunAsAny'
  
  # ✅ SELinux enforcement
  seLinux:
    rule: 'MustRunAs'
    seLinuxOptions:
      level: 's0:c123,c456'
```

## PSP vs Pod (Pod Wins Restrictions)

When a pod specification and PSP conflict, **the more restrictive wins**:

```yaml
# Pod wants to run as root
pod:
  securityContext:
    runAsUser: 0

# PSP says must be non-root
psp:
  runAsUser:
    rule: 'MustRunAsNonRoot'

# Result: Pod REJECTED
# PSP wins - more restrictive
```

## Using RBAC with PSP (Access Control)

PSP alone isn't enough - you need RBAC to control who can use which policies:

```yaml
---
# Restrictive PSP
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: restricted
spec:
  privileged: false
  runAsUser:
    rule: 'MustRunAsNonRoot'
  # ... other restrictions

---
# Permissive PSP (for special cases)
apiVersion: policy/v1beta1
kind: PodSecurityPolicy
metadata:
  name: privileged
spec:
  privileged: true
  allowPrivilegeEscalation: true
  # ... fewer restrictions

---
# RBAC: Regular devs use 'restricted'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: default-dev-psp
rules:
- apiGroups: ['policy']
  resources: ['podsecuritypolicies']
  verbs: ['use']
  resourceNames: ['restricted']

---
# RBAC: Admins can use 'privileged'
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: admin-psp
rules:
- apiGroups: ['policy']
  resources: ['podsecuritypolicies']
  verbs: ['use']
  resourceNames: ['restricted', 'privileged']
```

## Real-World Scenario: Pod Gets Rejected

### Attempt 1: Privileged Container ❌

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: myapp:1.0
    securityContext:
      privileged: true  # ❌ Not allowed!
```

**Error:**

```
Error creating pod:
pods "app" is forbidden:
unable to validate against any pod security policy:
[spec.containers[0].securityContext.privileged: Invalid value: true: privilege mode is not allowed]
```

---

### Attempt 2: Running as Root ❌

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: myapp:1.0
    securityContext:
      runAsUser: 0  # ❌ Root not allowed!
```

**Error:**

```
Error creating pod:
pods "app" is forbidden:
unable to validate against any pod security policy:
[spec.securityContext.runAsUser: Invalid value: 0: must run as a non-root user]
```

---

### Attempt 3: Using hostPath ❌

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  containers:
  - name: app
    image: myapp:1.0
    volumeMounts:
    - name: host-data
      mountPath: /data
  volumes:
  - name: host-data
    hostPath:
      path: /etc  # ❌ hostPath not allowed!
```

**Error:**

```
Error creating pod:
pods "app" is forbidden:
unable to validate against any pod security policy:
[spec.volumes[0].hostPath: Invalid value: "hostPath": hostPath volumes are not allowed]
```

---

### Attempt 4: Correct Pod ✅

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app
spec:
  securityContext:
    runAsUser: 1000        # ✅ Non-root
    fsGroup: 1000
  containers:
  - name: app
    image: myapp:1.0
    securityContext:
      allowPrivilegeEscalation: false  # ✅ No escalation
      readOnlyRootFilesystem: true     # ✅ Read-only
      capabilities:
        drop:
        - ALL
        add:
        - NET_BIND_SERVICE
    volumeMounts:
    - name: config
      mountPath: /etc/config
  volumes:
  - name: config
    configMap:               # ✅ Safe volume type
      name: app-config
```

**Result:**

```
Pod created successfully ✅
```

## Interview Answer Template

**Question: "What is Pod Security Policy?"**

**Answer:**

```
Pod Security Policy (PSP) is a cluster-level Kubernetes resource
that enforces security standards for pods before they're created.

Key points:

1. WHAT IT CONTROLS:
   ├─ Privileged containers (yes/no)
   ├─ Host namespace sharing (network, PID, IPC)
   ├─ Volume types (which are allowed)
   ├─ User/Group IDs (non-root requirement)
   ├─ Linux capabilities (drop dangerous ones)
   └─ SELinux/AppArmor contexts

2. EVOLUTION:
   ├─ Kubernetes 1.22: Beta
   ├─ Kubernetes 1.25: GA (Generally Available)
   └─ Now: Production-ready, standard practice

3. ENFORCEMENT:
   ├─ PSP admission controller validates pods
   ├─ If pod violates policy → Rejected
   ├─ If pod meets policy → Allowed
   └─ Works at cluster level (all namespaces)

4. BEST PRACTICES:
   ├─ Create restrictive PSP for most workloads
   ├─ Use RBAC to control who can use which PSP
   ├─ Combine with network policies for defense in depth
   └─ Regularly audit PSP violations

5. WHY IT MATTERS:
   ├─ Prevents privilege escalation
   ├─ Reduces container escape risks
   ├─ Enforces least privilege principle
   └─ Critical for multi-tenant clusters
```
