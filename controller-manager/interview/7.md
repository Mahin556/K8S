# Kubernetes Deployment Strategies — Complete Guide

---

## Strategy 1 — Recreate (simplest, has downtime)

**How it works:** terminates ALL old pods, then starts all new pods.
Zero overlap — no two versions ever run simultaneously.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 4
  strategy:
    type: Recreate          # terminates all v1 pods, then creates all v2 pods
  template:
    spec:
      containers:
        - name: myapp
          image: myapp:v2
```

**Timeline:**
```
T0: [v1] [v1] [v1] [v1]
T1: [ ↓] [ ↓] [ ↓] [ ↓]   ← all terminated (DOWNTIME starts here)
T2: [v2] [v2] [v2] [v2]   ← all new pods starting
T3: [v2] [v2] [v2] [v2]   ← (DOWNTIME ends)
```

✅ Use when: database schema changes that v1 and v2 are incompatible with,
   or stateful workloads where two versions running together causes corruption.
❌ Avoid when: any user-facing service where uptime matters.

## Strategy 2 — Rolling Update (default, most common)

**How it works:** gradually replaces pods. Two key knobs control behavior.

### `maxUnavailable` — how many pods can be DOWN during update
- Absolute number (`1`) or percentage (`25%`)
- Default: `25%`
- Set to `0` for zero-downtime guarantee — ensures you always have full
  capacity serving traffic. Tradeoff: slower rollout.

### `maxSurge` — how many EXTRA pods can be created above desired count
- Absolute number (`1`) or percentage (`25%`)
- Default: `25%`
- Higher = faster rollout but more CPU/memory quota temporarily consumed.

**Note:** both cannot be 0 at the same time — that would make progress
impossible (no pods can be terminated without replacing, no pods can be
added without terminating first).

---

### 2a — Safe Rolling Update (recommended production default)
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
  namespace: production
spec:
  replicas: 4
  revisionHistoryLimit: 10         # keep 10 old ReplicaSets for rollback
  progressDeadlineSeconds: 600     # fail if rollout stalls for 10 minutes
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                  # create 1 extra pod during update
      maxUnavailable: 0            # never drop below desired count
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: myapp
          image: myapp:v2

          readinessProbe:           # CRITICAL — controls when pod gets traffic
            httpGet:
              path: /ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            successThreshold: 2    # must pass TWICE before receiving traffic
            failureThreshold: 3

          livenessProbe:            # restarts deadlocked pods
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 15
            periodSeconds: 10
            failureThreshold: 5

          startupProbe:             # gates liveness/readiness during slow boot
            httpGet:
              path: /health
              port: 8080
            failureThreshold: 30
            periodSeconds: 5        # allows up to 150s for startup

          lifecycle:
            preStop:
              exec:
                command: ["/bin/sh", "-c", "sleep 10"]
                # Why: when a pod is terminated, its endpoint is removed from
                # the Service, but in-flight requests may still arrive during
                # propagation delay (~5-15s). The sleep gives load balancers
                # time to stop routing traffic before the process shuts down.
                # Without this, every rolling update drops some requests.
```

**Timeline (replicas=4, maxSurge=1, maxUnavailable=0):**
```
T0: [v1][v1][v1][v1]               — 4 running
T1: [v1][v1][v1][v1][v2]           — 1 new created (surge), wait for Ready
T2: [v1][v1][v1][v2]               — v2 Ready, 1 old terminated
T3: [v1][v1][v1][v2][v2]           — next surge
T4: [v1][v1][v2][v2]               — old terminated
... repeat until complete
T9: [v2][v2][v2][v2]               — done, 0 downtime
```

---

### 2b — Fast Rolling Update (high traffic, resource headroom available)
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 2          # create 2 extra pods at once = faster rollout
    maxUnavailable: 1    # allow 1 pod down = even faster, slight capacity dip
```

---

### 2c — Instant Rollout (effectively Blue/Green via rolling mechanism)
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 100%       # ceil(4 * 1.0) = 4 extra pods — all new created at once
    maxUnavailable: 0    # as each new pod passes readiness, one old is removed
```
All new pods spin up simultaneously, then old pods are removed as each new
one passes readiness — the effect is identical to blue/green but uses a
single Deployment instead of two.

---

### 2d — Ramped Slow Rollout (cautious, maximum safety)
```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # absolute minimum surge
    maxUnavailable: 0    # never reduce capacity
# Each iteration: create 1 pod → wait for readiness → remove 1 old pod → repeat.
# Slowest possible rollout — gives maximum time to observe each new pod's
# behaviour before the next one is replaced.
```

## Strategy 3 — Blue / Green (instant traffic switch)

**How it works:** run v1 (blue) and v2 (green) as separate Deployments at
full replica count. Switch traffic by updating the Service selector. Rollback
is also instant — just flip the selector back.

```yaml
# Blue (current production) Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-blue
spec:
  replicas: 4
  selector:
    matchLabels:
      app: myapp
      version: blue
  template:
    metadata:
      labels:
        app: myapp
        version: blue     # ← unique label for this version
    spec:
      containers:
        - name: myapp
          image: myapp:v1
---
# Green (new version) Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-green
spec:
  replicas: 4
  selector:
    matchLabels:
      app: myapp
      version: green
  template:
    metadata:
      labels:
        app: myapp
        version: green    # ← unique label for this version
    spec:
      containers:
        - name: myapp
          image: myapp:v2
---
# Service — points at whichever version is "live"
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp
    version: blue         # ← change this to "green" to switch traffic
  ports:
    - port: 80
      targetPort: 8080
```

**Traffic switch:**
```bash
# Switch all traffic from blue to green instantly:
kubectl patch service myapp-service -p '{"spec":{"selector":{"version":"green"}}}'

# Instant rollback if issues:
kubectl patch service myapp-service -p '{"spec":{"selector":{"version":"blue"}}}'

# Clean up blue once green is stable:
kubectl delete deployment myapp-blue
```

**Timeline:**
```
Before switch:   [v1][v1][v1][v1]    [v2][v2][v2][v2]
                  ↑ traffic                ↑ idle

After selector:  [v1][v1][v1][v1]    [v2][v2][v2][v2]
                  ↑ idle                   ↑ traffic
```

✅ Use when: payment services, auth flows — anywhere instant rollback matters
   more than cost.
❌ Tradeoff: requires 2× resource cost during deployment window.

## Strategy 4 — Canary (gradual traffic shift with real-user testing)

**How it works:** route a small percentage of real traffic to the new version
first, monitor metrics, then gradually increase (or roll back if problems found).

### Native Kubernetes (approximate, pod-count-based traffic split)
```yaml
# Stable Deployment — 9 replicas = ~90% of traffic
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-stable
spec:
  replicas: 9
  selector:
    matchLabels:
      app: myapp        # note: no version label in selector
  template:
    metadata:
      labels:
        app: myapp
        version: stable
    spec:
      containers:
        - name: myapp
          image: myapp:v1
---
# Canary Deployment — 1 replica = ~10% of traffic
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-canary
spec:
  replicas: 1           # 1 out of 10 total pods = ~10%
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
        version: canary
    spec:
      containers:
        - name: myapp
          image: myapp:v2
---
# Single Service — selects ALL pods with app: myapp regardless of version
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  selector:
    app: myapp          # routes to both stable and canary pods
  ports:
    - port: 80
      targetPort: 8080
```

**Gradually increase canary:**
```bash
# Increase to 20% (2 canary, 8 stable):
kubectl scale deployment myapp-canary --replicas=2
kubectl scale deployment myapp-stable --replicas=8

# 50/50:
kubectl scale deployment myapp-canary --replicas=5
kubectl scale deployment myapp-stable --replicas=5

# 100% canary (full rollout):
kubectl scale deployment myapp-canary --replicas=10
kubectl delete deployment myapp-stable

# Problem found — rollback:
kubectl delete deployment myapp-canary   # 100% traffic back to stable instantly
```

**Important limitation:** native pod-count approach is approximate — you
cannot get exactly 5.3% with whole-number pod counts. For precise traffic
splitting (exact percentages, header-based routing, session-based routing),
you need a service mesh:

### Exact traffic splitting with Istio (5% canary)
```yaml
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: myapp-vs
spec:
  hosts:
    - myapp-service
  http:
    - route:
        - destination:
            host: myapp-service
            subset: stable
          weight: 95      # exact 95% to v1
        - destination:
            host: myapp-service
            subset: canary
          weight: 5       # exact 5% to v2
```

✅ Use when: A/B testing behaviour changes, validating new versions with
   real users before full rollout, feature flags.
❌ Tradeoff: two versions serving traffic simultaneously — users can get
   inconsistent experiences if the versions behave differently.

## Strategy 5 — Shadow Deployment (zero user impact testing)

**How it works:** mirror real production traffic to v2 in real time, but
discard v2's responses entirely — users only ever see v1's responses.
v2 gets real production load without affecting any real users.

```yaml
# With Istio traffic mirroring:
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: myapp-vs
spec:
  hosts:
    - myapp-service
  http:
    - route:
        - destination:
            host: myapp-stable     # users see this response
      mirror:
        host: myapp-shadow         # v2 gets real traffic, response discarded
      mirrorPercentage:
        value: 100.0               # mirror 100% of requests
```

✅ Use when: validating a new service version handles real production traffic
   patterns correctly — database query performance, memory usage, error rates —
   without any risk to real users.
❌ Tradeoff: requires a service mesh, double the compute cost, shadow
   service must be careful about side effects (don't write to production
   databases from shadow — you need a separate shadow DB).

## PodDisruptionBudget — critical companion to all strategies

Without this, a node drain during a rolling update could take down MORE
pods than your maxUnavailable setting allows. PDB adds a hard constraint
Kubernetes respects across ALL disruption sources — node drains, cluster
upgrades, manual deletions:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-pdb
spec:
  maxUnavailable: 1       # at most 1 pod down at any time from ANY cause
  selector:
    matchLabels:
      app: myapp
```

## Rollback commands (all strategies)

```bash
# See rollout history
kubectl rollout history deployment/myapp

# Rollback to previous version (one step back)
kubectl rollout undo deployment/myapp

# Rollback to a specific revision
kubectl rollout undo deployment/myapp --to-revision=3

# Pause a rollout mid-way (assess the situation)
kubectl rollout pause deployment/myapp

# Resume a paused rollout
kubectl rollout resume deployment/myapp

# Watch rollout progress live
kubectl rollout status deployment/myapp --watch

# Force rollout without image change (useful after ConfigMap change)
kubectl rollout restart deployment/myapp
```

## Decision guide — which strategy for which situation

| Situation | Strategy | Reason |
|---|---|---|
| Standard stateless app update | Rolling Update (maxUnavailable:0, maxSurge:1) | Zero downtime, built-in, simple |
| DB schema incompatible with v1 | Recreate | Must prevent v1/v2 running together |
| Payment / auth service | Blue/Green | Instant rollback capability outweighs 2× cost |
| Validate new version with real traffic | Canary | Limit blast radius to a subset of users |
| Test perf/behaviour without user risk | Shadow | Zero user exposure, real load |
| Slow-starting application | Rolling + startupProbe | Prevents liveness killing pods during boot |
| Large replica count, lots of headroom | maxSurge: 100% | Creates all new pods at once for fastest rollout |
| Cluster at near-full resource capacity | maxUnavailable: 1, maxSurge: 0 | No surge prevents scheduling failures |

## The most common real-world gotchas

**1. Missing readiness probe = immediate downtime**
If you don't configure a readiness probe, Kubernetes assumes the pod is
Ready the moment the container process starts — it routes traffic to it
before your app has actually finished initializing, causing errors on
every deploy. Readiness probe is NOT optional for zero-downtime deploys.

**2. Missing preStop sleep = dropped requests**
When a pod terminates, kube-proxy takes ~5-15s to update iptables rules
on all nodes. Requests keep arriving during that window. Without a preStop
sleep of ~10-15s, those requests hit a terminating pod and get connection-refused.

**3. progressDeadlineSeconds not set**
Without a deadline, a stuck rollout (ImagePullBackOff, CrashLoopBackOff)
hangs indefinitely. Your CI/CD pipeline will wait forever and never know
the deployment failed. Always set this.

**4. Blue/Green resource cost overlooked**
Blue/green requires exactly 2× your normal replica count during the
switchover window. If your namespace has resource quotas, the green
deployment may fail to schedule. Check quotas before using this strategy.

**5. Canary pod-count math is approximate**
1 canary pod out of 10 total = approximately 10%, but Kubernetes's
Service routes to any ready pod — if 2 pods are slow to start, you're
briefly at a different ratio. For exact percentages, use Istio or NGINX
Ingress canary annotations.
