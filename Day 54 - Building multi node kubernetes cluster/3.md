The note in your screenshot is basically saying:

> After installing Kubernetes components, rebooting all nodes (workers first, then control plane) helped stabilize the cluster, and the pods stopped restarting.

Here’s what’s going on **technically** and why a reboot often fixes issues after installing Kubernetes + CNI (like Calico).

---

# Why Reboot Helps After Kubernetes Installation

When you install Kubernetes with `kubeadm`, a lot of things are configured:

* kubelet service
* container runtime (containerd)
* CNI plugin (like Calico)
* iptables rules
* kernel networking settings
* systemd services
* network routes

Sometimes these components:

* Start in the wrong order
* Don’t reload configs properly
* Miss kernel settings
* Don’t apply networking rules fully

A reboot forces everything to restart **cleanly in the correct order**.

---

# Example of What Might Be Broken Before Reboot

## 1. Container Runtime Not Fully Ready

Kubelet depends on containerd:

```
kubelet → containerd → pods
```

If containerd starts late or reloads configs incorrectly:

* Pods may crash
* Pods may restart
* Pods may stay Pending

Reboot fixes the startup order.

---

## 2. CNI Plugin Not Fully Initialized

CNI (like Calico) sets up:

* Pod networking
* Routes
* Interfaces
* iptables rules

If this is partially applied:

```
Pod → No network → Restart
```

Reboot ensures:

* Interfaces recreated
* Routes re-added
* Rules applied

---

## 3. Kernel Settings Not Applied

You probably ran commands like:

```bash
sysctl net.bridge.bridge-nf-call-iptables=1
sysctl net.ipv4.ip_forward=1
```

Sometimes these:

* Apply partially
* Need reload
* Need reboot

Without them:

* Pods can’t communicate
* DNS fails
* Networking fails

---

## 4. iptables Rules Not Fully Loaded

Kubernetes creates many rules:

```
KUBE-SERVICES
KUBE-FORWARD
KUBE-NODEPORTS
```

If they’re inconsistent:

* Services fail
* Pods restart
* Networking breaks

Reboot resets networking state.

---

# Why Workers First, Then Control Plane

The note says:

> workers first, then control plane

This is recommended because:

## Workers depend on Control Plane

Workers need:

* API server
* Scheduler
* Controller manager

If control plane restarts first:

* Workers disconnect
* Pods restart

Better order:

```
1 Worker reboot
2 Worker ready
3 Next worker
4 Control plane reboot
```

---

# Why Pods Were Restarting

Likely causes before reboot:

* CNI not ready
* Routes missing
* kubelet reconnecting
* DNS failing
* containerd restarting

After reboot:

```
kubelet → containerd → CNI → API server
```

Everything aligns properly.

---

# Why Waiting 10–15 Minutes Helps

After installation:

* Controllers start
* DNS starts
* CNI configures nodes
* Pods stabilize

If you check too early:

```
Pods → Restarting
DNS → Not ready
Node → NotReady
```

After waiting:

```
Pods → Stable
DNS → Running
Node → Ready
```

---

# When Reboot is Normal

Reboot is common after:

* kubeadm init
* kubeadm join
* CNI installation
* Kernel changes
* Container runtime install

Even in labs and training, reboot is often the fastest fix.

---

# When Reboot is NOT Enough

In production, you should instead check:

```
journalctl -u kubelet
systemctl status containerd
kubectl get events
kubectl describe pod
```

But for learning clusters, reboot is often acceptable.
