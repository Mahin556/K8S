# 1. CNI Plugin Installation (What Actually Happens)

In your setup you installed **Calico CNI**. A CNI plugin is responsible for:

* Assigning Pod IPs (IPAM)
* Setting up Pod networking
* Creating routes
* Enabling Pod-to-Pod communication

Before CNI is installed:

```
Pod → No IP
Pod → No Network
Node → NotReady
```

After CNI is installed:

```
Pod → Gets IP
Pod → Network works
Node → Ready
```

---

## What kubelet Does with CNI

When kubelet creates a Pod:

```
kubelet → CNI → "Give me IP"
CNI → Assigns IP
CNI → Configures networking
```

So kubelet depends on CNI to make Pods usable.

---

# 2. Pod CIDR Configuration

You initialized Kubernetes with:

```bash
kubeadm init \
  --pod-network-cidr=192.168.0.0/16
```

This means:

```
Pod Network Range:
192.168.0.0 → 192.168.255.255
```

This range is used **only for Pods**.

Not nodes.
Not VMs.
Only Pods.

---

# 3. Why CoreDNS Pods Were Pending

Before installing CNI:

```bash
kubectl get pods -A
```

You saw:

```
coredns → Pending
```

This happens because:

### CoreDNS Needs:

* A node
* An IP address
* Networking

But:

```
No CNI → No IP → Pod can't start
```

So:

```
Scheduler → Assigns node
kubelet → Tries to start Pod
kubelet → Calls CNI
CNI → Not installed
Pod → Pending
```

---

# 4. After Installing CNI

After installing Calico:

```bash
kubectl apply -f calico.yaml
```

Now:

```
kubelet → CNI → Request IP
CNI → Assign IP
Pod → Running
```

You saw:

```
coredns → Running
```

---

# 5. How CoreDNS Got IP Address

After CNI installation:

```bash
kubectl get pods -A -o wide
```

You saw something like:

```
coredns → 192.168.x.x
```

This IP comes from:

```
--pod-network-cidr=192.168.0.0/16
```

So internally:

```
kubelet
   ↓
CNI (Calico)
   ↓
IPAM allocates IP
   ↓
Pod gets IP
```

Example:

```
Pod CIDR = 192.168.0.0/16
CoreDNS = 192.168.235.132
```

That’s why CoreDNS only started after CNI was installed.

Is CNI ready?

# 7. Control Plane Pods IP Address

You saw:

```
kube-apiserver → 172.x.x.x or 10.x.x.x or VPC IP
```

These pods are **hostNetwork pods**.

They run using:

```
hostNetwork: true
```

So they use:

```
Node IP
(VPC CIDR)
```

Not Pod CIDR.

---

## Example

Node IP:

```
VPC CIDR = 172.31.0.0/16
Node = 172.31.43.189
```

Control plane pods:

```
kube-apiserver → 172.31.43.189
scheduler → 172.31.43.189
controller → 172.31.43.189
```

They share node network.

---

# 8. Why Control Plane Pods Don't Use Pod CIDR

Because they start **before CNI exists**.

If they depended on CNI:

```
API Server wouldn't start
Cluster wouldn't start
```

So they use:

```
hostNetwork = true
```

Meaning:

```
Use node network
Use VPC CIDR
```

---

# 9. Difference Between CIDRs

## VPC CIDR (Node Network)

Example:

```
172.31.0.0/16
```

Used for:

* Nodes
* SSH
* API Server
* Control Plane Pods

Example:

```
Node = 172.31.43.189
```

---

## Pod CIDR (Pod Network)

Example:

```
192.168.0.0/16
```

Used for:

* Pods
* CoreDNS
* Applications

Example:

```
CoreDNS = 192.168.235.132
```

---

# 10. Flow of Pod IP Assignment

When Pod is created:

```
Scheduler
   ↓
Assign node
   ↓
kubelet
   ↓
CNI request
   ↓
IPAM assigns IP
   ↓
Pod starts
```

---

# 11. Why Web Pods Were Still Pending

Even after CNI, your web pods were pending because:

```
Control plane has taint:
node-role.kubernetes.io/control-plane:NoSchedule
```

So:

```
CoreDNS → Has toleration → Runs
Web Pods → No toleration → Pending
```
