Here's a breakdown of how it works, based on the official MetalLB documentation.

### ✅ Point 1: Single-Node Load Balancing (Bottleneck)

This is entirely accurate. In Layer 2 mode, all traffic for a given Service IP is routed through a **single, leader-elected node**.

*   **Why this happens:** The leader node uses ARP (for IPv4) or NDP (for IPv6) to announce to your network that it owns the Service's IP address. Because only one node can claim that IP at a time, all ingress traffic must pass through that single node.
*   **The consequence:** Your Service's total ingress bandwidth is limited to the bandwidth capacity of that one node. This creates a **"single-node bottleneck"**.
*   **Clarification:** MetalLB itself doesn't perform load balancing in this mode. Instead, it's the `kube-proxy` on that leader node that distributes the incoming traffic to the service's Pods, regardless of which node they are on.

### ✅ Point 2: Failover

This is also correct. If the leader node fails, MetalLB provides automatic failover to another node.

*   **How it works:** The remaining nodes detect the leader's failure via a memberlist protocol. After a short period, one of them will take over ownership of the Service IP.
*   **The catch (why it's a "disadvantage"):** This failover is **not instantaneous**. The process involves sending out gratuitous ARP packets to notify clients on the network that the MAC address for the Service IP has changed.
*   **Potential delay:** While most modern operating systems handle this update promptly, the failover can be **"potentially slow"**, often taking around **10 seconds**. During this transition, there might be a brief service interruption for clients with outdated cache entries.

### Summary

| Your Statement | Accuracy | MetalLB's Reality |
| :--- | :--- | :--- |
| **"Only single node Loadbalancing"** | **True** | All traffic is funneled through a single leader node, creating a bandwidth bottleneck. |
| **"Provide failover if leader fails"** | **True** | Automatic failover occurs, but it's not instant and can take ~10 seconds. |

Essentially, MetalLB's Layer 2 mode prioritizes simplicity and universality (working on any Ethernet network) over performance and high availability. For true load balancing and faster failover, you would need to use its **BGP mode**.
