The biggest difference between **Layer 2 mode** and **BGP mode** is this:

| Layer 2                      | BGP                                  |
| ---------------------------- | ------------------------------------ |
| One node owns the Service IP | Every node advertises the Service IP |
| All traffic enters one node  | Traffic is distributed by the router |
| MetalLB provides failover    | MetalLB provides true load balancing |
| Bottleneck on one node       | No single-node bottleneck            |

Let's understand exactly how BGP mode works.

---

# Step 1: Kubernetes Service

Suppose you create this Service.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx
spec:
  type: LoadBalancer
```

MetalLB allocates

```
192.168.1.200
```

---

# Step 2: Every node advertises the IP

Suppose the cluster has

```
Worker1
Worker2
Worker3
```

Instead of one node announcing the IP like Layer 2,

**every node advertises**

```
192.168.1.200
```

using BGP.

```
          Router
         /   |   \
        /    |    \
   Worker1 Worker2 Worker3

Advertised routes:

192.168.1.200 via Worker1
192.168.1.200 via Worker2
192.168.1.200 via Worker3
```

The router now knows there are **three equal-cost paths** (called **ECMP – Equal Cost Multi-Path**) to reach the same Service IP.

---

# Step 3: Router installs multiple routes

The router's routing table might look like:

```
Destination        Next Hop
-----------------------------
192.168.1.200      Worker1
192.168.1.200      Worker2
192.168.1.200      Worker3
```

Notice:

The destination is the **same IP**.

Only the **next hop** is different.

---

# Step 4: Client sends a request

Suppose a client sends

```
Client

↓

192.168.1.200
```

The packet reaches the router.

The router now has multiple next hops.

It must decide

```
Worker1 ?

Worker2 ?

Worker3 ?
```

---

# Step 5: Router performs load balancing

The router computes a **hash**.

For example

```
Hash(

Source IP
Destination IP
Protocol
Source Port
Destination Port

)
```

Suppose

```
Client A

10.0.0.50:45678

↓

192.168.1.200:80
```

Hash result

```
Hash = Worker2
```

Every packet belonging to this connection goes to Worker2.

---

Another client

```
10.0.0.80:62000

↓

192.168.1.200:80
```

Hash

```
Hash = Worker1
```

---

Third client

```
10.0.0.90

↓

192.168.1.200
```

Hash

```
Hash = Worker3
```

Now traffic is naturally spread.

```
           Router
          /   |   \
         /    |    \
        ↓     ↓     ↓
      W1     W2     W3
```

This is **true load balancing across nodes**.

---

# Step 6: kube-proxy forwards to Pods

Suppose

```
Worker1
    Pod A

Worker2
    Pod B

Worker3
    Pod C
```

If the router chooses Worker2,

the packet reaches Worker2.

Then kube-proxy decides

```
PodA ?

PodB ?

PodC ?
```

Suppose it chooses PodC.

```
Client

↓

Router

↓

Worker2

↓

PodC
```

Notice

The router balances **between nodes**.

kube-proxy balances **between pods**.

So there are **two stages of load balancing**:

```
Router

↓

Node

↓

Pod
```

---

# Why is it called Per-Connection?

Imagine downloading a file.

Thousands of packets belong to one TCP connection.

If packets went

```
Packet1 → Worker1

Packet2 → Worker2

Packet3 → Worker3
```

they could arrive out of order.

TCP would think packets were lost, causing retransmissions and poor performance.

Instead, the router keeps all packets of the same TCP connection on one path.

Example:

```
Connection 1

Packet1 → Worker2

Packet2 → Worker2

Packet3 → Worker2
```

A different connection may go elsewhere:

```
Connection 2

Packet1 → Worker1

Packet2 → Worker1
```

So **connections** are balanced, not **individual packets**.

---

# 3-Tuple vs 5-Tuple Hashing

## 3-Tuple

The router hashes:

```
Protocol

Source IP

Destination IP
```

Example

```
TCP

10.0.0.50

192.168.1.200
```

Every connection between these two IPs goes to the same node.

Even if one client opens 20 browser tabs, all of them may go to Worker2 because the ports are ignored.

---

## 5-Tuple

Now the router hashes:

```
Protocol

Source IP

Destination IP

Source Port

Destination Port
```

Example

```
TCP

10.0.0.50:45000

↓

192.168.1.200:80
```

Hash

```
Worker1
```

Another connection

```
TCP

10.0.0.50:45001

↓

192.168.1.200:80
```

Hash

```
Worker3
```

Same client.

Different ports.

Different node.

This spreads traffic much more evenly.

---

# What happens if Worker2 dies?

Initially

```
Router

↓

Worker1
Worker2
Worker3
```

Worker2 crashes.

Its BGP session drops.

MetalLB stops advertising

```
192.168.1.200
```

through Worker2.

Router updates

```
Old

Worker1
Worker2
Worker3

↓

New

Worker1
Worker3
```

Future connections are sent only to Worker1 or Worker3.

---

# Why do existing connections break?

Suppose a client had an active TCP connection:

```
Client

↓

Router

↓

Worker2
```

Worker2 crashes.

The router now has only:

```
Worker1

Worker3
```

The router recomputes the hash.

The same connection might now be forwarded to Worker1.

However, Worker1 has **never seen this TCP session**. It doesn't know the sequence numbers or connection state.

So it responds by rejecting the packet (typically with a TCP reset), and the client sees **"Connection reset by peer."**

---

# Complete Flow

```text
                 Client
                    |
                    |
              +-----------+
              |  Router   |
              +-----------+
             /     |      \
            /      |       \
           ↓       ↓        ↓
       Worker1  Worker2  Worker3
          |         |         |
      kube-proxy kube-proxy kube-proxy
          |         |         |
       Pod A     Pod B     Pod C
```

1. MetalLB advertises the Service IP from **every node** using BGP.
2. The router learns multiple equal-cost routes (ECMP).
3. The router selects a node for each **connection** using a hash (typically 3-tuple or 5-tuple).
4. All packets for that connection continue to go to the same node.
5. On the chosen node, **kube-proxy** forwards the traffic to one of the Service's pods.
6. If a node fails, BGP withdraws its route and the router uses the remaining nodes, but **existing connections through the failed node are usually interrupted**, while new connections continue normally.

### Layer 2 vs. BGP at a glance

```
Layer 2
--------
Client
   |
Leader Node (single entry point)
   |
kube-proxy
   |
Pods

BGP
---
Client
   |
Router (ECMP)
 /   |   \
N1  N2  N3
 |   |   |
kube-proxy
 |   |   |
Pods
```

In short:

* **Layer 2 mode** provides **high availability** with a single ingress node at any given time.
* **BGP mode** provides **true network-level load balancing**, where your routers distribute connections across all participating Kubernetes nodes before kube-proxy selects the backend pod.
