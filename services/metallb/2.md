The most important thing to understand is that **MetalLB in Layer 2 mode is not a traditional load balancer.**

Many people assume it distributes requests across multiple nodes, but **it doesn't**. Kubernetes does the actual load balancing. MetalLB only makes the Service IP reachable from outside the cluster.

Let's break it down.

---

# Traditional Load Balancer

Suppose you have three Kubernetes worker nodes.

```
                Clients
                    |
          +----------------+
          | Load Balancer  |
          +----------------+
           /      |       \
          /       |        \
      Node1    Node2     Node3
```

The load balancer itself decides:

```
Request 1 -> Node1
Request 2 -> Node2
Request 3 -> Node3
Request 4 -> Node1
```

Traffic is distributed among all nodes.

---

# MetalLB Layer 2

Suppose you have

```
Worker1
Worker2
Worker3
```

MetalLB assigns

```
192.168.1.200
```

to a Kubernetes LoadBalancer Service.

Instead of advertising this IP from every node,

**only ONE node advertises it.**

For example

```
               Clients
                   |
          192.168.1.200
                   |
             (Leader Node)
                 Worker2
                /   |   \
               /    |    \
            PodA  PodB  PodC
```

From the LAN's perspective,

```
192.168.1.200
```

belongs to Worker2.

All traffic enters Worker2.

---

# How does the client find Worker2?

Suppose a laptop wants to reach

```
192.168.1.200
```

First it sends an ARP request.

```
Who has 192.168.1.200?
```

Only Worker2 replies.

```
192.168.1.200 is at
AA:BB:CC:DD:EE:FF
```

Now the client sends Ethernet frames directly to Worker2.

---

# What happens after Worker2 receives the packet?

Worker2 receives

```
Destination IP:
192.168.1.200
```

But there isn't actually a process listening on that IP.

Instead,

**kube-proxy** intercepts packets destined for the Service IP.

Suppose the Service looks like

```
payment-service

Pods

10.244.0.5
10.244.1.8
10.244.2.9
```

kube-proxy chooses one.

Example:

```
Incoming packet

192.168.1.200:80

↓

kube-proxy

↓

10.244.2.9:8080
```

---

# Actual Load Balancing

Suppose we have

```
Pod1 on Worker1

Pod2 on Worker2

Pod3 on Worker3
```

Traffic always enters Worker2 first.

```
Clients
   |
Worker2
```

But kube-proxy may forward

```
Request1 → Pod1

Request2 → Pod2

Request3 → Pod3

Request4 → Pod1
```

So **load balancing happens between pods, not between nodes.**

---

Every request first reaches Worker2.

# Why is this called a bottleneck?

Suppose each node has

```
10 Gbps NIC
```

Three nodes together have

```
30 Gbps total network capacity
```

But in Layer 2 mode,

```
ALL traffic

↓

Worker2
```

Worker2 can only receive

```
10 Gbps
```

So even if

```
Worker1
Worker2
Worker3
```

are idle,

the Service cannot exceed Worker2's NIC bandwidth.

```
           10Gbps

Clients
   |
Worker2
 /   \
↓     ↓
Pods everywhere
```

Hence:

**Maximum throughput = bandwidth of one node.**

---

# What if Worker2 dies?

MetalLB detects the failure using **memberlist**.

A new leader is elected.

Example:

```
Old Leader

Worker2
```

↓

```
New Leader

Worker3
```

Now Worker3 answers ARP requests for

```
192.168.1.200
```

Clients update their ARP cache and start sending traffic to Worker3.

```
Before

Client
   |
Worker2

After

Client
   |
Worker3
```

---

# Does the Service IP move?

Not really.

The IP address remains the same:

```
192.168.1.200
```

What changes is the **MAC address associated with that IP**.

Initially:

```
192.168.1.200

↓

AA:AA:AA
(Worker2)
```

After failover:

```
192.168.1.200

↓

BB:BB:BB
(Worker3)
```

MetalLB sends **gratuitous ARP** (for IPv4) or **unsolicited NDP** (for IPv6) to inform clients of this mapping change.

---

# Why doesn't MetalLB load balance between nodes?

Because **Layer 2 networking (ARP/NDP)** only allows one device to "own" a given IP address on an Ethernet network. If multiple nodes simultaneously claimed the same IP, clients would receive conflicting ARP replies, causing traffic to be unpredictable. MetalLB therefore elects a single leader to advertise the Service IP, while **kube-proxy** inside the cluster performs the actual distribution of traffic to the backend pods.

---

# Complete Flow

```text
                  Client
                     |
         ARP: Who has 192.168.1.200?
                     |
              Leader replies
                     |
                     v
             +----------------+
             |   Worker2      |  <-- MetalLB leader
             | kube-proxy     |
             +----------------+
               /     |      \
              /      |       \
             v       v        v
         Pod A    Pod B    Pod C
        Worker1  Worker2  Worker3
```

**Key takeaway:** In Layer 2 mode, **MetalLB provides IP advertisement and failover**, not request distribution. Every external request enters through a single leader node, and **kube-proxy** then load balances the traffic across the Service's pods throughout the Kubernetes cluster.
