Yes — LimitRange applies to **both requests and limits**, and they're controlled by separate fields. Here's the complete breakdown:

## All Four Things LimitRange Controls

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: resource-limits
  namespace: production
spec:
  limits:
    - type: Container
      default:           # injected as LIMIT if container sets no limits
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:    # injected as REQUEST if container sets no requests
        cpu: "100m"
        memory: "128Mi"
      max:               # container CANNOT exceed this (for limits)
        cpu: "2"
        memory: "2Gi"
      min:               # container CANNOT go below this (for requests)
        cpu: "50m"
        memory: "64Mi"
```

So yes — `defaultRequest` specifically targets resource **requests**, and `min` enforces a floor on requests.

## What Each Field Actually Does

| Field | Applies to | Effect |
|---|---|---|
| `default` | Limits | Injected when container has no `limits:` block |
| `defaultRequest` | Requests | Injected when container has no `requests:` block |
| `max` | Limits | Hard ceiling — pod rejected if limit exceeds this |
| `min` | Requests | Hard floor — pod rejected if request is below this |

## The Precise Injection Rules

```yaml
# Case 1: Container has NOTHING set
containers:
  - name: app
    image: nginx
    # no resources block at all

# LimitRange injects BOTH:
# requests.cpu    = defaultRequest.cpu    = 100m
# requests.memory = defaultRequest.memory = 128Mi
# limits.cpu      = default.cpu           = 500m
# limits.memory   = default.memory        = 256Mi
```

```yaml
# Case 2: Container sets limits but NOT requests
containers:
  - name: app
    resources:
      limits:
        cpu: "1"
        memory: "512Mi"

# LimitRange injects requests only:
# requests.cpu    = defaultRequest.cpu    = 100m  ← injected
# requests.memory = defaultRequest.memory = 128Mi ← injected
# limits stay as you set them
```

```yaml
# Case 3: Container sets requests but NOT limits
containers:
  - name: app
    resources:
      requests:
        cpu: "200m"
        memory: "256Mi"

# LimitRange injects limits only:
# requests stay as you set them
# limits.cpu    = default.cpu    = 500m  ← injected
# limits.memory = default.memory = 256Mi ← injected
```

## The min/max Validation (Different from defaults — these REJECT pods)

```yaml
# min enforces a floor on REQUESTS specifically:
min:
  cpu: "50m"
  memory: "64Mi"

# This pod gets REJECTED at admission:
resources:
  requests:
    cpu: "10m"       # ❌ below min.cpu of 50m
    memory: "64Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"

# Error: "minimum cpu usage per Container is 50m, but request is 10m"
```

## The Ratio Rule — Often Missed

There's one more constraint: if you set both `min` and `max`, Kubernetes enforces that `request ≤ limit` AND `request ≥ min` AND `limit ≤ max` — but it also prevents a request from exceeding the `max`:

```yaml
min:
  memory: "64Mi"
max:
  memory: "2Gi"

# This is also REJECTED:
resources:
  requests:
    memory: "3Gi"   # ❌ request exceeds max — request must also be ≤ max
  limits:
    memory: "4Gi"   # ❌ also exceeds max
```

## LimitRange for PVC Storage Requests Too

LimitRange isn't just for containers — it also applies to PVC storage requests:

```yaml
spec:
  limits:
    - type: PersistentVolumeClaim
      max:
        storage: "50Gi"    # no PVC can request more than 50Gi
      min:
        storage: "1Gi"     # no PVC can request less than 1Gi
```

## Quick Mental Model

```
defaultRequest → "fill in missing requests with this value"
defaultLimit   → "fill in missing limits with this value"
min            → "reject if request is too LOW" (floor validation)
max            → "reject if limit is too HIGH" (ceiling validation)

Injection happens FIRST (defaults fill gaps)
THEN validation runs (min/max checked against final values)
```

So to directly answer your question: yes, LimitRange fully controls resource requests — `defaultRequest` injects them when missing, and `min` validates they're not below the floor.
