# Kubernetes ResourceQuota & LimitRange — Complete Troubleshooting Guide

---

## Part 1 — What ResourceQuota Actually Controls

The original answer mentions only memory. ResourceQuota can block pod
creation for 8+ different reasons. Knowing all of them is essential
for diagnosing "why is my second pod not starting?"

### Compute quotas (what original answer covers)
```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: production
spec:
  hard:
    # CPU
    requests.cpu: "4"          # total CPU requests across all pods
    limits.cpu: "8"            # total CPU limits across all pods

    # Memory
    requests.memory: 4Gi       # total memory requests
    limits.memory: 8Gi         # total memory limits

    # Huge pages
    requests.hugepages-2Mi: 0  # usually 0 to disable huge pages
```

### Object count quotas (the ones people forget)
```yaml
spec:
  hard:
    # Pods
    pods: "20"                 # max number of pods in namespace
                               # ← THIS is another common reason
                               # deployment's 2nd pod can't start

    # Services
    services: "10"
    services.loadbalancers: "2"
    services.nodeports: "0"    # can block all NodePort services

    # Storage
    persistentvolumeclaims: "5"
    requests.storage: 100Gi    # total storage across all PVCs

    # Config
    configmaps: "20"
    secrets: "30"              # hit this more often than you'd think

    # Deployments, Jobs etc
    count/deployments.apps: "10"
    count/replicasets.apps: "50"
    count/jobs.batch: "5"
```

### Priority class quotas
```yaml
spec:
  scopeSelector:              # quota only applies to pods with this priority
    matchExpressions:
      - operator: In
        scopeName: PriorityClass
        values: ["high-priority"]
  hard:
    pods: "5"                 # only 5 high-priority pods allowed
    requests.cpu: "10"
    requests.memory: 10Gi
```

## Part 2 — The Hidden Culprit: LimitRange

This is what the original answer doesn't mention at all, and it's responsible
for a confusing class of failures: **pods fail quota even when your quota
seems to have headroom.**

### What LimitRange does
```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
    - type: Container
      default:              # applied to containers with NO limits set
        cpu: "500m"
        memory: "256Mi"
      defaultRequest:       # applied to containers with NO requests set
        cpu: "100m"
        memory: "128Mi"
      max:                  # container cannot EXCEED these
        cpu: "2"
        memory: "2Gi"
      min:                  # container cannot go BELOW these
        cpu: "50m"
        memory: "64Mi"
```

### The interaction that causes "ghost" quota failures

```
Scenario: You have ResourceQuota with requests.memory: 500Mi
          You have LimitRange with defaultRequest memory: 256Mi
          You deploy a pod with NO resources specified

What Kubernetes actually does:
  1. LimitRange applies default: requests.memory = 256Mi
  2. ResourceQuota sees this pod as consuming 256Mi
  3. You deploy 2 such pods: 256Mi + 256Mi = 512Mi
  4. 512Mi > 500Mi quota → SECOND POD BLOCKED

Your pod spec has no resources block at all.
kubectl describe pod shows 256Mi requested.
quota describe shows you're "over quota."
You never set any memory values anywhere.
This is the "ghost quota" problem — LimitRange set it without your knowledge.
```

### LimitRange + ResourceQuota interaction rules

```
When a pod is created:
1. LimitRange injects defaults for any unset requests/limits
2. THEN ResourceQuota checks the (now-modified) pod against limits
3. If quota exceeded → pod rejected

Critical rule: if ResourceQuota defines limits.memory,
then EVERY pod MUST have a memory limit set (or LimitRange must set one).
Without this, the admission webhook REJECTS the pod immediately:
"must specify limits.memory"
```

## Part 3 — Complete Debugging Methodology

The original gives 3 commands. Here's the complete sequence:

### Step 1 — Find the exact failure message
```bash
# Check events in the NAMESPACE (not cluster-wide)
kubectl get events -n <namespace> --sort-by='.lastTimestamp' | tail -20

# Look for these patterns:
# "exceeded quota: production, requested: limits.memory=256Mi,
#  used: limits.memory=3840Mi, limited: limits.memory=4Gi"
#                    ↑ exact resource    ↑ current usage   ↑ limit

# Or: "pods: must specify limits.memory"
#     ← LimitRange is missing, ResourceQuota requires limits

# Or: "exceeded quota: production, requested: pods=1,
#  used: pods=20, limited: pods=20"
#                    ↑ it's the pod COUNT quota, not memory
```

### Step 2 — Get a complete picture of quota status
```bash
kubectl describe resourcequota -n <namespace>
```

Expected output:
```
Name:            compute-quota
Namespace:       production
Resource         Used    Hard
--------         ----    ----
limits.cpu       3500m   4       ← 87.5% used
limits.memory    3840Mi  4Gi     ← 93.75% used — close to limit
pods             19      20      ← 95% used
requests.cpu     1750m   2
requests.memory  1920Mi  2Gi
secrets          8       10

# The second pod is requesting 256Mi limits.memory
# 3840Mi + 256Mi = 4096Mi = 4Gi → EXACTLY at limit → BLOCKED
```

### Step 3 — Check LimitRange (often forgotten)
```bash
kubectl describe limitrange -n <namespace>

# Look for:
# Container  cpu    -       100m        500m    2       -
# Container  memory -       128Mi       256Mi   2Gi     -
#            type   ratio  defaultReq  default  max     min

# If you see defaults here AND your pods have no resources block,
# LimitRange is silently adding resource requests → consuming quota
```

### Step 4 — Calculate exactly why the pod is stuck
```bash
# What does the STUCK pod actually request?
kubectl describe pod <stuck-pod-name> -n <namespace> | grep -A6 "Requests:"
# Requests:
#   cpu:     100m
#   memory:  256Mi      ← this is what it's asking for (from LimitRange default)

# What's available?
kubectl describe resourcequota -n <namespace> | grep memory
# limits.memory: 3840Mi / 4Gi
# Available: 4096Mi - 3840Mi = 256Mi

# 256Mi available, 256Mi needed → should work?
# Check if it's limits vs requests:
# Quota: limits.memory = 4Gi used = 3840Mi
# Pod needs limits.memory = 256Mi
# 3840 + 256 = 4096Mi = 4096Mi = exactly 4Gi
# EQUAL to the limit, not OVER → this actually should work
# If stuck: check PODS quota (count), not memory
```

### Step 5 — Check if it's a pod count issue
```bash
kubectl get pods -n <namespace> | wc -l
# If this number equals the pods quota → pod count is the blocker

# Check replicasets too (they count toward count/replicasets.apps quota)
kubectl get rs -n <namespace>
```

### Step 6 — Check if the pod even has a spec problem (unrelated to quota)
```bash
# ResourceQuota is an admission webhook — it runs BEFORE pod scheduling
# So "quota exceeded" events appear even if the pod would fail for other reasons
# Verify: after fixing quota, does the pod start?

# Check the ReplicaSet conditions — more detailed than events:
kubectl describe rs <replicaset-name> -n <namespace>
# Look under Conditions:
# ReplicaFailure  True  FailedCreate
# "exceeded quota: ..."
```

## Part 4 — Every Fix, Matched to Root Cause

### Fix 1: Increase the quota
```bash
# Increase memory quota
kubectl patch resourcequota compute-quota -n production \
  -p '{"spec":{"hard":{"limits.memory":"8Gi","requests.memory":"4Gi"}}}'

# Or edit directly:
kubectl edit resourcequota compute-quota -n production
```

### Fix 2: Reduce pod resource requests
```yaml
# Before (consuming too much quota per pod):
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"

# After (right-sized based on actual usage):
resources:
  requests:
    memory: "128Mi"    # what the pod actually needs to START
  limits:
    memory: "512Mi"    # what the pod can burst to under load
```

### Fix 3: Add explicit resources to stop LimitRange defaults from consuming quota unexpectedly
```yaml
# If LimitRange is injecting 256Mi default and consuming quota:
# Set explicit values to control exactly what quota is consumed
spec:
  containers:
    - name: app
      resources:
        requests:
          memory: "64Mi"      # explicit: overrides LimitRange default
          cpu: "50m"
        limits:
          memory: "128Mi"     # explicit: overrides LimitRange default
          cpu: "200m"
```

### Fix 4: Clean up unused resources consuming quota
```bash
# Find completed/failed pods that still count toward pod quota
kubectl get pods -n production --field-selector=status.phase=Succeeded
kubectl delete pods -n production --field-selector=status.phase=Succeeded

kubectl get pods -n production --field-selector=status.phase=Failed
kubectl delete pods -n production --field-selector=status.phase=Failed

# Find old replicasets with 0 desired (leftover from deploys)
kubectl get rs -n production | grep "0         0         0"
kubectl delete rs <old-rs-name> -n production
# Or clean all zero-replica RS:
kubectl delete rs -n production $(kubectl get rs -n production \
  -o jsonpath='{range .items[?(@.spec.replicas==0)]}{.metadata.name}{"\n"}{end}')
```

### Fix 5: Priority-based quota exemption
```yaml
# If you need this critical pod to bypass the quota:
# Create a high-priority class that gets its own quota
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-app
value: 1000000
globalDefault: false
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: critical-quota
  namespace: production
spec:
  hard:
    requests.memory: 2Gi
    limits.memory: 4Gi
    pods: "5"
  scopeSelector:
    matchExpressions:
      - operator: In
        scopeName: PriorityClass
        values: ["critical-app"]
---
# Then set priorityClassName on the critical pod:
spec:
  priorityClassName: critical-app    # uses critical-quota, not compute-quota
  containers:
    - name: app
      image: critical-app:latest
```

## Part 5 — All Possible Error Messages and What They Mean

```bash
# 1. Compute resource exceeded:
"exceeded quota: production, requested: limits.memory=256Mi,
 used: limits.memory=3840Mi, limited: limits.memory=4Gi"
→ Total memory limits across all pods hit the ceiling
→ Fix: increase quota, reduce pod limits, or delete unused pods

# 2. Pod count exceeded:
"exceeded quota: production, requested: pods=1,
 used: pods=20, limited: pods=20"
→ Too many pod objects in namespace (includes completed/failed pods)
→ Fix: increase pod count quota, or delete completed/failed pods

# 3. Missing limits (LimitRange + ResourceQuota interaction):
"pods "web-pod" is forbidden: [must specify limits.memory
 for: web, must specify limits.cpu for: web]"
→ ResourceQuota requires limits, but pod has no limits AND LimitRange
  isn't configured to inject defaults
→ Fix: add resources.limits to pod spec, OR configure LimitRange defaults

# 4. LimitRange min violation:
"minimum memory usage per Container is 64Mi, but limit is 32Mi"
→ Pod's limit is below LimitRange minimum
→ Fix: increase container limits above LimitRange minimum

# 5. LimitRange max violation:
"maximum memory usage per Container is 2Gi, but limit is 4Gi"
→ Pod is trying to request more than LimitRange allows per container
→ Fix: reduce container limits, OR increase LimitRange max

# 6. Secret count exceeded:
"exceeded quota: production, requested: secrets=1,
 used: secrets=30, limited: secrets=30"
→ Often hit because service accounts auto-create secrets,
  and pull secrets accumulate
→ Fix: increase secret quota, or clean up unused secrets

# 7. PVC storage quota:
"exceeded quota: production, requested: requests.storage=10Gi,
 used: requests.storage=95Gi, limited: requests.storage=100Gi"
→ Total storage requested by PVCs exceeds namespace quota
→ Fix: delete unused PVCs (and their PVs if policy is Retain)
```

## Part 6 — Monitoring Quota to Prevent Future Incidents

```yaml
# PrometheusRule — alert before you hit quota (not after)
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: quota-alerts
spec:
  groups:
    - name: quota
      rules:
        # Alert at 80% memory quota usage
        - alert: NamespaceQuotaMemoryHigh
          expr: |
            kube_resourcequota{resource="limits.memory", type="used"}
            /
            kube_resourcequota{resource="limits.memory", type="hard"}
            > 0.80
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Namespace {{ $labels.namespace }} memory quota > 80%"
            description: "{{ $value | humanizePercentage }} of memory quota used"

        # Alert at 80% pod count quota
        - alert: NamespaceQuotaPodCountHigh
          expr: |
            kube_resourcequota{resource="pods", type="used"}
            /
            kube_resourcequota{resource="pods", type="hard"}
            > 0.80
          for: 5m
          labels:
            severity: warning
          annotations:
            summary: "Namespace {{ $labels.namespace }} pod count quota > 80%"
```
