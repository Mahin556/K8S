## When you run `kubectl create deployment`, explain the complete flow from command execution until the pod is created?

### Complete Flow for a WRITE Command (kubectl create):

**Step 1: Syntax Validation (kubectl client-side)**
- The `kubectl` binary itself first validates the command syntax
- Checks if the command is valid and available
- This happens on the client machine, NOT on the API server

**Step 2: Authentication**
- When we connect to the API server, authentication happens first
- Every user needs authentication credentials
- Methods of authentication:
  - **Certificate-based authentication** (using kubeconfig file)
  - **Service Account Token** (for pods/services)
- The kubeconfig file (usually at `~/.kube/config` or `/etc/kubernetes/admin.conf`) contains the authentication credentials
- The default superuser of Kubernetes API is **kubernetes-admin**
- The admin certificate is stored in `/etc/kubernetes/admin.conf`
- This superuser uses **certificate-based authentication** by default

**Step 3: Authorization**
- After authentication, authorization is validated
- API server checks: **What permissions does this user have?**
- **Role Binding** is checked for the specific user
- Example: Does this user have permission to create a deployment?
- RBAC (Role-Based Access Control) rules are verified

**Step 4: Admission Controllers**
- After authorization, **Admission Controllers** come into the picture
- These are plugins that intercept requests before they are persisted
- They can:
  - Validate the request further
  - Modify the request (mutating admission controllers)
  - Deny the request (validating admission controllers)
- Examples: `NamespaceLifecycle`, `LimitRanger`, `ResourceQuota`

**Step 5: etcd (Database Storage)**
- Since this is a WRITE query, it goes to etcd
- All the authentication rules, authorization rules, and admission controller validations are verified AGAINST etcd
- etcd stores all cluster state
- The API server writes the new deployment information to etcd
- **Important:** Only the etcd LEADER handles write requests

**Step 6: kube-scheduler**
- After the deployment is stored in etcd, the scheduler enters the picture
- Scheduler decides **which worker node the pod will run on**
- If you haven't specified a node, the scheduler:
  - Checks node health
  - Checks resource availability (CPU, memory)
  - Checks port availability
  - Applies affinity/anti-affinity rules
  - Applies taints and tolerations
- This is called **predicate filtering and priority scoring**
- Scheduler assigns the pod to a specific node

**Step 7: kubelet (on Worker Node)**
- The instruction reaches the worker node
- **kubelet** receives the instruction from the API server
- kubelet passes the instruction to the container runtime

**Step 8: Container Runtime**
- Container runtime (containerd or CRI-O) creates the container
- The pod is actually created

**Step 9: CNI (Container Network Interface)**
- The pod connects to the network via CNI
- Examples: Calico, Flannel, AWS VPC CNI
- Pod gets its IP address

**Step 10: kube-controller-manager**
- After the pod is created, the controller enters the picture
- Controller monitors the pod state
- Maintains the desired state vs actual state
- If the pod goes down, controller detects it and informs the API server
- API server then creates a new pod to replace it

### Flow of a READ Command (kubectl get)

**Scenario:** What happens when you run `kubectl get pods -n default`?

#### Key Difference from Write Commands:

For a **GET/READ query**, many components are NOT involved:

**Components that come into play:**
- ✅ **kubectl** (client-side)
- ✅ **API Server** (authentication + authorization)
- ✅ **etcd** (reads the information directly)

**Components that DO NOT come into play:**
- ❌ **kube-scheduler** (no scheduling needed for reading)
- ❌ **kubelet** (no container creation needed)
- ❌ **Container Runtime** (no container to run)
- ❌ **kube-controller-manager** (no state to reconcile)

**Important:** For GET queries, the API server communicates directly with etcd and returns the information. The scheduler and controller services don't need to be running for GET queries to work.

### Summary Table: Write vs Read Query Flow

| Step | Write (kubectl create) | Read (kubectl get) |
|------|------------------------|---------------------|
| 1 | Client syntax validation | Client syntax validation |
| 2 | Authentication | Authentication |
| 3 | Authorization (RBAC) | Authorization (RBAC) |
| 4 | Admission Controllers | Admission Controllers |
| 5 | **Write to etcd (Leader)** | **Read from etcd (any member)** |
| 6 | **Scheduler** (node selection) | ❌ Not involved |
| 7 | **kubelet** (receives instruction) | ❌ Not involved |
| 8 | **Container Runtime** (creates pod) | ❌ Not involved |
| 9 | **CNI** (networking) | ❌ Not involved |
| 10 | **Controller** (maintains state) | ❌ Not involved |
