
## Question 1: What Prerequisites Are Needed Before Installing Kubernetes?

**Two critical prerequisites:**

### 1. Swap Memory Must Be Disabled
- **What is Swap?** Virtual memory in Linux - two types of memory exist:
  - Physical memory (actual RAM)
  - Virtual memory (Swap memory)
- **Why disable?** Kubernetes requires swap to be OFF on ALL nodes (both master and worker)
- **How to disable:**
  ```bash
  swapoff -a
  ```
- **Make permanent:** Comment out the swap entry in `/etc/fstab`
- Swap must be disabled on both Master AND Worker nodes

### 2. SELinux Must Be Disabled (on Master Node)
- SELinux is a Linux security policy
- By default, SELinux is NOT installed in RHEL/CentOS minimal installation
- If installed, it must be disabled on the Master node
- Worker nodes don't necessarily need this (but swap must be disabled everywhere)

**Check if SELinux is installed:**
```bash
getenforce
# or
sestatus
```

## Question 3: How to Initialize the Master Node?

**Command:**
```bash
kubeadm init --apiserver-advertise-address=<static-ip>
```

**Why `--apiserver-advertise-address` is needed:**
- If the system has multiple IP addresses (dynamic + static)
- The API server needs to bind to a specific IP
- This IP is used for:
  - Certificate signing
  - Worker node communication
  - Client (kubectl) communication
- Without this, kubeadm picks the primary (possibly dynamic) IP, causing issues

**What happens during `kubeadm init`:**
1. Pulls images for all control plane components:
   - kube-apiserver
   - etcd
   - kube-scheduler
   - kube-controller-manager
2. Generates and signs certificates
3. Creates static pod manifests in `/etc/kubernetes/manifests/`
4. Starts all control plane services as static pods
5. Generates bootstrap tokens for worker node join
6. Creates kubeconfig file at `/etc/kubernetes/admin.conf`

## Question 4: What Are the Required Port Numbers in Kubernetes?

**Important port numbers to remember for interviews:**

### Master Node Ports:
| Component | Port | Purpose |
|-----------|------|---------|
| **kube-apiserver** | **6443** | Client/worker communication (HTTPS) |
| etcd | 2379 | Client communication |
| etcd | 2380 | Peer communication (etcd cluster) |
| kube-scheduler | 10251 | Health check |
| kube-controller-manager | 10252 | Health check |

### Worker Node Ports:
| Component | Port | Purpose |
|-----------|------|---------|
| **kubelet** | **10250** | API server communication |
| kube-proxy | 10256 | Health check |
| NodePort Services | **30000-32767** | External access range |

### Firewall Considerations:
- These ports must be whitelisted in firewall
- Master node firewall needs different ports than worker nodes
- This is a common interview question: "Which ports need to be opened for a Kubernetes cluster?"

## Question 5: What is the Admin.conf File?

**Location:** `/etc/kubernetes/admin.conf`

**What it contains:**
1. **API Server IP address** (endpoint)
2. **Username** (kubernetes-admin - the superuser)
3. **Password/Certificate** (client certificate for authentication)

**How to use it:**
```bash
# Method 1: Pass reference with each command
kubectl get nodes --kubeconfig=/etc/kubernetes/admin.conf

# Method 2: Export as environment variable
export KUBECONFIG=/etc/kubernetes/admin.conf

# Method 3: Copy to user's home (permanent)
mkdir -p ~/.kube
cp /etc/kubernetes/admin.conf ~/.kube/config
```

**How kubectl finds the config (priority order):**
1. `--kubeconfig` flag (explicit)
2. `$KUBECONFIG` environment variable
3. `~/.kube/config` file (default location)

## Question 7: Why Do Control Plane Services Use Host Network?

**Question:** The four control plane services are containerized. Why do their port numbers show up on the base system?

**Answer:** Because they are deployed with **hostNetwork: true**

**Reason:**
- If they used container private IPs, worker nodes couldn't communicate with the API server
- Container IPs are not accessible from outside the host by default
- Port forwarding would be needed for every control plane component
- Host network makes them directly accessible on the node's IP
- This is a deliberate design choice for control plane components

## Question 8: What is NodePort Range?

**Default range:** **30000-32767**

**Why this specific range:**
- These are the ports available for NodePort type services
- When you expose a container via NodePort, a random port from this range is assigned
- You can also specify a port within this range manually

## Question 9: Why Does Master Node Show "NotReady" Status?

**Multiple possible reasons:**

1. **No CNI (Container Network Interface) installed**
   - Network plugin not deployed yet
   - Containers can't get IP addresses
   - CoreDNS pods stuck in Pending state

2. **Container runtime network not ready**
   - No bridge network configured
   - Runtime can't assign IPs

3. **kubelet service issues**
   - kubelet not running
   - kubelet health checks failing

4. **Resource pressure**
   - Disk pressure
   - Memory pressure
   - CPU pressure

5. **Network connectivity issues**
   - Container network switch/plugin failed
   - Communication between nodes broken

**Troubleshooting commands:**
```bash
kubectl describe node <node-name>
kubectl get events
journalctl -u kubelet
crictl ps
crictl logs <container-id>
```

## Question 10: What is CNI (Container Network Interface)?

**Full Form:** Container Network Interface

**What it is:**
- A software-defined networking solution for containers
- Provides Layer 3 (routing) capabilities in software form
- Acts as an advanced software switch with routing features

**Why CNI is needed:**
- The standard Docker bridge network only works within a single host
- No routing between different nodes
- In a cluster, containers on different nodes need to communicate
- CNI provides cross-node networking without port forwarding

**Popular CNI Solutions:**
| CNI | Description |
|-----|-------------|
| **Calico** | Most popular for on-premises, Layer 3 networking |
| Flannel | Simple, lightweight |
| Weave | Automatic mesh networking |
| Cilium | eBPF-based, advanced security |

**What CNI does:**
- Assigns IP addresses to containers
- Manages routing tables for cross-node communication
- Acts like all containers are connected to a single smart switch
- Each node has its own CNI switch, but they share routing information
- Switches form a cluster and sync information among themselves

## Question 11: What is an IP Pool in Kubernetes?

**What it is:**
- A range of IP addresses reserved for pod networking
- Defined by the CNI plugin

**Default (Calico):**
- If not specified: `172.16.0.0/16` or `192.168.0.0/16`

**How to check:**
```bash
kubectl get ippool -o yaml
```

**Key Point:**
- All pods across all nodes get IPs from this pool
- The CNI manages allocation and routing

## Question 12: What Information is Needed to Join a Worker Node to the Cluster?

**Three pieces of information required from the Master node:**

| Information | Description | Example |
|-------------|-------------|---------|
| **API Server IP & Port** | Where to connect | `192.168.1.10:6443` |
| **CA Certificate** | Trust establishment | CA certificate hash/signature |
| **Bootstrap Token** | One-time authentication | Generated by kubeadm init |

**How to get the join command:**
```bash
# On master node
kubeadm token create --print-join-command
```

**Join command includes all three:**
```bash
kubeadm join <api-server-ip>:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>
```

**Token lifecycle:**
- Tokens expire after 24 hours (TTL)
- A token is like a one-time password
- After joining, worker node gets its own certificate
- Future communication uses the certificate, not the token
- Token deletion doesn't affect already-joined nodes
- New tokens can be generated anytime

## Question 13: What Happens During Worker Node Join Process?

**Step-by-step flow:**

1. **kubeadm join** command is executed on worker node
2. Worker node contacts API server using the **bootstrap token** (first authentication)
3. API server validates the token
4. Worker node requests a **client certificate** signed by the cluster CA
5. API server signs and returns the certificate
6. Certificate is saved at `/var/lib/kubelet/pki/kubelet.crt`
7. kubelet starts and uses this certificate for future communication
8. Token is no longer needed after this point

**Trust mechanism:**
- API server only trusts communication over TLS/HTTPS
- The CA certificate ensures both sides belong to the same cluster
- If CA signatures match → trust is established

## Question 14: Why Does CoreDNS Stay in Pending State?

**Reason:** No CNI network installed

- CoreDNS pods need IP addresses from the pod network
- Without CNI, no IP can be assigned
- Once Calico (or any CNI) is deployed:
  - Each node gets a CNI switch
  - CoreDNS pods get IPs automatically
  - CoreDNS moves from Pending to Running

**This proves:** The node's NotReady status and CoreDNS Pending are both caused by missing CNI.

## Question 15: Complete Installation Flow Summary

### Master Node:
1. Disable swap
2. Disable SELinux (if enabled)
3. Install CRI-O, kubeadm, kubelet, kubectl
4. Enable IP forwarding
5. `kubeadm init --apiserver-advertise-address=<ip>`
6. Set up kubeconfig (`~/.kube/config`)
7. Install CNI (Calico)

### Worker Node:
1. Disable swap
2. Install CRI-O, kubeadm, kubelet
3. Enable IP forwarding
4. `kubeadm join` command (from master)
5. Worker joins cluster automatically

## Important Interview Takeaways

1. **Swap must be off** on all nodes - kubelet requirement
2. **API server port is 6443** - most important to remember
3. **kubelet port is 10250** - second most important
4. **NodePort range is 30000-32767**
5. **admin.conf** contains credentials for the superuser `kubernetes-admin`
6. **CNI is mandatory** for cluster readiness - without it, nodes stay NotReady
7. **Bootstrap tokens** are one-time use for joining; certificates are used thereafter
8. **Control plane components** run as static pods with host network
