#### Describe the Process and Considerations for Designing a High-Availability Kubernetes Cluster.
**Detailed Answer:**
A Highly Available (HA) cluster ensures the control plane and workloads remain available despite infrastructure failures.

**1. Control Plane HA (Multi-Master):**
- **API Server:** Run 3+ replicas across different **Availability Zones (AZs)** . Place a **TCP Load Balancer** in front of the API Servers to distribute `kubectl` and node traffic. *Note: API Server is stateless, so this is easy.*
- **etcd HA:** Run 3, 5, or 7 members across AZs. The quorum requirement is `(N/2)+1`. To survive 1 zone failure, you need 3 zones. **Network Latency:** Low latency (<10ms RTT) between etcd members is critical for performance; high latency causes leader elections and cluster instability.
- **Scheduler & Controller Manager:** Run 2+ replicas. Only one instance is the **Active Leader** at any time (using Lease locking in etcd). If the leader fails, another takes over instantly.

**2. Worker Node HA:**
- **Node Topology:** Spread worker nodes across at least 3 Availability Zones.
- **Pod Anti-Affinity:** Use rules to prevent all replicas of a critical app from landing on the same Node or same AZ.
- **Pod Disruption Budgets (PDB):** Ensure voluntary disruptions (node upgrades/drains) don't take down too many replicas at once.

**3. Considerations:**
- **Quorum Loss:** If you have 3 etcd nodes and 2 fail simultaneously, the cluster becomes **read-only**. You cannot deploy, scale, or delete. Existing workloads *keep running* but you lose management capability.
