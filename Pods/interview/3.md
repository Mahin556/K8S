## Application Pods Stuck in CrashLoopBackOff? Application pods repeatedly restart due to misconfigurations or runtime errors.

### Troubleshooting Steps:

```bash
# Step 1: Check pod logs for specific errors
kubectl logs <pod-name>

# Step 2: Inspect pod events and resource configurations
kubectl describe pod <pod-name>

# Step 3: Debug application configurations in YAML
kubectl get pod <pod-name> -o yaml

# Step 4: Fix the configuration and redeploy
kubectl apply -f deployment.yaml
```

### Common Causes:
- Missing environment variables
- Incorrect database credentials
- Wrong database URL stored in Secrets
- Runtime exceptions

## Understanding CrashLoopBackOff

### What's Happening?

```
Pod Lifecycle:
T0:   Container starts
      ↓
T1:   Application crashes (exit code != 0)
      ↓
T2:   Kubernetes detects crash
      ↓
T3:   Wait before restart (exponential backoff)
      ├─ Attempt 1: Wait 10 seconds
      ├─ Attempt 2: Wait 20 seconds
      ├─ Attempt 3: Wait 40 seconds
      ├─ Attempt 4: Wait 80 seconds
      ├─ Attempt 5: Wait 160 seconds
      └─ Max wait: 5 minutes between attempts
      ↓
T4:   Container restarts
      ↓
      Repeat forever ↻ (CrashLoopBackOff)
```

### Pod Status Progression

```
kubectl get pods

NAME                READY   STATUS              RESTARTS   AGE
my-app-xyz-abc      0/1     Pending             0          2s
my-app-xyz-abc      0/1     ContainerCreating   0          3s
my-app-xyz-abc      1/1     Running             0          5s
my-app-xyz-abc      0/1     Error               1          7s
my-app-xyz-abc      0/1     CrashLoopBackOff    2          12s
my-app-xyz-abc      0/1     CrashLoopBackOff    3          28s
my-app-xyz-abc      0/1     CrashLoopBackOff    4          48s
my-app-xyz-abc      0/1     CrashLoopBackOff    5          108s  ← Pod keeps restarting
```

## Step-by-Step Troubleshooting

### Step 1: Check Pod Logs

**Command:**
```bash
# Get logs from current crash
kubectl logs <pod-name>

# Get logs from previous crash (before restart)
kubectl logs <pod-name> --previous

# Watch logs in real-time
kubectl logs <pod-name> -f

# Get logs from specific container (if multiple)
kubectl logs <pod-name> -c <container-name>
```

**Example 1: Missing Environment Variable**

```bash
$ kubectl logs my-app-pod

Error: DATABASE_URL is not defined
  at Object.<anonymous> (/app/server.js:5:22)
  at Module._load (internal/modules/commonjs-loader.js:1449:19)
  at Function.Module._runModule (internal/modules/commonjs-loader.js:3:14)
  at startup (internal/bootstrap_module.js:612:4)
  at Function.Module._load (internal/modules/commonjs-loader.js:1449:19)

Process exited with code 1
```

**Diagnosis:** Application is looking for `DATABASE_URL` environment variable but it's not set.

**Fix:**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
      - name: app
        image: myapp:1.0
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: connection-string  # ← Add this
```

---

**Example 2: Database Connection Error**

```bash
$ kubectl logs my-app-pod

Error: unable to connect to database
Connection refused: postgres://user:pass@localhost:5432/mydb
  at PgClient.connect (/app/lib/db.js:15:44)

Process exited with code 1
```

**Diagnosis:** Pod trying to connect to `localhost:5432` but database isn't on localhost.

**Fix:**
```yaml
env:
- name: DATABASE_HOST
  value: postgres-service.default.svc.cluster.local  # ← Correct hostname
- name: DATABASE_PORT
  value: "5432"
- name: DATABASE_USER
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: username
- name: DATABASE_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password
```

## Common Causes & Solutions

### 1. Missing Environment Variables

**Symptom:**
```
ReferenceError: DATABASE_URL is not defined
```

**Root Cause:**
```yaml
# Bad - no env variables
spec:
  containers:
  - name: app
    image: myapp:1.0
    # env section missing!
```

**Solution:**
```yaml
# Good - env variables provided
spec:
  containers:
  - name: app
    image: myapp:1.0
    env:
    - name: DATABASE_URL
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: connection-string
    - name: API_KEY
      valueFrom:
        secretKeyRef:
          name: api-keys
          key: key
    - name: LOG_LEVEL
      value: "debug"
```

---

### 2. Wrong Database Connection String

**Symptom:**
```
Error: connect ECONNREFUSED 127.0.0.1:5432
```

**Root Cause:**
```yaml
# Bad - hardcoded localhost
env:
- name: DATABASE_HOST
  value: "localhost"  # ❌ Wrong! No database on localhost
```

**Solution:**
```yaml
# Good - use Kubernetes service DNS
env:
- name: DATABASE_HOST
  value: "postgres-service.default.svc.cluster.local"
- name: DATABASE_PORT
  value: "5432"

# Or use Secret
- name: DATABASE_URL
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: connection-string
      # Value: postgres://user:pass@postgres-service:5432/db
```

---

### 3. Wrong or Missing Secrets

**Symptom:**
```
Error: authentication failed for database
password does not match
```

**Root Cause:**
```yaml
# Secret has wrong password
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
data:
  password: c2VjcmV0MTIz  # "secret123" (wrong!)
```

**Solution:**

```bash
# Step 1: Check what's in the secret
kubectl get secret db-credentials -o yaml

# Step 2: Update with correct credentials
kubectl create secret generic db-credentials \
  --from-literal=username=admin \
  --from-literal=password=correctpassword123 \
  --dry-run=client -o yaml | kubectl apply -f -

# Step 3: Restart pods to pick up new secret
kubectl rollout restart deployment my-app
```

---

### 4. Insufficient Resources (OOM Kill)

**Symptom:**
```
Pod killed - Out of Memory
Exit code: 137 (SIGKILL)
```

**Root Cause:**
```yaml
# Memory limit too low
resources:
  limits:
    memory: "128Mi"  # App needs more!
```

**Solution:**
```yaml
# Increase memory limit
resources:
  requests:
    memory: "256Mi"
    cpu: "100m"
  limits:
    memory: "512Mi"
    cpu: "500m"
```

---

### 5. Port Already in Use

**Symptom:**
```
Error: listen EADDRINUSE :::8080
Address already in use
```

**Root Cause:**
Multiple containers trying to use same port, or port binding issue.

**Solution:**
```yaml
containers:
- name: app
  image: myapp:1.0
  ports:
  - name: http
    containerPort: 8080  # ← Ensure this is correct
  env:
  - name: PORT
    value: "8080"  # ← App should listen on this
```

---

### 6. Image Pull Errors

**Symptom:**
```
Failed to pull image "myapp:latest": not found
```

**Root Cause:**
```yaml
image: myapp:latest  # ← Image doesn't exist
# or image: private-registry.com/myapp:1.0 (no credentials)
```

**Solution:**
```yaml
# Use correct image
image: myapp:1.0

# If private registry, add imagePullSecrets
imagePullSecrets:
- name: docker-credentials

# Or push to correct registry
# docker build -t myregistry.azurecr.io/myapp:1.0 .
# docker push myregistry.azurecr.io/myapp:1.0
```

---

### 7. Liveness/Readiness Probe Failures

**Symptom:**
```
Probe failed: HTTP probe failed with statuscode: 500
```

**Root Cause:**
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 5  # Too early! App not ready yet
```

**Solution:**
```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30  # Give app time to start
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
```

## Prevention: Best Practices

```yaml
# ✅ GOOD: Complete, robust deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app
        image: myapp:1.0  # ✓ Specific version, not latest
        
        ports:
        - name: http
          containerPort: 8080
        
        # ✓ Environment variables from ConfigMap/Secret
        env:
        - name: DATABASE_URL
          valueFrom:
            secretKeyRef:
              name: db-secret
              key: connection-string
        - name: LOG_LEVEL
          value: "info"
        
        # ✓ Resource limits prevent OOM kills
        resources:
          requests:
            memory: "256Mi"
            cpu: "100m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        
        # ✓ Probes detect unhealthy pods
        livenessProbe:
          httpGet:
            path: /health
            port: http
          initialDelaySeconds: 30
          periodSeconds: 10
          failureThreshold: 3
        
        readinessProbe:
          httpGet:
            path: /ready
            port: http
          initialDelaySeconds: 10
          periodSeconds: 5
        
        # ✓ Proper volumes
        volumeMounts:
        - name: config
          mountPath: /etc/config
          readOnly: true
      
      volumes:
      - name: config
        configMap:
          name: app-config
```

## Interview Answer

**Question: "How would you troubleshoot a pod in CrashLoopBackOff?"**

**Answer:**

```
CrashLoopBackOff means the pod keeps crashing and Kubernetes 
keeps restarting it with exponential backoff delays. Here's my 
troubleshooting approach:

1. CHECK LOGS (most important):
   kubectl logs <pod-name>
   kubectl logs <pod-name> --previous
   
   Logs usually show the exact error - missing env var, 
   connection failure, etc.

2. DESCRIBE POD:
   kubectl describe pod <pod-name>
   
   Shows exit code, restart count, and events that indicate 
   when/why it crashed

3. INSPECT YAML:
   kubectl get pod <pod-name> -o yaml
   
   Check for missing env variables, wrong image, missing volumes,
   insufficient resources

4. COMMON CAUSES I'D CHECK:
   ├─ Missing environment variables (DATABASE_URL, API_KEY)
   ├─ Wrong database credentials in Secret
   ├─ Incorrect database hostname (localhost vs service DNS)
   ├─ Insufficient memory limits (OOM kill)
   ├─ Image pull errors (wrong tag, no credentials)
   ├─ Port binding issues (port already in use)
   ├─ Liveness probe failing (health check endpoint broken)
   └─ Missing ConfigMap/Secret mounts

5. FIX & REDEPLOY:
   Once root cause identified:
   - Update deployment YAML
   - Apply changes: kubectl apply -f deployment.yaml
   - OR restart: kubectl rollout restart deployment <name>

6. VERIFY:
   kubectl get pods -w
   kubectl logs <pod-name> -f
   
   Watch for pod to start successfully and logs to be clean.

Key insight: Always read the logs first - they almost always 
tell you exactly what's wrong!
```
